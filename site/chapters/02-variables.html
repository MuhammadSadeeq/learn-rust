let makes a promise

In PHP a variable is a name you can refill on any line. Assign it, reassign it, and nothing complains. Rust starts from the other end. A name made with let keeps the value it was given, and the compiler checks every later line against that promise. Rust calls that name and value pair a binding: a name bound to a value by let.

$x = 5;
echo $x;      // 5
$x = 6;
echo $x;      // 6
fn main() {
    let x = 5;
    println!("{x}");
    x = 6;
    println!("{x}");
}

The PHP version runs as written. The Rust version fails on the second assignment. Line 2 made a promise, and line 4 breaks it.

Before you read the compiler's answer: which line does rustc reject, and what one word would make the program compile?

Line 4, x = 6;. The word is mut, placed after let. The first let and the two println! calls are fine. Only the second assignment breaks the promise.

Here is the real output from rustc 1.97 for that program:

error[E0384]: cannot assign twice to immutable variable `x`
 --> src/main.rs:4:5
  |
2 |     let x = 5;
  |         - first assignment to `x`
3 |     println!("{x}");
4 |     x = 6;
  |     ^^^^^ cannot assign twice to immutable variable

2 |     let mut x = 5;
  |         +++

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0384`.

Read it from the top. The first line gives the error code and the summary. The arrows then tell the story in order: the let x = 5 line is the first assignment, and x = 6 is the second, the one the compiler refuses.

The help block is the compiler's suggested fix. It shows the corrected line, and the +++ marks the three characters to insert. Treat it as a question from the compiler: should this value really change? You decide the answer.

A let is a promise to every later line: this value won't change. Anyone reading the function can rely on that promise without tracking each line below it, and the compiler checks it everywhere.

mut: changing your mind, on purpose

When a value really must change, say so on the let. The mut keyword tells the reader and the compiler that this name will be assigned again.

fn main() {
    let mut count = 0;
    count += 1;
    count += 1;
    println!("{count}");
}

Each += assigns to the same variable. It is still one slot, and mut is what allows the refills.

In Rust a value stays the same unless you ask for a change.

Why the default is immutable

Rust could have made every variable mutable, the way PHP does. It doesn't, for three reasons.

  • Reasoning is easier. Without mut, a let holds one value for the rest of its scope. You can read a function top to bottom and know what each name holds at each line.
  • Intent is visible. A mut signals to the reader: this one will change. Reviewers, and agents reviewing code, can look for it first.
  • Sharing is safer later. Many threads can read a value that nobody can change, without taking a lock. Chapter 18 relies on this.

PHP checks immutable properties at runtime

PHP has the same idea for object properties, and it enforces it at a different time. PHP 8.1 added readonly properties. A readonly property is set once, usually in the constructor, and a later write throws an Error. PHP 8.2 added readonly class, which makes every property readonly.

The Rust version below uses a struct, a record with named fields. Chapter 09 covers structs.

final readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$money = new Money(500, 'USD');
echo "made\n";
$money->amount = 600;   // throws Error, when this line runs
struct Money {
    amount: i64,
    currency: String,
}

fn main() {
    let money = Money { amount: 500, currency: String::from("USD") };
    money.amount = 600;
}

Both versions refuse the write, but at different times. PHP throws when the line runs, so the program prints made first. rustc refuses before the program exists. In Rust, a field is immutable because the binding that owns it is immutable, and the same let and mut rule decides it.

PHP 8.4 added asymmetric visibility. A property can be readable from anywhere and writable only inside its class: public private(set) array $items = [];. A write from outside throws Error: Cannot modify private(set) property, again at runtime. Rust can get a similar effect with a private field and a method that reads it. Chapter 09 covers methods, and Chapter 16 covers the module rules that decide who can see a field.

The next program uses a for loop over the range 1..=3. Chapter 04 covers loops and ranges. For now, read it as: run the block once for 1, once for 2 and once for 3.

Does this compile?

fn main() {
    let total = 0;
    for n in 1..=3 {
        total += n;
    }
    println!("{total}");
}
  1. Yes. The loop runs three times, and each run changes total.
  2. No. total is not mut, and += assigns to it, which an immutable variable doesn't allow.
  3. Yes. The compiler only checks assignments that happen outside a loop.

This is error E0384. The loop doesn't change the rule. The rule is about the let, and the first pass through the loop already breaks it. Add mut after let and the program prints 6.

Inferred, but still typed

The programs above mostly leave types out, and they compile. The compiler works out the type from the value. An annotation is optional, and you write one when you want a particular type.

fn main() {
    let x = 5;               // no annotation: the compiler picks i32
    let y: u8 = 5;           // annotated: you pick u8
    let price: f64 = 9.99;   // f64 is the default for decimals; written out here
    println!("{x} {y} {price}");
}

An integer with no annotation becomes i32, and a decimal becomes f64. Chapter 03 covers the numeric types in full.

The type belongs to the variable

PHP and Rust disagree about where the type lives. In PHP the value carries the type, so one variable can hold a number and then a string. In Rust the variable carries the type, and every new value has to fit it.

$x = 5;
$x = "five";
echo $x;      // five
fn main() {
    let mut x = 5;
    x = "five";
    println!("{x}");
}

Look at the mut in the Rust version. It lets the value change, but it doesn't let the type change. A mut variable keeps its type for its whole life.

error[E0308]: mismatched types
 --> src/main.rs:3:9
  |
2 |     let mut x = 5;
  |                 - expected due to this value
3 |     x = "five";
  |         ^^^^^^ expected integer, found `&str`

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0308`.

The label expected due to this value points back at the 5. That number made x an integer, and the compiler holds to that decision. "five" is a &str, a piece of text, so the types don't match.

Does this compile?

fn main() {
    let total = 10;
    let ratio: f64 = total / 4;
    println!("{ratio}");
}
  1. Yes. Rust turns the integer result into an f64 when it's assigned.
  2. Yes, and it prints 2.5, because division always produces a decimal.
  3. No. total is an integer, so total / 4 is an integer too. It can't become an f64 without a conversion.

This is error E0308: expected f64, found integer. PHP's 10 / 4 gives 2.5, because PHP switches to a float when a division isn't exact. Rust keeps the type of the operation, and integer divided by integer is an integer. To get a decimal, start with one: let total = 10.0;, then divide by 4.0. That prints 2.5.

Shadowing: same name, new variable

You can use let again with a name that already exists. The new let hides the old name from that line on:

fn main() {
    let input = "42";
    let input: u32 = input.parse().unwrap();
    println!("{}", input + 1);
}

The second let doesn't change the first input. It creates a second variable with the same name. The first is a &str and the second is a u32. mut could never do that, because a mut variable keeps its type.

parse returns a Result, which is an error if the text isn't a number. unwrap takes the number out, or panics on an error. Chapter 11 handles errors properly. For now, read unwrap as "the value, or crash".

Two programs follow, and each one shows a different way to change a value. Step through both. The first keeps one slot, and the second makes a new slot each time. The narration mentions stack frames, the block of memory that holds one function call's local variables. Chapter 05 explains the stack and the heap, the two places a value can live.

Scopes and blocks



A variable lives from its let to the } that closes its block. That block is its scope. You just saw the inner x end at its brace. The same rule catches a variable used after the block that declared it.




  
Does this compile?

  
fn main() {
    let score = 72;
    if score > 50 {
        let grade = "pass";
    }
    println!("{grade}");
}

  
    
    
  1. Yes. It prints pass, the way PHP would.
    2. 
    
  2. No. grade lives only inside the if block, and that block closed before the println!.
    3. 
    
  3. No. An if block isn't allowed to declare a variable.
    4. 
  

  

    
The } on line 5 ends the scope of grade. On line 6 the name no longer exists, so rustc reports E0425, "cannot find value in this scope". The real output is below.

  





error[E0425]: cannot find value `grade` in this scope
 --> src/main.rs:6:16
  |
6 |     println!("{grade}");
  |                ^^^^^
  |
help: the binding `grade` is available in a different scope in the same function
 --> src/main.rs:4:13
  |
4 |         let grade = "pass";
  |             ^^^^^

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0425`.



The help line shows that rustc knows where grade does exist: inside the if. There are two ways to fix it. Move the println! inside the block, or declare grade before the if and give it a value on every path. The section "Declare now, assign later" shows the second one.




  
PHP creates a new scope only for a function or a closure. An if, a for or a bare { } leaves its variables in the surrounding function. Rust treats every block as a scope, so code that works in PHP fails here.





The same rule produces a common bug. Shadowing inside a loop looks like a running total, but the inner let is a new variable, and it disappears at the end of each pass. Chapter 04 covers for loops. The bug looks like this:



fn main() {
    let total = 0;
    for n in 1..=3 {
        let total = total + n;
    }
    println!("{total}");
}



The program compiles and prints 0. rustc warns about the real problem, because the inner total is never read:



warning: unused variable: `total`
 --> src/main.rs:4:13
  |
4 |         let total = total + n;
  |             ^^^^^ help: if this is intentional, prefix it with an underscore: `_total`
  |
  = note: `#[warn(unused_variables)]` (part of `#[warn(unused)]`) on by default

warning: 1 warning emitted



A running total needs one variable that changes, so declare it with mut and assign to it with +=.







Declare now, assign later



Sometimes a name has to exist before its value is known. Rust lets you declare the name without a value, and then assign it once on each path:



fn main() {
    let score = 72;
    let status;
    if score > 50 {
        status = "pass";
    } else {
        status = "fail";
    }
    println!("{status}");
}



status is immutable, and this still compiles. The compiler checks every path through the code. Each branch assigns status exactly once, so the println! always sees a value.



Now remove the else branch. The promise breaks:



fn main() {
    let score = 72;
    let status;
    if score > 50 {
        status = "pass";
    }
    println!("{status}");
}



error[E0381]: used binding `status` is possibly-uninitialized
 --> src/main.rs:7:16
  |
3 |     let status;
  |         ------ binding declared here but left uninitialized
4 |     if score > 50 {
  |        ---------- if this `if` condition is `false`, `status` is not initialized
5 |         status = "pass";
6 |     }
  |      - an `else` arm might be missing here, initializing `status`
7 |     println!("{status}");
  |                ^^^^^^ `status` used here but it is possibly-uninitialized

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0381`.



E0381 says the name might be uninitialized. The labels trace one path through the code. The if can be false, and on that path nothing sets status. The compiler follows the branches the way you would on paper.



Most Rust code writes this differently. An if produces a value, so you can bind it directly:



fn main() {
    let score = 72;
    let status = if score > 50 { "pass" } else { "fail" };
    println!("{status}");
}



The declare-first form still appears in real code, but the one-line form is the usual choice. Chapter 04 explains why an if can produce a value.




  
Does this compile?

  
fn main() {
    let total;
    total = 10;
    total = 20;
    println!("{total}");
}

  
    
    
  1. Yes. total was declared, so it can be set again.
    2. 
    
  2. No. Without mut, a deferred let can be assigned only once, and this one is assigned twice.
    3. 
    
  3. No. A let without a value isn't allowed at all.
    4. 
  

  

    
The first assignment is fine. The second is E0384, the same error as before. The compiler's help suggests let mut total;, which would allow both assignments.

  









Constants



A const is a value the compiler knows before the program runs. It is the Rust counterpart of the constants you already write in PHP, with stricter rules.




  
const TIMEOUT = 30;

final class Limits {
    public const int MAX_USERS = 100_000;
}

  
const TIMEOUT: u32 = 30;
const MAX_USERS: u32 = 100_000;

  
A PHP const must be a constant expression, and PHP reports a bad one before the file runs. Typed class constants, such as const int, arrived in PHP 8.3. define() is the exception, because it accepts a value computed while the program runs. A Rust const is computed by the compiler before the program runs, and it always names its type.





const MAX_USERS: u32 = 100_000;

fn main() {
    let signups: u32 = 99_950;
    let seats_left = MAX_USERS - signups;
    println!("{seats_left} seats left");
}



A constant can be declared outside any function, and every function in the file can use it. By convention its name is SCREAMING_SNAKE_CASE. The underscores in 100_000 are digit separators, and Rust ignores them.




  
The type is required.
const MAX: u32 = 100; is valid. const MAX = 100; is an error: missing type for const item.

  
The value must be known at compile time.
A function call inside the value has to be a const fn. The compiler evaluates the value while it builds the program.

  
The name is SCREAMING_SNAKE_CASE.
This is a convention, but rustc warns when you break it. A constant can sit at the top of a file or inside a function.





Here is the second rule in action. compute is an ordinary function, so the compiler can't run it while it builds the constant. Chapter 04 explains the function signature, the line that starts with fn:



const MAX: u32 = compute();

fn compute() -> u32 {
    3
}

fn main() {
    println!("{MAX}");
}

static, briefly



A const is a value the compiler places wherever you use it. A static is one location in memory that exists for the whole program. You will rarely need one. Do not confuse it with the 'static in &'static str. Chapter 08 explains that type, and Chapter 15 explains lifetimes.



static APP_NAME: &str = "Oxidize";

fn main() {
    println!("{APP_NAME}");
}



static mut also exists. Reading or writing it needs unsafe, which Chapter 21 covers. Until then, use const.




  
Complete the constant so the program prints the number of seconds in a day. Pick a type that can hold the value.

  
const [[SECONDS_PER_DAY]]: [[u32|u64|i32|i64]] = 24 * 60 * 60;

fn main() {
    println!("{SECONDS_PER_DAY}");
}

  
The name is SCREAMING_SNAKE_CASE, as the convention says. All four types can hold 86,400. u32 is the natural choice for a count that is never negative. The compiler evaluates 24 * 60 * 60 while it builds the program, which is what a constant needs.









Warnings you'll see



Warnings don't stop the build. They are rustc noticing something that is probably a mistake. This program compiles, and rustc still has two things to say:



fn main() {
    let retries = 3;
    let mut timeout = 30;
    println!("{timeout}");
}



warning: variable does not need to be mutable
 --> src/main.rs:3:9
  |
3 |     let mut timeout = 30;
  |         ----^^^^^^^
  |         |
  |         help: remove this `mut`
  |
  = note: `#[warn(unused_mut)]` (part of `#[warn(unused)]`) on by default

warning: unused variable: `retries`
 --> src/main.rs:2:9
  |
2 |     let retries = 3;
  |         ^^^^^^^ help: if this is intentional, prefix it with an underscore: `_retries`
  |
  = note: `#[warn(unused_variables)]` (part of `#[warn(unused)]`) on by default

warning: 2 warnings emitted



The first warning is about timeout. It is declared mut, but nothing changes it, so the fix is to remove the mut. The second is about retries, which is never used. A leading underscore says "I know, and it's on purpose". Here are both fixes applied, and the program compiles silently:



fn main() {
    let _retries = 3;
    let timeout = 30;
    println!("{timeout}");
}



A lone _ is different. let _ = value; doesn't create a variable at all, so it doesn't keep the value alive. Chapter 06 covers why that matters for drops.




  
Agents often add mut to code that never reassigns, and they reuse a name through shadowing deep inside a long function until nobody can say which total is which. The first habit shows up as a warning. The second is legal and sometimes right, but when the meaning changes, a new name is clearer.

  
In review, ask for a cargo build with no warnings, and look at every mut the diff adds. Each one should be there because the value really changes.






  
Does this compile, and what does rustc say?

  
fn main() {
    let mut label = "ready";
    println!("{label}");
}

  
    
    
  1. It fails with E0384, because label is assigned twice.
    2. 
    
  2. It compiles with no output from rustc at all.
    3. 
    
  3. It compiles, with a warning that label doesn't need to be mut.
    4. 
  

  

    
It compiles. label is never assigned again, so the mut does nothing, and rustc says so. The warning doesn't stop the program, which prints ready. Clean code has no warnings, and each warning is a cheap catch before review.

  









Practice



Two checks to finish on. The first is about time. Put the events of the shadowing program in the order they happen. It's the program from the quiz earlier in this chapter.




  
    
    
  1. The outer x = 5 is created.
    2. 
    
  2. x is shadowed by x + 1, a new variable holding 6.
    3. 
    
  3. The inner block shadows x with x * 2.
    4. 
    
  4. The inner block ends, and the inner x is gone.
    5. 
    
  5. The outer println! reads x, which is 6.
    6. 
  

  

    
Each let creates a new variable. The second let doesn't destroy the first x. It hides the name. A variable's life ends at the } of its block, so the inner x ends there, and the name refers to the middle x again, the one holding 6.

  





The second check goes the other way. Match each PHP line with the Rust line that does the same job. Pay attention to mutability.




  
    
    
  • let mut x = 5;
    • 
    
  • const RETRIES: u32 = 3;
    • 
    
  • let name = "Ana";
    • 
    
  • let x: i32 = "42".parse().unwrap();
    • 
  






  
Two of these pairs break in places. A PHP readonly property is fixed once it is set, and PHP enforces that at runtime, when the write runs. A Rust let is fixed per binding, and rustc enforces that before the program runs. A new let can shadow a name, which a readonly property can't do. The cast (int) "abc" never fails, and it gives 0. parse() returns a Result, and unwrap() panics on an error. Chapter 11 covers errors properly.

Recap




  
Promises, slots and names

  
    
    
  • A name made with let is immutable by default. Assigning to it again is error E0384. Add mut only when the value really must change.
    • 
    
  • mut lets one variable take new values, and its type stays the same for its whole life.
    • 
    
  • Shadowing is a new let with the same name. The new variable can have a different type. The old one lasts until its scope ends, but nothing can name it.
    • 
    
  • Integers default to i32 and decimals to f64. Annotate with a type like : u8 when you want another.
    • 
    
  • const needs a type and a value the compiler can compute. A let may be declared now and assigned later, but it must be assigned on every path before it is used, or the compiler reports E0381.
    • 
  









  Explain it back: a PHP colleague asks what mut is for, and why anyone would shadow a name. Explain both with one example, in three sentences.
  

    
One good answer: "mut lets one variable take new values, and its type never changes. Shadowing makes a new variable with the same name, so the type can change too.
