Two string types, one idea

Chapter 06 showed that a String owns a heap buffer. Rust has a second text type, &str, and most string questions come down to which of the two you hold.

A String is owned text that can grow. The variable holds a pointer, a length and a capacity, and the bytes live on the heap. A &str is a view: a pointer and a length, 16 bytes on the stack, pointing at bytes that somebody else owns. A view owns nothing, so it can't free anything, and it must not outlive the bytes it points at. Chapter 15 covers how the compiler checks that.

String literals are the third case. "hi" has type &'static str: a view of bytes that are compiled into the program itself.

Step through it and watch the three names. lit points into the binary, owned owns a heap buffer, and view borrows from owned. Only owned is allowed to free anything.

PHP has one string type. A string is a value, and substr() hands you a new string. You never choose between a view and a copy, because PHP makes a copy when it needs one. Rust asks you to choose, and the type in the signature records the choice.

The rule of thumb: if your code owns the text, store a String. If it only looks at text that someone else owns, take a &str. Section 5 turns that rule into function signatures.

Does this compile?

fn main() {
    let s: String = "hi";
    println!("{s}");
}
  1. Yes. A literal turns into a String when the annotation asks for one.
  2. No. A literal is a &str, and the annotation asks for a String.

This is error E0308, mismatched types. Convert the literal with "hi".to_string(), "hi".to_owned() or String::from("hi"). Section 6 lists the conversions.

Slices: a window into data

A slice is a window onto a run of data that already sits in memory. It is a pointer to the first element and a length. You write it with a range inside square brackets: &s[0..5] is the first five bytes of s, and &v[1..3] is the second and third elements of a vector.

RangeCoversOn "Laravel"
a..bfrom a up to, not including, b&s[2..4] is "ra"
a..from a to the end&s[3..] is "avel"
..bfrom the start up to, not including, b&s[..3] is "Lar"
a..=bfrom a up to and including b&s[2..=4] is "rav"
..everything&s[..] is "Laravel"

Two things to keep in mind. The numbers are byte positions, not character positions, and section 4 explains why that matters. And a slice is a borrow: it is valid only while the string it points into is alive.

Step through this program. The question on line 4 is the one most people get wrong.

Line 4 creates world with the same type as hello, but it points at byte 6 of the buffer that s owns. A slice is a shared borrow of s. Chapter 07 covered borrows, and a slice is the same rule seen through text.

Vectors work the same way. &v[1..3] has type &[i32], a slice of integers.

What does this print?

fn main() {
    let name = "Laravel";
    println!("{}|{}", &name[..3], &name[3..]);
}
  1. Lar|avel
  2. Lara|vel
  3. L|aravel

..3 covers bytes 0, 1 and 2, and 3.. starts at byte 3. Together they cover the whole word, with no overlap and nothing lost.

Why returning a slice beats returning an index

Here is a common first attempt at a function that finds the first word of a sentence. It returns a position, which is a plain number.

This compiles. What does it print, and why?

fn first_word(s: &str) -> usize {
    let bytes = s.as_bytes();
    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return i;
        }
    }
    s.len()
}

fn main() {
    let mut s = String::from("hello world");
    let end = first_word(&s);
    s.clear();
    println!("first word ends at {end}");
}
  1. It doesn't compile, because s is cleared while end still exists.
  2. It compiles and prints first word ends at 5. The number still says 5 after s is empty.
  3. It compiles and prints first word ends at 0, because clear() resets every number that came from s.

end is a plain usize, and nothing connects it to s. The compiler has no reason to object. After s.clear() the number is stale: it points at a position that no longer holds a word. The program runs, prints something plausible, and is wrong. That is the worst kind of bug, because nothing warns you.

Now return the word itself. A slice of the input is a borrow, so the compiler knows which string the result depends on.

fn first_word(s: &str) -> &str {
    let end = s.find(' ').unwrap_or(s.len());
    &s[..end]
}

fn main() {
    let mut s = String::from("hello world");
    let word = first_word(&s);
    s.clear();
    println!("first word: {word}");
}

Here is the real output for that program:

error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
  --> src/main.rs:9:5
   |
 8 |     let word = first_word(&s);
   |                           -- immutable borrow occurs here
 9 |     s.clear();
   |     ^^^^^^^^^ mutable borrow occurs here
10 |     println!("first word: {word}");
   |                            ---- immutable borrow later used here

For more information about this error, try `rustc --explain E0502`.

This is the error you want. The compiler now catches the bug that the index version let through. The timeline shows why: the borrow in word has to stay alive until its last use, and the clear sits inside that stretch.

Move the use above the clear and the program is fine:

fn first_word(s: &str) -> &str {
    let end = s.find(' ').unwrap_or(s.len());
    &s[..end]
}

fn main() {
    let mut s = String::from("hello world");
    let word = first_word(&s);
    println!("first word: {word}");
    s.clear();
    println!("after clear: [{s}]");
}

Return a slice when the answer is part of the input. Return an index only when you truly need a position, and remember that the position means something only for the string it came from.

UTF-8: bytes, chars and what you see

Rust strings are UTF-8. Each character takes between one and four bytes. An ASCII letter takes one, é takes two, most CJK characters take three, and emoji usually take four. The length in bytes and the length in characters are different numbers, and Rust makes you pick the one you mean.

Predict: what do "héllo".len() and "héllo".chars().count() return?

.len() gives 6 and .chars().count() gives 5. The é takes two bytes, but it is one character.

fn main() {
    let s = "héllo";
    println!("{} bytes", s.len());
    println!("{} chars", s.chars().count());
}

Indexing is where most of the trouble starts, because s[0] looks as if it should work on any string:

fn main() {
    let s = String::from("hello");
    let first = s[0];
    println!("{first}");
}
error[E0277]: the type `str` cannot be indexed by `{integer}`
 --> src/main.rs:3:19
  |
3 |     let first = s[0];
  |                   ^ string indices are ranges of `usize`
  |
  = help: the trait `SliceIndex<str>` is not implemented for `{integer}`
  = note: you can use `.chars().nth()` or `.bytes().nth()`
          for more information, see chapter 8 in The Book: <https://doc.rust-lang.org/book/ch08-02-strings.html#indexing-into-strings>

For more information about this error, try `rustc --explain E0277`.

The compiler won't guess. "The first character" could mean the first byte, the first char, or the first visible letter, and finding the nth char means walking the bytes from the start. Say which one you mean:

  • s.as_bytes()[0] gives the first byte, as a u8.
  • s.chars().nth(0) gives the first character, as an Option<char>.
  • &s[0..1] gives the first byte as a &str. That is a whole character only when the first character is one byte long. Otherwise it panics.

Slicing has a second trap. &s[0..2] has the right types, so it compiles. It fails when it runs:

fn main() {
    let s = "héllo";
    let part = &s[0..2];
    println!("{part}");
}

The program panics with this message:

end byte index 2 is not a char boundary; it is inside 'é' (bytes 1..3 of string)

Byte 2 is the second byte of é. The character occupies bytes 1 and 2, and the slice ends in the middle of it. The message writes that span as 1..3, with the end excluded. A &str must always hold valid UTF-8, so Rust stops the program here rather than hand you half a character.

s.get(0..2) returns None instead of panicking. Use it whenever the boundaries come from input you don't control.

Bytes, chars and graphemes

Three methods show three levels. .bytes() gives the raw bytes, .chars() gives Unicode scalar values, and .char_indices() gives each character together with the byte position where it starts.

fn main() {
    let s = "héllo";
    for c in s.chars() {
        print!("[{c}]");
    }
    println!();
    let bytes: Vec<u8> = s.bytes().collect();
    println!("{bytes:?}");
    for (i, c) in s.char_indices() {
        println!("{i}: {c}");
    }
}

A char is a Unicode scalar value, and it is not always what a reader sees as one character. The flag 🇵🇰 is two chars, but a reader sees one symbol, a grapheme cluster. Counting graphemes takes the unicode-segmentation crate: "🇵🇰".graphemes(true).count() returns 1. Most code works with chars() or bytes(). Graphemes matter for text that a person reads and counts, such as a name that must fit in a column.

$s = "héllo";
strlen($s);            // 6 bytes
mb_strlen($s);         // 5 characters
mb_substr($s, 0, 2);   // "hé"
substr($s, 0, 2);      // "h" plus half of "é"
  
fn main() {
    let s = "héllo";
    println!("{}", s.len());                                 // 6 bytes
    println!("{}", s.chars().count());                       // 5 characters
    println!("{}", s.chars().take(2).collect::<String>());  // hé
    println!("{:?}", s.get(0..2));                           // None, not a panic
}

PHP strings are byte arrays too, so the byte view matches. The difference is what happens at the boundary. substr() hands you a broken byte sequence, and that string keeps travelling through your code. Rust never lets a &str hold invalid UTF-8, and each method says whether it counts bytes or characters.

Agents often truncate text with &title[..80]. That compiles, and it passes every test that uses ASCII titles. The first title with an é or an emoji panics in production. When you review code that slices with numbers, check that each number is a byte offset that lands between characters. To cut by characters, write title.chars().take(80).collect::<String>().

Now try it. Type any text, choose a start and an end, and watch the bytes. Each square is one byte, and the squares for one character share a tint.

Take &str, return String

A parameter type decides what callers can pass in. For a function that only reads text, use &str. It accepts a string literal, a slice of a larger string, and a &String. The last one is converted automatically by deref coercion, because String dereferences to str. A String parameter accepts only a String, and it takes ownership of that value.

fn greet(name: &str) -> String {
    format!("Hello, {name}!")
}

fn main() {
    let owned = String::from("Ana");
    println!("{}", greet(&owned));  // &String becomes &str
    println!("{}", greet("Bo"));     // a literal is already a &str
}

The return type follows the same logic from the other side. A function that creates new text returns a String, because the caller has to own what was made. A function that returns part of its input returns a &str tied to that input, as first_word did in section 3.

Agents write fn f(s: &String) constantly, because &String is the type they already hold. Clippy flags it with the ptr_arg lint, which says: writing &String instead of &str involves a new object where a slice will do. Treat that as a review finding. A parameter that is only read should be &str. A String parameter claims that the function needs to own the text, so ask why it does.

A function only reads the text it receives. Which parameter type should it use?

  1. fn f(s: String)
  2. fn f(s: &String)
  3. fn f(s: &str)

&str accepts everything the other two accept, and it asks nothing extra of the caller. The other two forms are stricter for no benefit.

Building and changing strings

Most methods that change a String take &mut self and edit the buffer in place. Methods on a &str never change anything: they return a new value or a view. Read the return type first, because it tells you whether a method allocates.

MethodReturnsAllocates?
push_str, pushnothing; the String changesonly when the buffer must grow
to_uppercase, replace, format!a new Stringyes
trima &str view of the originalno
split, split_whitespace, linesan iterator of &str viewsno
contains, starts_with, findbool, or Option<usize> for findno
parse::<i32>()Result<i32, ParseIntError>no

This program uses most of them. Each line of output comes from one method call, so you can match them up:

fn main() {
    let mut greeting = String::from("hello");
    greeting.push_str(", world");
    greeting.push('!');
    println!("{greeting}");

    let shout = greeting.to_uppercase();
    println!("{shout}");

    println!("[{}]", "   trim me   ".trim());

    let words: Vec<&str> = "one two  three".split_whitespace().collect();
    println!("{words:?}");

    let parts: Vec<&str> = "a,b,c".split(',').collect();
    println!("{}", parts.join(" | "));

    for (n, line) in "line one\nline two".lines().enumerate() {
        println!("{}: {line}", n + 1);
    }

    println!("{}", "cats and cats".replace("cats", "dogs"));
    println!("{}", greeting.contains("world"));
    println!("{}", greeting.starts_with("hello"));
    println!("{:?}", greeting.find("world"));

    let n: i32 = "42".parse().unwrap();
    println!("{}", n + 1);
    println!("{}", "4x".parse::<i32>().is_err());

    let report = format!("{n} items, {} total", n * 2);
    println!("{report}");
}

There is one operator on strings, +, and it follows the ownership rules from Chapter 06. s1 + &s2 calls add(self, &str). The left side is moved into the call, and its buffer is reused for the result. The right side is only borrowed.

fn main() {
    let s1 = String::from("tic");
    let s2 = String::from("-tac");
    let s3 = s1 + &s2;
    println!("{s3}");
    println!("{s2}");
}

Converting between the two types is common enough to memorize. Each of these gives you an owned String from a literal, and they all end up with the same bytes:

ExpressionGivesNotes
String::from("x")StringThe explicit form. This course uses it.
"x".to_string()StringWorks for anything that implements Display.
"x".to_owned()StringSame result for a &str.
"x".into()StringNeeds the target type: let s: String = "x".into();
s.as_str()&strA view of the String. No copy.
&s&StringCoerces to &str wherever a &str is expected.
Which of these allocates a new buffer: trim(), to_uppercase() or split()?

Only to_uppercase(). It returns a new String with different letters, so it needs new bytes. trim() returns a view of the original text with the surrounding spaces left out, and split() returns an iterator of views. Neither copies a byte.

Practice

Four quick checks, then a fill-in and a match. Answer each one before you read the explanation.

Does this compile?

fn main() {
    let s1 = String::from("tic");
    let s2 = String::from("-tac");
    let s3 = s1 + &s2;
    println!("{s3} {s1}");
}
  1. Yes. + works on a copy of s1.
  2. No. s1 was moved into +, so it can't be read afterwards.

The left operand of + is moved, the same way let t = s1; moves it in Chapter 06. The right operand is only borrowed, which is why s2 is still usable. This is error E0382. To keep s1, write format!("{s1}{s2}"), which borrows both.

What does this print?

fn main() {
    let e = "é";
    println!("{} {}", e.len(), e.chars().count());
}
  1. 2 1
  2. 1 1
  3. 2 2

é is one character encoded in two bytes. .len() counts bytes, and .chars().count() counts characters.

Does this compile?

fn main() {
    let name = "Ana";
    let initial = name[0];
    println!("{initial}");
}
  1. Yes. It stores the byte 65, which is the letter A.
  2. No. A &str can't be indexed by an integer. This is error E0277.

A string literal is a &str, so the rule is the same as for a String. Choose a meaning explicitly: name.as_bytes()[0], name.chars().nth(0) or &name[0..1].

What does this print?

fn main() {
    for (i, c) in "añb".char_indices() {
        println!("{i} {c}");
    }
}
  1. Indexes 0, 1, 2, because b is the third character.
  2. Indexes 0, 1, 3, because ñ is two bytes wide.
  3. Indexes 0, 2, 3, because ñ starts at byte 2.

ñ starts at byte 1 and takes two bytes, so b starts at byte 3. char_indices() reports byte positions, not character counts.

Fill in the two types so that first_word reads a string without taking it, and returns a view of its first word.

fn first_word(s: [[&str]]) -> [[&str]] {
    s.split(' ').next().unwrap_or("")
}

fn main() {
    println!("{}", first_word("hello world"));
}

Both types are &str. The parameter is a borrow, so the caller keeps its String. The return value is a slice of that same input, so it is a borrow too, and nothing is allocated. Returning String would not compile here, because the value is a &str, and to make it a String you would have to copy the word.

  • the byte count: s.len()
  • the character count: s.chars().count()
  • split on a separator: s.split(' ')
  • join pieces: parts.join(", ")
  • uppercase: s.to_uppercase()
  • strip the edges: s.trim()

split returns a lazy iterator, not an array. When you need the array that explode gives you, add .collect::<Vec<_>>(). Nothing is split until something pulls on the iterator.

Act II wrap-up

Chapters 05 through 08 are one idea seen from several angles. Every value has one owner. Every borrow is a view that must not outlive the thing it looks at.

  • Copy types such as integers are copied. Values that own heap memory, such as a String, have exactly one owner (Chapters 05 and 06).
  • Assigning or passing a value that isn't Copy moves it, and the old name becomes unusable (Chapter 06).
  • A borrow is a shared &T or an exclusive &mut T: many readers or one writer (Chapter 07).
  • A slice or a &str is a borrow with a length, and it must not outlive its owner (Chapters 07 and 08).
  • String owns text and &str views it. Take a &str in, and return a String out when you create new text.
ToolUse it whenCost
MoveThe caller is finished with the value.Free
Borrow (&, &mut)The other code only needs to look at the value, or edit it for a moment.Free
Clone (.clone())You need two values that can change independently.An allocation and a copy
A function needs only the length of a String the caller already holds. Should it move, clone or borrow?

Borrow. Take a &str and call .len(). Moving gives the String away for no reason, and cloning allocates for nothing.

Recap

Two views, one idea

  • String owns heap text: pointer, length and capacity. &str is a view: pointer and length, and no ownership.
  • "hi" is a &'static str, and its bytes live in the program.
  • &s[a..b] is a slice, a shared borrow of the owner's bytes. Its numbers are byte positions.
  • Strings are UTF-8. .len() counts bytes, .chars() counts characters, and s[0] doesn't compile.
  • A slice that starts or ends inside a character panics. s.get(a..b) returns an Option instead.
  • Take &str in and return String out. + moves its left side, and a method's return type tells you whether it allocates.
Explain it back: explain String versus &str using the word "view".

One good answer: "A String owns its text. It has a heap buffer, and when it goes out of scope the buffer is freed. A &str is a view: a pointer and a length that look at text owned by something else. It allocates nothing and frees nothing. If your code owns the text, use a String. If it only looks at the text, take a &str."

If your version said owns, view and frees nothing, you have it.
