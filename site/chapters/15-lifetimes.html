You've been using lifetimes all along

Every reference in Rust has a lifetime: the span of code where that reference must stay valid. The borrow bars from Chapter 07 were lifetimes. Each one ran from a borrow to the last place that borrow was used.

The compiler works out nearly all of them for you, inside function bodies. That is why most Rust code never writes one down. You do write them in signatures, where the compiler needs a relationship spelled out. The next two sections show why.

Here is a program the compiler rejects. Step through it and watch which bar outlives its owner.

This is the compiler's report for that program. Read it from the top. The first label marks where x is declared. The caret marks the borrow. The closing brace is where x is dropped, and the last label marks the use that still needed it.

error[E0597]: `x` does not live long enough
 --> src/main.rs:5:13
  |
4 |         let x = 5;
  |             - binding `x` declared here
5 |         r = &x;
  |             ^^ borrowed value does not live long enough
6 |     }
  |     - `x` dropped here while still borrowed
7 |     println!("{r}");
  |                - borrow later used here

For more information about this error, try `rustc --explain E0597`.
Think first: what would make this program compile?

Two fixes work. Move let x = 5; out of the inner block, so x lives until the end of main, past the println!. Or stop using r after the block. Neither fix changes a type. Both change where a span ends, and the borrow has to fit inside the owner's span.

Watch the same program as a motion explainer. Each block has a Tick. Its sand is the lifetime of the value declared in that block: the span of code where a reference to the value must stay valid. When the sand runs out, the value is dropped.

The fix is to use r while the sand still runs, by printing it inside the block. This version compiles and prints 5.

fn main() {
    let r;
    {
        let x = 5;
        r = &x;
        println!("{r}");
    }
}

Why functions need annotations

Inside one function, the compiler sees every line. It can follow each borrow from start to finish and place the bars itself.

A function signature is different. Callers are checked against the signature, and the compiler does not re-read the body of a function that is being called. So the signature has to carry the relationship that the body depends on. Here is a function that returns the longer of two strings. It looks reasonable.

fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    println!("{}", longest("abc", "de"));
}

It does not compile. Here is the real output:

error[E0106]: missing lifetime specifier
 --> src/main.rs:1:33
  |
1 | fn longest(x: &str, y: &str) -> &str {
  |               ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y`
help: consider introducing a named lifetime parameter
  |
1 | fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
  |           ++++     ++          ++          ++

For more information about this error, try `rustc --explain E0106`.

Read the main message first. The signature does not say whether the result is borrowed from x or from y. A caller needs that answer. If the result came from x, the caller must keep x alive for as long as it keeps the result. If it came from y, the caller must keep y alive instead. The compiler refuses to guess.

The help line is the compiler's suggestion, and it is correct. It adds <'a> and gives the same name to both inputs and the output. That shared name says the output is tied to both inputs, which is the relationship the compiler was missing.

An annotation doesn't make anything live longer. It describes which borrow the output came from.

The same idea with two inputs. Watch which value the result depends on, and when the sand runs out.

Printing result inside the block, while y still exists, compiles and prints the longer string:

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    let x = String::from("long string");
    let result;
    {
        let y = String::from("xyz");
        result = longest(x.as_str(), y.as_str());
        println!("The longest string is {result}");
    }
}
Why not let the compiler read the body and work the answer out?

A caller is checked against the signature alone. If the compiler looked inside bodies, a change to one function could break a check in code far away, and a reader of the signature could not tell what the function promises. Rust keeps the promise in the signature, so every call can be checked by reading only the signature.

Reading 'a

Here is the signature the compiler accepts:

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

Read it in three parts. <'a> declares a lifetime, a name for a span of code. x: &'a str and y: &'a str say that both arguments must be valid for that span. -> &'a str says the result is valid for that span too.

In words: the result is valid for at most as long as both x and y are valid. The name 'a stands for the overlap of the two spans, so a caller can keep the result only while both inputs are still alive.

The name does not measure time. It links references together. Every reference that carries 'a has to be valid for 'a, and the compiler picks the span that makes all of them true.

A parameter that doesn't carry the name is not tied to the result. In this version only x is linked:

fn first<'a>(x: &'a str, y: &str) -> &'a str {
    x
}

y has no name, so the output has no relationship to it. A caller can drop y as soon as the call returns.

Does this compile?

fn first<'a>(x: &'a str, y: &str) -> &'a str {
    x
}

fn main() {
    let x = String::from("long string");
    let result;
    {
        let y = String::from("xyz");
        result = first(&x, &y);
    }
    println!("{result}");
}
  1. Yes. The result borrows only from x, so y can be dropped at the inner brace.
  2. No. The result might borrow from y, and y is dropped first.

Only the parameters that carry 'a are tied to the result. Here that is x and nothing else. y is a plain borrow for the length of the call, and the result has no use for it afterwards.

When you don't need to write them: elision

Most signatures need no lifetimes at all. The compiler fills in the common cases with three rules, called elision. If the rules give every output reference a lifetime, the signature compiles. If they can't, you get E0106 and write the lifetimes yourself.

Each reference parameter gets its own lifetime.

fn f(a: &str, b: &str) is read as fn f<'a, 'b>(a: &'a str, b: &'b str).

If there is exactly one input lifetime, it goes to every output.

fn first_word(s: &str) -> &str is read as fn first_word<'a>(s: &'a str) -> &'a str.

If one parameter is &self or &mut self, the output gets self's lifetime.

This holds whatever the other parameters are.

As writtenAs the compiler sees it
fn first_word(s: &str) -> &strfn first_word<'a>(s: &'a str) -> &'a str, by rule 2
fn name(&self, _locale: &str) -> &strfn name<'a, 'b>(&'a self, _locale: &'b str) -> &'a str, by rules 1 and 3
fn longer(a: &str, b: &str) -> &strRejected with E0106. Rule 1 gives two input lifetimes, and rule 2 needs exactly one. There is no self for rule 3.

Read the table as a check. Apply the rules to each signature, and see whether every output gets a lifetime. The first two rows pass. The third row is the case where you have to write the lifetimes yourself.

Rule 3 is the one people get wrong. It ties the output to self even when the function returns an argument. The compiler then checks the body against that claim, and it can reject the function. The practice section has an example.

Which of these three functions does not compile as written?

struct Doc {
    name: String,
}

impl Doc {
    fn name(&self, _locale: &str) -> &str {
        &self.name
    }
}

fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap_or("")
}

fn longer(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let d = Doc { name: String::from("Ana") };
    println!("{} {}", d.name("en"), first_word("hi there"));
    println!("{}", longer("ab", "c"));
}
  1. first_word(s: &str) -> &str
  2. name(&self, _locale: &str) -> &str
  3. longer(a: &str, b: &str) -> &str

longer has two reference inputs, so rule 1 gives them two lifetimes. Rule 2 needs exactly one input lifetime, and rule 3 needs a self. Nothing decides the output's lifetime, so the compiler asks you to name it. The other two follow the rules.

The anonymous lifetime, '_

Write '_ when a type has a lifetime parameter and you don't want to name it. It means "a lifetime here, which the compiler works out". Formatter<'_> is the formatter that the Display impl in Chapter 11 receives. Its lifetime ties it to the output it writes into, and the signature doesn't need a name for that. You can also write plain fmt::Formatter, which the compiler reads the same way.

The same mark appears in return types, as in impl Iterator<Item = String> + '_. It says that the returned iterator borrows from whatever &self points to. Since edition 2024 the compiler adds that link for you, so the + '_ is optional. Edition 2021 needs it, and without it the compiler stops with E0700.

struct Team {
    members: Vec<String>,
}

impl Team {
    fn names(&self) -> impl Iterator<Item = String> + '_ {
        self.members.iter().cloned()
    }
}

fn main() {
    let t = Team { members: vec!["Ana".to_string(), "Bo".to_string()] };
    for n in t.names() {
        println!("{n}");
    }
}

Structs that borrow

A struct can hold a reference too. It then needs a lifetime parameter, because a value of that struct is valid only while the reference inside it is valid.

Here is a small parser. It returns words from its input without copying any of them. Each word is a slice of the text it was given.

struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self {
        Parser { input, pos: 0 }
    }

    // The word is tied to the input ('a), not to the &mut borrow of the parser.
    fn next_word(&mut self) -> Option<&'a str> {
        let rest = &self.input[self.pos..];
        let trimmed = rest.trim_start();
        if trimmed.is_empty() {
            return None;
        }
        let start = self.input.len() - trimmed.len();
        let end = trimmed.find(' ').map_or(self.input.len(), |i| start + i);
        self.pos = end;
        Some(&self.input[start..end])
    }
}

fn main() {
    let text = String::from("let there be light");
    let mut parser = Parser::new(&text);
    let first = parser.next_word().unwrap();
    let second = parser.next_word().unwrap();
    println!("{first} | {second}");
}

Read the return type of next_word. Option<&'a str> says the word comes from the input, not from the parser. Each word stays valid after the next call, so main can keep both of them.

Now try the change most people make first. Write the return type with an elided lifetime, Option<&str>, and compile again. Here is what rustc says:

error[E0499]: cannot borrow `parser` as mutable more than once at a time
  --> src/main.rs:29:18
   |
28 |     let first = parser.next_word().unwrap();
   |                 ------ first mutable borrow occurs here
29 |     let second = parser.next_word().unwrap();
   |                  ^^^^^^ second mutable borrow occurs here
30 |     println!("{first} | {second}");
   |                ----- first borrow later used here

For more information about this error, try `rustc --explain E0499`.

Without 'a, rule 3 gives each word the lifetime of the &mut self borrow. The first word then still borrows the parser when the second call asks for a mutable borrow, and Rust allows only one of those at a time. The name 'a is what makes the two calls legal.

A struct also can't outlive the text it borrows. Its method returns &'a str, not &str, so the slice stays tied to the text and not to the borrow of the struct. The bar for a struct that holds a slice of a String sits inside the bar for the String:

Does this compile?

struct Excerpt<'a> {
    part: &'a str,
}

impl<'a> Excerpt<'a> {
    fn text(&self) -> &'a str {
        self.part
    }
}

fn main() {
    let excerpt;
    {
        let text = String::from("call me Ishmael. Some years ago");
        excerpt = Excerpt { part: &text[..15] };
    }
    println!("{}", excerpt.text());
}
  1. Yes. A slice stored in a struct is copied, so it can outlive text.
  2. No. text is dropped at the inner brace, but excerpt still points into it.
  3. No. A struct can't hold a reference at all.

The slice is not copied. The struct holds a reference into text, and that reference has to stay valid wherever excerpt is used. The error is E0597, on text.

Borrowing is the right choice for a short-lived view over text that someone else owns. A parser, or a report built from one request body, is a good fit. Owned fields are the better choice when the struct is long-lived, when it goes into a collection that outlives its input, or when it moves to another thread. A String field costs an allocation, and it removes the lifetime from every caller's signature.

PHP's explode() returns new strings, and the array owns them. Rust's split() returns views into the original string, with no copies. You save the copies, and you pay with a lifetime: each view is valid only while the string it points into is valid.

'static, and what T: 'static really means

The lifetime 'static lasts for the whole run of the program. String literals have that type. Their bytes are stored in the program itself, so the reference is valid from start to finish.

let greeting: &'static str = "hello";
println!("{greeting}");

You will meet the word in bounds too, such as T: 'static. Read it as "T holds no borrows shorter than the whole program." It does not mean "T lives forever". A value can be dropped at the end of a function and still satisfy the bound, as long as it doesn't borrow anything shorter-lived.

An owned String is the standard example. It contains no borrows, so it satisfies T: 'static, even though it is dropped early. A &String points at a local, so it doesn't satisfy the bound. Here is a function with that bound, and two calls to it. The other bound, Send, means the value is safe to move to another thread. Chapter 18 explains it.

fn spawn_it<T: Send + 'static>(t: T) {
    drop(t);
}

fn main() {
    let owned = String::from("owned");
    spawn_it(owned);
    let s = String::from("borrowed");
    spawn_it(&s);
}
One of the two calls is rejected. Which one, and why?

The second. spawn_it(&s) passes a borrow of s. The bound says T holds no borrows shorter than the program, and a borrow of a local is shorter. The first call moves a String in, and a String holds no borrows.

Here is what rustc says about the second call:

This is why thread::spawn asks for 'static. A spawned thread can keep running after the function that started it has returned, so the closure it runs can't borrow the caller's locals. Chapter 18 builds on that rule. For now, remember the test: does the value carry a borrow of something local?

The lifetime errors, decoded

Most lifetime trouble shows up as one of five errors. They all say the same thing in different words: a borrow is valid for one span, and the code needs it valid for a different span.

ErrorWhat it meansUsual fix
E0106 missing lifetime specifierAn output reference can't be tied to any input.Name the relationship with a lifetime on the inputs and the output, or return an owned value.
E0597 does not live long enoughA borrow is still used after its owner was dropped.Make the owner live longer, by moving it out of the block, or use the borrow earlier.
E0515 cannot return reference to localThe function returns a borrow of a value it owns. That value is dropped when the function returns.Return the owned value, such as a String, and let the caller own it.
E0716 temporary value dropped while borrowedA temporary, like the String from String::from, is freed at the end of its statement, but a borrow of it is still in use.Bind the temporary to a name with let, so it lives on.
lifetime may not live long enough (no code)A function returns a reference with one lifetime where its signature promises another.Decide where the data really comes from, and make the signature say so.

E0106 and E0597 you have already seen. Here are the other three, each with a real program and the real output.

E0515 returns a reference to a value the function owns. The text String is created inside greeting, so it is dropped when greeting returns. &text would point at a value that no longer exists:

fn greeting(name: &str) -> &str {
    let text = format!("hello, {name}");
    &text
}

fn main() {
    println!("{}", greeting("Ana"));
}
error[E0515]: cannot return reference to local variable `text`
 --> src/main.rs:3:5
  |
3 |     &text
  |     ^^^^^ returns a reference to data owned by the current function

For more information about this error, try `rustc --explain E0515`.

The fix is to give the owned value to the caller. Return the String, and the caller owns it from then on:

fn greeting(name: &str) -> String {
    format!("hello, {name}")
}

fn main() {
    println!("{}", greeting("Ana"));
}

E0716 is about temporaries. String::from("temporary") creates a value with no name. It is freed at the end of the statement, but the reference that as_str returns is used on a later line:

fn main() {
    let s: &str = String::from("temporary").as_str();
    println!("{s}");
}
error[E0716]: temporary value dropped while borrowed

  |                   ^^^^^^^^^^^^^^^^^^^^^^^^^         - temporary value is freed at the end of this statement
  |                   |
  |                   creates a temporary value which is freed while still in use
3 |     println!("{s}");
  |                - borrow later used here

For more information about this error, try `rustc --explain E0716`.

Bind the temporary to a name first, so it lives until the end of main:

fn main() {
    let text = String::from("temporary");
    let s: &str = text.as_str();
    println!("{s}");
}

Rust does extend some temporaries. This compiles, because a plain & on the right of a let keeps the temporary alive until the end of the enclosing block:

let r: &String = &String::from("kept");

The extension covers a plain &. It does not cover a method call such as as_str(), which is why the first example fails.

The last error has no code. It appears when a function returns a reference with one lifetime, where its signature promises another. pick promises a reference valid for 'a, the lifetime of the struct's field. It returns other, which has its own, unrelated lifetime 'b:

struct Holder<'a> {
    name: &'a str,
}

impl<'a> Holder<'a> {
    fn pick<'b>(&self, other: &'b str) -> &'a str {
        other
    }
}

fn main() {
    let h = Holder { name: "a" };
    println!("{}", h.pick("b"));
}
error: lifetime may not live long enough
 --> src/main.rs:7:9
  |
5 | impl<'a> Holder<'a> {
  |      -- lifetime `'a` defined here
6 |     fn pick<'b>(&self, other: &'b str) -> &'a str {
  |             -- lifetime `'b` defined here
7 |         other
  |         ^^^^^ method was supposed to return data with lifetime `'a` but it is returning data with lifetime `'b`
  |
  = help: consider adding the following bound: `'b: 'a`

The compiler's help suggests the bound 'b: 'a. That bound is a promise every caller would have to accept, and it is usually the wrong fix. Ask where the data really comes from. If it comes from the struct, return self.name. If it comes from the argument, the signature should say &'b str.

Agents, and people under deadline, fix lifetime errors in two bad ways. They add 'static to signatures until the error goes away, or they clone into a String at every call site. Both can make the message disappear while hiding the real design.

When you review agent-written Rust, ask the same question as before. Which value owns the data, and how long does it need to live? If owned data is the right answer, say so and make the owner live long enough. If a borrow is right, keep the borrow.

An agent says it fixed E0597 by changing a parameter from &str to &'static str. What should you check?

Whether the values really are 'static. A string literal is. A String built at runtime is not, so the callers that pass one will fail again, or they will have to leak it to satisfy the bound. The change moves the error to the call sites instead of removing it. Ask what owns the data, and make that owner live long enough, or return an owned value.

Practice

Answer each check before you open its explanation. Some of the programs are meant to fail. The compiler's verdict is the answer that counts.

What does the 'a in this signature promise?

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
  1. The strings live for 'a seconds, so they can't be dropped early.
  2. The result is valid only while both x and y are valid. It can't outlive either one.
  3. The function makes x and y live as long as the result, by copying them.
  4. Nothing. The annotation is documentation, and the compiler ignores it.

'a is a label for a span of code, not a duration. The result's span is the overlap of the two input spans. The function can't make x or y live longer. It can only state how they relate.

Does this compile?

struct Config {
    name: String,
}

impl Config {
    fn name_or(&self, fallback: &str) -> &str {
        if self.name.is_empty() { fallback } else { &self.name }
    }
}

fn main() {
    let c = Config { name: String::new() };
    println!("{}", c.name_or("guest"));
}
  1. Yes. The output is tied to self, and self lives long enough.
  2. No. Rule 3 ties the output to self, but fallback may not live as long as self. Returning it promises too much.
  3. No. A method can never return a reference.

Rule 3 fixes the output to self's lifetime. The body then returns fallback, which has no relationship to self, so the body breaks the promise the signature made. Name the relationship and the program compiles: fn name_or<'a>(&'a self, fallback: &'a str) -> &'a str. The output is now valid only while both inputs are.

Does this compile?

fn main() {
    let words: Vec<&str>;
    {
        let text = String::from("one two");
        words = text.split(' ').collect();
    }
    println!("{words:?}");
}
  1. Yes. split and collect copy the text into the Vec.
  2. No. words holds references into text, and text is dropped at the inner brace while words is still used.
  3. No. A Vec can never hold &str values.

split yields slices of text, and collecting them keeps those slices. So words borrows from text. The inner brace drops text, and then println! reads words. Mapping each piece to an owned String first copies the text. With words declared as Vec<String>, the line words = text.split(' ').map(String::from).collect(); compiles, because the Vec owns its words.

Does this compile? The function is meant to return a label for an id.

fn label(id: u32) -> &'static str {
    let text = format!("item-{id}");
    text.as_str()
}

fn main() {
    println!("{}", label(7));
}
  1. Yes. Returning &'static str makes any reference valid.
  2. No. text is dropped when label returns, but as_str returns a borrow of it.
  3. No. format! can't be used in a function that returns a reference.

The return type &'static str promises a reference that lives for the whole program. text is a local String, dropped when label returns, so the returned reference would point at freed memory. Return the owned value instead: fn label(id: u32) -> String.

Here spawn_it is called with an owned String. Does the bound T: 'static accept it?

fn spawn_it<T: Send + 'static>(t: T) {
    drop(t);
}

fn main() {
    spawn_it(String::from("owned"));
}
  1. No. Only string literals satisfy 'static.
  2. Yes. An owned String contains no borrows, so no part of it is shorter than the program.
  3. Only if the String is stored in a static variable first.

'static limits what a type borrows, not how long its value lives. A String owns its bytes and holds no references. A string literal is one example that passes the bound, but it is not the only one.

Fill in the blanks so the output is valid for at most as long as both inputs. The lifetime has to be declared on the function, and it has to be put on x.

fn longest<[['a]]>(x: &[['a]] str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

Declare 'a in the angle brackets, then put it on x. y and the result already use 'a. Now all three share one name, so the output is valid only while both inputs are.

  1. y is declared inside the inner block, so it will be dropped at that block's closing brace.
  2. longest ties its output to both x and y, so result may borrow from y.
  3. println! reads result after the block, so the borrow has to be valid on that line.
  4. At the closing brace, y is dropped while result still borrows from it.
  5. A borrow that outlives its owner is an error, so rustc reports E0597 on y.

A simple model of what happens: first, work out how long each borrow must be valid. Here that runs from the call on line 10 to the print on line 12. Then compare that span with the span where each owner lives. The borrow's span runs past the end of y, so the program is rejected.

Recap

Lifetimes are relationships

  • A lifetime is the span where a reference must stay valid. The compiler infers most of them inside function bodies.
  • An annotation like 'a never makes anything live longer. It says which borrow an output came from.
  • fn longest<'a>(x: &'a str, y: &'a str) -> &'a str returns a result valid for at most as long as both inputs.
  • Elision fills in the common cases. One input lifetime goes to every output, and &self lends its lifetime to the output.
  • A struct that holds a reference gets a lifetime parameter, and it can't outlive the value it borrows.
  • 'static means no borrow shorter than the program. Owned data satisfies T: 'static.
  • E0106, E0597, E0515 and E0716 each say that a borrow and its owner don't line up. Fix the relationship, or change who owns the data.
Explain it back: What does -> &'a str promise the caller?

One good answer: "It promises that the reference stays valid for the span 'a. Because 'a is the overlap of the input spans, the caller can keep the result only while both inputs are alive. The caller relies on that promise without reading the body, and the body has to keep it whichever input it returns."

If your version mentioned the overlap of the inputs and the caller doesn't read the body, you have the idea.
