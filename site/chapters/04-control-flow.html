Functions

A function is a named block of code with a signature. The signature lists the parameters, their types and the return type. It is a contract. The compiler checks every call against it, and it never has to read the body to do that.

fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() {
    let total = add(2, 3);
    println!("{total}");
}

Read the signature in order. fn add names the function. a: i32 is a parameter called a of type i32, the 32-bit integer from Chapter 03. -> i32 is the return type. The body is one expression, a + b, with no semicolon, so its value is what add returns.

Parameter types are mandatory. Rust does not work out a parameter's type from the calls. The signature has to be complete on its own, so the compiler can check every call without reading the body.

Names are snake_case. The compiler accepts addTwo, but it warns that the function addTwo should have a snake case name. Laravel methods are camelCase, so that habit comes with you. Rename the function when the warning appears.

function add(int $a, int $b): int {
    return $a + $b;
}
fn add(a: i32, b: i32) -> i32 {
    a + b
}

The shape is the same. PHP checks int at runtime, and in its default mode it converts a numeric string such as "2" into an integer for you. Rust checks types before the program runs and never turns a string into a number. PHP also needs return. Rust returns the last expression.

Functions that never return

PHP 8.1 added the never return type, for a function that always throws or exits. Rust has the same idea as the never type, written !. The difference is when the rule is checked.

function fail(string $why): never {
    throw new RuntimeException($why);
}
fn fail(why: &str) -> ! {
    panic!("{why}");
}

PHP checks never when the function returns. If the body finishes normally, PHP throws a TypeError at that point, after the body has already run. rustc checks ! before the program runs, so a body that could finish normally is error E0308. The same type also covers expressions. A break, a continue or a return has type !, so it fits in a match arm that must produce a value.

Does this compile?

fn double(n) -> i32 {
    n * 2
}
  1. Yes. The compiler works out the type of n from how double is called.
  2. No. Every parameter in a signature needs a type.
  3. No. A function with a return type must use return.

Rust does not infer parameter types from call sites, so the signature has to stand on its own. Write n: i32 and the function compiles. Returning n * 2 without return is fine too, because the last expression is the value.

Statements and expressions

Code is made of two kinds of things. A statement does something and produces no value. An expression produces a value.

A statement does its work and gives nothing back.

let y = 4; creates a binding. Nothing is left over that you could use.

An expression gives a value back.

x + 1 is 4 when x is 3. A function call, a literal and an if are expressions too.

A block, the code between { and }, is an expression. Its value is its last line, as long as that line has no semicolon.

fn main() {
    let y = {
        let x = 3;
        x + 1
    };
    println!("{y}");
}

The braces create their own scope, so x exists only inside them. The last line, x + 1, has no semicolon. The block evaluates to 4, and y is bound to that 4.

A function body is a block too. Its last expression is the return value, which is why most Rust functions never write return. Use return to leave early:

fn describe(n: i32) -> &'static str {
    if n < 0 {
        return "negative";
    }
    "zero or positive"
}

fn main() {
    println!("{}", describe(-2));
    println!("{}", describe(5));
}

The if on its own line is a statement. It has no else and is used only for its effect. You will meet if as an expression in a moment.

What does this print?

fn main() {
    let z = { 5; };
    println!("{:?}", z);
}
  1. 5
  2. ()
  3. Nothing. It doesn't compile, because a block must end with an expression.

The block's last line is 5;, a statement. A block that ends in a statement has no value to give back, so its type is (), the unit type. The program compiles and prints ().

Expressions chain

Most Rust code reads as a chain, where each expression's value feeds the next call. PHP 8.5 added the pipe operator |>, which chains plain functions the same way. Each step takes one value and passes its result on.

<?php
$slug = "  Hello Rust World  "
    |> trim(...)
    |> strtolower(...)
    |> (fn(string $s): string => str_replace(' ', '-', $s));
echo $slug;
fn main() {
    let slug = "  Hello Rust World  "
        .trim()
        .to_lowercase()
        .replace(' ', "-");
    println!("{slug}");
}

The pipe accepts any one-argument callable, so each step can be a plain function. Rust chains methods on the value, so each step has to be a method of its type. A free function goes in a nested call instead. Chapter 13 covers the iterator methods that make long Rust chains common.

The semicolon decides

Now the rule that trips up nearly everyone at first. Put a semicolon after the last expression of a function, and the function stops returning that value. Here is what the compiler says about a small example:

fn plus_one(x: i32) -> i32 {
    x + 1;
}
error[E0308]: mismatched types
 --> src/main.rs:1:24
  |
1 | fn plus_one(x: i32) -> i32 {
  |    --------            ^^^ expected `i32`, found `()`
  |    |
  |    implicitly returns `()` as its body has no tail or `return` expression
2 |     x + 1;
  |          - help: remove this semicolon to return this value

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0308`.

Read it from the top. The error is mismatched types. The arrow under the return type says the function expects i32, but the body has type (), the unit type. The note on line 1 gives the reason: the body has no tail expression, which is Rust's name for a block's last expression, and it has no return. The help on line 2 is the fix.

Semicolon Switch

Use the buttons at the end of the lines. Watch the type in the panel change, then read what the compiler says.

The rule underneath both examples is short. A line with a semicolon is a statement. A last line without one is the block's value. The rest of this chapter applies that rule to if, match and loop.

Does this compile?

fn double(x: i32) -> i32 {
    x * 2;
}
  1. Yes. The semicolon is only a style choice.
  2. No. The body ends in a statement, so the function returns () where it promised i32. This is E0308.
  3. No. Functions can't multiply without a return.

x * 2; is a statement, so the body's value is (), which does not match i32. Delete the semicolon and double returns x * 2.

if is an expression

Rust has no ternary operator. The if does that job, because it produces a value:

fn main() {
    let n = 7;
    let label = if n % 2 == 0 { "even" } else { "odd" };
    println!("{n} is {label}");
}
function label(int $n): string {
    return $n % 2 === 0 ? 'even' : 'odd';
}
fn label(n: i32) -> &'static str {
    if n % 2 == 0 { "even" } else { "odd" }
}

The ternary becomes an if with a block for each branch. The difference is in the condition. PHP treats most values as true or false, so if ($items) works on an array. Rust has no such rule, and the condition must be a bool.

Both branches have to produce the same type, because label can have only one. Here the compiler rejects an integer in one branch:

fn main() {
    let n = 4;
    let label = if n % 2 == 0 { "even" } else { 0 };
    println!("{label}");
}
error[E0308]: `if` and `else` have incompatible types
 --> src/main.rs:3:49
  |
3 |     let label = if n % 2 == 0 { "even" } else { 0 };
  |                                 ------          ^ expected `&str`, found integer
  |                                 |
  |                                 expected because of this

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0308`.

The condition follows the same strictness. It must be a bool. An integer is not a yes or a no, so there is no truthiness to fall back on. This is the Chapter 03 rule about types, applied to control flow.

In PHP, if ('0') is false and if ('00') is true. Rust has no table like that to memorize. If a condition is not a bool, the program does not compile.

Does this compile?

fn main() {
    let n = 4;
    if n {
        println!("truthy");
    }
}
  1. Yes. Like PHP, any non-zero number counts as true.
  2. No. An if needs a bool, and n is an integer.
  3. Yes. The compiler converts integers to bool inside an if.

Write if n != 0 instead. That compiles and prints truthy, because the comparison produces a bool. The compiler will not make that conversion for you.

A first look at match

match compares a value against a list of arms. Each arm is a pattern, =>, and the value it produces. The arms are tried from top to bottom, the first one that fits wins, and _ fits anything, so it goes last.

fn size(n: u32) -> &'static str {
    match n {
        0 => "zero",
        1 | 2 => "small",
        3..=9 => "medium",
        _ => "big",
    }
}

fn main() {
    for n in [0, 2, 7, 42] {
        println!("{n}: {}", size(n));
    }
}

Patterns get a full chapter later. For now, notice two things. Every arm must produce the same type. And the arms must cover every value that n can hold. Delete the _ line and the program stops compiling, because nothing covers 10 and up.

function label(int $status): string {
    return match ($status) {
        200 => 'ok',
        404 => 'not found',
    };
}

echo label(500);   // UnhandledMatchError, when this line runs
fn label(status: u16) -> &'static str {
    match status {
        200 => "ok",
        404 => "not found",
    }
}

PHP's match (8.0) is an expression too. Its arms compare with ===, and a value no arm covers throws UnhandledMatchError while the program runs. Rust checks the arms against every value status can hold. The gap is error E0004 at compile time, so a program with the gap never runs. Adding a _ arm closes the gap, and then it compiles.

Does this compile?

fn main() {
    let ready = true;
    let text = match ready {
        true => "go",
    };
    println!("{text}");
}
  1. Yes. A match with one arm is always fine.
  2. No. false is not covered. A match must handle every value of its type.
  3. Yes, because only true can reach that line at runtime.

The compiler knows a bool has exactly two values, and it checks both. Add false => "stop", and it compiles. With integers, you need the _ arm, because there are too many values to list.

loop, while, for

Rust has three loops, and each answers a different question. loop runs until you break. while runs as long as a condition holds. for walks through the items that something produces, such as a range. Most of your loops will be for.

loop can return a value

loop is the only loop that produces a value. A break can carry one, and the whole loop evaluates to it. This retry counter stops on the third attempt:

fn main() {
    let mut attempt = 0;
    let succeeded_on = loop {
        attempt += 1;
        // pretend the third call is the first one that works
        if attempt == 3 {
            break attempt;
        }
    };
    println!("worked on attempt {succeeded_on}");
}

What does this print?

fn main() {
    let mut counter = 0;
    let doubled = loop {
        counter += 3;
        if counter > 10 {
            break counter * 2;
        }
    };
    println!("{doubled}");
}
  1. 12
  2. 24
  3. It won't compile. A loop can't produce a value.

counter goes 3, 6, 9, 12. The first time it is greater than 10 is at 12, so the loop breaks with 12 × 2, which is 24.

while checks before every pass

while tests its condition before each pass, and it stops when the condition is false. It has no value. Only loop accepts a break with a value. Inside while or for, the compiler reports E0571.

fn main() {
    let mut fuel = 3;
    while fuel > 0 {
        println!("fuel {fuel}");
        fuel -= 1;
    }
    println!("empty");
}

for walks a range

A range is written start..end. The end is excluded, so 0..5 yields 0 to 4. Write ..= to include the end. A range can be reversed with .rev() or stepped with .step_by(3), and a plain array can be looped directly. Read the code and predict the output before you run it. Chapter 13 explains the iterator machinery behind these calls.

fn main() {
    print!("0..5   :");
    for i in 0..5 { print!(" {i}"); }
    println!();
    print!("0..=5  :");
    for i in 0..=5 { print!(" {i}"); }
    println!();
    print!("rev    :");
    for i in (0..10).rev() { print!(" {i}"); }
    println!();
    print!("step 3 :");
    for i in (0..10).step_by(3) { print!(" {i}"); }
    println!();
    print!("array  :");
    for x in [10, 20, 30] { print!(" {x}"); }
    println!();
}
for ($i = 0; $i < 5; $i++) { echo $i; }
foreach ([10, 20, 30] as $x) { echo $x; }
for i in 0..5 { print!("{i}"); }
for x in [10, 20, 30] { print!("{x}"); }

A PHP for is three pieces you write by hand: the start, the test and the step. A Rust range is one piece, and the end is excluded in the syntax itself. foreach and for x in do the same job.

How many times does for i in 1..5 run?

fn main() {
    for i in 1..5 {
        println!("{i}");
    }
}
  1. 5. It runs from 1 through 5.
  2. 4. The loop runs for 1, 2, 3 and 4.
  3. 3

The end, 5, is excluded. Write 1..=5 to include it, and the loop runs five times.

Labels break the right loop

A plain break leaves only the innermost loop. To leave an outer loop from inside an inner one, give the outer loop a label. Labels begin with an apostrophe and end with a colon. This search stops the whole grid at the first hit:

fn main() {
    let grid = [[1, 4, 7], [2, 9, 5], [3, 6, 8]];
    let target = 9;
    let mut checks = 0;

    'rows: for row in 0..3 {
        for col in 0..3 {
            checks += 1;
            if grid[row][col] == target {
                println!("found {target} at ({row}, {col}) after {checks} checks");
                break 'rows;
            }
        }
    }
}

Without the label, the break would end only the inner loop, and the search would carry on into the next row. The label says which loop you mean.

PHP's break 2; counts levels. It works until someone adds a loop between the two, and then the number quietly points at the wrong loop. A Rust label names its loop, so break 'rows; keeps meaning the same thing after a refactor.

Practice

Two exercises before the wrap-up. Fill in the blank first, then put the steps of a block in order.

Fill in the return type so that max returns the larger of its two arguments.

fn max(a: i32, b: i32) [[-> i32|->i32]] {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", max(3, 7));
}

Without -> i32, the function returns (). The if is the tail expression, and it produces an i32, so the compiler reports E0308 and suggests adding -> i32. There is no return and no semicolon. The value of the last line is the answer.

Put the steps for let y = { let x = 3; x + 1 }; in the order they happen.

  1. Create x with the value 3.
  2. Evaluate x + 1, which gives 4.
  3. The block ends, and x goes out of scope.
  4. The block's value, 4, is bound to y.

The last expression is evaluated before the block ends. The closing brace ends x's scope, and only then does the block's value become y. Nothing inside the block outlives it, except the value it produced.

Agents that learned in other languages often write return x; at the end of every function, or add a stray semicolon after the last expression. The first one compiles, but clippy's needless_return lint flags it, and idiomatic Rust ends with the expression. The second one is a compile error, E0308, which the compiler catches for you.

When you review agent-written Rust, look at the last line of each function. It should be an expression with no semicolon.

Before you go on, one check from Chapter 02, now meeting a loop. Does this compile?

Does this compile?

fn main() {
    let total = 0;
    for i in 1..4 {
        total += i;
    }
    println!("{total}");
}
  1. Yes. += is allowed on an immutable binding.
  2. No. total is not mut, so it can't be assigned again. This is E0384.
  3. Yes, but it prints 0, because the loop never changes total.

A let binding is immutable unless you write mut. total += i assigns to it on every pass, so it needs let mut total = 0;. The compiler suggests exactly that.

Recap

Blocks produce values

  • A block's value is its last expression. Without a semicolon, the last line is the value. With one, the block ends in a statement and its type is ().
  • A function returns its tail expression. Use return only to leave early.
  • if is an expression when its branches have the same type. The condition is always a bool.
  • match must cover every value. _ covers the rest.
  • loop can break with a value. while and for always have type ().
  • a..b excludes b, and a..=b includes it. A label such as 'outer lets break leave an outer loop.
Explain it back: why can one extra semicolon break a function's return value?

One good answer: "A function returns its body's last expression, the one with no semicolon. Add a semicolon and that line becomes a statement, so the body ends with nothing, and its type is (). The signature promised i32, so the compiler reports a type mismatch. Remove the semicolon, and the value comes back."

If your version mentioned the tail expression, the statement, and the unit type (), you've got it.
