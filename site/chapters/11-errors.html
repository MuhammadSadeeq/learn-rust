Two kinds of failure

Some failures are bugs in your code. Others are ordinary events, and your code is supposed to survive them. Rust gives each kind a different tool.

KindExamplesTool
A bug. The code asked for something that can't be done.An index past the end of a Vec, unwrap() on a None, a state your logic says is impossiblepanic!. The thread stops.
An expected failure. The outside world didn't cooperate.A file is missing, the user typed nonsense, the network timed out, the database is downResult<T, E>. The caller decides.

A panic unwinds the thread that panicked. Values on the way up are dropped as usual, and then the thread ends. If that thread is main, the whole program exits with status 101. Here is a panic caused by a bug:

fn main() {
    let scores = vec![90, 72, 85];
    let fourth = scores[3];
    println!("{fourth}");
}
thread 'main' (27578) panicked at src/main.rs:3:24:
index out of bounds: the len is 3 but the index is 3
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

Read the message from the top. The first line names the thread and the place: line 3 of src/main.rs. The second line says what went wrong. The number in parentheses is the process id, so yours will differ. Set RUST_BACKTRACE=1 and the same panic also prints a stack trace, the chain of calls that led to that line. Reach for it when a panic shows up somewhere you didn't expect.

Your app reads config.toml when it starts. Someone forgot to deploy the file. What should the code do?

  1. Call panic!. Without its config, the app can't run.
  2. Call unwrap() on the file read. The file will always exist in production.
  3. Return an Err, and let main print a clear message and exit. A missing file is outside the code's control, so it's an expected failure.

Panicking would stop the program, but it treats a deployment mistake as a bug in your code. The output is also noisier, and it doesn't tell the operator what to fix. A returned error can name the missing file and exit cleanly. Panic when your code is wrong. Return a Result when the world can be wrong.

function loadConfig(string $path): string
{
    $text = file_get_contents($path);
    if ($text === false) {
        throw new RuntimeException("cannot read $path");
    }
    return $text;
}
use std::fs;
use std::io;

fn load_config(path: &str) -> Result<String, io::Error> {
    fs::read_to_string(path)
}

In PHP, loadConfig(): string says nothing about failure. Any function can throw, and the only hint is a @throws docblock, if someone wrote one. In Rust, -> Result<String, io::Error> is part of the signature, and every caller has to deal with it. The break: nothing unwinds to a catch. The error is a value that the caller receives and inspects.

In Rust, a function that can fail says so in its return type.

Result: success or failure, in the type

Result is an ordinary enum from the standard library. It has two variants, and the function that returns it decides what goes inside each one:

enum Result<T, E> {
    Ok(T),   // success, with a value of type T
    Err(E),  // failure, with an error of type E
}

Anything that can fail returns one. Parsing text into a number is a good example. parse doesn't panic on bad text. It returns an Err that says why the text was rejected. The ::<i32> tells parse which type to produce:

fn main() {
    match "42".parse::<i32>() {
        Ok(n) => println!("parsed {n}"),
        Err(e) => println!("not a number: {e}"),
    }
}

What does this print?

fn main() {
    let result = "4x2".parse::<i32>();
    println!("{result:?}");
}
  1. Err(4x2)
  2. Err(ParseIntError { kind: InvalidDigit })
  3. Ok(0)
  4. The program panics, because the text is not a number.

{:?} prints the Debug view of the Result, including the fields of the error. InvalidDigit means the text has a character that isn't a digit. Empty text gives kind: Empty instead. The program doesn't panic, because parse returned an error and the code printed it.

A Result you ignore is a warning, not an error, and it's easy to miss. Rust marks Result as #[must_use], so the compiler reminds you:

fn main() {
    "42".parse::<i32>();
    println!("done");
}

  |     ^^^^^^^^^^^^^^^^^^^

In PHP, an uncaught exception stops the request, and the framework renders the error page. Nothing in the code has to acknowledge it. In Rust, an unused Result doesn't stop anything. The program keeps running, and the only sign is a warning. That warning is the one thing asking you to look.

Use let _ = only when ignoring the error is the right behavior, and say why in a comment. The warning exists because an ignored error is usually a bug that hasn't shown up yet.

unwrap and expect

unwrap() takes the value out of an Ok, or panics on an Err. expect("message") does the same, and prints your message in the panic. Both are right when a failure would be a bug: in tests, in a quick prototype, or when you can state why the value can't be an error. A good expect message names the fact that must be true, not the symptom:

fn main() {
    let port: u16 = "8080".parse().expect("the port constant is a valid u16");
    println!("listening on {port}");
}

Working with Results without match

match always works, but for a simple step it takes several lines. Result and Option have small methods, called combinators, that do the usual steps in one expression. Learn them by their types: what goes in, and what comes out.

MethodWhat happensUse it to
map(f)Ok(v) becomes Ok(f(v)). Err passes through.Change the success value
map_err(f)Err(e) becomes Err(f(e)). Ok passes through.Change the error, for example to add a message
and_then(f)Ok(v) calls f(v), which returns a Result itself.Chain a second step that can also fail
unwrap_or(d)Ok(v) becomes v. Err becomes d.Supply a default
unwrap_or_else(f)Err(e) becomes f(e). The closure runs only on Err.Compute a default from the error
ok()Ok(v) becomes Some(v). Err becomes None.Drop the error and keep an Option
ok_or(e)On an Option: Some(v) becomes Ok(v). None becomes Err(e).Turn "missing" into an error
 
fn parse_age(text: &str) -> Result<u32, String> {
    text.trim()
        .parse::<u32>()
        .map_err(|e| format!("{text}: {e}"))
        .and_then(|age| {
            if age >= 18 {
                Ok(age)
            } else {
                Err(format!("{age} is under 18"))
            }
        })
}

fn main() {
    println!("{:?}", parse_age("30").map(|a| a + 1));
    println!("{:?}", parse_age("x"));
    println!("{:?}", parse_age("12"));
    println!("{}", parse_age("12").unwrap_or(18));
    println!("{}", parse_age("x").unwrap_or_else(|e| {
        println!("({e})");
        0
    }));
    println!("{:?}", "7".parse::<i32>().ok());
    let found: Option<u32> = None;
    println!("{:?}", found.ok_or("no value"));
}

Read the output in order. The closure in unwrap_or_else runs while that line is being evaluated, so its message prints before the 0. Each combinator either handles an Err or passes it along, and an Ok keeps flowing through the chain.

What does this print?

fn main() {
    let v = "x1".parse::<i32>().map(|n| n * 2).unwrap_or(-1);
    println!("{v}");
}
  1. 0, the default for an integer
  2. -1
  3. x1, because the text comes back unchanged
  4. A compile error, because map isn't defined on Result

"x1" doesn't parse, so the result is an Err. map passes an Err through without calling its closure, so n * 2 never runs. unwrap_or(-1) sees an Err and returns -1. map is defined on Result, so the compile error choice is wrong too.

Use a combinator when the step is one line and reads well. Use match when each branch does different work, or when a chain stops being easy to read. A long chain of combinators is harder to follow than the match it replaced.

The ? operator

Most functions that can fail do the same thing: run a step, and if the step fails, hand that failure to whoever called the function. Written out with match every time, that buries the real work. The ? operator does the same job in one character.

Here is a function that reads two numbers out of text like 3,4. It uses ? twice:

use std::num::ParseIntError;

fn parse_pair(s: &str) -> Result<(i32, i32), ParseIntError> {
    let mut parts = s.split(',');
    let x = parts.next().unwrap_or("").trim().parse::<i32>()?;
    let y = parts.next().unwrap_or("").trim().parse::<i32>()?;
    Ok((x, y))
}

fn main() {
    println!("{:?}", parse_pair("3,4"));
    println!("{:?}", parse_pair("3,x"));
    println!("{:?}", parse_pair("5"));
}

Read ? as: if this is Err, return it from this function now. If it's Ok, take the value out and keep going. Predict what happens before you check:

The expression before ? produced an Err. What happens next?

  1. The program panics, the same as unwrap().
  2. The error is printed, and the next line runs with a default value.
  3. The function returns that error to its caller right away. The lines after the ? don't run.
  4. The value is replaced with Ok(0), and execution continues.

? is an early return. It's return Err(e) with the boilerplate removed. The caller receives the error and decides what to do with it. Section 5 covers the one more step ? takes on the way out: a conversion.

Here is what ? stands for, written out by hand. With ?, the let is one line: let n = s.parse::<i32>()?;.

use std::num::ParseIntError;

fn doubled(s: &str) -> Result<i32, ParseIntError> {
    let n = match s.parse::<i32>() {
        Ok(v) => v,
        Err(e) => return Err(From::from(e)),
    };
    Ok(n * 2)
}

fn main() {
    println!("{:?}", doubled("21"));
    println!("{:?}", doubled("x"));
}

The match is the whole idea. The Ok arm gives back the value and the code continues. The Err arm returns early, so the rest of the function doesn't run. From::from(e) converts the error into the function's error type. Here that conversion does nothing, because the types already match.

The real expansion

The compiler doesn't use a match directly. It goes through the standard library's Try trait, which is also how ? works on an Option. The effect is the same as the match above: continue with the value, or return early with the failure, converted by From.

The same operator works on Option, inside a function that returns Option. A None makes the function return None:

fn first_char_upper(s: &str) -> Option<char> {
    let c = s.chars().next()?;
    Some(c.to_ascii_uppercase())
}

fn main() {
    println!("{:?}", first_char_upper("rust"));
    println!("{:?}", first_char_upper(""));
}

? needs the function to return a type that can carry the failure. An Option function can't return an Err, and a Result function can't return a None. The two don't mix.

Where ? doesn't work

This rule trips up almost everyone. Try ? in main, which returns nothing:

Does this compile?

fn main() {
    let n: i32 = "42".parse()?;
    println!("{n}");
}
  1. Yes. ? works anywhere.
  2. No. main returns (), which has no place to put the error.
  3. No. ? only works on Option.

? needs somewhere to send the error. A function that returns () has nowhere to put it, so the compiler stops with E0277. The message is worth reading in full:

For more information about this error, try `rustc --explain E0277`.

Give main a return type that can hold an error. The simplest one is Result<(), ParseIntError>. When main returns an Err, Rust prints it and exits with status 1:

use std::num::ParseIntError;

fn main() -> Result<(), ParseIntError> {
    let n: i32 = "42".parse()?;
    println!("{n}");
    Ok(())
}

A program usually has more than one kind of error, and main can't name them all. Box<dyn Error> accepts any error type that implements the Error trait. A Box is a pointer to a value on the heap, and dyn Error hides the exact error type from the compiler, so calls go through a table of functions at run time. You'll meet both properly in Chapters 14 and 17. Here two different error types go through one main:

use std::error::Error;

fn main() -> Result<(), Box<dyn Error>> {
    let n: i32 = "42".parse()?;
    let price: f64 = "9.5".parse()?;
    println!("{n} {price}");
    Ok(())
}

Change "42" to "x42" and run it again. The error comes out of main in its Debug form, and the program exits with status 1:

Error: ParseIntError { kind: InvalidDigit }

Your own error type

A function that can fail in several ways needs an error type that says which way. A String can hold any message, but the caller can't match on it. An enum gives each failure its own variant, so the caller can react to each one differently.

use std::error::Error;
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum AppError {
    NotFound(u32),
    Invalid(String),
    Parse(ParseIntError),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AppError::NotFound(id) => write!(f, "user {id} not found"),
            AppError::Invalid(why) => write!(f, "invalid input: {why}"),
            AppError::Parse(e) => write!(f, "could not parse number: {e}"),
        }
    }
}

impl Error for AppError {}

impl From<ParseIntError> for AppError {
    fn from(e: ParseIntError) -> Self {
        AppError::Parse(e)
    }
}

fn find_name(id: u32) -> Result<&'static str, AppError> {
    let names = [(1, "Ana"), (2, "Bo")];
    names
        .iter()
        .find(|(uid, _)| *uid == id)
        .map(|(_, name)| *name)
        .ok_or(AppError::NotFound(id))
}

fn lookup(id_text: &str) -> Result<&'static str, AppError> {
    if id_text.is_empty() {
        return Err(AppError::Invalid("id is empty".to_string()));
    }
    let id: u32 = id_text.parse()?; // ParseIntError becomes AppError::Parse
    find_name(id)
}

fn main() {
    for input in ["1", "7", "seven", ""] {
        match lookup(input) {
            Ok(name) => println!("found {name}"),
            Err(e) => println!("error: {e}"),
        }
    }
}

Three things make this type work with ?:

  1. Display writes the message a person reads. println!("{e}") uses it.

  2. Error is the standard trait for error types. It requires Debug and Display, which the derive and the impl provide. The impl itself can be empty.

  3. From<ParseIntError> lets ? convert a parse error into AppError::Parse.

The third one is the conversion. On an Err, ? calls From::from to turn the error into the function's error type. In the doubled example that call did nothing, because the types already matched. In lookup, parse() produces a ParseIntError and the function returns an AppError, so the conversion does real work and needs the impl. Without the impl, the compiler rejects the ?. Notice what happens to the error itself: it's moved out to the caller, which becomes its owner. That's Chapter 6's move again.

Fill in the one line that makes the conversion work:

Complete the impl so ? can convert a ParseIntError into AppError.

use std::num::ParseIntError;

#[derive(Debug)]
enum AppError {
    Parse(ParseIntError),
}

impl [[From<ParseIntError>]] for AppError {
    fn from(e: ParseIntError) -> Self {
        AppError::Parse(e)
    }
}

fn main() {
    let err: AppError = "x".parse::<u8>().unwrap_err().into();
    println!("{err:?}");
}

From<ParseIntError> names the trait and the type it converts from. The body wraps the error in the Parse variant. Once this impl exists, ? on a ParseIntError converts automatically in any function that returns Result<_, AppError>. You can have one From impl per source type, so a From<io::Error> can sit beside it.

thiserror and anyhow

Writing Display and From by hand for every error gets repetitive. Two crates from the community handle most of that work, and they're built for different jobs. Choosing between them is a real decision:

thiserroranyhow
Use it inLibraries, the code other people importApplications, the programs that run and report errors
The error type isYour own enum, with a deriveOne type, anyhow::Error, that holds any error
Callers canMatch on each variant and react to itPrint it and add context. Matching on a specific failure means downcasting.

Add both crates to Cargo.toml. Major versions are enough to pin: Cargo picks the newest compatible release.

[dependencies]
thiserror = "2"
anyhow = "1"

A library defines its own enum. thiserror writes the Display and From impls from attributes:

use std::num::ParseIntError;

#[derive(Debug, thiserror::Error)]
enum AppError {
    #[error("user {0} not found")]
    NotFound(u32),

    #[error(transparent)]
    Parse(#[from] ParseIntError),
}

fn lookup(id_text: &str) -> Result<u32, AppError> {
    let id: u32 = id_text.parse()?; // #[from] gives the conversion
    if id == 1 {
        Ok(id)
    } else {
        Err(AppError::NotFound(id))
    }
}

fn main() {
    for input in ["1", "9", "nine"] {
        match lookup(input) {
            Ok(id) => println!("ok: {id}"),
            Err(e) => println!("error: {e}"),
        }
    }
}
ok: 1
error: user 9 not found
error: invalid digit found in string

#[error("…")] writes Display for you. #[from] writes the From impl from the previous section. transparent passes the wrapped error's message through unchanged. The enum is what callers see, so they can still match on NotFound.

An application's main doesn't need callers to match on anything. It needs to report a failure with enough context to act on. anyhow::Result<T> is Result<T, anyhow::Error>, and .context("…") wraps whatever error came before with a sentence that says what the program was doing:

use anyhow::{Context, Result};

fn load_port(path: &str) -> Result<u16> {
    let text = std::fs::read_to_string(path).context("could not read the port file")?;
    let port = text
        .trim()
        .parse::<u16>()
        .context("the port file must hold a number")?;
    Ok(port)
}

fn main() -> Result<()> {
    let port = load_port("config/port.txt")?;
    println!("port {port}");
    Ok(())
}

With no config/port.txt in the directory, the program reports this:

Error: could not read the port file

Caused by:
    No such file or directory (os error 2)

Each Caused by line is the error the previous line wrapped. with_context(|| …) does the same job with a closure, which only runs on the error path. That matters when building the message costs something. Set RUST_BACKTRACE=1 and anyhow adds a stack trace to the report.

The strategy in one line: libraries return typed errors. Applications add context at the boundary and report.

You're writing a crate that other teams will import. Which error type should its public functions return?

  1. anyhow::Result, because it takes the least code.
  2. An enum of errors, derived with thiserror, so callers can match on each failure.
  3. String, because every error can be turned into one.

Callers of a library act on specific failures. One may retry a timeout, another may show a 404 for NotFound, and a third may log the rest. A typed enum gives them variants to match. anyhow erases the type, which is right at the top of an application, where errors are only reported. The public boundary of a library is the place that needs the types.

From Laravel's exception handler to Rust

In Laravel, a failure is an exception. It travels up the stack until something catches it, and the exception handler turns it into a response. Rust has the same two roles, but the failure travels as a return value. Three Laravel habits have direct Rust counterparts:

  • findOrFail() becomes a lookup that returns an Option, followed by .ok_or(...)?, which says which error a missing value means.
  • A validation exception becomes a variant of your error enum, such as Invalid(String), with the messages inside it.
  • Handler::render becomes one place at the edge of the app that turns your error into an HTTP response.

The first habit in Rust:

#[derive(Debug)]
enum AppError {
    NotFound(u32),
}

fn find_user(id: u32) -> Option<&'static str> {
    if id == 1 { Some("Ana") } else { None }
}

fn show_user(id: u32) -> Result<String, AppError> {
    let name = find_user(id).ok_or(AppError::NotFound(id))?;
    Ok(format!("user: {name}"))
}

fn main() {
    println!("{:?}", show_user(1));
    println!("{:?}", show_user(2));
}

find_user returns an Option, because a missing user isn't a failure yet. It's a fact about the data. ok_or decides what the missing case means in this part of the program, and ? returns that error. Unlike findOrFail(), the error is written in the code, where a reader can see it.

try {
    $user = $users->findOrFail($id);
    $mailer->welcome($user);
} catch (ModelNotFoundException $e) {
    return response()->json(['error' => 'not found'], 404);
}
#[derive(Debug)]
enum AppError {
    NotFound(u32),
}

fn register(id: u32) -> Result<String, AppError> {
    if id == 1 {
        Ok("Ana".to_string())
    } else {
        Err(AppError::NotFound(id))
    }
}

fn main() {
    match register(2) {
        Ok(name) => println!("welcome, {name}"),
        Err(AppError::NotFound(id)) => println!("user {id} not found"),
    }
}

The try block catches any exception thrown below it, including ones you didn't expect, and it chooses the handler by class. The match sees only the Result of the call in front of it, and it has to cover every variant. Add a variant later and the compiler points at every match that needs it. That's the trade: fewer surprises, in exchange for touching more lines when the set of errors grows.

The third habit happens at the edge. Laravel's handler renders exceptions once, for the whole app. In Rust, you write the same kind of conversion for your web layer. A type implements a trait (axum calls it IntoResponse), so a route can return Result<Json<User>, AppError> and the framework turns the Err into a response. You'll build that in Chapter 20.

Think first: a repository finds no user. Where should that become a 404?

At the HTTP edge, once. The repository and the services under it return the NotFound variant. Only the code that builds responses knows what a 404 looks like. If a service turned the failure into a response itself, it would be tied to HTTP, and every other caller, such as a CLI command or a queued job, would have to undo that.

Coding agents reach for .unwrap() everywhere. The code compiles, the happy path runs, and the panic appears only on an input the agent never tried. Put the rule in your instructions, in these words or close to them: no unwrap or expect outside tests and main; propagate errors with ? and a thiserror enum.

When you review, search before you read. Every hit is a question: is this a test, a true invariant, or a bug waiting for the wrong input?

Practice

Two checks finish the chapter. The first puts the steps of ? in order. The second matches the PHP habits you know to their Rust forms.

  1. The expression before ? is evaluated, and it produces an Err(e).
  2. From::from(e) converts the error into the function's error type.
  3. The function returns that error right away. Its remaining lines don't run.
  4. The caller receives the Err and decides what to do with it.

If the expression had produced Ok, the first step would have taken the value out and kept going. The conversion always happens before the return, so the caller sees the function's own error type, never the one from deeper down.

  • return Err(x)
  • match result { Ok(v) => …, Err(e) => … }
  • -> Result<T, E> in the signature
  • a Drop impl, which runs whenever the value leaves its scope
  • let user = find(id).ok_or(AppError::NotFound(id))?;
  • if let Err(e) = step() { eprintln!("{e}"); }

These pairs are scaffolding, not equivalences. catch can recover from an exception thrown three calls down, while a match only sees the Result of the call in front of it. In Rust, a failure that should reach a caller further up must be passed up by every function in between, with ?. That's more typing, and it's why signatures carry the error type.

finally is a block you write at each use. Drop is cleanup written once on a type, and it runs on every path out of the scope, including the early return from ?. That's why a file or a lock can release itself even when a step fails.

Recap

Errors are values

  • Bugs panic. Expected failures return a Result<T, E>. A function that can fail says so in its return type.
  • match, map, map_err, and_then, unwrap_or and ok_or handle a Result or Option in one expression.
  • ? returns early on Err, after converting the error with From. The function must have a return type that can carry that error.
  • Write your own error enum with Display, Error and From, or derive them with thiserror. Applications can use anyhow at the top.
Explain it back: What does ? do, step by step?

One good answer: "It evaluates the expression before the ?. If the result is Ok, it takes the value out and the function keeps going. If the result is Err, it converts the error with From into the function's error type and returns it right away, so the lines after it don't run. The caller receives the Err and decides what to do."

If your version has Ok continues, Err returns early, and From converts, you've got it.
