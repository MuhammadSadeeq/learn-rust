A struct is a named shape

A struct groups related values under one name, and gives each piece a field name. If you have written a PHP class that only holds data, you have already written something like a struct. Here is one for a user account, with a program that creates a value, changes a field and reads the fields back.

struct User {
    name: String,
    email: String,
    active: bool,
    logins: u64,
}

fn main() {
    let mut u = User {
        name: String::from("Ana"),
        email: String::from("ana@x.io"),
        active: true,
        logins: 0,
    };
    u.logins += 1;
    println!("{} <{}>, active: {}, logins: {}", u.name, u.email, u.active, u.logins);
}

A struct literal names the type, then sets every field inside braces. The fields can appear in any order, but each one has to appear exactly once. Read a field with a dot, as in u.name. Change a field with an assignment, but only through a binding declared mut.

mut belongs to the binding, not to the fields. There is no way to make logins changeable while name stays fixed. Declare u as mut and every field can change. Leave it out and none of them can.

When a local variable has the same name as a field, you can write the name once. This is called field init shorthand. The bridge below puts it next to the PHP constructor you already know.

class User {
    public function __construct(
        public string $name,
        public string $email,
        public bool $active = true,
        public int $logins = 0,
    ) {}
}

$u = new User('Ana', 'ana@x.io');
struct User {
    name: String,
    email: String,
    active: bool,
    logins: u64,
}

fn new_user(name: String, email: String) -> User {
    User { name, email, active: true, logins: 0 }
}

fn main() {
    let u = new_user(String::from("Ana"), String::from("ana@x.io"));
    println!("{} {} {} {}", u.name, u.email, u.active, u.logins);
}

Constructor promotion declares the fields and the parameters in one place. A Rust struct declares each field once, and every literal has to name every field. A forgotten PHP argument fails when the code runs. A forgotten Rust field fails when the code compiles. Rust also has no default parameter values, so the function supplies the defaults itself.

Does this compile?

struct User {
    name: String,
    email: String,
    active: bool,
    logins: u64,
}

fn main() {
    let u = User {
        name: String::from("Ana"),
        email: String::from("ana@x.io"),
        active: true,
    };
    println!("{}", u.name);
}
  1. Yes. logins starts at 0 by default.
  2. No. A struct literal must set every field. The compiler reports E0063 and names logins.
  3. Yes, with a warning. logins is null until you set it.

Rust has no default field values and no implicit null. Every field has to appear in the literal. The check runs at compile time, so the program never runs with a half-built User.

Struct update syntax

Often a new value is an old value with one or two fields changed. The .. form fills in every field you did not write from another value of the same struct. The program below uses it. Predict what the compiler does with the last line, which reads a field of u1, the value the update was taken from.

Does this compile?

struct User {
    name: String,
    email: String,
    active: bool,
    logins: u64,
}

fn main() {
    let u1 = User {
        name: String::from("Ana"),
        email: String::from("ana@x.io"),
        active: true,
        logins: 0,
    };
    let u2 = User {
        email: String::from("bo@x.io"),
        ..u1
    };
    println!("{} {}", u2.name, u2.email);
    println!("{}", u1.name);
}
  1. Yes. The update replaced email, so u1.name is untouched.
  2. No. ..u1 moved the String in name out of u1 and into u2. u1.name is gone.
  3. No. A struct with a bool field can't use update syntax.

Only name moved. active and logins are Copy, so u2 copied them and u1 keeps its own. email was written in the literal, so u2 never took u1's email. Change the last line to println!("{}", u1.email); and the program compiles.

Here is what rustc says about the last line:

error[E0382]: borrow of moved value: `u1.name`
  --> src/main.rs:20:20
   |
15 |       let u2 = User {
   |  ______________-
16 | |         email: String::from("bo@x.io"),
17 | |         ..u1
18 | |     };
   | |_____- value moved here
19 |       println!("{} {}", u2.name, u2.email);
20 |       println!("{}", u1.name);
   |                      ^^^^^^^ value borrowed here after move
   |
   = note: move occurs because `u1.name` has type `String`, which does not implement the `Copy` trait

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0382`.

The arrow value moved here covers the whole update, because that is where the move happens. The arrow value borrowed here after move points at u1.name, not at all of u1. The compiler tracks moves one field at a time.

After ..u1, u1 is partly moved. Its name is gone, but email, active and logins are still usable, because the update never took them. Check which fields the update actually took before you reuse the original.

Tuple structs and unit structs

A tuple struct has fields without names. You read them by position, with .0, .1 and so on. Use one when the position already says what the value is.

struct Meters(f64);
struct Point3(i32, i32, i32);
struct Marker;

fn main() {
    let d = Meters(3.5);
    let p = Point3(1, 2, 3);
    let _m = Marker;
    println!("{} {} {}", d.0, p.0, p.1 + p.2);
}

A tuple struct with a single field is called a newtype. It gives a plain type its own name. Meters and Seconds can both wrap an f64, but the compiler treats them as different types, so a distance can't be passed where a time belongs. Predict whether this call compiles.

Does this compile?

struct Meters(f64);
struct Seconds(f64);

fn speed(distance: Meters, time: Seconds) -> f64 {
    distance.0 / time.0
}

fn main() {
    let d = Meters(100.0);
    let t = Seconds(9.6);
    println!("{}", speed(t, d));
}
  1. Yes. Both wrap an f64, so the arguments match.
  2. No. speed wants Meters first. Two newtypes around the same f64 are still different types.
  3. No. Tuple structs can't be passed to functions.

The compiler reports E0308, "arguments to this function are incorrect", and suggests swapping them. The mistake is caught before the program runs, and the wrapper costs nothing at runtime. Meters is 8 bytes, the same size as the f64 inside it.

A unit struct has no fields at all. It is written struct Marker; and takes zero bytes. Use one when you need a distinct type and have nothing to store in it. You will meet unit structs again with traits in Chapter 14.

impl: methods live next to the data

Behavior goes in an impl block for the type. A method is a function in that block whose first parameter is self. The program below has three methods, and each one takes self in a different way.

struct Rectangle {
    w: u32,
    h: u32,
}

impl Rectangle {
    fn area(&self) -> u32 {
        self.w * self.h
    }

    fn scale(&mut self, k: u32) {
        self.w *= k;
        self.h *= k;
    }

    fn into_square(self) -> Rectangle {
        let side = self.w.max(self.h);
        Rectangle { w: side, h: side }
    }
}

fn main() {
    let mut r = Rectangle { w: 2, h: 3 };
    println!("{}", r.area());
    r.scale(2);
    println!("{}", r.area());
    let sq = r.into_square();
    println!("{}", sq.area());
}

The first parameter tells you what the method may do with the value. There are three forms:

&self: look.

The method borrows the value for reading. Most methods are this kind.

&mut self: change.

The method borrows the value for writing. The caller's binding has to be mut.

self: consume.

The method takes the value by value. The caller's value moves in, and it is usually gone afterwards.

The first parameter says what a method may do to the value.

You never write the & at the call site. The method call borrows for you. r.area() is the same call as Rectangle::area(&r), and r.scale(2) is Rectangle::scale(&mut r, 2). Step through the three forms below. The three programs share one struct and one starting value, and only the call changes.

A method is an ordinary function with one special parameter, and the dot is shorthand for passing that parameter. Once you read r.area() as Rectangle::area(&r), the three receivers are just three different parameters.

Now choose the receiver yourself. This method is meant to change a field, but it doesn't compile.

Which receiver does rename need, so that it can change name?

struct User {
    name: String,
}

impl User {
    fn rename(&self, name: &str) {
        self.name = name.to_string();
    }
}
  1. &self. It is the default receiver, so it should work here.
  2. &mut self. It is the one borrow that lets a method assign to fields in place.
  3. self. It works, and the caller keeps the value.

&self is a read-only borrow, so the assignment is refused with E0594: "cannot assign to self.name, which is behind a & reference". Use &mut self. The caller's binding must then be mut. Reach for plain self only when the method should consume the value and return a new one.

Associated functions and constructors

A function in an impl block that takes no self is an associated function. You call it on the type, with two colons: User::new(...). Rust has no special constructor syntax. By convention, the constructor is a function named new that returns Self.

struct User {
    name: String,
    email: String,
    active: bool,
    logins: u64,
}

impl User {
    fn new(name: &str, email: &str) -> Self {
        Self {
            name: name.to_string(),
            email: email.to_string(),
            active: true,
            logins: 0,
        }
    }
}

impl User {
    fn is_active(&self) -> bool {
        self.active
    }
}

fn main() {
    let u = User::new("Ana", "ana@x.io");
    println!("{} {} {} {}", u.name, u.email, u.is_active(), u.logins);
}

That example has two impl blocks for one type, and Rust allows as many as you like. Trait implementations are also separate impl blocks, which is how a type gets methods from a trait.

Constructors follow a few naming conventions. The standard library uses them everywhere, so learn them once:

NameUse it forReal example
newThe ordinary constructor, with no special input.Vec::new()
with_capacityA constructor that reserves room up front.Vec::with_capacity(10)
from_xA conversion from another type.String::from_utf8(bytes)
 
class User {
    public function __construct(
        public string $name,
        public string $email,
    ) {}

    public static function fromRow(array $row): static
    {
        return new static($row['name'], $row['email']);
    }
}

$u = User::fromRow($row);
struct User {
    name: String,
    email: String,
}

impl User {
    fn from_row(name: &str, email: &str) -> Self {
        Self { name: name.to_string(), email: email.to_string() }
    }
}

fn main() {
    let u = User::from_row("Ana", "ana@x.io");
    println!("{} {}", u.name, u.email);
}

A PHP static method and a Rust associated function both hang off the class name, so User::fromRow() and User::from_row() read the same way. Rust has no static keyword on methods. Any function in an impl block without self belongs to the type, and it returns Self to name the type it builds.

Now fill in the blanks. The constructor takes two numbers and builds a Rect. The two blanks are the return type and the struct literal inside the body.

Fill in the two blanks so that new returns a Rect built from its arguments.

struct Rect {
    w: u32,
    h: u32,
}

impl Rect {
    fn new(w: u32, h: u32) -> [[Self|Rect]] {
        [[Self|Rect]] { w, h }
    }
}

fn main() {
    let r = Rect::new(2, 3);
    println!("{} {}", r.w, r.h);
}

Self means the type that the impl block is for. Inside impl Rect, Self and Rect name the same type, so both blanks accept either word. Prefer Self. If you rename the type later, the constructor body doesn't need to change with it.

derive: free abilities

A new struct can't be printed, compared or copied until you tell the compiler how. #[derive(...)] above a struct asks the compiler to write the standard version of an ability for you. These four are the ones you will use most:

DeriveWhat it gives you
Debug{:?} and {:#?} print the value, with the type name and every field.
Clone.clone() makes a new value by cloning each field.
PartialEq== and != compare the fields one by one.
DefaultSettings::default() fills each field with its default: 0, false, an empty String.
 
#[derive(Debug, Clone, PartialEq, Default)]
struct Settings {
    name: String,
    retries: u32,
    verbose: bool,
}

fn main() {
    let base = Settings::default();
    println!("{base:?}");
    let api = Settings {
        name: String::from("api"),
        ..Default::default()
    };
    println!("{api:#?}");
    let copy = dbg!(api.clone());
    println!("{}", copy == api);
}

Read the output. {:?} prints on one line, and {:#?} spreads the value over several lines with indentation. ..Default::default() fills every field you did not write. The comparison copy == api works because the struct derives PartialEq.

PHP's == on two objects of the same class compares their properties, and print_r and var_dump print them. Rust asks you to opt in to each of those. Without PartialEq, a == b on your struct is a compile error (E0369). Without Debug, there is no way to print the struct at all.

dbg! is for quick debugging. It prints the file, the line, the expression and its value to stderr, then returns the value. You can wrap any expression in it without changing what the program does. The line it printed went to stderr, so it doesn't appear in the stdout above.

Without the derive, {:?} doesn't exist for your type, and the compiler stops:

}

What does this print?

#[derive(Debug)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let p = Point { x: 1, y: 2 };
    println!("{:?} sum {}", p, p.x + p.y);
}
  1. 1 2 sum 3
  2. Point { x: 1, y: 2 } sum 3
  3. Point(1, 2) sum 3

{:?} prints the type name, then each field with its name and value, in declaration order. {:#?} prints the same content with one field per line. A tuple struct prints with parentheses, because its fields have no names.

A derive can also make a struct Copy. Then assignment copies the value instead of moving it, the way it already does for integers. Copy is allowed only when every field is Copy, and it requires Clone as well, so you derive both. This Point holds two integers, so it qualifies:

#[derive(Debug, Clone, Copy, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let p = Point { x: 1, y: 2 };
    let q = p;
    println!("{p:?} {q:?} {}", p == q);
}

Give the same struct a String field, and the derive fails:

Does this compile?

#[derive(Clone, Copy)]
struct Person {
    name: String,
}

fn main() {
    let p = Person { name: String::from("Ana") };
    println!("{}", p.name);
}
  1. Yes. Clone makes the String copyable.
  2. No. Copy needs every field to be Copy, and String is not. The compiler reports E0204.
  3. No. A struct with a String field can't derive anything.

A String owns heap memory, and duplicating its bits would give two owners of one buffer. Only the types that are Copy can be copied that way, and Chapter 6 listed them. For this struct, derive Clone alone and call .clone() when you need a second value.

What a struct looks like in memory

A struct's fields are stored inline, one after another, in a single block of memory. Each field starts at an address that suits its alignment. A u32 wants an address that is a multiple of four, so the compiler may leave a few unused bytes before it. Those unused bytes are padding. A String field takes 24 bytes inside the struct: its pointer, length and capacity. Its characters stay on the heap.

Padding changes the total size, and it is easy to get wrong by hand. Predict what this program prints. The struct has a u32 between two single bytes.

What does this print?

use std::mem::size_of;

struct Padded {
    a: u8,
    b: u32,
    c: u8,
}

fn main() {
    println!("{}", size_of::<Padded>());
}
  1. 12
  2. 8
  3. 6

The fields add up to 6 bytes, but b needs an address that is a multiple of 4. The default layout here puts b first, then a and c after it. That leaves only 2 bytes of padding, so the total is 8.

Why the default layout is not the C layout

With #[repr(C)] on the same struct, the fields keep their declaration order. a sits at byte 0, three bytes of padding follow, b starts at byte 4, c sits at byte 8, and three more padding bytes round the total up to 12. The default layout is not specified, so rustc may choose a different order, and that can change between versions. Don't write code that depends on field offsets. #[repr(C)] exists for talking to C libraries, and you will meet it again in the unsafe chapter, Chapter 21.

The same rules explain a User. Two Strings take 24 bytes each, the u64 takes 8 and the bool takes 1. That totals 57. The compiler rounds up to 64, so that every User in an array starts on an aligned address.

No inheritance, and that's fine

Rust has no extends. A struct cannot inherit fields or methods from another struct. You get the same kinds of reuse another way. One is composition: a struct holds another struct as a field and reaches its data through that field. The other is traits, which describe behavior that any type can implement. Traits get their own chapter, 14.

struct User {
    name: String,
    email: String,
}

struct Admin {
    user: User,
    level: u8,
}

impl Admin {
    fn name(&self) -> &str {
        &self.user.name
    }
}

fn main() {
    let a = Admin {
        user: User { name: String::from("Ana"), email: String::from("ana@x.io") },
        level: 3,
    };
    println!("{} {} {}", a.name(), a.user.email, a.level);
}

class User {
    public string $name;
    public string $email;
}

class Admin extends User {
    public int $level = 3;

    public function label(): string
    {
        return $this->name;
    }
}
struct User {
    name: String,
    email: String,
}

struct Admin {
    user: User,
    level: u8,
}

impl Admin {
    fn label(&self) -> &str {
        &self.user.name
    }
}

fn main() {
    let a = Admin {
        user: User { name: String::from("Ana"), email: String::from("ana@x.io") },
        level: 3,
    };
    println!("{} {}", a.label(), a.level);
}

PHP's extends gives Admin every property and method of User, and lets it override them. In Rust, Admin holds a user field, and you write self.user.name to reach the data. There is no override. Shared behavior comes from traits, which you will write in Chapter 14.

Agents that learned object-oriented style often write Rust the same way: a getter and a setter for every field, &mut self on every method, and a shared base for everything. The code compiles, but it reads badly. Idiomatic Rust uses pub fields for plain data, methods where a rule has to hold, and &self unless a method really has to change the value.

When you review that code, ask one question about each &mut self: does this method really change the value, or does it only need to read it?

Here is the mapping you will use most often when you translate a PHP class:

  • self, the first parameter of every method
  • User::new(...), an associated function
  • A function in the impl block with no self
  • pub name: String, visible outside its module
  • impl Display (Chapter 14)
  • Composition plus traits: a field of type User, and shared behavior in traits

The match leaves out one rule. Fields are private to the module that defines them unless you mark them pub. You will meet modules in Chapter 16. In a single file everything can see everything else, so this rule is easy to miss until your code grows.

Recap

Data and behavior

  • A struct groups named fields, and a literal has to set every one of them. mut belongs to the binding, so it covers all the fields at once.
  • ..base fills in the fields you did not write. Non-Copy fields move out of base, and the fields you wrote are untouched.
  • Tuple structs have positional fields. A newtype wraps one value, so the compiler can tell two types apart even when they hold the same data.
  • Methods live in impl blocks. The first parameter sets what the method may do: &self looks, &mut self changes, self consumes.
  • Associated functions take no self. You call them as Type::name(). Constructors are usually named new and return Self.
  • #[derive(...)] writes Debug, Clone, PartialEq, Default and Copy for you. Copy needs every field to be Copy.
  • A struct's size is its fields plus padding. Rust has no inheritance, so reuse comes from composition and traits.
Explain it back: when would you take self instead of &self?

One good answer: "Take self when the method has to own the value. It might consume the value, or build a new one from its fields and hand that back, the way into_square does. Ownership moves into the method, so the caller can't use the value afterwards. That is only right when the caller is done with it. Otherwise take &self, and reach for &mut self only when the method really has to change the value."

If your version mentioned ownership moves into the method and the caller loses the value, you've got it.
