From shared-nothing to shared memory

Your PHP code almost never thinks about two things running at the same moment, and that comes from how PHP runs. A PHP-FPM worker handles one request from start to finish. Each worker is a separate process with its own memory, so two workers share nothing and cannot corrupt each other. More load means more workers. Background work goes to queue workers under Horizon, which are separate processes too. Octane is the one setup to watch. It boots your app once and keeps each worker alive between requests, so a static variable can outlive the request that set it. Octane's docs warn that this can leak memory.

A Rust program usually runs the other way. One process starts several threads, and all of them live in the same memory. That is fast: starting a thread is much cheaper than starting a process, and threads can hand each other data without copying it. It is also dangerous. When two threads touch the same memory with no coordination, and at least one of them writes, you have a data race. The result depends on timing, and it is often wrong without any error.

Rust's claim is that the ownership and borrowing rules you already know also rule out data races in safe code. The compiler reads who owns each value and who may write to it, and it refuses code where two threads could collide. The rest of this chapter shows how that works, and where it stops.

Why can a PHP app run fifty workers with no locks in your code?

Each worker is its own process with its own memory, so nothing in one worker is reachable from another. The state that is shared (sessions, counters, rows) lives in MySQL, Redis or the cache, and those systems handle concurrency themselves.

Rust threads take that wall away. Their memory is reachable from every thread in the process, so the compiler has to prove that every shared access is safe.

Your PHP brain says: concurrency means more processes. A process is a wall, and the wall keeps data apart for free. Threads have no wall. The language rules have to do the work the process boundary did for you.

A data race needs three things: two threads, the same memory, and at least one write with no coordination. Remove any one of them and the race is gone. Rust's job is to make the compiler check the last two.

Spawning threads

thread::spawn takes a closure, starts it on a new thread, and returns a JoinHandle straight away. The closure runs at the same time as the code after the call. join() blocks until that thread finishes and returns whatever the closure returned. This program splits a sum across four threads:

use std::thread;

fn main() {
    let mut handles = Vec::new();
    for i in 0..4u64 {
        handles.push(thread::spawn(move || {
            let start = i * 250 + 1;
            let end = start + 249;
            (start..=end).sum::<u64>()
        }));
    }

    let mut total = 0;
    for handle in handles {
        total += handle.join().unwrap();
    }
    println!("total = {total}");
}

Each closure is marked move, so each thread gets its own copy of i. The threads may finish in any order, but the total is the same on every run, because main joins all of them before it prints.

join() returns a Result. It is Err if the thread panicked. unwrap() turns that into a panic in main, which is fine for a short program. In a long-running service, match on the error and decide what a crashed worker means for the work it was doing.

Now the case that trips most people up. Borrow a local instead of moving it:

use std::thread;

fn main() {
    let names = vec![String::from("Ana"), String::from("Bo")];
    let handle = thread::spawn(|| {
        println!("{names:?}");
    });
    handle.join().unwrap();
}

Read it from the top. The summary says the closure may outlive the function. The arrows show why. names is borrowed inside the closure, and thread::spawn makes no promise about when its thread ends. The closure therefore has to own what it uses. A borrow of names ends when main ends, and the thread might still be running then. The help line gives the fix.

Complete the closure so the thread owns name.

use std::thread;

fn main() {
    let name = String::from("worker");
    let handle = thread::spawn([[move]] || {
        println!("hello from {name}");
    });
    handle.join().unwrap();
}

move transfers name into the closure, so the thread owns the String. main can no longer use it, and that is the point. Chapter 06's move rule applies to closures exactly the same way.

Sometimes the threads should borrow instead of own. Say you want several threads to read parts of one list. thread::scope makes that safe. Every thread spawned inside the scope is joined before scope returns, so the borrows end while the data is still alive.

use std::thread;

fn main() {
    let numbers = vec![1, 2, 3, 4, 5, 6, 7, 8];
    let (left, right) = numbers.split_at(4);

    let (left_sum, right_sum) = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<i32>());
        let b = s.spawn(|| right.iter().sum::<i32>());
        (a.join().unwrap(), b.join().unwrap())
    });

    println!("{left_sum} {right_sum}");
}

Both threads borrow slices of numbers. Nothing is moved, and numbers is still usable after the scope ends.

Why does thread::scope accept borrows that thread::spawn rejects?

thread::spawn promises nothing about when its thread ends, so the closure must own its data. thread::scope joins every thread before it returns, so the borrowed data is guaranteed to outlive them. The signature of scope expresses that, and the compiler checks it.

Laravel's Concurrency facade

Laravel has a helper for running independent tasks at the same time. The Concurrency facade takes an array of closures, runs them together, and returns the results in the same order:

use Illuminate\Support\Facades\Concurrency;
use Illuminate\Support\Facades\DB;

[$userCount, $orderCount] = Concurrency::run([
    fn () => DB::table('users')->count(),
    fn () => DB::table('orders')->count(),
]);
use std::thread;

fn main() {
    let users = vec!["ana", "bo", "cy"];
    let orders = vec![10, 20];

    let (user_count, order_count) = thread::scope(|s| {
        let users_task = s.spawn(|| users.len());
        let orders_task = s.spawn(|| orders.len());
        (users_task.join().unwrap(), orders_task.join().unwrap())
    });

    println!("{user_count} users, {order_count} orders");
}

The shape matches: two tasks run at once, and you get both results back. The memory model does not. Concurrency::run serializes each closure, runs it in a child PHP process, and serializes the result back. Each child works on a copy of what its closure captured, so it cannot change your variables. The scoped threads borrow users and orders from main. They share that memory, and the compiler checks that both threads finish before main uses the data again.

Message passing

Threads can share memory, and they can also send each other values. A channel is a queue with two ends: a Sender and a Receiver. send moves a value into the queue, and the receiver takes values out in order. Because send takes ownership, the sending thread cannot touch the value afterwards, so there is nothing to race on.

Here three workers report back to main. Each one gets its own clone of the sender:

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(format!("worker {id} done")).unwrap();
        });
    }
    drop(tx); // without this line, the loop below never ends

    let mut messages = Vec::new();
    for msg in rx {
        messages.push(msg);
    }
    messages.sort();
    for msg in messages {
        println!("{msg}");
    }
}

Cloning a Sender makes a new handle to the same queue. The receiver's loop ends only when every sender has been dropped. Each clone is dropped when its thread finishes. The original tx is still owned by main, which is why the program has the drop(tx) line.

Forgetting drop(tx) is the most common channel bug. The loop waits for one more message that can never arrive, and the program hangs. It doesn't panic and it doesn't print an error. When you review code with for msg in rx, check that every sender gets dropped.

This program has no drop(tx). What does it do?

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(id).unwrap();
        });
    }
    let mut total = 0;
    for n in rx {
        total += n;
    }
    println!("{total}");
}
  1. It prints 3 and exits, because the threads finish.
  2. It hangs. main still holds a sender, so the loop never ends.
  3. It doesn't compile, because tx is never dropped.
  4. It prints 0, because the loop ends before the threads send.

The threads finish and drop their clones, but the tx that main created is still alive. The channel stays open, so for n in rx waits for a message that is never sent. Add drop(tx); before the loop. Don't run this program as written: it will hang.

In Laravel 13, a job states its own retry rules with attributes. Each attribute sets one rule for that job class:

namespace App\Jobs;

use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Queue\Attributes\Backoff;
use Illuminate\Queue\Attributes\Timeout;
use Illuminate\Queue\Attributes\Tries;

#[Tries(3)]
#[Backoff([10, 60, 300])]
#[Timeout(30)]
class ProcessInvoice implements ShouldQueue
{
    use Queueable;

    public function __construct(public readonly int $invoiceId) {}

    public function handle(): void
    {
        // Send the invoice. The worker calls this once per attempt.
    }
}

Tries sets how many attempts the job gets. Backoff sets how many seconds Laravel waits before each retry. Timeout sets how long one attempt may run, and it needs the pcntl extension. Here is how the job travels from a controller to a worker:

// In a controller: hand the work to the queue.
ProcessInvoice::dispatch($invoice->id);

// Later, a worker started by `php artisan queue:work`
// pulls the job and runs its handle() method.
use std::sync::mpsc;
use std::thread;

fn main() {
    let (jobs, queue) = mpsc::channel::<u32>();

    let worker = thread::spawn(move || {
        for invoice_id in queue {
            println!("sending invoice {invoice_id}");
        }
    });

    jobs.send(41).unwrap(); // ProcessInvoice::dispatch(41)
    drop(jobs);             // no more jobs: the worker's loop ends
    worker.join().unwrap();
}

The shape is the same: one side hands off a job, and one consumer takes jobs in order. The differences matter. A Laravel queue is stored in Redis or a database, so jobs survive a crash and the workers can run on other machines. A channel lives in one process's memory and disappears with it. Use the queue for durable work between processes, and channels for coordination inside one program. The Rust worker above has no retries. A job that fails is gone unless your loop puts it back. In Laravel, Tries and Backoff handle that part for you.

Shared state: Arc<Mutex<T>>

Sometimes threads really do need the same value: a counter, a cache, a list of results. Rust splits that job in two. Arc<T> lets several owners hold one value. It works like Rc from Chapter 17, except its count is updated atomically, so it is safe across threads. Mutex<T> wraps the data and hands out access one thread at a time. It is the single key to the room.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();

    for _ in 0..8 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                let mut guard = counter.lock().unwrap();
                *guard += 1;
            }
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("count = {}", *counter.lock().unwrap());
}

lock() returns a MutexGuard. The guard dereferences to the number, so *guard += 1 changes the value inside the mutex. The lock is released when the guard is dropped. Here that happens at the end of each loop pass, so each thread holds the lock for exactly one increment. Keep critical sections that short. Anything slow inside the lock makes every other thread wait.

The guard is the lock. let _ = counter.lock(); drops the guard at once, so nothing is protected. This is the same trap as in Chapter 06. Give the guard a name, as above.

Laravel's Cache::lock() is the cross-process cousin. It coordinates separate PHP processes through the cache store. A Mutex coordinates threads inside one process, and the guard releases the lock for you when it goes out of scope.

Does this compile? What happens when it runs?

use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);
    let a = m.lock().unwrap();
    let b = m.lock().unwrap();
    println!("{} {}", *a, *b);
}
  1. No. A Mutex can't be locked twice, so the second lock() is a borrow error.
  2. It compiles. At runtime the second lock() waits for a lock this same thread already holds. The documentation says that may deadlock or panic.
  3. Yes, and it prints 5 5.

lock() takes &self, so the type system happily allows two guards to exist at once. The lock itself knows nothing about which thread owns it. Never lock the same mutex twice on one thread without dropping the first guard. Don't run this program: it will hang or panic.

A RwLock is the borrow rule at runtime. Any number of threads can hold a read guard at once, like many &T. A writer needs the write guard, which waits until every reader has let go, like &mut T. Use it when reads far outnumber writes. For short critical sections, a plain Mutex is simpler and is often the better choice.

use std::sync::RwLock;

fn main() {
    let config = RwLock::new(String::from("v1"));
    {
        let a = config.read().unwrap();
        let b = config.read().unwrap(); // many readers at once
        println!("{} {}", *a, *b);
    }
    *config.write().unwrap() = String::from("v2");
    println!("{}", config.read().unwrap());
}

For a single number, a lock is more machinery than you need. AtomicUsize offers operations such as fetch_add, which adds to the value and returns the old one as one indivisible operation. No thread can read between the add and the store, so no update is lost.

use std::sync::Arc;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

fn main() {
    let hits = Arc::new(AtomicUsize::new(0));
    let handles: Vec<_> = (0..8)
        .map(|_| {
            let hits = Arc::clone(&hits);
            thread::spawn(move || {
                for _ in 0..1000 {
                    hits.fetch_add(1, Ordering::Relaxed);
                }
            })
        })
        .collect();

    for handle in handles {
        handle.join().unwrap();
    }
    println!("hits = {}", hits.load(Ordering::Relaxed));
}

The Ordering argument says how this operation is ordered relative to other memory accesses. Relaxed is enough for a standalone counter, where nothing else depends on the order. Once an atomic is used to publish other data, you need stronger orderings. Rust Atomics and Locks by Mara Bos covers them in depth.

One more detail. If a thread panics while it holds a guard, the mutex is poisoned. Later calls to lock() return Err, because the data may be half-updated. lock().unwrap() turns that into a panic, which is the usual choice.

Watch a data race happen

This is the bug the rest of the chapter guards against. The simulator plays two threads that each run count = count + 1 a thousand times. Each increment is really three steps: READ the shared count into a register, ADD 1 to the register, and WRITE the register back. The threads interleave those steps. Step through a few by hand first, then run the random batch.

Press A, B, A, B, A, B in No lock mode. Both threads read 0 before either one writes, so both write 1. Two increments ran, and the count is 1. Nothing crashed and nothing reported an error. The bug only shows up in the number.

The write that overwrote the other one is a lost update. It was computed from an old read. The batch loses close to half of its increments, because the scheduler switches threads after every step. Real races are rarer and harder to reproduce, but they are just as wrong when they happen. With Mutex or Atomic, the random run always finishes at exactly 2,000. The Mutex turns the five steps LOCK, READ, ADD, WRITE, UNLOCK into one piece of work the other thread cannot enter. The Atomic mode makes the whole increment one indivisible step.

Send and Sync

Rust decides which types may cross threads with two marker traits. You rarely write them yourself. The compiler checks them every time you call thread::spawn.

  • Send: a value of this type can be moved to another thread.
  • Sync: a shared reference &T can be used from several threads at once. A type is Sync exactly when &T is Send.

Both traits are automatic. A struct or enum is Send only when every field is Send, and the same goes for Sync. You never add a line for it. A few standard types opt out, and the compiler stops you from sending them. Rc is the classic example.

use std::rc::Rc;
use std::thread;

fn main() {
    let shared = Rc::new(5);
    let handle = thread::spawn(move || {
        println!("{shared}");
    });
    handle.join().unwrap();
}

The count inside an Rc is updated without atomic operations. If two threads cloned or dropped the same Rc at the same moment, the count could end up wrong. So Rc is not Send, and the compiler stops the move at the spawn call. The fix is Arc. It has the same API and an atomic count:

use std::sync::Arc;
use std::thread;

fn main() {
    let shared = Arc::new(5);
    let handle = thread::spawn(move || {
        println!("{shared}");
    });
    handle.join().unwrap();
}

RwLock<T> follows the same pattern as Mutex, but it is Sync only when T is both Send and Sync, because readers share &T at the same time.

use std::cell::RefCell;
use std::sync::Arc;
use std::thread;

fn main() {
    let cell = Arc::new(RefCell::new(0));
    let c = Arc::clone(&cell);

  1. Yes. The Arc makes the RefCell safe to share.
  2. No, E0277. RefCell is not Sync, so Arc<RefCell<i32>> can't be sent to another thread.
  3. No. borrow_mut can't be called from a spawned thread.

Arc<T> is Send only when T is both Send and Sync. The borrow count inside a RefCell is updated without a lock, so it isn't Sync. Replacing it with Arc<Mutex<i32>> fixes the code, because a Mutex<i32> is both Send and Sync.

What Rust doesn't prevent

The compiler rules out data races. It does not rule out every concurrency bug, and several of the most common ones compile cleanly. Here are three.

Deadlock: two locks, two orders

Each thread takes one lock and then waits for the other. Neither thread can move on, so both wait forever. Nothing in the types is wrong.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let accounts = Arc::new(Mutex::new(0));
    let orders = Arc::new(Mutex::new(0));

    let (a1, o1) = (Arc::clone(&accounts), Arc::clone(&orders));
    let t1 = thread::spawn(move || {
        let _a = a1.lock().unwrap();
        let _o = o1.lock().unwrap(); // waits for thread 2 to release orders
    });

    let (a2, o2) = (Arc::clone(&accounts), Arc::clone(&orders));
    let t2 = thread::spawn(move || {
        let _o = o2.lock().unwrap();
        let _a = a2.lock().unwrap(); // waits for thread 1 to release accounts
    });

    t1.join().unwrap();
    t2.join().unwrap();
}

The usual cure is a rule: every thread takes the locks in the same order. Don't run this one. It will hang.

Check, then act, across two locks

Each lock() below is safe on its own, and there is no data race. The check and the withdrawal are two separate critical sections, though. If both threads see 100 before either one subtracts, both pass the check, and the balance ends at -60. The data is protected. The logic is not.

use std::sync::Mutex;

fn withdraw(balance: &Mutex<i32>, amount: i32) -> bool {
    // Lock 1: check.
    let enough = *balance.lock().unwrap() >= amount;
    if enough {
        // Lock 2: act. Another thread may have withdrawn in between.
        *balance.lock().unwrap() -= amount;
    }
    enough
}

fn main() {
    let balance = Mutex::new(100);
    std::thread::scope(|s| {
        s.spawn(|| withdraw(&balance, 80));
        s.spawn(|| withdraw(&balance, 80));
    });
    println!("{}", balance.lock().unwrap());
}

Leaks are safe

Leaking memory is not undefined behavior, so the compiler doesn't stop it. std::mem::forget leaks a value on purpose, and an Rc cycle leaks without anyone noticing (Chapter 17 covers Rc). A leak is a waste rather than a memory-safety bug, and it is still a bug to fix.

The easy button: rayon

For data parallelism, where you apply the same work to many items, the rayon crate removes most of the boilerplate. It spreads the work over a pool of threads, so you write no spawn, no channel and no lock.

use rayon::prelude::*;

fn main() {
    let numbers: Vec<u64> = (1..=1_000).collect();
    let total: u64 = numbers.par_iter().map(|n| n * n).sum();
    println!("{total}");
}

Add rayon = "1" to Cargo.toml. The par_iter() call replaces iter(), and the rest of the chain stays the same. Reach for it when each item is real work and no item depends on another. For tiny loops, the cost of coordinating threads is more than the loop itself.

Agents reach for Arc<Mutex<…>> in almost every concurrent program they write, because it compiles once the types line up. Treat it the way you treat a .clone(). Find where each guard is dropped. A guard held across slow I/O, or across an .await (Chapter 19), blocks every other thread that needs the lock. Ask whether the program needs shared state at all. When an agent builds an Arc<Mutex<Vec<…>>> only to collect results from workers, a channel or the values returned by join() usually says the same thing with nothing shared.

Which of these bugs does the Rust compiler prevent?

  1. Two threads take two locks in opposite orders and wait forever.
  2. A thread checks a balance, releases the lock, and withdraws based on the old check.
  3. Two threads hold a &mut to the same Vec at the same time, with no lock.
  4. A thread holds a MutexGuard for a long time, and everything else waits.

That is a data race in its plain form. The compiler refuses it, because two live &mut borrows of one value can't exist, even across threads. The other three compile. Deadlocks, logic races and long lock holds are design problems, and they need review and tests.

Practice

These checks use everything above. Some have code the compiler must reject, and some ask you to predict output.

Does this compile?

use std::thread;

fn main() {
    let label = String::from("nightly report");
    let handle = thread::spawn(|| {
        println!("running {label}");
    });
    handle.join().unwrap();
}
  1. Yes. Threads can see the locals of the function that spawned them.
  2. No, E0373. The closure borrows label, and the thread may outlive main. Adding move fixes it.
  3. No, E0382. label was moved into the closure.

Nothing was moved. The closure borrows label, and thread::spawn won't accept a borrow of a local, because the thread might still run after the function that owns label has returned. E0382 is the error for use after a move, and this program never moves anything.

What type is answer?

use std::thread;

fn main() {
    let handle = thread::spawn(|| 40 + 2);
    let answer = handle.join();
}
  1. i32, because the closure returns 40 + 2.
  2. Result<i32, Box<dyn Any + Send>>: Ok with the value, or Err if the thread panicked.
  3. Option<i32>, which is None if the thread panicked.
  4. (), because join only waits.

Ask for () directly and rustc says: expected (), found Result<{integer}, Box<dyn Any + Send>>. The Err side carries the panic payload. That is why join().unwrap() panics in the thread that called join.

Does this compile?

use std::rc::Rc;
use std::sync::Mutex;
use std::thread;

fn main() {
    let counter = Rc::new(Mutex::new(0));
    let c = Rc::clone(&counter);
    thread::spawn(move || {
        *c.lock().unwrap() += 1;
    })
    .join()
    .unwrap();
}
  1. Yes. The Mutex makes the Rc safe to share.
  2. No, E0277. An Rc is not Send, and wrapping it in a Mutex doesn't change that. Use Arc.
  3. No. A Mutex can't be used with threads.

The Mutex protects the number inside it. It doesn't change the type of the handle that holds the Mutex. The Rc count is still updated without atomic operations, so the compiler refuses to move the handle into a thread. Change Rc to Arc and the code compiles.

What does this print?

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let total = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();
    for _ in 0..4 {
        let total = Arc::clone(&total);
        handles.push(thread::spawn(move || {
            for _ in 0..10 {
                *total.lock().unwrap() += 1;
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    println!("total = {}", *total.lock().unwrap());
}
  1. total = 40, on every run.
  2. total = 40 most of the time, and less under load.
  3. total = 4, because each thread adds once.
  4. It doesn't compile, because total is moved into four closures.

Each thread adds 10, and four threads make 40. Every += 1 happens under the lock, so no update is lost, whatever the timing. The Mutex makes the total exact.

Complete the counter so that four threads can share it and add to it safely.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = [[Arc]]::new([[Mutex]]::new(0));
    let mut handles = Vec::new();
    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            *counter.lock().unwrap() += 1;
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());
}

Arc::new creates the shared owner, and Arc::clone gives each thread its own handle. Cloning an Arc only bumps the count. Mutex::new puts the number behind the lock, so each += 1 happens under the guard. The program prints 4.

Does this compile?

use std::thread;

fn main() {
    let words = vec![String::from("alpha"), String::from("beta")];
    let handle = thread::spawn(move || {
        println!("{words:?}");
    });
    handle.join().unwrap();
    println!("{}", words.len());
}
  1. Yes. The thread is joined before words.len() runs.
  2. No, E0382. The move closure took words when it was created, so main can't use it afterwards.

The join changes when the thread finishes, not who owns the vector. Ownership moved when the closure was created. Chapter 06's rule holds for threads too: once a value has been moved, its old name can't be used. If main still needs the vector, use a scoped thread, or clone the vector before the move.

Recap

Threads, messages and shared state

  • thread::spawn runs a closure on a new thread and returns a JoinHandle. join() waits for the thread and returns its result as a Result.
  • A spawned closure must own what it uses, so you write move. thread::scope lets threads borrow locals, because it joins every thread before it returns.
  • A channel moves values from many senders to one receiver. The receiver's loop ends only when every sender has been dropped.
  • Arc<Mutex<T>> shares one value safely. The lock is released when the guard is dropped, so keep the critical section short.
  • RwLock allows many readers or one writer. Atomics such as AtomicUsize::fetch_add make a single counter update indivisible.
  • Send means a type can move to another thread. Sync means &T can be shared between threads. Rc is neither, and Cell and RefCell are not Sync.
  • The compiler prevents data races. It does not prevent deadlocks, logic races or leaks.
Explain it back: why does the borrow checker also prevent data races? Answer in three sentences.

One good answer: "A data race needs two threads touching the same memory, with at least one write and no coordination. The borrow rules allow many shared borrows or one mutable borrow, never both, so the compiler will not let two threads hold writable access to the same value at once. Sharing a value that must be written across threads needs a type that does the coordination itself, such as Mutex or an atomic, and the compiler checks that the value is Send and Sync before it crosses a spawn."

If your version mentions one writer or many readers, no unsynchronized writable access and Send and Sync checked at spawn, you have it.
