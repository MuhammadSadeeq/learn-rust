A trait is a capability

Chapter 09 gave your structs methods. A trait is a named set of methods, and a type implements the trait by writing those methods. Once a type has done that, code can ask for anything that can do the job, using the trait's name as the requirement.

Here is the smallest useful trait. It declares a method with no body. Each type writes the body in its own impl block.

trait Summary {
    fn summarize(&self) -> String;
}

struct Tweet {
    user: String,
    text: String,
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("@{}: {}", self.user, self.text)
    }
}

fn main() {
    let t = Tweet {
        user: "ferris".to_string(),
        text: "Hello, crab!".to_string(),
    };
    println!("{}", t.summarize());
}

The trait is the list. impl Summary for Tweet is the promise that Tweet provides every method the list names. The body lives in the impl, not in the struct. A struct can implement as many traits as it needs, and each one adds its own methods.

Predict first: if you delete the impl Summary for Tweet block, does t.summarize() still compile?

No. The method exists only because the impl promises it. Without the block, the compiler reports error[E0599]: no method named `summarize` found for struct `Tweet` in the current scope, and it points at the Summary trait as the place that defines the method.

Default methods

A trait method can have a body. That body is the default. Every type that implements the trait gets it, and a type can replace it with its own version. A default can call the required methods, because every implementor is guaranteed to have them.

trait Summary {
    fn summarize(&self) -> String;

    // Default: written once, here. It calls the required method.
    fn preview(&self) -> String {
        let short: String = self.summarize().chars().take(20).collect();
        format!("{short}…")
    }
}

struct Article {
    headline: String,
    body: String,
}

struct Tweet {
    user: String,
    text: String,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("{} ({} bytes)", self.headline, self.body.len())
    }
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("@{}: {}", self.user, self.text)
    }
}

fn main() {
    let a = Article {
        headline: "Ownership".to_string(),
        body: "Every value has one owner.".to_string(),
    };
    let t = Tweet {
        user: "ferris".to_string(),
        text: "Hello, crab!".to_string(),
    };
    println!("{}", a.summarize());
    println!("{}", t.summarize());
    println!("{}", t.preview());
    println!("{}", a.preview());
}

Only summarize is required. preview is written once, in the trait, and neither type has its own copy of it.

This is the trap that catches almost every PHP developer. In PHP, trait is a copy-paste mixin. use Loggable; pastes the methods into the class body. A Rust trait pastes nothing. It has no fields, and it does not change the layout of your struct. It is a contract: a list of methods a type has to provide, with optional default bodies.

The closest PHP thing to a Rust trait is an interface. The difference that matters is that PHP interfaces cannot hold a method body, and Rust traits can.

interface Summary {
    public function summarize(): string;
}

final readonly class Tweet implements Summary {
    public function __construct(
        public string $user,
        public string $text,
    ) {}

    #[\Override]
    public function summarize(): string {
        return "@{$this->user}: {$this->text}";
    }
}
trait Summary {
    fn summarize(&self) -> String;
}

struct Tweet {
    user: String,
    text: String,
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("@{}: {}", self.user, self.text)
    }
}

The implements clause sits on the class. In Rust the impl block stands beside the struct, and it can be written later or in another file. That is the next section. PHP interfaces have no place for a default body, so the default-method half of a Rust trait has no PHP equivalent at all.

PHP 8.3 added #[\Override] for part of this check. Put it on a method, and PHP verifies that a parent or an interface really declares a method with that name. If the method is spelled summarise, the class fails to load. Rust checks every impl at compile time. A misspelled method is error E0407, and a missing required method is E0046.

Traits for types you didn't write

PHP has no direct equivalent of this. You can implement your trait for a type from the standard library, such as String, Vec<i32> or str. After that, the method works on those values like any other method.

trait Shout {
    fn shout(&self) -> String;
}

impl Shout for str {
    fn shout(&self) -> String {
        format!("{}!", self.to_uppercase())
    }
}

trait Summary {
    fn summarize(&self) -> String;
}

impl Summary for String {
    fn summarize(&self) -> String {
        format!("text of {} bytes", self.len())
    }
}

impl Summary for Vec<i32> {
    fn summarize(&self) -> String {
        format!("{} numbers, sum {}", self.len(), self.iter().sum::<i32>())
    }
}

fn main() {
    println!("{}", "hello".shout());
    let s = String::from("hello");
    let v = vec![1, 2, 3];
    println!("{}", s.summarize());
    println!("{}", v.summarize());
}

The call "hello".shout() works because shout takes &self and the impl is for str. A string literal is a &str, which is exactly the receiver the method expects. A trait written to add methods to types you don't own is called an extension trait. The itertools crate uses the same idea to add methods to every iterator.

The orphan rule: one side must be yours

You may implement a trait for a type only when the trait or the type is defined in your crate. This is the orphan rule. Without it, two crates could each implement Display for Vec<i32> in different ways, and nothing would say which one a program should use.

Predict first: this impl sits in your own crate. Is it allowed?

No. Display is defined in the standard library, and Vec is too. Neither type is yours. Read the compiler's answer below.

use std::fmt;

impl fmt::Display for Vec<i32> {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{:?}", self)
    }
}

fn main() {
    println!("{}", vec![1, 2, 3]);
}

use std::fmt;

    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{:?}", self.0)
    }
}

fn main() {
    let n = Numbers(vec![1, 2, 3]);
    println!("{n}");
}

Laravel's Collection::macro('total', ...) is the nearest thing you already know. It adds a method to a class you did not write. Rust does the same job, with two differences that matter:

  • A macro is registered at runtime, usually in a service provider's boot method. A Rust impl is part of the compiled program. There is nothing to register, and nothing to forget to register.
  • A trait method is visible only where the trait is in scope. Call it from a module that did not import the trait and you get error[E0599], with the note that items from traits can only be used if the trait is in scope.

Accepting anything that can do it

A function can ask for a trait instead of a concrete type. This program uses the four spellings you will meet most often:

use std::fmt::{Debug, Display};

trait Summary {
    fn summarize(&self) -> String;
}

#[derive(Debug)]
struct Tweet {
    user: String,
    text: String,
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("@{}: {}", self.user, self.text)
    }
}

fn notify(item: &impl Summary) {
    println!("Breaking: {}", item.summarize());
}

fn notify_bounds<T: Summary + Debug>(item: &T) {
    println!("{:?} -> {}", item, item.summarize());
}

fn notify_where<T>(item: &T)
where
    T: Summary + Debug,
{
    println!("{:?} => {}", item, item.summarize());
}

fn make_tweet() -> impl Summary {
    Tweet { user: "ferris".to_string(), text: "hello".to_string() }
}

fn show<T: Display>(item: T) -> String {
    format!("[{item}]")
}

fn main() {
    let t = Tweet { user: "ana".to_string(), text: "hi".to_string() };
    notify(&t);
    notify_bounds(&t);
    notify_where(&t);
    println!("{}", make_tweet().summarize());
    println!("{}", show(5));
}
SpellingRead it as
item: &impl SummarySome type that implements Summary. Short and clear for one parameter.
fn notify<T: Summary>(item: &T)The same thing with a name for the type. Use it when two parameters must share one type, or when the type must be named in the return type.
T: Summary + DebugSeveral bounds joined with +. The type must have both traits.
where T: Summary + DebugThe same bounds, moved after the signature. Use it when the bounds get long.

A return type can be -> impl Summary. The caller can call the trait's methods, but it cannot name the concrete type. There is one limit. The function must return the same concrete type on every path. If one branch returns a Tweet and the other an Article, the compiler reports error[E0308]: `if` and `else` have incompatible types. For that you need a trait object, which is section 6.

The compiler checks a generic body once, for any T. The body may use only what the bounds promise. Here the bound is missing, so the method call is not allowed.

fn notify<T>(item: &T) {
    println!("Breaking news! {}", item.summarize());

Generics: one body, many types

A generic function has type parameters in angle brackets. The classic example finds the largest item in a slice. The bound PartialOrd gives you >. The bound Copy lets the function copy values out of the slice, which is what list[0] and for &item in list do.

fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list[0];
    for &item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}

fn main() {
    println!("{}", largest(&[34, 50, 25, 100, 65]));
    println!("{}", largest(&['y', 'm', 'a', 'q']));
}

Nothing in the body mentions i32 or char. The compiler checks the body against the bounds, then makes a specialized copy for each type it is used with. Section 5 explains that step.

PHP 8.5 has no generics. Its syntax has no type parameters, so function first<T>(array $xs): T is a parse error. The closest tool is a docblock: @template T and @param list<User> $users. PHPStan and Psalm read those comments. PHP itself ignores them, so a wrong element type goes unnoticed until you run the analyzer.

Rust generics are part of the language. The compiler checks the body against the bounds, and it checks each call against the concrete types.

Leave out a bound and the body fails

Remove PartialOrd and > stops working on T. The compiler cannot assume that every T can be compared.

fn largest<T: Copy>(list: &[T]) -> T {
    let mut largest = list[0];
    for &item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}

fn main() {
    println!("{}", largest(&[34, 50, 25, 100, 65]));
}

You cannot move a value out of a borrowed slice, and a generic T might not be Copy. Chapter 06 covered moves. This is the same rule, applied to a type parameter.

Generic structs and specific impls

Structs take type parameters the same way. An impl<T> block covers every T. An impl Point<f64> block covers only the points whose fields are f64, so a method can exist for one concrete type and not for the others.

struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn x(&self) -> &T {
        &self.x
    }
}

impl Point<f64> {
    fn dist_from_origin(&self) -> f64 {
        (self.x * self.x + self.y * self.y).sqrt()
    }
}

fn main() {
    let p = Point { x: 3.0, y: 4.0 };
    println!("{}", p.dist_from_origin());
    let q = Point { x: 3, y: 4 };
    println!("{}", q.x());
}

Calling q.dist_from_origin() on a Point<i32> is an error. The compiler reports that the method was found for Point<f64>, which is exactly the point of the specific impl.

Option<T> and Result<T, E> are generic enums built the same way. You have used them since Chapters 10 and 11. Your own enums can take type parameters too.

Monomorphization: the compiler stamps out copies

How does a generic function run at full speed? The compiler does not pass around a value that could be any type. At build time it finds every concrete type that each generic function is used with, and it generates a specialized copy for each one. That step is called monomorphization. Picture a stamp: one template, one stamped copy per type.

In a debug build you can see the copies. Take a program that calls describe six times with five different types. Two of the calls pass an i32, so the binary holds five copies, not six. This is the list nm -C prints for that program:

main::describe::<&str>
main::describe::<bool>
main::describe::<char>
main::describe::<f64>
main::describe::<i32>

The exact names depend on the compiler version, and a release build may inline the copies away. The idea holds either way. Each copy is more machine code. Each call goes straight to its copy, with no lookup at runtime. The press below shows the same process one call at a time.

Predict first: a loop calls describe(42) a thousand times, and calls describe(3.5) once. How many copies are in the binary?

Two. One copy for i32 and one for f64. The number of calls doesn't matter. Only the number of distinct types does.

Trait objects: dyn Trait

Generics fix the type at compile time. Sometimes one collection has to hold different types, and the choice is only known at runtime. For that you use a trait object. dyn Shape means "some value that implements Shape, and I don't know which one." A trait object always sits behind a pointer, usually Box<dyn Shape> or &dyn Shape.

trait Shape {
    fn area(&self) -> f64;
}

struct Circle {
    r: f64,
}

struct Square {
    side: f64,
}

impl Shape for Circle {
    fn area(&self) -> f64 {
        std::f64::consts::PI * self.r * self.r
    }
}

impl Shape for Square {
    fn area(&self) -> f64 {
        self.side * self.side
    }
}

fn main() {
    let shapes: Vec<Box<dyn Shape>> = vec![
        Box::new(Circle { r: 1.0 }),
        Box::new(Square { side: 2.0 }),
    ];
    for s in &shapes {
        println!("{:.2}", s.area());
    }
}

The vector holds a circle and a square. The loop calls area() on each element without knowing its type. The call still works, because each box carries a pointer to the table of methods for its own type.

What a trait object is made of

A &dyn Shape is not one pointer. It is two: a data pointer to the value, and a vtable pointer to a table built for that type's implementation of Shape. The table holds the size, the alignment, a drop entry and one pointer per method. A call to area reads the method pointer from the table, then jumps to it.

You can measure the extra word. On a 64-bit machine, &i32 is 8 bytes and &dyn Display is 16. The extra 8 bytes are the vtable pointer. Box<dyn Display> is 16 bytes for the same reason.

When a trait can't become dyn

Not every trait can be made into a trait object. The vtable needs one fixed entry for each method. A method that returns Self would force the caller to know the size of the concrete type, and the caller holds only the trait object. A method with its own type parameter would need a separate entry for every type it is ever called with. The compiler refuses such a trait. Older books call this object safety. The compiler now calls it dyn compatibility.

trait Cloner {
    fn dup(&self) -> Self;
}

struct A;

impl Cloner for A {
    fn dup(&self) -> Self {
        A
    }
}

fn main() {
    let items: Vec<Box<dyn Cloner>> = vec![Box::new(A)];
    println!("{}", items.len());
}

Most types you write should implement a handful of standard traits, because the people who use them expect those traits to exist. Some you can get from #[derive(...)]. Others you write by hand.

Two of these you will write by hand more often than the rest: Display and From. Display is what {} prints. From is the conversion. Here is a Money type with both.

Predict first: if you implement From<i64> for Money, can an i64 call .into() to become a Money?

Yes. Implementing From gives you Into in the other direction for free. The program below uses it.

use std::fmt;

struct Money {
    cents: i64,
}

impl fmt::Display for Money {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "${}.{:02}", self.cents / 100, self.cents % 100)
    }
}

impl From<i64> for Money {
    fn from(cents: i64) -> Self {
        Money { cents }
    }
}

fn main() {
    let price: Money = 1999.into();
    println!("{price}");
    println!("{}", Money::from(250));
}

let price: Money = 1999.into(); compiles because the standard library has a blanket implementation: any type with From<A> for B also gets Into<B> for A. You write From once and get both spellings of the conversion.

Associated types or generic parameters?

Some traits take a generic parameter, such as From<T>. Others declare an associated type, such as Iterator with its type Item. The rule of thumb: use an associated type when each implementing type has exactly one right answer. An iterator yields one kind of item, so Item is chosen by the impl. Use a generic parameter when one type may implement the trait several ways. Money can implement From<i64> and From<&str> at the same time, and the compiler picks the impl from the argument's type.

Operators are traits too. a + b calls Add::add, and the Output associated type says what + returns.

use std::ops::Add;

#[derive(Debug, Clone, Copy, PartialEq)]
struct Money {
    cents: i64,
}

impl Add for Money {
    type Output = Money;

    fn add(self, other: Money) -> Money {
        Money { cents: self.cents + other.cents }
    }
}

fn main() {
    let total = Money { cents: 1250 } + Money { cents: 399 };
    println!("{:?}", total);
}

Agents over-generalize. Ask one for a helper and you may get this: fn f<T: AsRef<str> + Into<String> + Clone>(x: T). Three bounds, and a reader has to work out what the function actually needs. Agents also reach for Box<dyn Trait> everywhere, which adds indirection that nothing asked for.

In review, ask two questions. First, what actually varies here? If the answer is one concrete type, use that type. Second, what does the function call on the value? Bound only for those methods. Usually one concrete type, or one generic parameter with one bound, is enough. Keep the API simple until the caller needs more.

Practice

Seven checks. Try each one before you open the answer. They cover trait-versus-PHP ideas, the orphan rule, missing bounds, trait objects, and the standard bounds you will write most often.

A colleague says: "Rust traits are just PHP traits." What is the most accurate reply?

  1. Yes. use in PHP and impl in Rust both paste methods into the class.
  2. Not quite. A Rust trait is a contract, closer to a PHP interface. The type writes its own impl, and nothing is pasted in.
  3. Rust has no equivalent of interfaces. Its only tool for this is generics.
  4. Yes, except Rust traits can also hold properties.

A PHP trait copies methods into the class body. A Rust trait describes methods and holds no fields. The type provides the methods with its own impl. The nearest PHP tool is the interface, and a PHP interface can't contain a method body.

Does this compile?

use std::fmt;

impl fmt::Display for Option<i32> {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "maybe")
    }
}

fn main() {
    println!("{}", Some(1));
}
  1. Yes. The compiler accepts any impl for a type in the standard library.
  2. No. Neither Display nor Option is defined in this crate, so the orphan rule rejects it with E0117.
  3. Yes. It's a Display impl, and every Display impl is allowed.

This is the same rule as the Vec example, with a different foreign type. The fix is a newtype you own, such as struct Maybe(Option<i32>);, with the impl written for Maybe.

Does this compile?

fn bigger<T>(a: T, b: T) -> bool {
    a > b
}

fn main() {
    println!("{}", bigger(1, 2));
}
  1. Yes. Every type can be compared with >.
  2. No. > needs T: PartialOrd, and T has no bounds, so the body fails with E0369.
  3. Yes. The call passes integers, so T is i32 inside the body.

The body is checked for any T, not for the integers in main. The fix is fn bigger<T: PartialOrd>.

What does this print?

trait Speak {
    fn speak(&self) -> String;
}

struct Dog;
struct Cat;

impl Speak for Dog {
    fn speak(&self) -> String {
        "woof".to_string()
    }
}

impl Speak for Cat {
    fn speak(&self) -> String {
        "meow".to_string()
    }
}

fn main() {
    let animals: Vec<Box<dyn Speak>> = vec![Box::new(Dog), Box::new(Cat), Box::new(Dog)];
    for a in animals.iter() {
        println!("{}", a.speak());
    }
}
  1. The compiler rejects the vector, because Dog and Cat are different types.
  2. woof, meow, woof, one per line.
  3. woof, woof, meow, one per line.
  4. meow, woof, woof, one per line.

Each element is a Box<dyn Speak>, so the vector holds one type, and the box decides which speak runs. The loop visits the elements in order. The first choice describes a different situation: a plain vec![Dog, Cat] with two struct types fails with E0308, because a Vec<T> has one T. The boxes are what make the mix legal.

Fill in the bound so print_all accepts any type that can be shown with {}.

use std::fmt::Display;

fn print_all<T: [[Display|std::fmt::Display]]>(items: &[T]) {
    for item in items {
        println!("{item}");
    }
}

fn main() {
    print_all(&[1, 2, 3]);
}

The body prints with {item}, which uses Display, so the bound must name Display. Without the bound the body fails with E0277: T doesn't implement Display. The answer std::fmt::Display is the same trait with the full path, which works without the use line.

  • trait
  • impl I for X
  • required method (no body)
  • default method
  • match on an enum variant, or a generic bound
  • impl fmt::Display
  1. Check the body of describe<T: Display> against its bound alone.
  2. Find each concrete type it is called with: i32, f64, &str.
  3. Generate one specialized copy for each of those types.
  4. Point every call at the copy for its type.

The generic body is checked first, once, against its bounds. That is why a missing bound is an error even when nothing calls the function. Only then does the compiler look at the call sites and stamp out the copies. The last step is what makes a generic call as direct as an ordinary one.

Recap

Capabilities and generics

  • A trait is a set of methods a type promises to provide. impl Trait for Type is the promise. Default methods are shared bodies, and they can call the required methods.
  • You may implement a trait for a type only when the trait or the type is defined in your crate. That is the orphan rule. A newtype is the usual way around it.
  • impl Trait, <T: Trait> and where all accept any type with the trait. A missing bound fails inside the generic body, with E0599 for a method or E0369 for an operator.
  • Generics are monomorphized: the compiler makes one specialized copy per concrete type. Calls are direct, and the binary holds more code.
  • dyn Trait behind a pointer is one copy of the code plus a fat pointer, the data pointer and the vtable pointer. Calls go through the vtable. The trait must be dyn compatible, so no method may return Self or take its own type parameters, unless that method is excluded with where Self: Sized.
  • Implement Display for {} and From for conversions. Into comes free from From.
Explain it back: generics or dyn Trait? How do you decide?

One good answer: "Start with generics. The compiler makes a specialized copy for each type, so calls are direct, can be inlined, and are checked at compile time. Use dyn Trait when one collection or field has to hold different types, or when the set of types isn't known until runtime. Then you pay one indirect call per method, and you get one copy of the code."

If your version mentioned compile time or runtime, one copy or many, and mixed types in one collection, you've got it.
