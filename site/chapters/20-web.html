Laravel, translated

You already know how a Laravel request moves. It enters public/index.php, passes through middleware, matches a route, runs a controller and returns a response. An axum app moves a request through the same stages. Most of the names change. The jobs stay the same.

Two rows need a closer look. Rust has no built-in ORM, so the database choice is yours. The middleware row hides a real difference in timing, and the next section is about that.

Laravel 13 gets its API routes from routes/api.php, which php artisan install:api creates. One line registers the five resource routes, and each route calls one method on the controller:

// routes/api.php, created by `php artisan install:api`
use App\Http\Controllers\NoteController;
use Illuminate\Support\Facades\Route;

Route::apiResource('notes', NoteController::class);

The show method is the one that matches the Rust handler below:

final class NoteController extends Controller
{
    public function show(Note $note): JsonResponse
    {
        return response()->json($note);
    }
}
/// GET /api/notes/{id}
pub async fn show(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<Note>, AppError> {
    let db = state.db.read().await;
    let note = db.find(id).ok_or(AppError::NotFound(id))?;
    Ok(Json(note.clone()))
}

Route model binding is the big difference. Note $note made Laravel load the model before show ran. Axum has no implicit binding. The handler takes the id, looks the note up, and returns an error when it is missing.

Laravel resolves the controller, the model and the response for you. In axum, each of those steps is a function parameter or a return type, so you can read them in the signature.

Which row in the table has no counterpart in axum at all?

Eloquent. Routes, controllers, the container and middleware all have direct counterparts. axum does not ship a database layer, so you pick a library such as sqlx. Section 7 covers that choice.

Request lifecycle

Laravel builds the application for every request. public/index.php loads the framework, the service providers register their bindings, and then the middleware, router and controller run. With PHP-FPM, the next request starts from scratch.

An axum app is built once. main builds the router and the state, binds a port, and starts serving. After that, each request runs only the per-request stages. The two lanes below handle the same request. Press a button and watch each lane walk its stages. A request stops at the first stage that fails, and the stages after it are skipped.

Read the axum lane again, and notice the order. The router chooses the route first. Only then do the layers run, and they wrap the route that was chosen. Laravel's global middleware runs before the router. Axum's Router::layer runs after it, which makes it closer to Laravel's route middleware. You can check this from inside a layer. A layer added with .layer() can read MatchedPath from the request. For a URL that matched nothing, the value is missing, and the layer still runs for the fallback.

If some code must see the raw URL before the router does, wrap the whole router in a tower service instead. That wrapper runs before routing. Changing the URL inside a .layer() cannot change which route runs, because the route is already chosen.

Laravel registers global middleware in bootstrap/app.php. The same file configures routing and exceptions, so there is no HTTP Kernel to edit. Here is a global middleware next to the axum layers:

<?php

use App\Http\Middleware\LogRequests;
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Middleware;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        api: __DIR__.'/../routes/api.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware): void {
        $middleware->append(LogRequests::class);  // global: runs before routing
    })->create();
let app = Router::new()
    .route("/api/notes", get(index).post(store))
    .layer(TraceLayer::new_for_http());

append adds LogRequests to the global stack, so it runs for every request before the router picks a route. The axum .layer() runs after the router has chosen the route, so it wraps the route that was picked. The row in the table above is about this difference. To run code before routing in axum, wrap the whole router, as the trap above says.

A POST body has no title. Which stage stops the request, and does store run?

The extractor stage. ValidJson reads the body, and serde fails on the missing field. The rejection becomes a 422 before store is called. Nothing is inserted.

The request stops at the first stage that fails. Later stages never run.

Hello, axum

Start with cargo new hello-axum, then add the dependencies. Pin the versions. Axum 0.8 changed the path syntax and removed several APIs, so older examples often fail to compile. A pinned version also tells you which API you are reading.

[dependencies]
axum = "0.8.9"
serde = { version = "1.0.229", features = ["derive"] }
serde_json = "1.0.151"
tokio = { version = "1.53.2", features = ["full"] }
tower-http = { version = "0.7.1", features = ["trace", "timeout"] }
tracing = "0.1.44"
tracing-subscriber = { version = "0.3.23", features = ["env-filter"] }

The project uses every line above. The hello program below needs only axum and tokio.

use axum::Router;
use axum::extract::Path;
use axum::routing::get;
use tokio::net::TcpListener;

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(|| async { "Hello, axum\n" }))
        .route("/hello/{name}", get(greet));

    let listener = TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

async fn greet(Path(name): Path<String>) -> String {
    format!("Hello, {name}\n")
}
  • #[tokio::main] turns main into the entry point of the tokio runtime. Axum runs on tokio, so the server needs it.
  • Router::new().route(path, handler) registers a path. get(greet) says that the function answers GET.
  • {name} is a path parameter. Path(name): Path<String> pulls the value out of the URL.
  • TcpListener::bind opens the port. 0.0.0.0 listens on every network interface. 127.0.0.1 listens only on this machine, which is the safer choice while you learn.
  • axum::serve runs the server. The .await keeps main running until the server stops.

Run it, and send a request from another terminal:

cargo run
curl http://127.0.0.1:3000/hello/Ana
Hello, Ana

Path parameters use braces in axum 0.8. You will still find /:name in older posts. In 0.8 that form panics as soon as the router is built. The panic message says what to do:

Path segments must not start with `:`. For capture groups, use `{capture}`. If you meant to literally match a segment starting with a colon, call `without_v07_checks` on the router.
A blog post shows .route("/hello/:name", get(greet)). You paste it in and run cargo run. What happens?

The program panics while the router is built, before it binds the port. The message names the fix: use {name}.

The data

The models come first, because everything else passes them around.

//! The data shapes. Laravel counterpart: the Eloquent model plus the
//! request payloads a Form Request would accept.

use serde::{Deserialize, Serialize};

/// A stored note. `Serialize` turns it into JSON for responses.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct Note {
    pub id: u64,
    pub title: String,
    pub body: String,
    pub pinned: bool,
}

/// Body of `POST /api/notes`. Missing `body` and `pinned` fall back to
/// their defaults; a missing `title` is a deserialization error.
#[derive(Debug, Deserialize)]
pub struct CreateNote {
    pub title: String,
    #[serde(default)]
    pub body: String,
    #[serde(default)]
    pub pinned: bool,
}

/// Body of `PATCH /api/notes/{id}`. Every field is optional: `None` means
/// "leave this field alone".
#[derive(Debug, Default, Deserialize)]
pub struct UpdateNote {
    pub title: Option<String>,
    pub body: Option<String>,
    pub pinned: Option<bool>,
}

Note derives Serialize, so it can become JSON, and Deserialize, so it can be read from JSON. The request types leave out id, because the server assigns it. CreateNote marks its optional fields with #[serde(default)]. UpdateNote makes every field an Option, where None means leave the field alone. That is how PATCH works.

Output shapes

A Laravel API resource decides which fields leave the server. Note serializes every field it has, so the notes API has no such step. If a field must stay private, add a view struct:

namespace App\Http\Resources;

use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\JsonResource;

final class NoteResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id' => $this->id,
            'title' => $this->title,
            'pinned' => $this->pinned,
        ];
    }
}
#[derive(Serialize)]
pub struct NoteView {
    pub id: u64,
    pub title: String,
    pub pinned: bool,
}

impl From<&Note> for NoteView {
    fn from(note: &Note) -> Self {
        Self { id: note.id, title: note.title.clone(), pinned: note.pinned }
    }
}

Both classes decide the output in one place. The resource's toArray lists the fields, and the Rust From impl must set every field of NoteView, or the code will not compile. A column added to Note stays out of the response until you add it to the view.

Shared state

//! Shared application state. Laravel counterpart: a singleton bound in the
//! service container, plus the repository that owns the data.

use std::collections::BTreeMap;
use std::sync::Arc;

use tokio::sync::RwLock;

use crate::models::{CreateNote, Note, UpdateNote};

/// Cloned into every handler that asks for `State<AppState>`.
/// Cloning only bumps the `Arc` counter: every clone sees the same notes.
#[derive(Clone, Default)]
pub struct AppState {
    pub db: Arc<RwLock<Db>>,
}

/// An in-memory table. A `BTreeMap` keeps the ids sorted, so listing the
/// notes always returns them in creation order.
#[derive(Debug, Default)]
pub struct Db {
    notes: BTreeMap<u64, Note>,
    last_id: u64,
}

impl Db {
    pub fn all(&self) -> Vec<Note> {
        self.notes.values().cloned().collect()
    }

    pub fn find(&self, id: u64) -> Option<&Note> {
        self.notes.get(&id)
    }

    pub fn insert(&mut self, input: CreateNote) -> Note {
        self.last_id += 1;
        let note = Note {
            id: self.last_id,
            title: input.title.trim().to_string(),
            body: input.body,
            pinned: input.pinned,
        };
        self.notes.insert(note.id, note.clone());
        note
    }

    /// Applies only the fields that are `Some`. Returns `None` if the id
    /// doesn't exist.
    pub fn update(&mut self, id: u64, patch: UpdateNote) -> Option<Note> {
        let note = self.notes.get_mut(&id)?;
        if let Some(title) = patch.title {
            note.title = title.trim().to_string();
        }
        if let Some(body) = patch.body {
            note.body = body;
        }
        if let Some(pinned) = patch.pinned {
            note.pinned = pinned;
        }
        Some(note.clone())
    }

    pub fn remove(&mut self, id: u64) -> Option<Note> {
        self.notes.remove(&id)
    }
}

Axum clones the state for every handler that asks for it. A clone of AppState only bumps the Arc counter, so each clone points at the same table. The RwLock applies the borrowing rule from Chapter 07 at runtime: many readers, or one writer. BTreeMap keeps the notes sorted by id, so the list comes out in creation order with no extra sort.

Handlers

//! The handlers. Laravel counterpart: a resource controller
//! (`index`, `store`, `show`, `update`, `destroy`).
//!
//! Each handler is a plain async fn. Its arguments are extractors (they run
//! before the body), and its return type implements `IntoResponse`.

use axum::Json;
use axum::extract::{Path, State};
use axum::http::StatusCode;

use crate::error::AppError;
use crate::models::{CreateNote, Note, UpdateNote};
use crate::state::AppState;
use crate::validation::ValidJson;

/// GET /api/notes
pub async fn index(State(state): State<AppState>) -> Json<Vec<Note>> {
    let db = state.db.read().await;
    Json(db.all())
}

/// POST /api/notes
pub async fn store(
    State(state): State<AppState>,
    ValidJson(input): ValidJson<CreateNote>,
) -> (StatusCode, Json<Note>) {
    let note = state.db.write().await.insert(input);
    tracing::info!(id = note.id, "note created");
    (StatusCode::CREATED, Json(note))
}

/// GET /api/notes/{id}
pub async fn show(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<Note>, AppError> {
    let db = state.db.read().await;
    let note = db.find(id).ok_or(AppError::NotFound(id))?;
    Ok(Json(note.clone()))
}

/// PATCH /api/notes/{id}
pub async fn update(
    State(state): State<AppState>,
    Path(id): Path<u64>,
    ValidJson(patch): ValidJson<UpdateNote>,
) -> Result<Json<Note>, AppError> {
    let note = state
        .db
        .write()
        .await
        .update(id, patch)
        .ok_or(AppError::NotFound(id))?;
    Ok(Json(note))
}

/// DELETE /api/notes/{id}
pub async fn destroy(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<StatusCode, AppError> {
    state
        .db
        .write()
        .await
        .remove(id)
        .ok_or(AppError::NotFound(id))?;
    Ok(StatusCode::NO_CONTENT)
}

Each handler is an ordinary async function. Its parameters are extractors, and axum runs them in order before the body starts. Put the extractor that reads the request body last, because it consumes the body. The return type is what the client receives. store returns a status code and JSON, so the client gets a 201. show returns a Result. When ok_or(...) finds no note, the ? sends the error down the error track, and AppError turns it into a 404.

The order rule is easy to break, so here is what the compiler says when you break it. In this version the body extractor comes first:

use axum::Json;
use axum::Router;
use axum::extract::State;
use axum::routing::post;
use serde::Deserialize;

#[derive(Deserialize)]
struct NewNote {
    title: String,
}

async fn store(Json(input): Json<NewNote>, State(prefix): State<String>) -> String {
    format!("{prefix}{}", input.title)
}

fn main() {
    let _app: Router = Router::new()
        .route("/notes", post(store))
        .with_state(String::from("note: "));
}

Errors

//! One error type for the whole API. Laravel counterpart: the exception
//! handler (`bootstrap/app.php` -> `withExceptions`) that renders every
//! exception as a JSON response.

use axum::Json;
use axum::extract::rejection::JsonRejection;
use axum::http::StatusCode;
use axum::response::{IntoResponse, Response};
use serde_json::json;

#[derive(Debug)]
pub enum AppError {
    /// 404: no note with this id.
    NotFound(u64),
    /// 404: no route matches the URL. Laravel: the router's
    /// `NotFoundHttpException`, rendered by the exception handler.
    NoRoute,
    /// 422: the JSON was well-formed but a rule failed.
    Validation {
        field: &'static str,
        message: String,
    },
    /// 400/415/422: axum could not turn the body into our type.
    BadJson(JsonRejection),
}

impl AppError {
    pub fn validation(field: &'static str, message: impl Into<String>) -> Self {
        AppError::Validation {
            field,
            message: message.into(),
        }
    }
}

/// Lets `?` turn axum's JSON rejection into our error type.
impl From<JsonRejection> for AppError {
    fn from(rejection: JsonRejection) -> Self {
        AppError::BadJson(rejection)
    }
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, body) = match self {
            AppError::NotFound(id) => (
                StatusCode::NOT_FOUND,
                json!({ "message": format!("Note {id} not found.") }),
            ),
            AppError::NoRoute => (
                StatusCode::NOT_FOUND,
                json!({ "message": "Route not found." }),
            ),
            AppError::Validation { field, message } => (
                StatusCode::UNPROCESSABLE_ENTITY,
                json!({ "message": message, "errors": { field: [message] } }),
            ),
            AppError::BadJson(rejection) => (
                rejection.status(),
                json!({ "message": rejection.body_text() }),
            ),
        };
        (status, Json(body)).into_response()
    }
}

Every failure in this API is an AppError. IntoResponse maps each variant to a status code and a JSON body. From<JsonRejection> lets ? convert axum's rejection into an AppError. That is how ValidJson can return a JSON 422 instead of axum's plain-text message. In Laravel, this job belongs to the exception handler in bootstrap/app.php. Here it is one type.

Validation

// … the rules and their unit tests are in the rest of the file
/// Like `Json<T>`, but also runs `T::validate`, and rejects with our
/// `AppError` (always a JSON body) instead of axum's plain-text rejection.
pub struct ValidJson<T>(pub T);

impl<S, T> FromRequest<S> for ValidJson<T>
where
    S: Send + Sync,
    T: DeserializeOwned + Validate,
{
    type Rejection = AppError;

    async fn from_request(req: Request, state: &S) -> Result<Self, Self::Rejection> {
        let Json(value) = Json::<T>::from_request(req, state).await?;
        value.validate()?;
        Ok(ValidJson(value))
    }
}

ValidJson is a Form Request in extractor form. It deserializes the body the same way Json does, then calls validate(). A failed rule returns an AppError, so the handler only ever sees input that passed.

Routes and startup

//! The router. Laravel counterpart: `routes/api.php` plus the middleware
//! registered in `bootstrap/app.php`.

use std::time::Duration;

use axum::Router;
use axum::http::StatusCode;
use axum::routing::get;
use tower_http::timeout::TimeoutLayer;
use tower_http::trace::TraceLayer;

use crate::error::AppError;
use crate::handlers;
use crate::state::AppState;

pub fn app(state: AppState) -> Router {
    // Route::apiResource('notes', NoteController::class), spelled out.
    let notes = Router::new()
        .route("/", get(handlers::index).post(handlers::store))
        .route(
            "/{id}",
            get(handlers::show)
                .patch(handlers::update)
                .delete(handlers::destroy),
        );

    Router::new()
        .route("/health", get(|| async { "ok" }))
        .nest("/api/notes", notes)
        // Any URL that matched nothing above. Without this, axum answers
        // with an empty 404 instead of the JSON body every other error uses.
        .fallback(|| async { AppError::NoRoute })
        // `Router::layer` wraps each route (and the fallback) AFTER the router
        // has picked it, so these layers can see `MatchedPath`. Laravel's
        // global middleware runs before routing; this is closer to route
        // middleware. The last layer added is the outermost: a request meets
        // TraceLayer first.
        .layer(TimeoutLayer::with_status_code(
            StatusCode::REQUEST_TIMEOUT,
            Duration::from_secs(10),
        ))
        .layer(TraceLayer::new_for_http())
        .with_state(state)
}

nest mounts the notes router under /api/notes, so /{id} inside it becomes /api/notes/{id}. The fallback catches every URL that matched nothing. The layers come last. TimeoutLayer gives up after 10 seconds and answers 408. TraceLayer logs each request and its status. The last layer added is the outermost, so a request meets TraceLayer first.

//! Boots the server. Laravel counterpart: `public/index.php` plus
//! `bootstrap/app.php`, except this runs once, not once per request.

use notes_api::{AppState, app};
use tokio::net::TcpListener;
use tracing_subscriber::EnvFilter;

#[tokio::main]
async fn main() -> std::io::Result<()> {
    // Log/Monolog: RUST_LOG=debug cargo run shows more.
    tracing_subscriber::fmt()
        .with_env_filter(
            EnvFilter::try_from_default_env()
                .unwrap_or_else(|_| EnvFilter::new("notes_api=info,tower_http=debug")),
        )
        .init();

    let addr = std::env::var("APP_ADDR").unwrap_or_else(|_| "127.0.0.1:3000".to_string());
    let listener = TcpListener::bind(&addr).await?;
    tracing::info!("listening on http://{}", listener.local_addr()?);

    axum::serve(listener, app(AppState::default()))
        .with_graceful_shutdown(shutdown_signal())
        .await
}

/// Finish in-flight requests on Ctrl+C instead of cutting them off.
async fn shutdown_signal() {
    if let Err(err) = tokio::signal::ctrl_c().await {
        tracing::error!(%err, "could not listen for Ctrl+C");
    }
}

main runs once. It sets up logging, reads the address from APP_ADDR, and hands app(AppState::default()) to axum::serve. with_graceful_shutdown lets in-flight requests finish when you press Ctrl+C. Laravel's public/index.php repeats this work for every request. Here it happens once, and the same router serves every request after that.

serde: JSON in, JSON out

serde converts in both directions. #[derive(Serialize)] writes the code that turns a Rust value into JSON. #[derive(Deserialize)] writes the code that reads JSON back into a Rust value. Attributes adjust the result. The struct below is not part of the project. Its field names are longer than one word, which is where the attributes start to matter.

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
struct NoteDto {
    id: u64,
    title: String,
    created_at: String,
    #[serde(default)]
    pinned: bool,
    body: Option<String>,
}

fn main() {
    let input = r#"{"id": 1, "title": "x", "createdAt": "2026-10-09"}"#;
    let note: NoteDto = serde_json::from_str(input).unwrap();
    println!("{note:?}");
    println!("{}", serde_json::to_string(&note).unwrap());

    let snake: Result<NoteDto, _> =
        serde_json::from_str(r#"{"id": 1, "title": "x", "created_at": "x"}"#);
    println!("snake_case key: {}", snake.unwrap_err());

    let null_body: NoteDto = serde_json::from_str(
        r#"{"id": 2, "title": "y", "createdAt": "z", "body": null, "pinned": true}"#,
    )
    .unwrap();
    println!("{}", serde_json::to_string(&null_body).unwrap());
}

The output:

NoteDto { id: 1, title: "x", created_at: "2026-10-09", pinned: false, body: None }
{"id":1,"title":"x","createdAt":"2026-10-09","pinned":false,"body":null}
snake_case key: missing field `createdAt` at line 1 column 42
{"id":2,"title":"y","createdAt":"z","pinned":true,"body":null}

Read the output line by line. rename_all maps created_at to createdAt in both directions, so the Rust name stays snake_case. A missing Option field becomes None, and None is written as null. #[serde(default)] fills a missing bool with false. The snake_case key is rejected, because serde looks only for the renamed key.

Unknown fields

serde ignores keys it does not know, unless you tell it not to. The notes API works that way. Laravel ignores them by default too. A key that no rule mentions is never validated. Both frameworks have an opt-in that rejects extra keys. In Laravel 13 you add the #[FailOnUnknownFields] attribute to the Form Request:

use Illuminate\Foundation\Http\Attributes\FailOnUnknownFields;
use Illuminate\Foundation\Http\FormRequest;

#[FailOnUnknownFields]
class StoreNoteRequest extends FormRequest
{
    public function rules(): array
    {
        return [
            'title' => ['required', 'string'],
            'body' => ['nullable', 'string'],
            'pinned' => ['boolean'],
        ];
    }
}
#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct CreateNote {
    pub title: String,
    #[serde(default)]
    pub body: String,
    #[serde(default)]
    pub pinned: bool,
}

The idea is the same in both: name the fields you accept, and reject the rest. The serde version fails while the JSON is parsed. The error names the key that broke the rule: unknown field `color`, expected one of `title`, `body`, `pinned`. Laravel's check is part of the Form Request, so it runs with your other rules. Add deny_unknown_fields to CreateNote and a request with an extra key gets a 422 instead of a 201. StoreNoteRequest is a sketch, not a file in this project.

The Json extractor turns every problem with a body into a rejection. These are the responses the notes API returns for each kind of bad request, checked against the running server:

A struct has a field named created_at, and the attribute #[serde(rename_all = "camelCase")]. What key does serde write to JSON?

  1. created_at
  2. createdAt
  3. CreatedAt
  4. created-at

rename_all applies one naming rule to every field. camelCase turns created_at into createdAt. The Rust field keeps its name, so your code does not change.

Testing handlers without a server

A Laravel feature test sends a request through the framework and checks the response. The axum test does the same thing. A Router is a tower service, and oneshot sends one request into it and returns the response. No port opens, but every layer and handler runs.

The helper and the first test come from tests/api.rs:

/// Sends a request and returns the status and the body: parsed JSON,
/// `Value::Null` when empty, or a JSON string when the body isn't JSON.
async fn send(app: &Router, method: &str, uri: &str, body: Option<Value>) -> (StatusCode, Value) {
    let mut request = Request::builder().method(method).uri(uri);
    let body = match body {
        Some(json) => {
            request = request.header(header::CONTENT_TYPE, "application/json");
            Body::from(json.to_string())
        }
        None => Body::empty(),
    };
    // Router is cheap to clone (it is reference counted inside), and the
    // clones share the same AppState, so data survives between requests.
    let response = app
        .clone()
        .oneshot(request.body(body).unwrap())
        .await
        .unwrap();
    let status = response.status();
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let body = if bytes.is_empty() {
        Value::Null
    } else {
        serde_json::from_slice(&bytes)
            .unwrap_or_else(|_| Value::String(String::from_utf8_lossy(&bytes).into_owned()))
    };
    (status, body)
}
#[tokio::test]
async fn create_then_show_a_note() {
    let app = app(AppState::default());

    let (status, created) = send(
        &app,
        "POST",
        "/api/notes",
        Some(json!({ "title": "  Learn axum  " })),
    )
    .await;
    assert_eq!(status, StatusCode::CREATED);
    assert_eq!(
        created,
        json!({ "id": 1, "title": "Learn axum", "body": "", "pinned": false })
    );

    let (status, shown) = send(&app, "GET", "/api/notes/1", None).await;
    assert_eq!(status, StatusCode::OK);
    assert_eq!(shown, created);
}

The PHP helper hides the request, the response and the assertions. In Rust they are separate values: a status code, a parsed body, and a plain assert_eq!. Nothing is hidden behind a helper method.

Each test calls app(AppState::default()), so each test starts with an empty table. Inside one test, the helper sends every request through app.clone(). Cloning a router is cheap, and the clones share one AppState. That is why a note created by one request can be read back by the next.

Two tests run at the same time, and each one calls app(AppState::default()). Can one test see the other test's notes?

  1. Yes, because the state is a global variable.
  2. No. Each call builds a new AppState with its own empty table.
  3. Only if both tests use the same port.
  4. Yes, when the tests share a router with app.clone().

AppState::default() creates a new Arc<RwLock<Db>>, so two calls make two tables. Clones of one router share one table. That is why create followed by show works inside a single test, and why tests cannot see each other's data.

Where Eloquent would go

The project keeps notes in a BTreeMap, so a restart clears them. A real API stores its data in a database. The usual choices in Rust are sqlx, which lets you write the SQL yourself, and the ORMs SeaORM and Diesel. The code below is a teaser for sqlx. It is separate from the project, and it uses a SQLite file.

use serde::Serialize;
use sqlx::FromRow;
use sqlx::sqlite::SqlitePool;

#[derive(Debug, Serialize, FromRow)]
struct Note {
    id: i64,
    title: String,
    body: String,
    pinned: bool,
}

#[derive(Clone)]
struct AppState {
    pool: SqlitePool,
}

async fn find(state: &AppState, id: i64) -> Result<Option<Note>, sqlx::Error> {
    sqlx::query_as::<_, Note>("SELECT id, title, body, pinned FROM notes WHERE id = ?")
        .bind(id)
        .fetch_optional(&state.pool)
        .await
}

#[tokio::main]
async fn main() -> Result<(), sqlx::Error> {
    let pool = SqlitePool::connect("sqlite://notes.db?mode=rwc").await?;
    sqlx::migrate!("./migrations").run(&pool).await?;
    sqlx::query("INSERT INTO notes (title, body, pinned) VALUES (?, ?, ?)")
        .bind("Learn sqlx")
        .bind("")
        .bind(false)
        .execute(&pool)
        .await?;
    let state = AppState { pool };
    println!("{}", serde_json::to_string(&find(&state, 1).await?).unwrap());
    println!("{}", serde_json::to_string(&find(&state, 999).await?).unwrap());
    Ok(())
}

The migration that creates the table is a SQL file:

CREATE TABLE notes (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    body TEXT NOT NULL,
    pinned INTEGER NOT NULL DEFAULT 0
);

Running the program prints:

{"id":1,"title":"Learn sqlx","body":"","pinned":false}
null
  • The pool lives in the state. SqlitePool manages the connections. Cloning it is cheap, because the pool shares its inner data, just as the Arc does in our table.
  • Rows become structs. query_as::<_, Note> maps each row to a Note by column name, using FromRow.
  • Not found is None. fetch_optional returns an Option<Note>. A missing row is not an error. A handler turns the None into AppError::NotFound.
  • Migrations are SQL files. sqlx migrate add scaffolds a new version-prefixed file. sqlx::migrate! embeds those files in the binary and runs the ones that have not been applied yet.
  • Compile-time checks need a database. query_as! checks the SQL against a real database while your code compiles. Without DATABASE_URL set, the build stops and asks you to set it, or to run cargo sqlx prepare to save the query cache.

A handler calls a synchronous database driver, and that call waits for the query to finish. What happens to the other requests on the same worker thread?

  1. Tokio moves them to another thread, so nothing changes.
  2. They wait too, because the thread is blocked until the query returns.
  3. They are answered first, because async code runs before blocking code.
  4. Axum cancels them after one second.

Tokio runs many tasks on a few worker threads. A blocking call holds its thread, so the other tasks on that thread wait. Use an async driver such as sqlx. If you must call blocking code, move it to tokio::task::spawn_blocking.

Agents write axum code from whichever version they saw most often. You will meet axum::Server::bind, which is gone in 0.8. You will meet /:id routes, which panic in 0.8. You will meet #[async_trait] on every trait, which native async functions in traits made mostly unnecessary. And you will meet blocking database drivers called from async handlers.

Pin the versions in Cargo.toml, and paste them into your prompt. Then let the compiler and the tests decide whether the code is right. A test that sends a real request fails at once on stale route syntax, because the router panics when it is built.

When Laravel still wins

Rust is not the right answer for every API. Laravel gives you an admin panel ecosystem, queues, mail, auth, and a mature ORM in one place. A team that knows PHP can ship CRUD features faster in Laravel, and it is easier to hire for.

Keep Laravel whenConsider Rust when
The product is CRUD with an admin panel, such as Filament or NovaThe API is high-throughput, and CPU or memory per request matters
You are iterating quickly on product featuresThe service runs for a long time: a worker, a stream consumer, or an agent harness
Your team knows PHP, and the packages you need, such as Cashier or Horizon, fitA CLI or tool must start instantly and ship as one file
Most of the app is forms, views and emailYou deploy to small machines or the edge, where memory is tight
You rely on PHP packages that have no Rust equivalentYou want a PHP extension written in Rust, with ext-php-rs

Many teams run both. The Laravel app keeps the admin side and the business rules. One hot path moves into a Rust service, which the app calls over HTTP or through a queue. Each part stays in the tool that fits it.

Practice

These checks use the ideas from the chapter. The first one is about order. The rest are about the code you have just read.

  1. axum::serve accepts the connection and parses the request.
  2. The router picks the route for the method and the path.
  3. The route's layers wrap the handler: TraceLayer first, then TimeoutLayer.
  4. Extractors run in argument order, with the body extractor last.
  5. The handler body runs.
  6. The return value becomes a Response through IntoResponse.
  7. The response passes back out through the layers, and TraceLayer logs its status.

Routing comes before the route's layers, because Router::layer wraps the route that the router has already chosen. Extractors run before the handler, so a failed extractor stops the request before any handler code runs. The response travels back out through the layers, which is why TraceLayer sees the final status.

Which handler argument reads the JSON body?

  1. State<AppState>
  2. Path<u64>
  3. Json<CreateNote>
  4. Query<Filter>

Only the body extractor reads the body. ValidJson<CreateNote> works the same way and also runs validation. State gives shared state, Path reads the URL, and Query reads the query string after the ?.

A POST body is valid JSON, but title is the number 42. What happens?

  1. 201 Created, with the number converted to a string.
  2. 422 Unprocessable Entity, before the handler runs.
  3. 400 Bad Request, because the body is malformed.
  4. 500 Internal Server Error, from a panic inside the handler.

serde refuses the number, and the extractor rejects the request. The handler never starts, so nothing is stored. A 400 would mean the body was not JSON at all.

Which route path is correct in axum 0.8 for a note id?

  1. /notes/:id
  2. /notes/{id}
  3. /notes/<id>
  4. /notes/*id

Axum 0.8 uses braces for captures. /notes/:id is the 0.7 syntax, and it panics now. /notes/*id panics too. The wildcard form is {*rest}. /<id> is accepted without a panic. It is a literal segment, so it captures nothing. A URL cannot contain a bare <, so no request can match it.

A handler needs the notes table. What is the axum way to give it access?

  1. Declare a static mut variable, and read it from the handler.
  2. Ask for State<AppState>. The state is built once and cloned into each handler.
  3. Store it in a thread-local variable that a middleware sets for each request.
  4. Call a global function that opens a new database connection every time.

with_state attaches the state to the router. Each handler that asks for State<AppState> gets a clone. The clones share one Arc, so every handler sees the same table.

  • .route("/notes", get(index))
  • Json(input): Json<CreateNote>
  • Path(id): Path<u64>, then a lookup in the handler
  • .layer(TraceLayer::new_for_http())
  • State(state): State<AppState>
  • (StatusCode::CREATED, Json(note))

Complete the function, so that each error maps to its status code.

#[derive(Clone, Copy)]
enum AppError {
    NotFound,
    Validation,
}

fn status_code(error: AppError) -> u16 {
    match error {
        AppError::NotFound => [[404]],
        AppError::Validation => [[422]],
    }
}

fn main() {
    println!("{}", status_code(AppError::NotFound));
}

The mapping mirrors error.rs. A missing note is a 404, and a failed rule is a 422. The match must cover every variant. Add a variant without a status code, and the program does not compile until you add one.

Recap

One request, many stages

  • Laravel builds the application for every request. Axum builds the router and the state once, at startup, and then runs only the per-request stages.
  • Axum chooses the route first, and then the route's layers run. Laravel's global middleware runs before routing.
  • Extractors run in argument order, before the handler. The body extractor goes last. A failed extractor returns its error, and the handler never runs.
  • State<T> shares one value. Each handler gets a clone, and an Arc keeps a single copy of the data.
  • AppError implements IntoResponse, so ? can return a JSON 404 or 422 from anywhere in a handler.
  • serde maps JSON keys to fields. rename_all sets the naming rule. A body that does not fit the type becomes a 422.
  • oneshot tests the router without a server. The tests are fast, and they run the real layers and handlers.
  • A Rust API ships as one binary.
Explain it back: trace one POST /api/notes request through the axum app.

One good answer: "The request arrives on a connection that axum::serve accepted. The router matches POST /api/notes to store, and the route's layers start. TraceLayer opens a span, and TimeoutLayer starts its 10-second clock. Then the extractors run in order. State gives a clone of the state, and ValidJson reads the body and validates it. A bad body returns an AppError, and store never runs. A good body is inserted, and store returns (StatusCode::CREATED, Json(note)). That value becomes the response. It passes back out through the layers, and TraceLayer logs the status."
