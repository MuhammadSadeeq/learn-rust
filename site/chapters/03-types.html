One value, one type, decided before running

In PHP, adding a numeric string to a number just works. "5" + 5 is 10, because PHP reads the string as a number and carries on. A string that isn't a number, such as "five", throws a TypeError. Rust doesn't guess in either case. Predict first.

Does "5" + 5 compile in Rust? If not, what stops it?

It doesn't compile. A &str is text, and Rust has no + that takes a text and a number. The error comes from the compiler, before the program runs.

fn main() {
    let n = "5" + 5;
    println!("{n}");
}

rustc refuses to build it. This is the real output:

error[E0369]: cannot add `{integer}` to `&str`
 --> src/main.rs:2:17
  |
2 |     let n = "5" + 5;
  |             --- ^ - {integer}
  |             |
  |             &str

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0369`.

The first line names the error code and what went wrong. The arrows under the code show the two sides of the +: a &str on the left and an integer on the right. Rust never converts one to the other behind your back.

var_dump("5" + 5);   // int(10)
  
fn main() {
    let text = "5";
    let n: i32 = text.parse().unwrap();
    println!("{}", n + 5);
}

PHP converts the string for you, silently. Rust makes the conversion a step you write. parse returns a Result, because "five" is not a number. Chapter 11 covers how to handle that case instead of calling unwrap.

Does this compile? (Chapter 02 covered shadowing.)

fn main() {
    let spaces = "   ";
    let spaces = spaces.len();
    println!("{spaces}");
}
  1. Yes. The second spaces is a new binding, and it can have a different type. It prints 3.
  2. No. A variable can't change its type once it has one.

Shadowing creates a new binding. The first spaces is a &str and the second is a usize. Each binding has one type, and a new let is allowed to pick a different one.

Types are shapes. A value only fits the hole it was cut for.

Every value has one exact type, and the compiler settles it before the program runs. The type is either written in the source or inferred from how the value is used. In PHP you usually have to work it out from context, or find out at runtime.

Integers come in sizes

An integer type is a fixed number of bits. The first letter says whether it can be negative (i for signed) or not (u for unsigned). The number says how many bits it takes. A u8 is eight bits, so it can count from 0 to 255 and nothing more.

isize and usize match the pointer size: 64 bits on a 64-bit machine, 32 bits on a 32-bit one. The table shows a 64-bit machine. You can print any of these yourself with i8::MIN, u64::MAX and the rest.

Four rules of thumb cover most of the integers you will write.

  • i32 is the default. An integer literal with nothing else to decide its type becomes an i32. Use it unless you have a reason not to.
  • usize is for sizes and positions. len() returns a usize, and indexes are usize too.
  • u8 is for bytes. Raw data, such as a file or a network packet, is a list of u8.
  • Money is an i64 in cents. Never store money in a float. Section 4 shows why.

Rust accepts the number styles you know from PHP, plus a few more. Underscores are only there for your eyes, and a suffix such as u8 pins the type of one literal. Read the output, then check each line against its comment.

fn main() {
    let million = 1_000_000;   // underscores are ignored
    let mask = 0xff;           // hexadecimal: 255
    let perms = 0o77;          // octal: 63
    let bits = 0b1010_1010;    // binary: 170
    let letter = b'A';         // a byte literal: a u8 holding 65
    let small = 5u8;           // the suffix sets the type
    let big = 300_i64;         // a suffix can follow an underscore too

    println!("{million} {mask} {perms} {bits} {letter} {small} {big}");
}

var_dump(PHP_INT_MAX);      // int(9223372036854775807)
var_dump(PHP_INT_MAX + 1);  // float(9.223372036854776E+18)
  
fn main() {
    let max = i64::MAX;
    println!("{max}");
    println!("{:?}", max.checked_add(1));
}

PHP quietly switches to a float when an integer runs out of room. In Rust, an i64 stays an i64. Adding 1 to i64::MAX is an overflow. A debug build panics, and a release build wraps to i64::MIN. The next section covers each choice, and the methods that let you pick one in the code.

Which type does let n = 42; get, if nothing else in the program decides it?

  1. i64
  2. i32
  3. u32
  4. usize

Integer literals default to i32. This program only compiles if n is an i32:

fn main() {
    let n = 42;
    let m: i32 = n;
    println!("{m}");
}

An index must be a usize. An i32 index doesn't compile, even when its value is positive, because Rust won't guess what a negative index would mean:

fn main() {
    let arr = [1, 2, 3];
    let i: i32 = 1;
    println!("{}", arr[i]);
}

What happens at the edge

What happens when a result doesn't fit? It depends on how the program was built, and the answer is not the same in both builds.

  • Debug builds (cargo run) check every arithmetic operation. An overflow panics, which stops the program with a message.
  • Release builds (cargo run --release) skip the check. The result wraps around the range instead.

Sometimes the compiler sees the overflow coming, and then it refuses to build the program at all:

fn main() {
    let x: u8 = 255 + 1;
    println!("{x}");
}

error: this arithmetic operation will overflow
 --> src/main.rs:2:17
  |
2 |     let x: u8 = 255 + 1;
  |                 ^^^^^^^ attempt to compute `u8::MAX + 1_u8`, which would overflow
  |
  = note: `#[deny(arithmetic_overflow)]` on by default

error: aborting due to 1 previous error

This is a lint, so it has no error code. To see the runtime panic, hide the value from the compiler. Here the number comes from parse, and the compiler can't evaluate it:

fn main() {
    let x: u8 = "255".parse().unwrap();
    let y = x + 1;
    println!("{y}");
}

thread 'main' (2420) panicked at src/main.rs:3:13:
attempt to add with overflow
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

The panic names the file and line where the addition happened. The number in parentheses is the process id, so yours will differ.

A release build doesn't panic. The same program run with cargo run --release prints 0, and nothing tells you the arithmetic went wrong. Debug builds protect you while you develop. Code that handles input from outside the program should not depend on that, so use the explicit methods below wherever a value can overflow.

Each overflow mode has a method, and the methods make the choice visible in the code. Here are four of them on the same sum, 250 plus 10 in a u8:

fn main() {
    let a: u8 = 250;
    println!("wrapping: {}", a.wrapping_add(10));
    println!("checked: {:?}", a.checked_add(10));
    println!("saturating: {}", a.saturating_add(10));
    println!("overflowing: {:?}", a.overflowing_add(10));
}

wrapping_add4, the sum modulo 256Wrapping is the behavior you want: checksums, hash functions, counters that roll over.

What does 250u8.checked_add(10) return?

fn main() {
    println!("{:?}", 250u8.checked_add(10));
}
  1. 4
  2. None
  3. 255
  4. It panics, because the sum overflows.

The sum is 260, which doesn't fit in a u8, so checked_add returns None. It never panics. wrapping_add would give 4, and saturating_add would give 255.

Floats, bools and chars

Rust has two floating-point types, f64 and f32. f64 is the default, and it is the same 64-bit kind of number PHP uses. Reach for f32 only when memory is tight. A float is an approximation. Most decimal fractions have no exact binary form, so arithmetic on them drifts in small steps.

fn main() {
    let sum = 0.1 + 0.2;
    println!("{sum}");
    println!("{}", sum == 0.3);
}

PHP gives the same answer: var_dump(0.1 + 0.2 == 0.3) prints bool(false). This is how binary floats work in any language, and it is the reason money never goes in a float.

There is also a float value that is not equal to itself. NaN, "not a number", comes from an operation such as 0.0 / 0.0. Comparing it to anything, including itself, gives false. To test for it, call is_nan().

fn main() {
    let nan = 0.0_f64 / 0.0;
    println!("{}", nan == nan);
    println!("{}", nan.is_nan());
    println!("{nan}");
}

bool is one byte and holds only true or false. Rust has no truthiness. An if needs a bool, so a number is never a condition.

Does this compile?

fn main() {
    let count: i32 = 3;
    if count {
        println!("some");
    }
}
  1. Yes. Any non-zero number counts as true.
  2. No. if needs a bool, and count is an i32.

In PHP, if ($count) takes any non-zero number as true, and an empty string or an empty array as false. Rust asks you to write the comparison: if count != 0. The reader never has to remember which values count as false.

char is 4 bytes. It holds one Unicode scalar value, which is a code point: the number Unicode assigns to a character. 'a' is 97, 'é' is 233, and the crab is 129,408. Every char takes 4 bytes, however small the character is. The number of bytes it needs in a string is a separate question, and len_utf8 answers it.

use std::mem::size_of;

fn main() {
    println!("char is {} bytes", size_of::<char>());
    for c in ['a', 'é', '🦀'] {
        println!("{c}  utf-8 bytes: {}  code point: {}", c.len_utf8(), c as u32);
    }
    println!("the string é: {} bytes", "é".len());
}

In PHP, strlen("é") is 2, and $s[0] is one byte, not one character. You reach for mb_substr($s, 0, 1) when you want a character. Rust makes the difference a type: a char is one decoded character, and a u8 is one byte. Chapter 08 covers strings, which are UTF-8 bytes underneath and can't be indexed by number.

Tuples: a few values, fixed shape

A tuple groups a few values under one name, and the values can have different types. Its shape is part of its type. (i32, f64, char) and (i32, f64) are different types, and the compiler will not mix them up.

fn sorted_pair(a: i32, b: i32) -> (i32, i32) {
    (a.min(b), a.max(b))
}

fn main() {
    let p: (i32, f64, char) = (1, 2.5, 'x');
    println!("{} {} {}", p.0, p.1, p.2);

    let (a, b, c) = p;
    println!("{a} {b} {c}");

    let (lo, hi) = sorted_pair(9, 4);
    println!("{lo} {hi}");
}

Read a field with .0, .1 and so on, counting from zero. Or destructure the whole tuple with let (a, b, c) = p;, which gives each field its own name. A function that needs to return two values returns a tuple, as sorted_pair does.

function sortedPair(int $a, int $b): array {
    return [min($a, $b), max($a, $b)];
}
[$lo, $hi] = sortedPair(9, 4);
  
fn sorted_pair(a: i32, b: i32) -> (i32, i32) {
    (a.min(b), a.max(b))
}

fn main() {
    let (lo, hi) = sorted_pair(9, 4);
    println!("{lo} {hi}");
}

A PHP array can hold anything, in any order, and it grows at runtime. A tuple has exactly as many fields as its type says, and each field keeps its own type. Mistakes that PHP lets through quietly become compile errors. The quiz below shows one.

Chapter 06 said a tuple is Copy only when every field is Copy. (i32, f64, char) qualifies, so let q = p; copies it, and p stays usable. A tuple that holds a String would move instead.

The empty tuple, (), is called the unit type. It holds nothing. A function with no return type returns (), and Chapter 04 shows where else it turns up:

fn say(name: &str) {
    println!("hello {name}");
}

fn main() {
    let nothing: () = say("crab");
    println!("{nothing:?}");
}

Does this compile?

fn main() {
    let p = (1, "two");
    let (a, b, c) = p;
    println!("{a} {b} {c}");
}
  1. Yes. The extra name just gets no value.
  2. No. The pattern has three names, but the tuple has two fields.

A tuple pattern has to match the shape of the tuple exactly. The compiler reports E0308, mismatched types. PHP's [$a, $b, $c] = [1, 'two']; doesn't stop. It warns about the missing key and sets $c to null.

Arrays: fixed length, on the stack

An array holds values of one type in a fixed number of slots. The length is part of the type: [i32; 3] has three i32 slots, and [i32; 4] is a different type.

fn main() {
    let nums = [1, 2, 3];
    let zeros = [0; 5];
    let typed: [i32; 3] = [10, 20, 30];

    println!("{} {}", nums.len(), zeros.len());
    println!("{:?} {:?} {:?}", nums, zeros, typed);

    for x in typed {
        println!("{x}");
    }
}

[0; 5] means five copies of 0. len() reports the length, and for x in typed walks the slots in order.

The size of an array is known at compile time, so the whole array lives in the function's stack frame, next to the other local values. The figure shows typed.

Indexing is checked

Indexing with [] checks the position against the length. A constant index that is out of range is a compile error:

fn main() {
    let arr = [1, 2, 3];
    println!("{}", arr[5]);
}

error: this operation will panic at runtime
 --> src/main.rs:3:20
  |
3 |     println!("{}", arr[5]);
  |                    ^^^^^^ index out of bounds: the length is 3 but the index is 5
  |
  = note: `#[deny(unconditional_panic)]` on by default

error: aborting due to 1 previous error

When the index comes from outside the program, the compiler can't see its value, so the check happens at runtime:

fn main() {
    let arr = [1, 2, 3];
    let i: usize = "7".parse().unwrap();
    println!("{}", arr[i]);
}

thread 'main' (2421) panicked at src/main.rs:4:20:
index out of bounds: the len is 3 but the index is 7

In C, reading arr[5] from a three-element array returns whatever bytes sit next to the array, and nothing complains. Rust's check means an array can't hand you memory outside itself. The cost is a comparison on each index, and the compiler often removes it when it can prove the index is in range.

$nums = [1, 2, 3];
$nums[] = 4;      // arrays grow
echo $nums[9];    // Warning: Undefined array key 9
  
fn main() {
    let nums = [1, 2, 3];
    // nums.push(4) does not compile: arrays don't grow.
    println!("{:?}", nums.get(9));
}

A PHP array is an ordered map that grows and shrinks. A Rust array is a fixed block. A list that grows is a Vec, which Chapter 12 covers. get returns an Option instead of a warning and a null, so the missing slot becomes a value you have to handle.

Does this compile?

fn takes_three(a: [i32; 3]) -> i32 {
    a[0]
}

fn main() {
    let four = [1, 2, 3, 4];
    println!("{}", takes_three(four));
}
  1. Yes. Both are arrays of i32.
  2. No. The length is part of the type, so a four-slot array is not a [i32; 3].

E0308 reports the mismatch at the call, with the expected and found lengths. If you want one function to take any length, the parameter is a slice, &[i32], which Chapter 08 introduces.

PHP's strict mode is the closest match

PHP converts arguments for you by default. A file that starts with declare(strict_types=1); turns that off for the calls it makes, so a scalar of the wrong type is an error. The rule belongs to the calling file. A strict file that calls a function in a weak file is still checked, and a weak file that calls a strict function gets the conversion.

<?php
declare(strict_types=1);

function add(int $a, int $b): int {
    return $a + $b;
}

echo add("5", 5);   // TypeError: "5" is a string
fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() {
    println!("{}", add("5", 5));
}

Both reject the call before any sum is computed. PHP does it while the program runs, on the line that makes the call. rustc does it before the program exists. Rust has no weak mode to switch off, because it never converts a string to a number for you.

Strict mode also checks union types, such as int|string, which PHP 8.0 added, and DNF types, such as (HasId&HasName)|null, which PHP 8.2 added. Rust has no union type in a function signature. The closest match is an enum with one variant per type, and the caller has to choose a variant. Chapter 10 covers enums in full.

enum Id {
    Number(i64),
    Text(String),
}

fn show(id: Id) -> String {
    match id {
        Id::Number(n) => format!("number {n}"),
        Id::Text(t) => format!("text {t}"),
    }
}

fn main() {
    println!("{}", show(Id::Number(5)));
    println!("{}", show(Id::Text(String::from("abc"))));
}

A DNF type has no direct match in a signature. The nearest Rust shape is Option<T> with a trait bound such as T: HasId + HasName, which Chapter 14 covers.

as is the explicit conversion between number types. It compiles for any pair of them, and it doesn't report when information is lost:

fn main() {
    println!("{}", 300i32 as u8);     // keeps the low 8 bits: 300 - 256 = 44
    println!("{}", -1i32 as u8);      // the same bits, read as unsigned: 255
    println!("{}", 3.99f64 as i32);   // a float cuts toward zero: 3
    println!("{}", 1e10 as i32);      // too big for an i32: clamped to i32::MAX
}

Use From when the conversion can't lose anything, and TryFrom when it might. From returns the new type directly, so i64::from(x) works for any integer that fits in an i64. TryFrom returns a Result, which Chapter 11 covers in full, so the program has to handle a value that doesn't fit.

fn main() {
    let wide = u16::from(200u8);            // always fits, so there is no Result
    println!("{wide}");
    println!("{:?}", u8::try_from(200i32));  // fits: Ok
    println!("{:?}", u8::try_from(300i32));  // does not fit: Err
    println!("{:?}", "42".parse::<i32>());   // ::<i32> names the type to produce
}

Complete the call so that a value which doesn't fit reports an error instead of being truncated.

fn main() {
    let small = u8::[[try_from]](300i32);
    println!("{small:?}");
}

u8::try_from(300i32) returns Err(TryFromIntError(PosOverflow)). The error says why the conversion failed. With as, the same line would quietly print 44.

Agents write as constantly, because it compiles for any pair of numbers. That is the problem. When you review agent-written Rust, ask one question of every cast: can this value be outside the target range? If it came from a request, a file, a database or a parser, it can. Then ask for try_from and a real error path. If the code around the cast proves the range, as is fine, and a short comment that says why helps the next reader.

Check your types

What type does x get in this program?

fn main() {
    let x = 3.0;
}
  1. f32
  2. f64
  3. i32
  4. None. A float literal has no type until you annotate it.

Float literals default to f64, in the same way integer literals default to i32. Write 3.0_f32 or let x: f32 = 3.0; to choose the smaller type.

What does this program print?

fn main() {
    let big: i32 = 300;
    let byte = big as u8;
    let next = byte.wrapping_add(230);
    println!("{byte} {next}");
}
  1. 300 274
  2. 44 274
  3. 44 18
  4. It panics on the wrapping_add line.

300 as u8 keeps the low 8 bits, which gives 44. Then 44 + 230 is 274, and wrapping_add takes that modulo 256, which gives 18. Neither as nor a wrapping_ method panics.

  • i64
  • f64
  • bool
  • u8
  • char
  • (A, B) tuple

Two rows deserve a second look. PHP's "é"[0] is a single byte, which is why the right-hand match is u8 and not char. And PHP's int is 64 bits on a 64-bit build, so i64 is the closest match, while i32 is what Rust picks when nothing else decides the type.

Recap

Types are shapes

  • Rust never converts between number types for you. "5" + 5 is a compile error (E0369), not 10.
  • Integers are signed (i) or unsigned (u), 8 to 128 bits wide, plus the pointer-sized isize and usize. A bare literal is an i32. Lengths and indexes are usize.
  • Overflow panics in debug builds and wraps in release builds. The wrapping_, checked_, saturating_ and overflowing_ methods make the choice in your code.
  • char is one 4-byte Unicode scalar value. bool has no truthiness, so an if needs a comparison.
  • A tuple has a fixed shape and an array has a fixed length. Both are part of the type.
  • as truncates silently. From is for conversions that can't lose data. TryFrom returns a Result when a value might not fit.
  • PHP's declare(strict_types=1) is the closest match to Rust's rule. It checks scalar arguments, but only for calls made from the file that declares it.
Explain it back: why does Rust make you choose integer sizes when PHP doesn't?

One good answer: "PHP gives every integer one size, 64 bits, and quietly becomes a float when it runs out of room. Rust asks for the size because the size decides how much memory a value takes, the range it can hold and what happens at the edge. The choice is written in the code, where a reviewer can see it, and the compiler rejects the mismatches it can see."

If your version mentions memory, range and what overflow does, you have the core of it.
