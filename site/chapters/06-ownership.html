Somebody has to free the memory

Every running program borrows memory from the operating system. The string you build, the array of users you load from the database, the JSON response you assemble: each one occupies bytes, and at some point those bytes have to be handed back. Programming languages differ in who does that and when.

Manual
C, C++		At runtime
PHP, JS, Java, Go		At compile time
Rust
Who frees?You call free()A reference counter or garbage collector, while the program runsThe compiler writes the free for you, at the end of the owner's scope

PHP keeps a reference count on every value. When the count reaches zero, the value is freed immediately, and a cycle collector occasionally cleans up objects that point at each other. On top of that, a classic PHP-FPM request throws away all of its memory when the response is sent. That is why you have rarely had to think about memory: most leaks die with the request.

Rust programs are usually long-running: servers, CLIs, agents, game loops. There is no end-of-request reset to clean up after you, so the language needs a precise rule for when every single value is freed.

Rust has no garbage collector and you never call free(). So how does it know when to free a String?

At every line of your program the compiler knows exactly one variable that owns that String. When that variable's scope ends, the compiler inserts the code that frees it.

That is the whole trick. The rest of this chapter is the small set of rules that keeps "exactly one owner" true at every line.

The three rules

Here they are. Read them slowly. Everything in Act II follows from them.

Each value in Rust has an owner.

Usually a variable; it can also be a struct field, a vector slot or a function parameter.

There can only be one owner at a time.

Ownership can be handed over (a move), but it is never shared by two variables at once.

When the owner goes out of scope, the value is dropped.

Dropping runs cleanup code and frees any heap memory. It happens at a } you can point to.

A value is a parcel with exactly one name on its label.

Picture every heap value as a parcel with a shipping label. The label has room for one name. Whoever is on the label must dispose of the parcel when they leave the room (the end of their scope). You can:

  • hand it over: the label is rewritten with a new name. That is a move.
  • photocopy it: a brand-new parcel with its own label. That is a clone.
  • let someone look at it without taking it. That is a borrow, and it's the next chapter.

Scope is the owner's lifetime

A scope is the region between a { and its matching }. A variable is valid from the line that declares it until the end of its scope. Step through this program and watch the heap.

Watching drops happen

You can attach your own code to the moment a value is dropped by implementing the Drop trait. You'll learn impl blocks in Chapter 09 and traits in Chapter 14; for now, read it as "run this when a Noisy is dropped".

What does this program print?

struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn main() {
    let _a = Noisy("a");
    let _b = Noisy("b");
    {
        let _c = Noisy("c");
    }
    println!("end of main");
}
  1. end of main, drop a, drop b, drop c
  2. drop c, end of main, drop b, drop a
  3. drop c, end of main, drop a, drop b
  4. The order isn't defined; it depends on the allocator.

_c lives in the inner block, so it's dropped when that block closes, before end of main prints. At the end of main, locals are dropped in reverse order of declaration: _b, then _a. Later values may depend on earlier ones, so they have to go first.

The order is fully deterministic. You can rely on it for things like closing files, releasing locks, or committing transactions.

class Noisy {
    public function __construct(
        public string $name
    ) {}

    public function __destruct() {
        echo "drop {$this->name}\n";
    }
}

$a = new Noisy("a");
// __destruct runs when the refcount
// reaches zero, which might be much
// later if something else (a cache,
// a closure, a cycle) still holds $a.
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

let a = Noisy("a");
// drop runs at the end of a's scope.
// Always. You can see the exact line
// by finding the closing brace.

__destruct and Drop look alike, but PHP's timing depends on who else holds a reference at runtime. Rust's timing is decided at compile time and is visible in the source.

let _ = value; is not the same as let _x = value;. A plain underscore doesn't bind anything, so a temporary like let _ = Noisy("t"); is dropped at the end of that statement, immediately. _x is a real variable that lives to the end of the scope. This matters later with locks: let _ = mutex.lock(); releases the lock straight away.

Move: handing over the parcel

Now the line that surprises every PHP developer. Before you step through it, decide what you think let b = a; does.

For more information about this error, try `rustc --explain E0382`.

Why a move, and not one of the alternatives?

The String on the stack is just three numbers: pointer, length, capacity. When you write let b = a; Rust copies those three numbers. Now there are two pointers to the same heap bytes, and the language has to choose what that means.

OptionWhat would happenVerdict
Both own the bufferBoth would free it at the end of main: a double free, which corrupts memory.unsafe
Silently deep-copy the heapEvery assignment could allocate and copy megabytes behind your back.slow and invisible
Count references at runtimeThat is PHP's model. It costs a counter update on every copy and still needs a cycle collector.runtime cost
Transfer ownershipCopy the 24 stack bytes, mark a as unusable. Zero heap work, exactly one free.Rust's choice

In PHP, $b = $a means one of two different things depending on the type:

  • Arrays and strings act like copies (copy-on-write: they share memory until one side changes, then PHP copies quietly).
  • Objects are handles: $b and $a point at the same object, and a change through one is visible through the other.

Rust's let b = a; is neither. It is a transfer. After it, there is still one value and still one owner; only the owner's name has changed. If you want PHP-array behavior, you write .clone(). If you want PHP-object behavior (shared handles), you use Rc, covered in Chapter 17.

What does a move compile to?

A move is a plain copy of the stack bytes (for a String, 24 bytes on a 64-bit machine), and the optimizer usually removes even that. The old slot isn't zeroed or flagged. The compiler simply refuses to compile any later use of it.

When a move happens only on some paths, for example inside an if, Rust keeps a hidden one-byte "drop flag" so that the value is freed exactly once whichever path runs. That is the only runtime trace ownership ever leaves.

Copy and Clone

Try the same thing with an integer:

fn main() {
    let x = 5;
    let y = x;
    println!("{x} {y}");
}

This compiles. An i32 has no heap part: its four bytes on the stack are the whole value. Copying them is as cheap as moving them, and there's nothing to free twice. Types like this implement the Copy trait, and for them assignment copies instead of moving.

Copy (assignment copies)Not Copy (assignment moves)
i32, u8, usize and all other integersString
f32, f64Vec<T>
bool, charBox<T>, HashMap<K, V>
shared references &Tmutable references &mut T
tuples and arrays of Copy types: (i32, bool), [u8; 4]anything containing a non-Copy type: (i32, String)

When you really do want two independent copies of heap data, ask for one with .clone():

Copy is implicit, and Rust only allows it for types where copying is guaranteed to be cheap. Clone is explicit because it may allocate. When you see .clone() in a code review, you're looking at a deliberate cost.

Does this compile?

fn main() {
    let point = (3, String::from("north"));
    let copy = point;
    println!("{}", point.0);
}
  1. Yes. point.0 is an integer, and integers are Copy.
  2. No. The tuple contains a String, so the whole tuple moved into copy.
  3. No, because tuples can never be copied.

A tuple is Copy only if every element is Copy. (i32, String) isn't, so let copy = point; moves the whole tuple and point can't be used afterwards, not even its integer field. (Moving out of individual fields is possible, but here the whole tuple was moved.) (3, 4) would have compiled.

Functions move values too

Passing a value to a function works exactly like assigning it to a variable: the parameter becomes the new owner. Returning a value moves it out to the caller. Pick a scenario and step through it:

That means a function signature tells you who owns what, before you read a single line of its body:

SignatureWhat happens to the caller's value
fn f(s: String)Moved in. The caller can't use it afterwards. f drops it unless it hands it on.
fn f() -> Stringf creates a value and moves it out. The caller becomes the owner.
fn f(s: String) -> StringTaken and given back (maybe changed). Works, but clumsy.
fn f(s: &String)Borrowed: f looks, the caller keeps ownership. This is the next chapter.

Complete the signature so add_bang takes ownership, changes the string, and hands it back.

fn add_bang([[mut]] s: String) -> [[String]] {
    s.push('!');
    s
}

fn main() {
    let a = String::from("hi");
    let b = add_bang(a);
    println!("{b}");
}

A parameter is a variable like any other, so it needs mut before you can change it. Declaring -> String and ending with s (no semicolon) moves ownership back out to b. Note that a is unusable after the call; ownership went in and came back under a new name.

Taking ownership and giving it back works, but it gets tiresome fast. Imagine every function that only needs to read a string having to return it again. That frustration is exactly what borrowing fixes in Chapter 07.

Three ways out of a move error

When the compiler says "use of moved value", you have three tools. Each one says something different about your intent, so choose deliberately.

fn main() {
    let a = String::from("hi");
    println!("{a}");     // use a while you still own it
    let b = a;           // then hand it over
    println!("{b}");
}

Use when you're finished with the original anyway. It costs nothing.

fn main() {
    let a = String::from("hi");
    let mut b = a.clone(); // a second, independent String
    b.push('!');
    println!("{a} {b}");
}

Use when you really need two independent values that can change separately. It costs an allocation and a copy.

fn main() {
    let a = String::from("hi");
    let b = &a;            // b looks at a, a keeps ownership
    println!("{a} {b}");
}

Use when the other code only needs to read. It costs nothing, and it's what you'll reach for most often. Details in the next chapter.

AI coding agents love option 2. When an agent hits a borrow-checker error, the fastest way to make the error disappear is to sprinkle .clone() until it compiles. The code works, but it allocates on every call and hides the real ownership design.

When you review agent-written Rust, treat every .clone() as a question: does this code need its own copy, or does it only need to look? If it only looks, the fix is a borrow. You'll practice this in the Agent Code Review Dojo.

Be the borrow checker

Four short programs. For each one, decide whether rustc accepts it before you look at the answers. Every snippet on this page has been compiled with the real compiler.

Does this compile?

fn main() {
    let v = vec![1, 2, 3];
    let w = v;
    println!("{}", v.len());
}
  1. Yes. It's a Vec of integers, and integers are Copy.
  2. No. v moved into w.

The elements are Copy, but a Vec owns a heap buffer, so the Vec itself is not. let w = v; moves it. Error E0382.

Does this compile?

fn main() {
    let names = vec![String::from("Ana"), String::from("Bo")];
    for n in names {
        println!("{n}");
    }
    println!("{}", names.len());
}
  1. Yes. The loop only reads the names.
  2. No. The for loop took ownership of names.

for n in names calls names.into_iter(), which consumes the vector and hands you each String by value. After the loop the vector is gone. Write for n in &names to borrow it instead. This catches almost everyone, and it's quest move4.

Does this compile?

fn main() {
    let s = String::from("hi");
    let t = s;
    let s = String::from("new");
    println!("{s} {t}");
}
  1. Yes. It prints new hi.
  2. No. s was moved on line 3.

Line 4 doesn't reuse the moved s; it declares a brand-new variable that happens to have the same name (shadowing, from Chapter 02). The old, moved s is never read again.

Does this compile?

fn shout(s: String) -> String {
    s.to_uppercase()
}

fn main() {
    let word = String::from("rust");
    let loud = shout(word);
    println!("{word} became {loud}");
}
  1. Yes. shout returns a new String, so word is untouched.
  2. No. word was moved into shout.

shout takes String by value, so calling it moves word in. It returns a different String; the original was dropped at the end of shout. Changing the parameter to s: &str and calling shout(&word) fixes it.

Map it to what you know

  • let b = a.clone(); (but explicit and eager)
  • two Rc handles to one value
  • drop(a);
  • impl Drop
  • drop calls inserted by the compiler
  • fn f(s: &str) (a borrow)

Analogies are scaffolding, not foundations. PHP's unset() only decrements a counter, so the value may live on if something else refers to it. Rust's drop(a) really ends a's ownership, and the compiler forbids any later use of a.

Recap

One owner

  • Every value has exactly one owner. When the owner's scope ends, the value is dropped, in reverse order of declaration.
  • let b = a; and passing a to a function move non-Copy values: the stack part is copied, the heap is untouched, and a becomes unusable.
  • Copy types (numbers, bool, char, &T, tuples and arrays of them) are copied instead. Clone is an explicit, possibly expensive deep copy.
  • Returning a value moves it out to the caller.
  • To fix E0382: reorder, clone deliberately, or borrow.
Explain it back: a PHP colleague asks why let b = a; "breaks" a. What do you say in three sentences?

One good answer: "A String owns heap memory, and Rust frees heap memory when its single owner goes out of scope. If a and b both owned the same buffer it would be freed twice, so assignment transfers ownership to b instead of sharing it. If you want two copies, call .clone(); if you just want to look at it, borrow it with &a."

If your version mentioned one owner, scope end frees, and double free, you've got it.
