Memory is a long row of numbered bytes

Every value your program uses sits somewhere in memory. Picture memory as a long row of cells, one byte each. Every cell has a number, its address. An i32 takes up four cells in a row. A pointer is a value that holds an address: a number that says where some other value starts.

Your PHP code never shows you any of this. The numbers exist, but the engine keeps them out of sight. Rust shows them to you through types, and the rest of this chapter depends on that visibility.

Think first: in PHP, how much memory does $x = 5; use?

Guess before you read on, and be specific about what you counted.

The answer is more than four bytes. The value 5 is stored in a zval, PHP's internal container for any value. On a 64-bit build, a zval is 16 bytes, and it keeps the type tag next to the value. The variable needs a slot of its own too. Inside a function, that is a slot in the call's frame. In the global scope, it is an entry in a symbol table, which has bookkeeping of its own. The exact total depends on the PHP build and on where $x lives, so treat any figure as approximate. The 5 itself sits inside the zval, so PHP does not allocate anything extra on the heap for it.

The lesson is that every value carries overhead, and PHP hides that overhead from you. Rust shows you the overhead in the types, and the Size Lab later in this chapter lets you check it.

The stack: one frame per call

When a function runs, it needs room for its parameters and its local variables. That room comes from the stack. Picture a stack of trays. Each call puts a new tray, called a frame, on top. The frame holds that call's values. When the function returns, its tray comes off, and the room under it is free again.

The stack is fast for a simple reason. The compiler knows the size of every local before the program runs, so the size of each frame is fixed. Making room is just moving the stack pointer by a known amount. Giving room back is moving it back.

Only the number 12 travelled back to main. The variables a, w and h lived in the frame of area, so they went away with it.

This is a model, and the optimizer is allowed to do better than the model. A small value like a may live only in a CPU register, and the compiler may skip the copy altogether. The model is still the right way to reason about cost and about who owns a value, so keep it in mind when you read a profile or a compiler error.

Which of these costs the least?

  1. Calling a function whose locals are three u32 values.
  2. Asking the allocator for a new 100-byte buffer on the heap.
  3. Calling .clone() on a String.

A call moves the stack pointer by an amount the compiler already knows. The other two ask the allocator for memory, and cloning a String also copies every byte of it.

The heap: ask for space at runtime

The stack needs every size fixed before the program runs. A lot of data has no fixed size. The text a user typed, or the rows a database query returns, are as large as the input happens to be. For those values the program asks for room at runtime, from the heap.

Think of the heap as a warehouse with numbered shelves. You tell the warehouse how much space you need, and it hands you a shelf number. That number is a pointer. You keep the pointer in a variable, usually on the stack, and reach the shelf through it. When you are finished, you have to give the shelf back. If you don't, it stays occupied, and nobody else can use it.

Think first: why can't a Vec<User> loaded from the database be a fixed local on the stack?

The database decides how many rows there are, and it does so at runtime, after the program was compiled. The stack needs each frame's size fixed at compile time, so a list whose length is known only at runtime cannot be a stack local. Its elements go on the heap, and the stack keeps a pointer to them.

Stack space comes back in order, by itself. Heap space comes back only when someone gives it back.

The stack is fast because it is strict: each slot's size is fixed before the program runs. The heap accepts any size, and the program pays for that flexibility with allocator work and with the duty to give the block back.

Where does the text of String::from("hello") live?

let s = String::from("hello");
  1. On the stack, inside the variable s.
  2. On the heap. The variable s on the stack holds a pointer to it.
  3. In the compiled program, as a constant, so it never has to be freed.

The literal "hello" is stored in the compiled program, but String::from copies it into a new heap block that the String owns. The 24 bytes on the stack are three words: the pointer, the length 5 and the capacity 5. The five letters live on the heap.

What a String really is

A String is two things. The part on the stack is three words: a pointer to the text bytes, the length (how many bytes are in use) and the capacity (how many bytes the block can hold). On a 64-bit machine that is 24 bytes, and it stays 24 bytes however long the text is. The text itself lives on the heap. A Vec<T> has the same shape: three words on the stack, and the elements on the heap.

What does this print on a 64-bit machine?

use std::mem::size_of;

fn main() {
    println!("{}", size_of::<String>());
}
  1. 5, the length of the text it will hold.
  2. 8, one pointer.
  3. 24, three words.
  4. It depends on the text, because the bytes are part of the value.

24. The String value is always three words, whatever the text. The bytes live on the heap, outside those 24.

Here is the whole table, straight from the compiler on a 64-bit machine. Run it, or read the output.

use std::mem::size_of;

fn main() {
    println!("i32: {}", size_of::<i32>());
    println!("u8: {}", size_of::<u8>());
    println!("char: {}", size_of::<char>());
    println!("(i32, u8): {}", size_of::<(i32, u8)>());
    println!("String: {}", size_of::<String>());
    println!("Vec<u64>: {}", size_of::<Vec<u64>>());
    println!("&str: {}", size_of::<&str>());
    println!("Box<i32>: {}", size_of::<Box<i32>>());
}

Two of these numbers look wrong at first. A (i32, u8) holds 5 bytes of data, yet it takes 8. A &str is one pointer and one length, which is 16 bytes, not 8.

The 8 comes from alignment. An i32 must start at an address that is a multiple of 4. On this machine the compiler puts the i32 at offset 0 and the u8 at offset 4. Bytes 5, 6 and 7 are padding: space nobody uses. The compiler adds them so the total becomes 8, a multiple of the largest alignment in the tuple. Without that trailing padding, the second element of an array of these tuples would start at an address that is not a multiple of 4, and some processors would refuse that access or pay a speed penalty for it.

Why is (i32, u8) 8 bytes?

  1. Tuples always round up to 8 bytes, whatever their fields are.
  2. Because the fields take 4 + 1 = 5 bytes, and the compiler stores the extra space as well.
  3. An i32 must start on a multiple of 4, so 3 bytes of padding follow the u8, and the total becomes a multiple of 4.

That is alignment. Each type needs its values to start at a multiple of its alignment. The padding is unused memory, and it is the price of that rule. It also keeps every element of an array aligned, because the size of the tuple is a multiple of its alignment.

Why is Option<Box<i32>> the same size as Box<i32>? An Option normally needs a tag, one extra value that says "Some" or "None". A Box can never be null, so the compiler can use the null address to mean None, and the pointer carries the tag for free. This is the niche optimization: the compiler reuses a value the type can never hold.

A u32 has no spare bit patterns, so Option<u32> needs a real tag. The tag takes a byte, and the u32 then needs 4-byte alignment, so the total is 8. A bool has spare values, so Option<bool> is still 1 byte.

When a String grows

A String made with String::new() starts with no room at all. String::with_capacity(n) asks for room for n bytes up front. Two methods tell you where you stand. len() is how many bytes are in use. capacity() is how many the block can hold before it needs more. Capacity is never smaller than length.

Push past the capacity and the String has to grow. Step through a small one.

The allocator can sometimes grow a block where it sits. When it can't, it finds a bigger block, copies the bytes across and frees the old one. The picture shows that second case. Your code never handles any of this. It calls push_str, and the standard library does the rest. But the address changed, and anything still holding the old address now points at memory that has been given back.

A Vec grows the same way. Here the cells are the elements, not bytes.

Five pushes caused two reallocations. If you know roughly how many elements you will need, ask for that capacity up front and the reallocations go away.

Here is one of those reallocations as a picture. The Vec keeps its items, and only the plot under them changes.

A reallocation can mean a new allocation, a copy and a free. Reserving the capacity once avoids that series of steps. The standard library does not promise particular growth amounts, so the numbers you see are an implementation detail. What you can count on is that capacity() is never less than len(), and that with_capacity only reserves room. It does not put any text in the String.

Here is the same growth in code. Run it, and watch len climb while capacity jumps in steps. Don't write code that depends on the exact numbers.

fn main() {
    let mut s = String::new();
    for word in ["hi", "!!", "?"] {
        s.push_str(word);
        println!("len {} cap {}", s.len(), s.capacity());
    }
}

Why does this matter when you write code? Because the compiler is strict about references for exactly this reason. Here is a program that holds a pointer to an element and then pushes.

fn main() {
    let mut v = vec![1, 2, 3, 4, 5];
    let first = &v[0];
    v.push(6);
    println!("{first}");
}

first points into the buffer. push(6) might have to move the buffer to make room, and then first would point at freed memory. So the compiler refuses the program. Chapter 07 explains the rule. For now, notice that it protects a pointer you cannot see.

A Vec has its buffer at address A. A push forces a reallocation. Is address A still valid afterwards?

  1. Yes. The allocator keeps the old block where it was.
  2. No. The old block has been freed, so anything that points into it now dangles.
  3. Only if the new capacity is at least twice the old one.

After a reallocation the old block is gone. Reading through a pointer to it reads memory the allocator may already have handed to something else. The borrow checker refuses programs that could do this, as you just saw.

Fill in the blank so the program prints true.

fn main() {
    let s = String::[[with_capacity]](10);
    println!("{}", s.capacity() >= 10);
}

with_capacity(10) reserves room for at least ten bytes before the first push, and capacity() reports that room. The number is a promise of at least that much room. It is not an exact figure.

Box: one value on the heap



A Box<T> is the simplest way to put one value on the heap. Box::new(5) asks for room for an i32, stores 5 in it and returns a pointer. The Box that lives in your variable is only that pointer. It takes 8 bytes on a 64-bit machine, whatever the type inside the box is.






The Box has exactly one owner, the variable b. When b goes out of scope, the heap bytes are freed. This is the ownership rule from Chapter 06, applied to a single heap value. Chapter 17 uses boxes for recursive data, where the size of a value would otherwise be unknown.







How PHP does it, and why Rust shows you



PHP manages all of this for you, and it does it well. Every variable holds a zval, the engine's container for one value, with the type tag beside it. Strings, arrays and objects live on the heap and are reference counted, so each one is released when its last reference goes away. Arrays and strings are copy on write: $b = $a; shares the memory until one side changes. Objects follow a different rule. A variable holds a handle to the object, so $b = $a; copies the handle, and both names reach the same object. A cycle collector finds objects that point at each other, which reference counting alone would leave alive. At the end of a request, PHP releases everything the request allocated. memory_get_usage() tells you how much PHP is holding, but not what it is holding it for.




  Think first: a PHP function builds an array of 100,000 rows and returns it. When is that memory released?
  

    
The array lives for as long as something refers to it. If the function returns it, the caller holds it, and the memory stays. If nothing holds it, the reference count drops to zero and PHP frees it at that moment. Anything still allocated is released when the request ends.

  






  
$a = [1, 2, 3];
$b = $a;       // shares the array
$b[] = 4;      // now PHP copies it, quietly

  
let a = vec![1, 2, 3];
let mut b = a.clone(); // a new heap buffer, copied now
b.push(4);

  
PHP copies later, and you don't see the copy. Rust copies a Vec only where you write clone(), so the cost sits on a line you can point to. The comparison breaks when you look closely: in PHP a copy can happen inside any write, while in Rust the copy is always written out. Chapter 06 covers the ownership rules behind this.





Objects are the other case. In PHP, $b = $a; with an object copies only the handle, and no copy of the object is made. Rust has no such default. A struct has one owner, and shared access takes an explicit handle:




  
final class Counter {
    public function __construct(public int $n = 0) {}
}

$a = new Counter();
$b = $a;          // copies the handle, not the object
$b->n = 1;
echo $a->n;       // 1

  
use std::cell::RefCell;
use std::rc::Rc;

struct Counter {
    n: i32,
}

fn main() {
    let a = Rc::new(RefCell::new(Counter { n: 0 }));
    let b = Rc::clone(&a);   // a second handle to the same value
    b.borrow_mut().n = 1;
    println!("{}", a.borrow().n);
}

  
PHP makes every object a handle, and you never ask for it. In Rust, the handle is a choice you write. Rc counts its owners at runtime, and RefCell checks its borrows at runtime. Chapter 17 covers both. A plain Rust struct is never shared behind your back, so the question of who may change it is answered in the code.






  
Rust exposes this model on purpose. Once you can see where data lives, when it is copied and when it is freed, you can control what your program costs. PHP can hide the model because a request is short, and its memory is thrown away at the end. A Rust server or agent may run for days, and its costs add up.






  
Agent-written Rust often allocates inside hot loops: to_string(), format! and collect() repeated for every item. The code below works, but it makes two heap allocations for every name. When you review it, ask whether each copy is needed.

  
fn tags(names: &[String]) -> Vec<String> {
    let mut out = Vec::new();
    for name in names {
        let key = name.to_string();        // a new heap copy on every pass
        out.push(format!("user:{key}"));   // and another new String here
    }
    out
}

  
format! can read name directly. Reading through a reference costs nothing extra, so out.push(format!("user:{name}")); leaves one allocation per item instead of two. Knowing what lives on the heap is how you spot this kind of cost in review.









Somebody has to give the shelf back



Every heap block has to be given back exactly once, at the right moment. Get the timing wrong, and it can fail in one of three ways.




  
Too early.
The block is freed while a pointer still points at it. That pointer now dangles, and reading through it reads memory that may already belong to something else.

  
Twice.
The block is freed a second time. The allocator's bookkeeping is damaged, and the next allocation can fail somewhere that has nothing to do with the line that caused it.

  
Never.
Nothing frees the block. That is a leak. A long-running program slowly fills up with memory it can no longer reach.






  
Freeing a block does not erase its bytes. The old contents often still look like perfectly good text, so a read through a dangling pointer can seem to work for a while and then fail far away from the cause. That is why these bugs are so hard to find.





C leaves all three jobs to you. PHP and Java hand the job to a runtime that works out what is still in use. Rust gives the job to the compiler, through ownership: each heap value has exactly one owner, and the compiler inserts the free when that owner's scope ends. The rules that keep it to one owner are the subject of the next chapter.

Stack and heap

  
    
    
  • The stack holds one frame per call. Sizes are fixed at compile time, and making room means moving a pointer.
    • 
    
  • The heap holds data whose size is decided at runtime. You get a pointer back, and you must give the block back.
    •
