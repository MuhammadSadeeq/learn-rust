Packages, crates and modules

You already know the layers of a PHP project: a package described by composer.json, a namespace, and the file that declares a class. Rust has the same layers under three different names. The compiler uses each name exactly, so it is worth learning them now.

WordWhat it isClosest PHP idea
PackageA folder with a Cargo.toml. Cargo versions and publishes it as one unit.A Composer package
CrateOne unit of compilation: a library, or a program.No exact equivalent
ModuleA named section of a crate, declared with mod.A namespace, plus the file that defines it

A package can hold at most one library crate and any number of binary crates. The usual layout has both. src/lib.rs is the library, and src/main.rs is the program that uses it.

shop/
├── Cargo.toml       the package
└── src/
    ├── lib.rs       library crate, named shop
    └── main.rs      binary crate, also named shop

How many crates does this package contain?

  1. One. The package is the crate.
  2. Two: one library crate and one binary crate.
  3. Three, one for each file.

Two. Both are named shop, after the package. The binary reaches the library through that name, as use shop::....

{
    "name": "acme/shop",
    "require": {
        "php": "^8.5"
    },
    "autoload": {
        "psr-4": {"App\\": "app/"}
    }
}
[package]
name = "shop"
version = "0.1.0"
edition = "2024"

Both files name the package and state the language version the code needs. require.php in Composer does that, and ^8.5 means 8.5 or any later 8.x. Cargo's rust-version field does that for the Rust compiler, and edition picks the language rules. Composer maps namespaces to folders with psr-4. Cargo has no such mapping, because the module tree is written in your source (you will see that in the files section below). The name in Cargo.toml does different work: it names the library crate, so other crates write shop:: at the start of every path they use to reach it.

Every crate starts at one root file, src/lib.rs or src/main.rs. Everything else hangs off that root through mod lines, and those lines form a tree. Most of this chapter is about that tree: how it is built, and who is allowed to see into it.

Modules and privacy

A module is a box with a name. Inside a crate you open one with mod. Everything in the box is private by default. Code outside the box cannot use it, even when that code sits in the same file. Here is a program that calls a private function from outside its module.

mod billing {
    pub fn total(cents: u32) -> u32 {
        cents + fee()
    }

    fn fee() -> u32 {
        50
    }
}

fn main() {
    println!("{}", billing::total(100));
    println!("{}", billing::fee());
}
error[E0603]: function `fee` is private
  --> src/main.rs:13:29
   |
13 |     println!("{}", billing::fee());
   |                             ^^^ private function
   |
note: the function `fee` is defined here
  --> src/main.rs:6:5
   |
 6 |     fn fee() -> u32 {
   |     ^^^^^^^^^^^^^^^

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0603`.

The error is on the call from main. The name fee exists inside billing, but main has no permission to use it. Calling total works, because total is declared pub. Read E0603 as "this item is private to where it is declared".

Four levels control who can see an item. Read each row as "visible to".

WrittenVisible to
(nothing)This module, and the modules nested inside it.
pub(super)The parent module, and everything inside the parent.
pub(crate)Every module of this crate. No other crate.
pubAnyone who can reach the path, including other crates.

PHP's private and protected belong to classes and their subclasses. Rust's privacy belongs to modules. A private item is visible to the module that contains it and to that module's children, and that is the whole rule. Rust has no inheritance, so there is no protected level.

Struct fields have their own visibility

Making a struct pub does not make its fields pub. Each field has its own visibility, and the default is private. That is how a type protects its own rules. Predict the compiler's verdict before you open the answer.

Does this compile?

mod account {
    pub struct Account {
        pub owner: String,
        balance: i64,
    }

    impl Account {
        pub fn balance(&self) -> i64 {
            self.balance
        }
    }
}

fn main() {
    let b = account::Account { owner: "Bo".to_string(), balance: 5 };
    println!("{} {}", b.owner, b.balance());
}
  1. Yes. It prints Bo 5.
  2. No. E0451: the field balance is private, so a struct literal from main can't set it.
  3. No. E0603: the struct Account is private.

Account and owner are pub, so main can name them. balance is private, and a struct literal has to set every field, so the literal fails. Reading the field with b.balance would fail with E0616 instead. The method balance() is pub, so it works, and that is how outside code reads the value.

Enum variants follow their enum. They are exactly as visible as the enum, so a pub enum has public variants, and you never write pub on a variant.

Private fields are also how you enforce a rule. This pattern is worth recognizing, because you will see it throughout real crates. Keep the field private, and give the type one constructor that checks its input.

mod account {
    pub struct Email(String);

    impl Email {
        pub fn new(raw: &str) -> Result<Email, String> {
            if raw.contains('@') {
                Ok(Email(raw.to_string()))
            } else {
                Err(format!("not an email: {raw}"))
            }
        }

        pub fn as_str(&self) -> &str {
            &self.0
        }
    }
}

fn main() {
    match account::Email::new("ana@example.com") {
        Ok(e) => println!("valid: {}", e.as_str()),
        Err(msg) => println!("{msg}"),
    }
    match account::Email::new("nope") {
        Ok(e) => println!("valid: {}", e.as_str()),
        Err(msg) => println!("{msg}"),
    }
}

Outside code cannot skip the check. Writing account::Email(String::from("nope")) from main fails with E0603, and the message says the tuple struct constructor Email is private. A tuple struct's constructor is only as visible as its fields, and this field is private. A wrapper like this is called a newtype. Chapter 21 uses it for values that carry meaning, such as an email address or an order ID.

Paths and use

A path is a list of names joined by ::. Three words start a path from a fixed place. crate:: starts at the root of the current crate. self:: starts at the current module. super:: starts at the parent module. Predict the output of this program before you open the answer.

What does main print?

mod billing {
    pub fn total(cents: u32) -> u32 {
        cents + self::fee()
    }

    fn fee() -> u32 {
        50
    }

    pub mod invoice {
        pub fn line(cents: u32) -> u32 {
            super::fee() + cents
        }

        pub fn sum(cents: u32) -> u32 {
            crate::billing::total(cents) * 2
        }
    }
}

fn main() {
    println!("{}", billing::total(100));
    println!("{}", billing::invoice::line(100));
    println!("{}", billing::invoice::sum(100));
}
  1. 150, 150 and 300, one per line.
  2. 150, 150 and 150, one per line.
  3. Nothing. invoice can't call fee, because fee is private.

All three lines compile. invoice is a child of billing, and a child can see its parent's private items, so super::fee() works. The reverse is not true. main is the parent of billing, so it cannot call billing::fee(). That is the error you saw in the previous section.

Writing the full path every time gets long. use brings a name into scope, so you can write it short. It does not load anything, and it does not change what the code means.

use std::collections::{BTreeMap, HashMap as Map};
use std::fmt::{self, Display};

struct Badge(u32);

impl Display for Badge {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "#{}", self.0)
    }
}

fn main() {
    let mut counts: Map<&str, u32> = Map::new();
    counts.insert("ana", 2);
    let sorted: BTreeMap<_, _> = counts.into_iter().collect();
    println!("{:?} {}", sorted, Badge(7));
}
FormMeaning
use a::b;Bring b into scope.
use a::b as c;Bring b into scope under the name c.
use a::{b, c::d};Several imports on one line.
use a::{self, B};The module a itself, plus B.
use a::*;Everything public in a. Avoid this outside tests and preludes.

A glob import hides where names come from, and that makes code harder to read. The one place where it is routine is a test module, which starts with use super::*; so that the tests can see the code they test.

Re-exports build a clean front door

Sometimes the layout that makes sense inside a crate is not the one you want callers to see. pub use re-exports a name, so a private module can keep its structure while the public path stays short.

mod engine {
    mod internal {
        pub struct Piston {
            pub strokes: u32,
        }
    }

    pub use self::internal::Piston;

    pub fn fire(p: &Piston) -> u32 {
        p.strokes * 2
    }
}

fn main() {
    let p = engine::Piston { strokes: 4 };
    println!("{}", engine::fire(&p));
}

Callers use engine::Piston. The path through internal is still closed, and the compiler says so, and it even suggests the public path.

fn main() {

PHP's use App\Models\User; is also an alias, but PHP finds the class later, at runtime, through the autoloader. Rust checks every use while it compiles. A use that names nothing stops the build, so you find out before the program runs.

From files to modules

Here is the surprise that catches most PHP developers. Creating src/models/user.rs does not add a module to your program. Nothing reads that file until a mod line names it. Composer finds App\Models\User in app/Models/User.php by path, the first time the class is needed. Rust works the other way round: the module tree is written in source, and the files follow from it.

Declarationrustc looks for
mod models; in src/lib.rssrc/models.rs, or src/models/mod.rs
mod user; in src/models/mod.rssrc/models/user.rs, or src/models/user/mod.rs
mod handlers; in src/http/mod.rssrc/http/handlers.rs, or src/http/handlers/mod.rs
 
// No require needed. The autoloader finds
// App\Models\User in app/Models/User.php on first use.
use App\Models\User;

$user = new User('Ana');
// src/lib.rs
pub mod models;      // reads src/models/mod.rs and makes it part of the crate

// src/models/mod.rs
pub mod user;        // reads src/models/user.rs, which is now part of the crate

Composer maps a name to a file and loads it when it is used. A PHP namespace is a prefix on class names, and PSR-4 makes the folder path follow that prefix by convention. Rust has no autoloader and no runtime lookup. A module is a node in the crate's tree, and a mod line creates that node. A file is compiled only if a mod line reaches it, and a file with no such line is ignored, even when it sits in src/.

The map shows the rule in action. src/util.rs is a complete, valid file, and it does nothing, because no mod util; names it. Adding that one line to lib.rs is enough to make it part of the crate. Until then, no tool in the build will read it.

Picture the module tree as a building. Each mod line is a door that opens into a room, and the room is a file. A path into an item is a walk through several doors, and each door has to be open to you. A pub keyword opens a door for the callers you choose. A file with no mod line is a room with no door, so nobody walks in.

Cargo.toml in depth

Cargo.toml is the manifest for a package. Dependencies are where most decisions live, and most surprises come from version requirements. Here is an annotated example. Each comment explains the line it sits on.

[package]
name = "shop"          # the crate name. Other code writes `use shop::...`
version = "0.1.0"      # bumped for each release you publish
edition = "2024"       # which edition's syntax and rules apply

[dependencies]
serde = { version = "1", features = ["derive"] }   # crates.io, with the derive macros
money = { path = "../money" }                       # a folder on disk, common in monorepos

[dev-dependencies]
pretty_assertions = "1"   # compiled only for tests and examples

[features]
default = []
metrics = []              # a compile-time switch: #[cfg(feature = "metrics")]

[profile.release]
opt-level = 3             # how hard the optimizer works
lto = true                # link-time optimization: slower builds, often faster binaries

The [dependencies] table has three sources. A version comes from crates.io. A path points at a folder on disk, which is how a monorepo shares code between packages. A git source points at a repository. [dev-dependencies] are compiled only for tests and examples, so they never ship in your binary.

Version requirements mean ranges

A version written in Cargo.toml is a range, not a pin. The default meaning is caret, the same as Composer's ^. Here is what each form allows.

WrittenAllows
"1.2", same as "^1.2"1.2.0 up to, but not including, 2.0.0
"~1.2"1.2.0 up to, but not including, 1.3.0
"=1.2.0"Exactly 1.2.0

The range has a floor, and that causes a real error. Serde has no 1.2 release, so asking for "1.2" fails. Here is the real output when you make that request.

error: failed to select a version for the requirement `serde = "^1.2"`
candidate versions found which didn't match: 1.0.229, 1.0.228, 1.0.227, ...
location searched: crates.io index

When you add a dependency, cargo add writes the newest version it found, and it writes that version as a caret requirement:

serde = { version = "1.0.229", features = ["derive"] }

That line means ^1.0.229. Any 1.x release at least as new as 1.0.229 satisfies it, and Cargo picks the newest matching release when it resolves dependencies.

Think first: should Cargo.lock go in git for an application?

Yes. The lock file records the exact version of every dependency that was resolved, so every machine and every CI run builds the same code. Libraries are less clear-cut. Consumers always resolve their own lock file, so the one in your library is only a record of what you tested. Many teams commit it anyway, so that CI tests the versions they actually run.

Cargo keeps the resolved versions in Cargo.lock. cargo update moves those versions forward, but only inside the ranges that Cargo.toml allows. Composer's composer.lock plays the same role, and the same rule applies to both: commit the lock file for applications.

CargoWhat it doesComposer
cargo add serde --features deriveAdds the dependency and updates Cargo.lock.composer require
cargo remove serdeRemoves it.composer remove
cargo updateMoves locked versions forward, within the ranges in Cargo.toml.composer update
cargo treePrints the whole dependency tree.composer show --tree
cargo tree -i serdeShows what depends on serde, working upward.composer why serde

crates.io is the registry where published crates live, and it plays the role Packagist plays for PHP. docs.rs builds the API documentation for each published crate automatically, so a crate you find on crates.io usually has its docs one click away.

Workspaces hold several packages together

A workspace is one root Cargo.toml that lists several packages. They share one Cargo.lock and one target/ directory. This course's repository is one. Its root manifest names the members, the default member that a bare cargo command acts on, and the folders that are excluded:

[workspace]
members = ["forge", "quests"]
default-members = ["forge"]
exclude = ["projects", "solutions"]
resolver = "3"

Testing is built in

Cargo runs three kinds of tests with one command, cargo test. Unit tests live in the same file as the code they test, inside a #[cfg(test)] module. Integration tests live in a tests/ folder. Doc tests live in the /// comments. Start with unit tests.

pub fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        return Err(String::from("division by zero"));
    }
    Ok(a / b)
}

pub fn nth(items: &[i32], index: usize) -> i32 {
    items[index]
}

fn main() {
    println!("{:?} {}", divide(7, 2), nth(&[5, 6], 1));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn divides_evenly() {
        assert_eq!(divide(10, 2), Ok(5), "10 / 2 should be 5");
    }

    #[test]
    fn refuses_zero() {
        assert!(divide(1, 0).is_err());
    }

    #[test]
    #[should_panic(expected = "index out of bounds")]
    fn panics_past_the_end() {
        nth(&[1, 2, 3], 9);
    }

    #[test]
    fn works_with_question_mark() -> Result<(), String> {
        let half = divide(10, 2)?;
        assert_eq!(half, 5);
        Ok(())
    }

    #[test]
    #[ignore = "slow: run with cargo test -- --ignored"]
    fn slow_case() {
        assert_eq!(nth(&[4], 0), 4);
    }
}

The fn main at the bottom exists only so this block runs on its own here. A real src/lib.rs would not have one. Running cargo test on that file prints one line per test. The order can change from run to run, because tests run in parallel. This is real output from the file above.

test tests::works_with_question_mark ... ok

The assertion macros are assert! for a condition, assert_eq! for two values that must be equal, and assert_ne! for two that must differ. Each takes an optional message after its arguments. When assert_eq! fails, it prints both sides, and that is most of the reason to prefer it. The table lines up the two sets of tools.

Here are the same two tests in a Laravel 13 app. PHPUnit marks each test method with the #[Test] attribute. Pest turns each test into a function that takes a name and a closure. Both ship with Laravel, and PHPUnit 12 no longer reads @test docblocks.

declare(strict_types=1);

namespace Tests\Unit;

use DivisionByZeroError;
use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\TestCase;

final class DivideTest extends TestCase
{
    #[Test]
    public function dividesEvenly(): void
    {
        $this->assertSame(5, intdiv(10, 2));
    }

    #[Test]
    public function refusesZero(): void
    {
        $this->expectException(DivisionByZeroError::class);
        intdiv(1, 0);
    }
}
test('divides evenly', function () {
    expect(intdiv(10, 2))->toBe(5);
});

php artisan test --filter dividesEvenly   # one test, by name
php artisan test                        # every test, PHPUnit and Pest alike
cargo test divides                      # tests whose path contains "divides"
cargo test                              # every test in the crate

php artisan test wraps the same runners as vendor/bin/pest and vendor/bin/phpunit, and it passes their arguments through. cargo test needs no wrapper. The test harness is part of the toolchain, and #[test] marks the functions it runs.

A few details matter. #[should_panic] with no expected passes on any panic, including one caused by a bug, so always give it text. A test can return Result<(), E> and use ?, which makes an Err fail the test. cargo test divide runs every test whose name contains divide, and cargo test -- --ignored runs the ignored ones.

Does this compile, and can the test call the private function?

fn double(x: i32) -> i32 {
    x * 2
}

fn main() {
    println!("{}", double(21));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn doubles_four() {
        assert_eq!(double(4), 8);
    }
}
  1. No. Private means private to the file, and a test is in another module.
  2. Yes. A child module can see the private items of its parent, and tests is a child of the module that defines double.
  3. Only if double is changed to pub(crate) first.

Yes. The test module is nested inside the module that defines double, so use super::*; brings it in, even though it is private. The same rule as before, read from the other side. The cfg(test) module is compiled only by cargo test, so cargo run never looks at it. Run cargo test to see the test pass.

Integration tests sit in tests/. Each file there is its own crate, and it can reach only the pub API of your library. That is a good test of your public design, because a test that needs private code is a test of the internals.

// A separate crate. It sees only what `calc` makes pub.
use calc::{add, divide};

#[test]
fn public_api_adds() {
    assert_eq!(add(10, 20), 30);
}

#[test]
fn public_api_divides() {
    assert_eq!(divide(9, 3), Ok(3));
}

Doc tests are code blocks in /// comments. cargo test compiles each one and runs it, so the example in your documentation can't drift from the code. This one lives in a library crate named calc. The fn main at the bottom exists only so this block runs on its own here. A real library wouldn't have one.

/// Adds two numbers.
///
/// ```
/// assert_eq!(calc::add(2, 3), 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() {
    println!("{}", add(2, 3));
}

An agent asked to make a failing test pass has an easy shortcut. It can weaken the assertion, add #[ignore], or delete the test. The test then passes, and the bug is still there. When an agent reports green tests, check the diff of the test files as well as the code. Treat a change to an assertion as a change to the requirement.

The rest of the toolbox

The standard toolchain includes a formatter and a linter. A PHP team would run them the way it runs Pint and PHPStan. Here are the tools you will meet most often.

Clippy warnings don't stop a build on their own. Here is a common one, from a small crate. A length check against zero reads better as is_empty(), and clippy says so.

warning: length comparison to zero
 --> src/main.rs:2:5
  |
2 |     names.len() == 0
  |     ^^^^^^^^^^^^^^^^ help: using `is_empty` is clearer and more explicit: `names.is_empty()`
  |

Clippy printed two warnings and no errors. What exit code does cargo clippy return?

  1. 0. Warnings are reported, but they don't fail the command.
  2. 101, the same code as a failed build.
  3. 1, because the code has warnings.

Zero. A script that only runs cargo clippy will pass on warnings. To make them fail the build, pass the flag after the double dash: cargo clippy --all-targets -- -D warnings. -D means deny, and it turns each warning into an error.

This is how you keep AI agents honest. Put the checks in the project's agent instructions, in CLAUDE.md or AGENTS.md, so the agent runs them before it says it is done:

Before you say a change is done, run, in this order:
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test

A rule like this turns "it compiles on my side" into a result you can check. Read the tool output, not the agent's summary of it.

Practice

Six checks, one for each idea in this chapter. Answer each one before you open it.

Does this compile, and if not, which error appears?

mod shapes {
    pub mod area {
        pub fn square(side: u32) -> u32 {
            side * side
        }
    }

    mod scale {
        pub fn triple(n: u32) -> u32 {
            n * 3
        }
    }
}

fn main() {
    println!("{}", shapes::area::square(4));
    println!("{}", shapes::scale::triple(2));
}
  1. Yes. It prints 16 and 6.
  2. No. E0603: module scale is private, even though triple is pub.
  3. No. E0433: cannot find scale.

The function is pub, but the path to it runs through shapes::scale, and scale has no pub. Each segment on a path must be visible. The same rule explains the handlers question in the module map.

A project has src/util.rs containing a pub fn. No line anywhere says mod util;. Is util.rs part of the crate?

  1. Yes. Everything under src/ is compiled.
  2. No. rustc never opens a file that no mod line names.

No. The file is valid Rust, and it does nothing. Add mod util; to lib.rs, and it becomes part of the crate, with its pub items reachable as crate::util::....

What does serde = "1.2" in Cargo.toml allow?

  1. Exactly version 1.2.0.
  2. Any version from 1.2.0 up to, but not including, 2.0.0.
  3. Any version from 1.2.0 onward, including 2.0.0 and later.

The second one. A requirement without an operator is a caret range, so "1.2" means ^1.2. Versions 1.0 and 1.1 fall below the floor, and 2.0.0 falls above the ceiling. That floor is why the serde example earlier fails: no serde release is at 1.2 or later within the major version 1.

You are testing that parse_price("12,50") returns 1250. Which assertion gives the most useful failure message?

  1. assert!(parse_price("12,50") == 1250);
  2. assert_eq!(parse_price("12,50"), 1250, "a comma decimal should be cents");
  3. assert_ne!(parse_price("12,50"), 0);

The assert_eq! version. When it fails, it prints the left value, the right value and your message. assert! reports only that the condition was false, and assert_ne! checks the opposite of what you want to know.

Inside report, bring area into scope. Fill in the path that leads to geometry. Two answers are right: one goes up a level, and one starts at the crate root.

mod geometry {
    pub fn area(w: u32, h: u32) -> u32 {
        w * h
    }

    pub mod report {
        use [[super|crate::geometry]]::area;

        pub fn line(w: u32, h: u32) -> String {
            format!("area = {}", area(w, h))
        }
    }
}

fn main() {
    println!("{}", geometry::report::line(3, 4));
}

super steps from report up to geometry. crate::geometry walks down from the root. Both reach the same function, so both are accepted. Writing use geometry::area; without either fails with E0432, because geometry is not in scope inside report.

Recap

Modules, crates and tests

  • A package holds crates. A crate is one tree of modules, rooted at src/lib.rs or src/main.rs.
  • Items are private by default. pub, pub(crate) and pub(super) widen the view. A path works only when every segment is visible.
  • crate::, self:: and super:: start a path. use brings a name into scope. pub use re-exports one.
  • A file is part of the crate only when a mod line names it. Nothing is autoloaded.
  • In Cargo.toml, "1.2" means ^1.2: a range with a floor. Cargo.lock pins exact versions, and you commit it for applications.
  • Unit tests sit in #[cfg(test)] modules, integration tests in tests/, and doc tests in /// comments. cargo test runs all three.
  • Run cargo fmt --check, cargo clippy --all-targets -- -D warnings and cargo test before you accept any change, human or agent.
Explain it back: why doesn't adding src/util.rs make it part of your program?

One good answer: "Rust compiles only the files that the module tree reaches. The crate root declares its modules with mod lines, and each line tells the compiler which file to read. Nothing in this project says mod util;, so the compiler never opens util.rs. The file sits on disk, but it is not part of the module tree. Add a mod util; line and it becomes part of the crate."

If your version mentioned the module tree, a mod line names the file, and no autoloading, you have the idea.
