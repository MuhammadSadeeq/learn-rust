The waiting problem

Most of a web request is spent waiting. It waits for the database to answer, for an HTTP call to come back, for a file to be read. The CPU does real work for a small share of the time.

The classic model gives each connection its own thread. That thread handles the request from start to finish, and while it waits it does nothing useful. It still holds its stack, and the operating system still has to schedule it. Ten thousand slow connections means ten thousand threads, most of them asleep.

Async changes what a waiting connection costs. A task that is waiting is not a thread. It is a small saved state that says where to resume. One thread can keep thousands of those tasks, and run only the ones that are ready.

Kind of workBetter tool
Many connections that spend most of their time waiting on a database, an HTTP call or a socketAsync, with a runtime such as tokio
Heavy computation: hashing a large file, resizing images, parsing a huge datasetThreads, or rayon for parallel iterators
A blocking library you cannot changespawn_blocking, or a dedicated thread

PHP-FPM runs one request per worker. When your controller calls Eloquent and the worker waits for MySQL, that worker is blocked until the answer comes back. You scale by adding workers.

PHP has async tools, but most Laravel apps do not use them. Fibers arrived in PHP 8.1. A Fiber can pause a whole call stack. PHP has no async or await keywords, so a Fiber is the closest model. Amp and ReactPHP give PHP event loops, and Amp's async functions run on Fibers. Swoole runs coroutines inside its own server.

Laravel Octane is a different idea. It boots the app once and keeps it in memory between requests, and it runs on FrankenPHP, Open Swoole, Swoole or RoadRunner. Keeping the app warm does not, by itself, change how waits behave. Whether a wait blocks depends on the server underneath, so check that server's documentation. With Swoole, Octane can also run closures as background tasks through Octane::concurrently.

Async does not make code faster. A loop that crunches numbers takes the same time inside an async function, and while it runs, every other task on that thread waits too. The gain is in how cheaply the waiting is handled.

public function show(int $id): JsonResponse
{
    $user = User::findOrFail($id);     // this worker waits for MySQL here
    $orders = $user->orders()->get();  // and waits again here
    return response()->json(['user' => $user, 'orders' => $orders]);
}
async fn show(db: &Db, id: u32) -> String {
    let user = db.find_user(id).await;    // this task parks; the thread serves others
    let orders = db.orders_for(&user).await;
    format!("{} has {} orders", user.name, orders.len())
}

The Rust version reads almost the same. The Db type stands in for your database layer, so this sketch is not meant to compile on its own. The difference is what happens at each .await. The thread is free to run another task. In PHP the worker waits, and nothing else runs on it.

Think first: what is the PHP worker's thread doing while MySQL is slow?

Nothing useful. It is blocked, and that request is its only job. In Rust, the same wait returns Pending to the executor, so the same thread can poll another ready task. The waiting task costs only its saved state.

A future is a paused computation

An async fn looks like a normal function with one extra word. The difference is what calling it does. Calling an async fn does not run its body. It returns a future: a value that describes work that has not happened yet.

Here is a program with two async functions. Predict what it prints, then open the answer.

async fn fetch() -> u32 {
    println!("fetch runs");
    42
}

async fn report() {
    fetch();
    println!("report runs");
}

fn main() {
    let _report = report();
}
Predict: what does this program print?

Nothing. report() creates a future and stores it in _report, but nothing polls it, so its body never runs. Even fetch() never runs, because report never gets to that line.

The compiler warns about the line fetch();:

warning: unused implementer of `Future` that must be used
 --> src/main.rs:7:5
  |
7 |     fetch();
  |     ^^^^^^^
  |
  = note: futures do nothing unless you `.await` or poll them
  = note: `#[warn(unused_must_use)]` (part of `#[warn(unused)]`) on by default

The warning states the rule. A future does nothing until you .await it or poll it. In report, the call to fetch() made a future and dropped it on the spot. The fix is fetch().await, inside another async function.

What a future actually is

Every future implements one trait from the standard library. It has one method, poll. An executor calls poll, and the future answers with one of two results.

use std::pin::Pin;
use std::task::{Context, Poll};

// The real trait lives in std::future. This copy has the same shape.
trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

fn main() {}
ResultMeaning
Poll::Ready(value)The work is finished. Here is the output.
Poll::PendingNot yet. The future has arranged to be polled again, and it gave its waker to whatever it waits on.

The Waker is what makes Pending workable. When a future returns Pending, it hands its waker to the thing it is waiting on, such as a socket. When the data arrives, that source calls wake(), and the executor knows which task to poll again. A task that never gets its wake() is never polled again.

A future is a paused order. The executor, the Waiter, picks up whichever order is ready. .await means "pause here, and let the Waiter work on something else".

Think first: the "Waiting on load_orders" state keeps user. The function only needs user to call load_orders. Why must the state keep it?

load_orders(&user) returns a future that borrows user. That future lives inside the state while it waits, so the value it borrows must stay in the state too. This is the self-reference that the Pin callout later in this chapter explains.

A runtime in 20 lines

You can drive a future with nothing but the standard library. This block_on takes one future and polls it until it returns Ready. It is a busy loop, which is fine for a demo and wasteful for real work. A real executor sleeps until a waker fires.

use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

fn block_on<F: Future>(fut: F) -> F::Output {
    let waker = Waker::noop();
    let mut cx = Context::from_waker(waker);
    let mut fut = pin!(fut);
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

async fn fetch_user() -> u32 {
    println!("fetching user");
    7
}

async fn greet() -> String {
    let id = fetch_user().await;
    println!("got id {id}");
    format!("hello, user {id}")
}

fn main() {
    let msg = block_on(greet());
    println!("{msg}");
}

Read greet line by line. The .await on fetch_user() polls the inner future. It is ready at once, so greet keeps going. If it had returned Pending, greet would return Pending as well, all the way up to block_on, which would then poll again.

A future that returns Pending

Here is a future you write yourself. Countdown returns Pending three times before it is ready. Each time it asks to be polled again by calling wake_by_ref. This block_on ignores that request, because it polls in a loop anyway. A real executor uses the request to put the task back on its ready queue.

How many times does block_on call poll on Countdown { left: 3, polls: 0 }?

use std::future::Future;
use std::pin::{Pin, pin};
use std::task::{Context, Poll, Waker};

fn block_on<F: Future>(fut: F) -> F::Output {
    let waker = Waker::noop();
    let mut cx = Context::from_waker(waker);
    let mut fut = pin!(fut);
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

struct Countdown {
    left: u32,
    polls: u32,
}

impl Future for Countdown {
    type Output = u32;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u32> {
        self.polls += 1;
        println!("poll {}: {} left", self.polls, self.left);
        if self.left == 0 {
            return Poll::Ready(self.polls);
        }
        self.left -= 1;
        cx.waker().wake_by_ref();
        Poll::Pending
    }
}

fn main() {
    let polls = block_on(Countdown { left: 3, polls: 0 });
    println!("finished after {polls} polls");
}
  1. Once. It is ready as soon as it is polled.
  2. Three times, one for each Pending.
  3. Four times: three Pending results, then one Ready.
  4. Never. A future that returns Pending can't finish without a timer.

Each poll prints one line. Polls 1 to 3 decrement left and return Pending. Poll 4 sees left == 0 and returns Ready(4), so the program prints finished after 4 polls.

One Waiter, many orders

A restaurant has one Waiter and several orders. Some orders need the Waiter's hands for a minute. Others go to the kitchen and need nothing from the Waiter for ten minutes. A good Waiter sets the kitchen order down and takes the next one. That is an executor. It runs whichever task is ready, and it never stands still waiting for a task that is waiting on I/O.

Each task below is a script of steps. A compute step takes one tick of the Waiter's time. An I/O wait takes the number of ticks shown, and the task cannot run during that wait. Each tick, the Waiter polls the first ready task in the queue. When an I/O finishes, the task's waker rings its bell. wake() is the call that rings it, and it puts that task at the back of the queue.

Press Tick a few times and watch the queue. Then press Run to completion, and turn on Thread per task. Both versions run the same scripts, and a tick is the same unit of time in both.

With these scripts, the thread version finishes at tick 8 and the async version at tick 10. Threads win on wall-clock time here, because each task gets a worker of its own for its compute steps. Async wins on the cost of waiting. The async version used one thread. Its three waiting tasks cost saved state, not threads. The thread version used three threads, and they sat blocked for 13 thread-ticks, doing nothing.

Async is cheap waiting, not extra speed. It wins when tasks mostly wait: a thousand connections that each spend most of their time on a database cost a thousand small tasks, not a thousand threads. It loses when tasks mostly compute. Then the one Waiter is the bottleneck, and you need more Waiters, which means more threads or more cores.

In thread-per-task mode, what is a thread doing while its task waits on I/O?

  1. Running another task's compute step.
  2. Blocked. It keeps its stack and does nothing until the I/O returns.
  3. Handed back to the operating system, so it costs nothing while it waits.
  4. Polling the I/O source in a loop until the data arrives.

That is the cost the simulator shows. In thread mode, every waiting task keeps a thread, and the thread is blocked on the I/O call. In async mode the waiting task has no thread at all, so the same wait costs only its saved state.

tokio: the runtime you'll actually use

tokio is the runtime most async Rust code uses. It supplies the executor, the I/O drivers, timers and channels. The language gives you async and .await, but nothing runs a future by itself. You need a runtime.

[dependencies]
tokio = { version = "1", features = ["full"] }

Start the runtime and spawn a task

use std::time::Duration;

async fn fetch_user(id: u32) -> String {
    tokio::time::sleep(Duration::from_millis(50)).await;
    format!("user {id}")
}

#[tokio::main]
async fn main() {
    let handle = tokio::spawn(fetch_user(1));
    let name = handle.await.unwrap();
    println!("{name}");
}

#[tokio::main] turns main into a runtime starter. It builds the runtime and runs main on it. tokio::spawn hands a future to the runtime, which runs it on one of its worker threads, and returns a JoinHandle. Awaiting the handle gives you the task's output. If the task panicked, you get a JoinError instead.

The spawn rules

A spawned task can outlive the function that spawned it, so its future must be Send + 'static. Send means the future can move to another thread. 'static means it holds no borrows of local variables. It may own its data. Here is the common mistake:

#[tokio::main]
async fn main() {
    let name = String::from("Ana");
    let handle = tokio::spawn(async {
        println!("hello {name}");
    });
    handle.await.unwrap();
}

The compiler's fix is printed for you: move. It hands the async block ownership of name, so the task no longer borrows from main.

Run futures side by side

join! polls several futures together and waits for all of them. The two sleeps below run at the same time, so the whole program takes about 100 ms, not 200 ms.

use std::time::Duration;

async fn get_user() -> String {
    tokio::time::sleep(Duration::from_millis(100)).await;
    String::from("ana")
}

async fn get_orders() -> u32 {
    tokio::time::sleep(Duration::from_millis(100)).await;
    3
}

#[tokio::main]
async fn main() {
    let (user, orders) = tokio::join!(get_user(), get_orders());
    println!("{user} has {orders} orders");
}

Laravel's nearest match for join! is the Concurrency facade. Like join!, it starts several tasks and waits for all of them:

[$users, $orders] = Concurrency::run([
    fn () => DB::table('users')->count(),
    fn () => DB::table('orders')->count(),
]);
let (users, orders) = tokio::join!(count_users(), count_orders());

The purpose matches, and the mechanism does not. join! polls futures on one thread, in one process, and nothing is copied. Concurrency::run gives each closure its own PHP process, and each process works on a serialized copy. Starting a process costs far more than polling a future, so the facade suits tasks that take real time.

select! waits for the first branch to finish and runs only that branch's handler. The other branches are dropped. Here the 500 ms lookup loses to the 100 ms timer, so the program prints gave up after 100 ms.

use std::time::Duration;

async fn slow_lookup() -> &'static str {
    tokio::time::sleep(Duration::from_millis(500)).await;
    "found it"
}

#[tokio::main]
async fn main() {
    tokio::select! {
        answer = slow_lookup() => println!("answer: {answer}"),
        _ = tokio::time::sleep(Duration::from_millis(100)) => println!("gave up after 100 ms"),
    }
}

Dropping a future is how Rust cancels it. The future stops at its last .await, and anything it owns is dropped. This program has a guard whose Drop prints a line, so you can see the cancellation happen:

use std::time::Duration;

struct Guard(&'static str);

impl Drop for Guard {
    fn drop(&mut self) {
        println!("dropped {}", self.0);
    }
}

async fn slow_work() {
    let _guard = Guard("slow_work");
    tokio::time::sleep(Duration::from_millis(500)).await;
    println!("slow_work finished");
}

#[tokio::main]
async fn main() {
    tokio::select! {
        _ = slow_work() => println!("slow_work won"),
        _ = tokio::time::sleep(Duration::from_millis(100)) => println!("timer won"),
    }
    println!("main continues");
}
dropped slow_work
timer won
main continues

The guard's message comes before timer won. The losing branch is dropped before the winning handler runs, and slow_work finished never prints.

Time limits, groups of tasks and channels

timeout wraps any future with a deadline. It returns Ok(value) or Err(Elapsed).

use std::time::Duration;
use tokio::time::timeout;

async fn slow() -> u32 {
    tokio::time::sleep(Duration::from_secs(2)).await;
    42
}

#[tokio::main]
async fn main() {
    match timeout(Duration::from_millis(100), slow()).await {
        Ok(value) => println!("got {value}"),
        Err(err) => println!("timed out: {err}"),
    }
}

JoinSet owns a group of spawned tasks. join_next returns each result as its task finishes, in completion order, not spawn order.

use std::time::Duration;
use tokio::task::JoinSet;

#[tokio::main]
async fn main() {
    let mut set = JoinSet::new();
    for id in 1..=3u64 {
        set.spawn(async move {
            tokio::time::sleep(Duration::from_millis(10 * id)).await;
            id * id
        });
    }
    let mut total = 0;
    while let Some(result) = set.join_next().await {
        total += result.unwrap();
    }
    println!("total {total}");
}

mpsc is a channel with many senders and one receiver. recv returns None only after every sender has been dropped. That is why the code below drops tx before the loop. The order in which messages arrive can vary, so the program counts them.

use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<String>(8);
    for id in 1..=3 {
        let tx = tx.clone();
        tokio::spawn(async move {
            tx.send(format!("job {id} done")).await.unwrap();
        });
    }
    drop(tx); // the loop below ends only when every sender is gone
    let mut count = 0;
    while let Some(_message) = rx.recv().await {
        count += 1;
    }
    println!("received {count} messages");
}
Think first: you call two APIs and need both answers before you can respond. Which macro do you want, join! or select!?

join!. It waits for every branch and returns every result. select! would give you the first answer and drop the other one, which is the wrong behavior when both are needed.

Cancel safely, shut down cleanly

Dropping a future cancels it, as the tokio section showed. The harder question is what the dropped future had already done. A task that has read part of a message, or taken a step toward a result, loses that progress when it is dropped. Whether that matters has a name: cancellation safety.

The examples in the next three sections use these crates. Add them to Cargo.toml, and you will need all three for the streams section:

[dependencies]
tokio = { version = "1.53", features = ["full"] }
tokio-util = "0.7.20"
futures = "0.3.34"

select! drops the losers

Each round of select! runs one winning branch and drops the other branches where they are waiting. In a loop, the losing futures are built again on the next round, so they start over. Here a 4-byte read is half done when the timer wins:

use std::time::Duration;
use tokio::io::{AsyncReadExt, AsyncWriteExt};

#[tokio::main]
async fn main() {
    let (mut writer, mut reader) = tokio::io::duplex(64);
    writer.write_all(b"ab").await.unwrap(); // only 2 of the 4 bytes so far

    let mut frame = [0u8; 4];
    tokio::select! {
        result = reader.read_exact(&mut frame) => println!("frame: {result:?}"),
        _ = tokio::time::sleep(Duration::from_millis(50)) => println!("timer won"),
    }

    writer.write_all(b"cdef").await.unwrap();
    let mut next = [0u8; 4];
    reader.read_exact(&mut next).await.unwrap();
    println!("next frame: {}", std::str::from_utf8(&next).unwrap());
}

The first read took ab from the stream and then waited for two more bytes. The timer won, so the read was dropped, and its progress went with it. The next read starts at the next byte the stream has, so it returns cdef, not abcd. Nothing panicked and nothing printed an error. The bytes were simply gone.

Cancel safe and not cancel safe

tokio documents cancellation safety for many of its methods. Its rule is this: if a future has not completed, dropping it must be a no-op, and building it again must be fine. A future can be cancelled only at an .await, so ask what the method has already done at each one. The table lists the methods you will meet most often. Check the docs for any other method you use.

MethodIf it is dropped while it waits
mpsc::Receiver::recvSafe. The docs guarantee that no message was received.
AsyncReadExt::read_exactNot safe. Bytes it has already read are lost.
AsyncWriteExt::write_allNot safe. The docs warn that data can be lost.
mpsc::Sender::sendThe message you passed in is dropped. Use reserve to keep it.
Mutex::lock, Semaphore::acquireNot safe. You lose your place in the queue.

The rule of thumb is to find the .await points in a future. If the code still does the right thing when it is started again at each one, it is cancel safe.

A shutdown branch

A worker loop should watch for shutdown as one of its branches. The usual signal is a CancellationToken from tokio-util. Cancelling a token wakes every task that waits on it. A child token made with child_token is cancelled when its parent is, so one call can stop a whole tree of tasks. cancelled() returns a future that finishes once the token is cancelled.

use std::time::Duration;
use tokio_util::sync::CancellationToken;

#[tokio::main]
async fn main() {
    let shutdown = CancellationToken::new();
    let worker_stop = shutdown.child_token();

    let worker = tokio::spawn(async move {
        let mut ticks = 0u32;
        loop {
            tokio::select! {
                biased;
                _ = worker_stop.cancelled() => break,
                _ = tokio::time::sleep(Duration::from_millis(10)) => ticks += 1,
            }
        }
        ticks
    });

    tokio::time::sleep(Duration::from_millis(50)).await;
    shutdown.cancel();
    let ticks = worker.await.unwrap();
    println!("worker stopped: {}", ticks > 0);
}

The worker leaves its loop as soon as the token is cancelled, and it returns the number of ticks it counted. The biased; line makes the shutdown branch checked first. The next part explains why that matters.

biased; checks the branches in order

By default select! checks its branches in random order. tokio's docs say this gives some fairness when a loop has several branches that are always ready. When one branch must win, begin the macro with biased;. The branches are then checked in the order you wrote them.

use std::future::ready;

#[tokio::main]
async fn main() {
    // Both branches are ready at once. With `biased;` the first branch always wins.
    let winner = tokio::select! {
        biased;
        _ = ready(()) => "shutdown",
        _ = ready(()) => "work",
    };
    println!("{winner}");
}

Ctrl+C is not the only stop signal

On Unix, Ctrl+C sends SIGINT. Docker and Kubernetes stop a container with SIGTERM. tokio::signal::ctrl_c() listens only for SIGINT, so a server that waits for Ctrl+C alone is killed without any cleanup when it is stopped with SIGTERM. Listen for both:

async fn shutdown_signal() {
    let ctrl_c = async {
        tokio::signal::ctrl_c().await.expect("could not listen for Ctrl+C");
    };
    #[cfg(unix)]
    let terminate = async {
        tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("could not listen for SIGTERM")
            .recv()
            .await;
    };
    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        _ = ctrl_c => {}
        _ = terminate => {}
    }
}

shutdown_signal returns when either signal arrives. Hand it to your server, then finish the work that is still running before you exit. The server in Chapter 20 passes a shutdown signal to with_graceful_shutdown in the same way.

Abort a task, or a whole set

JoinHandle::abort asks a task to stop. The task stops at its next .await, and it drops everything it owns. Awaiting the handle then returns a JoinError whose is_cancelled() is true. JoinSet::abort_all does the same for every task in a set. The set still holds the handles, so call join_next until the set is empty to wait for all of them to finish.

use std::time::Duration;
use tokio::task::JoinSet;

#[tokio::main]
async fn main() {
    let job = tokio::spawn(async {
        tokio::time::sleep(Duration::from_secs(60)).await;
        "finished"
    });
    job.abort();
    let err = job.await.unwrap_err();
    println!("cancelled: {}", err.is_cancelled());

    let mut set = JoinSet::new();
    for _ in 0..3 {
        set.spawn(tokio::time::sleep(Duration::from_secs(60)));
    }
    set.abort_all();
    let mut cancelled = 0;
    while let Some(result) = set.join_next().await {
        if let Err(err) = result {
            if err.is_cancelled() {
                cancelled += 1;
            }
        }
    }
    println!("cancelled in set: {cancelled}");
}

A task started with spawn_blocking cannot be stopped this way. Once its closure has started, abort has no effect on it.

Agents write select! loops that look right and lose data. When you review one, check three things. Which branch reads partial data, because that branch is not cancel safe if it does. Whether shutdown is a branch at all. Whether the code awaits the handle after it aborts a task. A tokio::spawn whose handle nobody keeps gives you no way to wait for it during shutdown.

In this loop, which branch can lose data when another branch wins?

use tokio::io::{AsyncReadExt, DuplexStream};
use tokio::sync::mpsc::Receiver;
use tokio_util::sync::CancellationToken;

async fn pump(mut reader: DuplexStream, mut jobs: Receiver<String>, shutdown: CancellationToken) {
    let mut frame = [0u8; 4];
    loop {
        tokio::select! {
            result = reader.read_exact(&mut frame) => println!("frame {result:?}"),
            Some(job) = jobs.recv() => println!("job {job}"),
            _ = shutdown.cancelled() => break,
        }
    }
}

#[tokio::main]
async fn main() {
    let (_writer, reader) = tokio::io::duplex(64);
    let (_tx, rx) = tokio::sync::mpsc::channel::<String>(8);
    let shutdown = CancellationToken::new();
    shutdown.cancel();
    pump(reader, rx, shutdown).await;
    println!("stopped");
}
  1. jobs.recv(). A message can be taken off the channel and then dropped.
  2. reader.read_exact(&mut frame). The bytes it has already read go with the dropped future.
  3. shutdown.cancelled(). Cancelling a token can lose the signal.
  4. None. select! finishes a branch before it drops anything.

recv is cancel safe. tokio's docs guarantee that no message was received when another branch wins. The shutdown branch holds no progress to lose. read_exact is the branch that loses bytes, as the first example in this section showed. If you need a read that can stop at any moment, use read, which is cancel safe. Keep any partial frame in your own buffer.

Limits and backpressure

A server that spawns one task per request has no limit. Ten thousand requests can mean ten thousand tasks, all calling the same database at once. A limit keeps the amount of work in progress fixed. Backpressure is the same idea seen from the queue side: when the limit is reached, the producer waits.

Semaphore: at most N at once

A Semaphore holds a fixed number of permits. A task takes a permit before it does its work and gives the permit back when the permit is dropped. acquire_owned takes an Arc of the semaphore, so the permit can move into a spawned task. The program below starts ten tasks. Each one needs a permit, and the high-water mark records the most tasks that worked at the same time.

use std::sync::Arc;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::time::Duration;
use tokio::sync::Semaphore;

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let permits = Arc::new(Semaphore::new(3));
    let in_flight = Arc::new(AtomicUsize::new(0));
    let high_water = Arc::new(AtomicUsize::new(0));

    let mut handles = Vec::new();
    for _ in 0..10 {
        let permits = Arc::clone(&permits);
        let in_flight = Arc::clone(&in_flight);
        let high_water = Arc::clone(&high_water);
        handles.push(tokio::spawn(async move {
            let _permit = permits.acquire_owned().await.unwrap();
            let now = in_flight.fetch_add(1, Ordering::SeqCst) + 1;
            high_water.fetch_max(now, Ordering::SeqCst);
            tokio::time::sleep(Duration::from_millis(10)).await;
            in_flight.fetch_sub(1, Ordering::SeqCst);
        }));
    }
    for handle in handles {
        handle.await.unwrap();
    }
    println!("high water mark: {}", high_water.load(Ordering::SeqCst));
}

The example uses the current_thread runtime, so all the tasks share one thread. The semaphore limit holds on any runtime. tokio's docs list Semaphore::acquire as not cancel safe, because cancelling a call makes you lose your place in the queue.

Bounded channels and try_send

A bounded channel limits how many messages can wait in its queue. The async version is tokio::sync::mpsc::channel(n). Its send(..).await waits while the queue is full, and the sending task gives up its thread so other tasks keep running. try_send never waits. When there is no room, it returns TrySendError::Full and gives the message back, so the caller can drop it, retry it, or report the overload.

use tokio::sync::mpsc::{self, error::TrySendError};

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<u32>(2);
    for n in 1..=3 {
        match tx.try_send(n) {
            Ok(()) => println!("queued {n}"),
            Err(TrySendError::Full(v)) => println!("full, rejected {v}"),
            Err(TrySendError::Closed(v)) => println!("closed, rejected {v}"),
        }
    }
    println!("first: {:?}", rx.recv().await);
}

buffer_unordered: N futures at a time

A stream of futures can run a few at a time with buffer_unordered(n). It keeps up to n of them in progress, and it yields each result as that future finishes. Results come out in completion order, not in the order you put the futures in. The program below runs seven jobs two at a time. It adds up the results and prints the total, because the order of completion depends on timing.

use futures::{StreamExt, stream};
use std::time::Duration;

#[tokio::main]
async fn main() {
    // Seven jobs, at most two running at a time.
    let results: Vec<u64> = stream::iter(1..=7u64)
        .map(|n| async move {
            tokio::time::sleep(Duration::from_millis(10 * (8 - n))).await;
            n * n
        })
        .buffer_unordered(2)
        .collect()
        .await;
    let total: u64 = results.iter().sum();
    println!("sum of squares: {total}");
}

Retries with backoff and jitter

A retry that waits the same time on every attempt can make many clients retry at the same moment. Exponential backoff doubles the ceiling of the wait after each attempt, up to a cap. Jitter picks a random wait below that ceiling, so the clients spread out. This example uses only std. Std has no random number generator, so it uses a small linear congruential generator. That is enough to spread retries. It is not random enough for anything that must be unpredictable, such as a token. A real project would use the rand crate.

use std::time::Duration;

/// A tiny pseudo-random generator (a linear congruential generator).
/// It spreads retries out. It is not for security.
struct Jitter(u64);

impl Jitter {
    fn next_u64(&mut self) -> u64 {
        self.0 = self
            .0
            .wrapping_mul(6_364_136_223_846_793_005)
            .wrapping_add(1_442_695_040_888_963_407);
        self.0 >> 33
    }
}

/// Full jitter: wait a random time between zero and the capped, doubling delay.
fn backoff(attempt: u32, base_ms: u64, cap_ms: u64, rng: &mut Jitter) -> Duration {
    let doubled = base_ms.saturating_mul(1u64 << attempt.min(20));
    let ceiling = doubled.min(cap_ms);
    Duration::from_millis(rng.next_u64() % (ceiling + 1))
}

fn main() {
    let mut rng = Jitter(42);
    for attempt in 0..5 {
        let wait = backoff(attempt, 100, 1_000, &mut rng);
        println!("attempt {attempt}: wait {} ms", wait.as_millis());
    }
}

The ceilings here are 100, 200, 400 and 800 ms, and then 1000 ms, which is the cap. Each wait falls between zero and its ceiling. Put a timeout on each attempt with tokio::time::timeout, so one slow call cannot hold the retry loop forever.

Async closures (stable since 1.85)

A closure that returns a future has worked for a long time: |x| async move { ... }. Rust 1.85 added async closures, written async |x| .... The bound AsyncFn(u32) -> u32 names them, the way Fn names an ordinary closure. The closure below captures offset from main, like any other closure.

use std::time::Duration;

async fn apply_all<F>(f: F, items: &[u32]) -> Vec<u32>
where
    F: AsyncFn(u32) -> u32,
{
    let mut out = Vec::new();
    for &item in items {
        out.push(f(item).await);
    }
    out
}

#[tokio::main]
async fn main() {
    let offset = 10;
    let shifted = apply_all(
        async |x| {
            tokio::time::sleep(Duration::from_millis(1)).await;
            x + offset
        },
        &[1, 2, 3],
    )
    .await;
    println!("{shifted:?}");
}

Agents often write "spawn one task for each item" loops with no limit. Ask two questions when you review one: how many tasks can run at once, and where that limit lives. If the answer is "as many as there are items", the program has no backpressure. A bounded channel or a semaphore fixes that. A timeout around each piece of work keeps one slow item from holding a permit forever.

You want at most three downloads running at once, each in its own task. Which tool fits?

  1. mpsc::channel(3). A bounded channel limits the messages in its queue, not the tasks that run.
  2. Semaphore::new(3), with each task calling acquire_owned before it downloads.
  3. tokio::time::timeout set to three seconds. A timeout limits how long one call runs, not how many run together.
  4. JoinSet. It runs tasks together, and it never limits them.

The permits are the limit. A task that cannot get a permit waits, so at most three downloads are in progress at any moment. A channel limits messages, and a timeout limits time. Neither one counts running tasks.

Streams and server-sent events

An iterator gives you the next value right away, or it says there are no more. A stream is the async version. Each value may take time to arrive, so asking for the next one returns a future. The futures crate provides the Stream trait, and StreamExt::next gives you that future. The loop has a familiar shape:

use futures::{StreamExt, stream};

#[tokio::main]
async fn main() {
    let mut lines = stream::iter(["data: one", "data: two", "data: three"]);
    while let Some(line) = lines.next().await {
        println!("{line}");
    }
}

next() returns a future of an Option. The .await waits for the next item, and None means the stream has ended. Most streaming code you will read uses this while let loop.

What server-sent events are

Server-sent events (SSE) are a text format for a long HTTP response. The server keeps the response open and writes events as they happen, and the client reads each one as it arrives. Many AI APIs stream their answers this way. The format is plain lines of text with a few rules:

  • Each line is a field, written as name: value.
  • data: carries the payload. An event can have several data: lines, and the lines are joined with newlines.
  • event: names the kind of event, and id: gives it an identifier.
  • A blank line ends the event.
  • A line that starts with a colon is a comment. Servers send one now and then to keep the connection open.

This is a simplified description. The full specification has more rules, and this chapter covers the core. The parser below is enough for the examples here.

A parser that survives chunk boundaries

The network does not deliver events in neat pieces. One read may end in the middle of a line. The parser keeps the bytes it has not finished, and it decodes a line only when its newline arrives. A newline byte never appears inside a UTF-8 character, so a finished line always holds whole characters.

#[derive(Debug)]
struct Event {
    name: Option<String>,
    data: String,
}

#[derive(Default)]
struct SseParser {
    buf: Vec<u8>,
    name: Option<String>,
    data: Option<String>,
}

impl SseParser {
    /// Feed bytes from the network. Returns the events completed by this chunk.
    fn push(&mut self, chunk: &[u8]) -> Vec<Event> {
        self.buf.extend_from_slice(chunk);
        let mut events = Vec::new();
        // Only whole lines are decoded. A line ends at b'\n', which never occurs
        // inside a UTF-8 character, so a split character cannot be read wrongly.
        while let Some(end) = self.buf.iter().position(|&b| b == b'\n') {
            let line_bytes: Vec<u8> = self.buf.drain(..=end).collect();
            let line = String::from_utf8_lossy(&line_bytes[..end]).into_owned();
            if line.is_empty() {
                // A blank line ends the event.
                if let Some(data) = self.data.take() {
                    events.push(Event { name: self.name.take(), data });
                }
            } else if line.starts_with(':') {
                // A line starting with a colon is a comment. Ignore it.
            } else {
                let (field, value) = line.split_once(':').unwrap_or((line.as_str(), ""));
                let value = value.strip_prefix(' ').unwrap_or(value);
                match field {
                    "data" => match self.data.as_mut() {
                        Some(data) => {
                            data.push('\n');
                            data.push_str(value);
                        }
                        None => self.data = Some(value.to_string()),
                    },
                    "event" => self.name = Some(value.to_string()),
                    _ => {} // id, retry and unknown fields are ignored here
                }
            }
        }
        events
    }
}

fn main() {
    let mut parser = SseParser::default();
    let chunks: [&[u8]; 3] = [
        b"event: greet\ndata: hel",
        b"lo\ndata: wor",
        b"ld\n\n: a comment\n\ndata: bye\n\n",
    ];
    for chunk in chunks {
        for event in parser.push(chunk) {
            let name = event.name.as_deref().unwrap_or("(no name)");
            println!("{name}: {}", event.data.replace('\n', " + "));
        }
    }
}

The first chunk ends in the middle of the data: line. The parser keeps data: hel, and the next chunk completes it. The comment line is skipped, and the blank line after bye ends the second event. This version ignores id: and does not handle carriage returns.

Chapter 20 shows how an HTTP client gives you the chunks of a response, so you can feed them to a parser like this one.

A network read ends in the middle of a line: data: hel. What should the parser do?

  1. Treat hel as a finished event.
  2. Keep the bytes and wait for the rest, because the newline has not arrived.
  3. Drop the bytes and wait for the server to send them again.
  4. Stop with an error, because the line is incomplete.

A line ends at its newline, and a blank line ends an event. Until the newline arrives, the line is not finished, so the parser keeps the partial bytes in its buffer for the next chunk.

The mistakes everyone makes

Blocking inside async

use std::time::Duration;

async fn handler() {
    std::thread::sleep(Duration::from_secs(1));           // freezes the whole thread
    tokio::time::sleep(Duration::from_secs(1)).await;     // gives the thread back
}

The first line freezes the thread that runs the executor, so that thread can run nothing for a second. On the multi-thread runtime, other worker threads can take many of the tasks queued on it. The pool is still one thread short, and a task that cannot be moved waits the full second. On a current_thread runtime, every task waits. The second line yields to the executor. A blocking call inside async code compiles without any complaint, and it shows up later as latency under load.

Use the async version: tokio::time::sleep, tokio::fs, or an async database driver. For CPU-heavy work or a blocking library, use spawn_blocking, which runs the closure on a separate pool of threads:

#[tokio::main]
async fn main() {
    let sum = tokio::task::spawn_blocking(|| {
        // CPU-heavy work runs on a separate thread pool,
        // so the async workers keep serving other tasks.
        (1..=1_000_000u64).sum::<u64>()
    })
    .await
    .unwrap();
    println!("{sum}");
}

Holding a lock across an .await

Think first: the lock is taken and released inside one function. Will tokio::spawn accept record?

No. The guard is still alive at the .await on line 7, so the guard is held across that await. A std MutexGuard is not Send, so the future that holds it is not Send either.

async fn record(log: Arc<Mutex<Vec<&'static str>>>) {
    let mut guard = log.lock().unwrap();
    guard.push("start");
    tokio::time::sleep(Duration::from_millis(10)).await; // guard is still alive here
    guard.push("end");
}

async fn main() {
    let log = Arc::new(Mutex::new(Vec::new()));
    tokio::spawn(record(log.clone())).await.unwrap();
    println!("{:?}", log.lock().unwrap());
}

async fn record(log: Arc<Mutex<Vec<&'static str>>>) {
    {
        let mut guard = log.lock().unwrap();
        guard.push("start");
    } // the guard is dropped here, before the await
    tokio::time::sleep(Duration::from_millis(10)).await;
    log.lock().unwrap().push("end");

use std::sync::Arc;
use std::time::Duration;
use tokio::sync::Mutex;

async fn record(log: Arc<Mutex<Vec<&'static str>>>) {
    let mut guard = log.lock().await;
    guard.push("start");
    tokio::time::sleep(Duration::from_millis(10)).await;
    guard.push("end");
}

async fn main() {
    let log = Arc::new(Mutex::new(Vec::new()));
    tokio::spawn(record(log.clone())).await.unwrap();

}

Forgetting .await, and runtime shutdown

A future you never await or poll does nothing. The warning from section two is the compiler telling you that. Treat it as an error in your own code.

Also, when main returns, the runtime shuts down, and any spawned task still running is dropped. If the work matters, keep its JoinHandle and await it.

A panic inside a task: JoinError

A panic inside a spawned task does not stop the runtime. It ends that task, and the JoinHandle resolves to Err(JoinError). Call is_panic() to check for a panic, or is_cancelled() to check for an abort. If you unwrap the result, your own code panics too. If you drop the handle, nothing in your program looks at the result.

#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async {
        let values: Vec<u32> = Vec::new();
        values[0] // panics: the index is out of bounds
    });
    let err = handle.await.unwrap_err();
    println!("task panicked: {}", err.is_panic());
}
Why does Pin exist?

An async fn can hold a reference to one of its own locals across an .await. That reference points into the future's state, so the state must not move in memory once it has been polled. Pin<&mut T> is the promise that a value stays where it is, for types that are not Unpin. You rarely write Pin yourself: .await and tokio's macros pin futures for you, and Pin mostly shows up in signatures such as fn poll(self: Pin<&mut Self>, ...).

AI coding agents put async in the wrong places. They mix blocking calls into async handlers, hold a lock across an .await, call block_on inside code that is already async, and spawn tasks whose handles nobody checks. When you review agent-written async code, check four things:

  1. Is there a std::thread::sleep, a blocking file or network call, or a long CPU loop inside an async fn?
  2. Is a lock guard (MutexGuard or an RwLock guard) still alive at an .await?
  3. Does the code start a second runtime, or call block_on, inside something that already runs on one?
  4. Is every future awaited or spawned, and is every JoinHandle checked?

Practice

Seven checks. Each one applies a rule from this chapter to code you have not seen before.

What does this program print?

async fn fetch() -> u32 {
    println!("fetch runs");
    42
}

fn main() {
    println!("start");
    fetch();
    println!("end");
}
  1. start, fetch runs, end
  2. start, then end. Nothing else.
  3. fetch runs, start, end
  4. It does not compile, because a future cannot be dropped without running.

fetch() creates a future, and the future is dropped at the end of its statement, never polled. Its println! never runs. The compiler warns about exactly this. A future only does work when something polls it, and an .await needs an async context to live in.

What does this program print?

use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

fn block_on<F: Future>(fut: F) -> F::Output {
    let waker = Waker::noop();
    let mut cx = Context::from_waker(waker);
    let mut fut = pin!(fut);
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

async fn step(name: &str) -> String {
    println!("step {name}");
    name.to_uppercase()
}

async fn pipeline() -> String {
    let a = step("one").await;
    let b = step("two").await;
    format!("{a}-{b}")
}

fn main() {
    println!("{}", block_on(pipeline()));
}
  1. ONE-TWO, and nothing else.
  2. step one, then step two, then ONE-TWO.
  3. step two, then step one, then ONE-TWO.
  4. step one, then ONE-TWO, then step two.

The awaits run in order. step("one") prints and returns ONE. Then step("two") prints and returns TWO. format! joins them, and block_on drives pipeline until it is Ready. Each step is ready at once here, so nothing returns Pending.

fetch_quick is ready in 10 ms and fetch_slow needs 500 ms. What does this program print, and what happens to fetch_slow?

use std::time::Duration;

async fn fetch_quick() -> u32 {
    tokio::time::sleep(Duration::from_millis(10)).await;
    1
}

async fn fetch_slow() -> u32 {
    tokio::time::sleep(Duration::from_millis(500)).await;
    2
}

#[tokio::main]
async fn main() {
    tokio::select! {
        v = fetch_quick() => println!("quick: {v}"),
        v = fetch_slow() => println!("slow: {v}"),
    }
}
  1. quick: 1. fetch_slow keeps running in the background until it finishes.
  2. quick: 1. fetch_slow is dropped at its last .await, so it never prints.
  3. quick: 1, then slow: 2 after 500 ms.
  4. It does not compile, because select! needs every branch to finish.

The first branch to finish wins, and its handler runs. The other future is dropped right away. It is not left running, and its output is never used. Compare this with join!, which waits for every branch.

heartbeat runs on a multi-thread tokio runtime. What happens to its worker thread while std::thread::sleep runs?

use std::time::Duration;

async fn heartbeat() {
    loop {
        println!("alive");
        std::thread::sleep(Duration::from_secs(1));
    }
}
  1. Other tasks on that worker keep running, and only heartbeat pauses.
  2. That worker is blocked for the whole second and runs nothing. The other worker threads carry on, and they can take many of the tasks queued behind it.
  3. tokio moves heartbeat to a new thread, so nothing else is affected.
  4. It is a compile error, because async code cannot call std::thread::sleep.

std::thread::sleep parks the operating system thread. The executor cannot switch tasks on that thread while it is parked, and one worker is lost for the whole second. Use tokio::time::sleep(...).await instead, which hands the thread back to the executor until the timer fires.

Fill in the two blanks, so fetch_user is an async function and greet waits for its result.

use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

fn block_on<F: Future>(fut: F) -> F::Output {
    let waker = Waker::noop();
    let mut cx = Context::from_waker(waker);
    let mut fut = pin!(fut);
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

[[async]] fn fetch_user() -> u32 {
    println!("fetching user");
    7
}

async fn greet() -> String {
    let id = fetch_user()[[.await]];
    println!("got id {id}");
    format!("hello, user {id}")
}

fn main() {
    let msg = block_on(greet());
    println!("{msg}");
}

Only an async function can use .await. Without async, fetch_user returns a plain u32, and .await on a u32 does not compile. Once the function is async, fetch_user() returns a future, and .await polls it to get the u32.

  1. The executor calls poll on the task.
  2. The future starts its I/O and gives its waker to the I/O source.
  3. The future returns Poll::Pending, and the executor parks the task.
  4. The I/O completes, and the source calls wake() on the stored waker.
  5. The executor calls poll on the task again.
  6. The future returns Poll::Ready with its output.

The waker has to be registered before Pending is returned. If it were not, step 4 would have nowhere to send its wake(), and the task would never be polled again.

  • the Future trait
  • tokio::join!
  • tokio::select!
  • tokio::time::sleep(duration)
  • the executor, such as tokio's runtime

The matches are close, not identical. A JavaScript promise starts running as soon as you create it. A Rust future does nothing until something polls it. Also, Promise.race leaves the losing promises running, while select! drops the losing futures.

Recap

Waiting, not working

  • Async is for work that waits. Many waiting tasks cost saved state, not threads. CPU-heavy work still needs threads or rayon.
  • An async fn returns a future. Nothing runs until something polls it: an .await in another async function, or an executor.
  • poll returns Ready(value) or Pending. Pending means the future gave its waker to whatever it waits on, and it will be polled again after wake().
  • .await polls the inner future, and pauses the current one whenever that future returns Pending.
  • The executor, such as tokio's runtime, is the Waiter. It polls ready tasks, one step at a time.
  • tokio::spawn needs Send + 'static. join! waits for all branches. select! takes the first and drops the rest. Dropping a future cancels it at its last .await.
  • Never block a worker thread with std::thread::sleep, heavy CPU work or blocking I/O. Use the async version, or spawn_blocking.
  • Never hold a std MutexGuard across an .await. Drop it first, or use tokio::sync::Mutex.
  • Dropping a future cancels it at its last .await. A future is cancel safe when dropping it loses nothing. tokio's recv is cancel safe, and read_exact is not. Shut down with a CancellationToken branch, and put biased; first so shutdown wins.
  • A Semaphore limits how many tasks work at once. A bounded channel makes a full sender wait, which is backpressure. buffer_unordered(n) keeps at most n futures from a stream in progress.
  • A Stream is an async iterator. A server-sent event is a text message made of data: lines that ends with a blank line, and it can arrive split across chunks.
  • A JoinError means the task panicked or was aborted. Check it, or unwrap it and let your own code panic too.
Explain it back: a PHP colleague asks how one async thread can serve thousands of connections. What do you say in three sentences?

One good answer: "A PHP worker is busy from the start of a request to the end, including the time it spends waiting for the database. A Rust task that is waiting is not running on a thread at all. It is a saved state that says where to resume, and its future returns Pending while the I/O is in flight. When the data arrives, the I/O source wakes the task, and the thread that polls it does the next step."

If your version said waiting costs saved state, not a thread, and the thread is free to run other tasks, you have the core idea. Add that it only helps when most of the time is waiting, and you have the limit too.
