Macros: code that writes code

You have called macros since your first program. println!, vec! and format! all end in !, and that bang is the signal. A macro is not a function call. The compiler expands it early, before it type-checks anything. The macro replaces the tokens you wrote with other tokens, and then the compiler checks the result as if you had typed it yourself.

That is why println! can check your format string when you compile. A function receives values, so it has to take a fixed number of arguments with fixed types. A macro receives the raw tokens, so it can accept any number of arguments and any syntax its author allows.

Laravel's Macroable trait adds methods at runtime, as in Collection::macro('avg', ...). The program is different while it runs. A Rust macro changes the source before the binary exists, and the result is fixed at build time. The nearest PHP idea is a code generator that writes .php files before you deploy.

What does this program print?

macro_rules! square {
    ($x:expr) => {
        $x * $x
    };
}

fn main() {
    let n = square!(3 + 1);
    println!("{n}");
}
  1. 7
  2. 16
  3. 4
  4. It doesn't compile. A macro can't do arithmetic.

The fragment $x:expr captures 3 + 1 as one complete expression, so the expansion is (3 + 1) * (3 + 1), which is 16. The grouping survives because the macro works on syntax, not on text.

A C preprocessor macro pastes text. The same mistake there gives 3 + 1 * 3 + 1, which is 7. That bug is why Rust macros parse their input before they substitute it.

Matchers, fragments and repetition

A macro_rules! macro is a list of rules. Each rule has a matcher on the left and a transcriber on the right. The compiler tries the rules from top to bottom and uses the first one that matches. Inside a matcher, a name with a fragment specifier captures a piece of your input:

FragmentMatchesExamples
exprone expression3 + 1, "ana", f(x)
identone identifiertotal, Point
tyone typeVec<u8>, &str
literalone literal value42, "hi", true
ttone token tree: a single token, or a whole group in (), [] or {}+, (a, b), { x }

There are more specifiers, such as pat, block and path, but these five cover most of the macros you will read.

A repetition $( ... ),* matches the pattern inside it zero or more times, with a comma between matches. + means one or more, and ? means zero or one. Real code often ends a list with a comma, so the idiom $(,)? accepts one optional trailing comma. Practice has a quiz on what goes wrong without it.

Macros also keep their own local variables to themselves. A let inside the macro body cannot collide with a name at the call site. This is called hygiene, and it is why this example prints 20:

macro_rules! double_it {
    ($e:expr) => {{
        let x = 2;
        $e * x
    }};
}

fn main() {
    let x = 10;
    println!("{}", double_it!(x));
}

The x inside the macro is a different x from yours. Without hygiene, the macro's let x = 2; would shadow your x, and the answer would be 4.

Build hashmap! one step at a time

Start with one pair. The matcher captures a key and a value, and the transcriber builds a HashMap and inserts the pair. The doubled braces matter. The outer pair belongs to macro_rules!. The inner pair makes a block, which is an expression, and the block keeps map out of the caller's scope.

macro_rules! hashmap {
    ($key:expr => $value:expr) => {{
        let mut map = std::collections::HashMap::new();
        map.insert($key, $value);
        map
    }};
}

fn main() {
    let one = hashmap! { "ana" => 3 };
    println!("{}", one["ana"]);
}

Now accept any number of pairs. The matcher's $( ... ),* captures a list of pairs, and the transcriber's $( map.insert($key, $value); )* repeats its body once for each pair. The output is sorted, and that is deliberate.

macro_rules! hashmap {
    ($( $key:expr => $value:expr ),*) => {{
        let mut map = std::collections::HashMap::new();
        $( map.insert($key, $value); )*
        map
    }};
}

fn main() {
    let scores = hashmap! { "ana" => 3, "bo" => 5 };
    let mut keys: Vec<_> = scores.iter().collect();
    keys.sort();
    for (name, score) in keys {
        println!("{name}: {score}");
    }
}

Finish with the trailing comma. The matcher gains $(,)?, and the rest is unchanged. A HashMap iterates in an order that can change from one run to the next, so a program that prints a map without sorting can pass once and fail the next time.

macro_rules! hashmap {
    ($( $key:expr => $value:expr ),* $(,)?) => {{
        let mut map = std::collections::HashMap::new();
        $( map.insert($key, $value); )*
        map
    }};
}

fn main() {
    let scores = hashmap! { "ana" => 3, "bo" => 5, };
    let mut keys: Vec<_> = scores.iter().collect();
    keys.sort();
    for (name, score) in keys {
        println!("{name}: {score}");
    }
}

When not to write a macro

Write a function unless you can name a reason it cannot do the job. A function is easier to read, its errors name the types involved, and every editor can complete it. Reach for a macro when:

  • the input is syntax rather than a value: a field name, a type, or a whole struct or impl;
  • the number of arguments varies, as it does with vec! or hashmap!;
  • you need the compiler to check a literal, as println! checks its format string.

An error inside a macro points at the expansion, which you may never have looked at. If you cannot read the expansion, you cannot debug the macro.

Procedural macros: programs that rewrite tokens

A procedural macro is a Rust function that runs during the build. It receives a stream of tokens and returns a new stream, and the compiler puts that result where the macro was. Procedural macros must live in their own crate, marked proc-macro = true. There are three kinds, and you have met them already:

KindWritten asCrateWhat it does
Derive#[derive(Serialize)]serdeWrites an impl for the type below it.
Attribute#[tokio::main]tokioRewrites the item it sits on.
Function-likesqlx::query!("...")sqlxLooks like a call and returns code. sqlx checks the SQL against a real database schema when the program compiles.

A procedural macro is a program that the compiler runs on your machine, during every build. Treat a macro crate like any other dependency: check what it does, and pin the version you use.

unsafe: the five superpowers



unsafe is not a switch that turns Rust off. It is a promise you make about one block, and it unlocks exactly five operations that the compiler cannot check for you:






  
OperationExampleWhy the compiler can't check it

  
    
Dereference a raw pointer*pThe address might be null, dangling or misaligned.

    
Call an unsafe fnabs(-7) from CThe function's rules depend on facts the compiler can't see.

    
Read or write a static mutCOUNTER = 5;Any code can touch a global at any time.

    
Implement an unsafe traitunsafe impl Send for Handle {}The type has to keep a promise the compiler can't verify.

    
Read a field of a unionu.iThe bytes may not be a valid value for that field's type.

  






Everything else in an unsafe block is ordinary Rust. The borrow checker still runs, and so does the type checker. Predict before you read the explanation.




  
Does this compile?

  
fn main() {
    let x = 5;
    let p = &x as *const i32;
    let y = *p;
    println!("{y}");
}

  
    
    
  1. Yes. A raw pointer is only an address, and reading an address is safe.
    2. 
    
  2. No. Dereferencing p is one of the five operations, so it needs an unsafe block. This is error E0133.
    3. 
    
  3. No. Creating a raw pointer with as needs an unsafe block.
    4. 
  

  

    
&x as *const i32 is safe. Making a raw pointer is harmless, so it never needs unsafe. Reading through the pointer is the dangerous step, and the compiler points at the *p.

  





Keep the creation outside the block and the dereference inside it:



fn main() {
    let mut n = 10;
    let p = &mut n as *mut i32;   // safe: creating a raw pointer
    unsafe {
        *p += 5;                  // unsafe: dereferencing it
    }
    println!("{n}");
}



Every unsafe block explains itself



A reviewer should not need the rest of the program to check an unsafe block. So every block gets a // SAFETY: comment that names the invariant it depends on. The comment is a claim, and a reviewer can check the claim.



fn first_or(v: &[i32], default: i32) -> i32 {
    if v.is_empty() {
        return default;
    }
    // SAFETY: the check above proves `v` has at least one element,
    // so index 0 is in bounds.
    unsafe { *v.get_unchecked(0) }
}

fn main() {
    println!("{}", first_or(&[4, 9], -1));
    println!("{}", first_or(&[], -1));
}



The comment proves the one thing the compiler could not check here: the index is in bounds. In real code you would write v[0] or v.first(), and the bounds check those carry costs little. Reach for get_unchecked only when a measurement says the check matters, and let the SAFETY comment be the proof.



Comments can be wrong, so test the code too. Miri is an interpreter for Rust programs that runs your tests and reports many kinds of undefined behavior it sees, such as out-of-bounds access, use after free and misaligned pointers. Run it with cargo +nightly miri test. It is slow, so point it at the tests for the code that uses unsafe.



Calling C: the everyday reason



The most common reason to write unsafe code is to call a C library. The C standard library's abs is a good first example:



unsafe extern "C" {
    // Unsafe to call: the compiler can't check C's preconditions for us.
    fn abs(x: i32) -> i32;
}

fn main() {
    // SAFETY: abs is in the C standard library that Rust links on every
    // platform, and -7 is a valid argument.
    let n = unsafe { abs(-7) };
    println!("{n}");
}



Since edition 2024, an extern block must be marked unsafe extern. Here is the older form, and the error it now produces:



extern "C" {
    fn abs(x: i32) -> i32;
}

fn main() {
    let n = unsafe { abs(-7) };
    println!("{n}");
}

Inside an unsafe extern block, each function is unsafe to call. You can mark one safe fn if you accept responsibility for its contract. Be careful with that choice.

Performance: measure first



Rust is fast by default, and the fastest code is usually code that does less work. Slow programs rarely hide their cost in a clever part. The cost is in a clone inside a loop, a String built one piece at a time, or a query run once per row. You find those with a measurement, not a hunch.



Always measure a release build. cargo run builds a debug binary, which has no optimizations and extra checks, so its timings say little about the program you ship. Build with cargo build --release, and time the binary that lands in target/release/.



The release profile



The release profile lives in Cargo.toml. Cargo reads it only from the root of a workspace, and it applies to every dependency as well:



[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
panic = "abort"

A function is slow. What do you do first?

  
    
    
  1. Rewrite the hot loop with unsafe and raw pointers.
    2. 
    
  2. Build in release mode, reproduce the slow case, and profile it.
    3. 
    
  3. Add threads, so the work runs in parallel.
    4.

    5. 
  

  

    
Without a measurement you are guessing, and guesses about speed are often wrong. Unsafe code and threads add complexity, and threads add overhead. Recursion is not faster in general.

  





Waste that allocates



Most allocation waste comes from a few habits:



    
  
  • Cloning to satisfy the borrow checker. A clone() inside a loop allocates on every pass.
    • 
  
  • Calling to_string() on each item in a loop when a &str would do.
    • 
  
  • Building a String with format! for each line, then copying it into a bigger one. Write into one buffer instead, and reuse that buffer across passes: clear() empties a String but keeps its capacity, so the next pass doesn't allocate again.
    • 
  
  • Collecting into a Vec only to loop over it again. Chain the iterators.
    • 
  
  • Growing a Vec or String without a size hint. with_capacity allocates once.
    • 
  
  • Taking String or Vec<T> parameters where &str or &[T] would do. Every caller then has to allocate before it can call you.
    • 




Here is the format! habit fixed. writeln! writes into one buffer, and with_capacity sizes that buffer once:



use std::fmt::Write;

fn report(rows: &[(&str, u32)]) -> Result<String, std::fmt::Error> {
    let mut out = String::with_capacity(rows.len() * 16);
    for (name, n) in rows {
        writeln!(out, "{name}: {n}")?;
    }
    Ok(out)
}

fn main() {
    let rows = [("ana", 3), ("bo", 5)];
    print!("{}", report(&rows).unwrap());
}



writeln! works on any type that implements fmt::Write, and String does. The function returns a Result because the write can fail in principle, and the ? keeps that visible. The buffer is sized once, using the row count as a rough guess.



Measure, then change




  
    
    
  1. Reproduce the slow case in a release build, with realistic input.
    2. 
    
  2. Profile it to find the hot code.
    3. 
    
  3. Change one thing.
    4. 
    
  4. Measure again on the same input.
    5. 
    
  5. Keep the change if the number moved. Otherwise revert it.
    6. 
  

  

    
Profiling comes before any change, because the hot code is rarely where you expect it. One change at a time means that when the number moves, you know which change moved it. The same input keeps the comparison honest.

  






  
Agents tend to optimize by guessing. They add unsafe, add a cache, or swap in a clever data structure, then say the code is faster. Ask what they measured, and on which input. If the answer is nothing, the change is a guess, and you can review it like one.









Idioms that mark expert code



An idiom is a shape of code that experienced Rust developers reach for again and again, because it prevents a specific bug. Code that uses them reads like Rust. Code that doesn't often compiles and still carries the bug.






  
IdiomThe bug it prevents

  
    
NewtypeA value of the right type with the wrong meaning, such as an unchecked string used as an email address.

    
BuilderSettings that are half applied, or a value that changes after it was built.

    
TypestateA method called at the wrong moment, such as sending a request twice.

Newtype: give a value a meaning



A newtype wraps one value in a struct of its own. Email(String) is a different type from String, so a function that wants an Email can't be handed any string by accident. Make the field private, and make the only constructor validate. Then every Email you can hold has passed the check.



#[derive(Debug)]
struct Email(String);

#[derive(Debug)]
enum EmailError {
    Missing,
    NoAt,
}

impl Email {
    fn parse(raw: &str) -> Result<Self, EmailError> {
        let raw = raw.trim();
        if raw.is_empty() {
            return Err(EmailError::Missing);
        }
        if !raw.contains('@') {
            return Err(EmailError::NoAt);
        }
        Ok(Email(raw.to_lowercase()))
    }

    fn as_str(&self) -> &str {
        &self.0
    }
}

fn send_welcome(to: &Email) {
    println!("welcome, {}", to.as_str());
}

fn main() {
    match Email::parse("  Ana@Example.test ") {
        Ok(email) => send_welcome(&email),
        Err(e) => println!("rejected: {e:?}"),
    }
    println!("{:?}", Email::parse("no-at-sign"));
}




  
Privacy in Rust works per module. This example keeps everything in one module, so main could still write Email("x".into()) directly. In real code, put the newtype in its own module so the constructor really is the only way in.





Builder and typestate



A builder collects settings one call at a time and produces the finished value at the end. Each setter takes self and returns it, so the calls chain. build consumes the builder, so the finished value can't change later through the builder.



#[derive(Debug)]
struct Request {
    url: String,
    timeout_secs: u64,
    retries: u32,
}

struct RequestBuilder {
    url: String,
    timeout_secs: u64,
    retries: u32,
}

impl RequestBuilder {
    fn new(url: impl Into<String>) -> Self {
        RequestBuilder {
            url: url.into(),
            timeout_secs: 30,
            retries: 0,
        }
    }

    fn timeout_secs(mut self, secs: u64) -> Self {
        self.timeout_secs = secs;
        self
    }

    fn retries(mut self, n: u32) -> Self {
        self.retries = n;
        self
    }

    fn build(self) -> Request {
        Request {
            url: self.url,
            timeout_secs: self.timeout_secs,
            retries: self.retries,
        }
    }
}

fn main() {
    let req = RequestBuilder::new("https://example.test")
        .timeout_secs(5)
        .retries(2)
        .build();
    println!("{req:?}");
}




  
A PHP fluent setter usually ends with return $this, so every call changes the same shared object. PHP 8.5 also offers an immutable style. clone($this, [...]) copies the object with the new values, and the original stays as it was.





final readonly class RequestOptions
{
    public function __construct(public int $retries = 0, public int $timeout = 30) {}

    public function withRetries(int $retries): static
    {
        return clone($this, ['retries' => $retries]);
    }
}



A Rust builder method takes self by value, so the old value is moved into the call. A PHP caller can still read $base after withRetries(), because the original object is still there. In Rust, let more = base.retries(2); moves base. A later use of base is error E0382, and the compiler reports it before the program runs.



Typestate goes one step further. Sometimes the state of a value decides which methods make sense. A request that hasn't been sent has no response to read. Typestate puts that state in the type, using a marker type for each state:



use std::marker::PhantomData;

struct Unsent;
struct Sent;

struct Request<State> {
    url: String,
    _state: PhantomData<State>,
}

impl Request<Unsent> {
    fn new(url: &str) -> Self {
        Request { url: url.to_string(), _state: PhantomData }
    }

    fn send(self) -> Request<Sent> {
        println!("sending {}", self.url);
        Request { url: self.url, _state: PhantomData }
    }
}

impl Request<Sent> {
    fn status(&self) -> u16 {
        200
    }
}

fn main() {
    let req = Request::new("https://example.test/api");
    let sent = req.send();
    println!("status {}", sent.status());
}



send takes self by value and returns a Request<Sent>. The unsent value is gone after the call, so it can't be sent twice. status exists only for Request<Sent>. Practice has a quiz on what happens when you call send on the sent value.



RAII guards: cleanup you can't forget



RAII stands for resource acquisition is initialization. The rule behind the name is simple: a value that holds a resource releases it in its Drop. Chapter 06 introduced Drop. A guard puts that pattern to work. It does its cleanup on every exit path, including an early return and a ?.



struct Transaction {
    committed: bool,
}

impl Transaction {
    fn begin() -> Self {
        println!("BEGIN");
        Transaction { committed: false }
    }

    fn commit(mut self) {
        self.committed = true;
        println!("COMMIT");
    }
}

impl Drop for Transaction {
    fn drop(&mut self) {
        if !self.committed {
            println!("ROLLBACK");
        }
    }
}

fn main() {
    let tx = Transaction::begin();
    tx.commit();
    let _tx2 = Transaction::begin();
    println!("work is done, but we forgot to commit");
}



The second transaction was never committed. It rolls back at the end of main, when its scope ends, and nothing had to remember to do that.




  
DB::transaction(function () use ($data) {
    $order = Order::create($data);
    throw new PaymentDeclined();  // rolls back
});

  
fn place_order(card_ok: bool) -> Result<(), String> {
    let tx = Transaction::begin();
    if !card_ok {
        return Err("card declined".into());  // tx drops here: ROLLBACK
    }
    tx.commit();
    Ok(())
}

  
Laravel's transaction is a callback. The framework wraps your closure and rolls back if it throws. The Rust guard needs no callback: the rollback happens when the scope ends, so every return path is covered, including ones you add later. The guard only works while it stays in a variable. let _ = Transaction::begin(); drops it at once, which is the Chapter 06 trap again.





From and ?: converting errors



? on an error calls From::from to turn it into the function's error type. Implement From once, and every ? in that function converts for you.



#[derive(Debug)]
enum AppError {
    Parse(std::num::ParseIntError),
}

impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> Self {
        AppError::Parse(e)
    }
}

impl AppError {
    fn reason(&self) -> String {
        match self {
            AppError::Parse(e) => format!("bad port: {e}"),
        }
    }
}

fn read_port(s: &str) -> Result<u16, AppError> {
    let port: u16 = s.trim().parse()?;
    Ok(port)
}

fn main() {
    println!("{:?}", read_port(" 8080 "));
    match read_port("http") {
        Ok(port) => println!("port {port}"),
        Err(e) => println!("{}", e.reason()),
    }
}



The parse call returns a ParseIntError, and the function returns an AppError. The ? calls AppError::from in between. That call is the whole conversion, and you can see it in the source.



Parameters that accept both



Take impl Into<String> when you need to own the text, and impl AsRef<str> when you only read it. Both accept a &str and a String, so callers don't have to convert before they call you.



fn label(name: impl Into<String>) -> String {
    let name: String = name.into();
    format!("user:{name}")
}

fn shout(text: impl AsRef<str>) -> String {
    text.as_ref().to_uppercase()
}

fn main() {
    println!("{}", label("ana"));
    println!("{}", label(String::from("bo")));
    println!("{}", shout("hi"));
    println!("{}", shout(String::from("there")));
}



Let the compiler find every place to change



Two attributes and one habit do the same job. #[must_use] asks for a warning when a value is ignored. #[non_exhaustive] lets a library add an enum variant later without breaking its callers, because callers must keep a _ arm. Inside the crate that defines the enum, that attribute has no effect. The habit is to leave match arms unwritten as a wildcard, so the compiler lists the places that need the new case.




  
Does this compile, and does rustc say anything about it?

  
fn save(n: u32) -> Result<(), String> {
    if n > 0 { Ok(()) } else { Err("empty".to_string()) }
}

fn main() {
    save(3);
}

  
    
    
  1. No. A Result can be dropped without a word.
    2. 
    
  2. Yes, with no warning. Ignoring a value is allowed.
    3. 
    
  3. Yes, with a warning. The Result is unused, and rustc says it must be used.
    4. 
  

  

    
The standard library marks Result as #[must_use], so ignoring one produces a warning that it may hold an error. Handle it with ?, match on it, or write let _ = save(3); when dropping it is truly intended. The underscore makes the decision visible in the code.

Error layering: a typed library, a flexible app



A library should return an error type its callers can match on. An application mostly needs to report errors with context. Two crates cover those jobs, and most Rust projects use one or both. thiserror writes the boilerplate for a typed error. anyhow gives you one error type that carries context. Libraries use thiserror, and applications use anyhow.



With thiserror = "2" in Cargo.toml, a library error looks like this:



#[derive(Debug, thiserror::Error)]
pub enum ConfigError {
    #[error("missing key `{0}`")]
    Missing(String),
    #[error("`{0}` must be a number")]
    NotNumber(String, #[source] std::num::ParseIntError),
}

fn port(raw: Option<&str>) -> Result<u16, ConfigError> {
    let raw = raw.ok_or_else(|| ConfigError::Missing("PORT".to_string()))?;
    raw.parse::<u16>()
        .map_err(|e| ConfigError::NotNumber("PORT".to_string(), e))
}

fn main() {
    println!("{:?}", port(Some("8080")));
    println!("{:?}", port(None));
    match port(Some("http")) {
        Ok(p) => println!("port {p}"),
        Err(e) => println!("error: {e}"),
    }
}



An application with anyhow = "1" can skip the enum. It adds context at each step, and main reports the whole chain:



use anyhow::Context;

fn load_port(raw: &str) -> anyhow::Result<u16> {
    let port = raw.trim().parse::<u16>().context("reading PORT")?;
    Ok(port)
}

fn main() -> anyhow::Result<()> {
    let port = load_port(" 8080 ")?;
    println!("listening on {port}");
    load_port("http")?;
    Ok(())
}




  
Agents often pick Box<dyn Error> for every function, because it compiles everywhere. In a library, that choice takes away the caller's ability to match on what went wrong. When you review a library's error type, ask which cases a caller would need to handle, and write those as variants.

Find the smells



Here is a function an agent wrote. It compiles, and it prints the right answer for the input it was given. Read it once, and then open the think block to check what you found.



#[derive(Clone)]
struct User {
    name: String,
    status: String,
    age: String,
}

fn active_adults(users: &Vec<User>) -> Vec<String> {
    let copy = users.clone();
    let mut names = Vec::new();
    for u in copy.iter() {
        if u.status == "active" {
            let age: u32 = u.age.parse().unwrap();
            if age >= 18 {
                names.push(u.name.clone());
            }
        }
    }
    names
}

fn main() {
    let users = vec![
        User { name: "ana".into(), status: "active".into(), age: "34".into() },
        User { name: "bo".into(), status: "banned".into(), age: "40".into() },
        User { name: "cy".into(), status: "active".into(), age: "16".into() },
        User { name: "di".into(), status: "active".into(), age: "22".into() },
    ];
    println!("{:?}", active_adults(&users));
}




  Four smells. Did you find them before you looked?
  

    
The parameter is &Vec<User>, which forces callers to own a Vec. The function also clones the entire list just to read it. The status is a string, so "actve" would compile and quietly match nothing. And unwrap() on the age means one bad value from the caller panics the whole program.

  





Here is the reviewed version. It returns the same output, ["ana", "di"], from a design where the bad input is caught when it enters.



#[derive(Debug, Clone, Copy, PartialEq)]
enum Status {
    Active,
    Banned,
}

struct User {
    name: String,
    status: Status,
    age: u32,
}

fn active_adults(users: &[User]) -> Vec<&str> {
    users
        .iter()
        .filter(|u| u.status == Status::Active && u.age >= 18)
        .map(|u| u.name.as_str())
        .collect()
}

fn main() {
    let users = vec![
        User { name: "ana".into(), status: Status::Active, age: 34 },
        User { name: "bo".into(), status: Status::Banned, age: 40 },
        User { name: "cy".into(), status: Status::Active, age: 16 },
        User { name: "di".into(), status: Status::Active, age: 22 },
    ];
    println!("{:?}", active_adults(&users));
}



What changed, in order of importance. The age is parsed once, where the input enters, so this function has nothing left to panic on. The status is an enum, so a typo is a compile error. The parameter is a slice, so any caller can use it. And the function borrows the names instead of cloning them.



The last change alters the signature. A caller that stored the result as Vec<String> must change too, and that is part of the review. A reviewer checks the callers of a changed signature, not only the function.



Give the agent a rulebook



The fastest review is the one that doesn't need to happen, because the agent followed the rules from the start. Put these in CLAUDE.md or AGENTS.md at the repository root. Agents read those files before they start, and you can review the result against the same list.



## Rust workflow
Before you report a task as finished:
1. Run `cargo fmt`.
2. Run `cargo clippy --all-targets -- -D warnings` and fix every warning.
3. Run `cargo test`.

## Rules
- No `unwrap()` or `expect()` outside tests and `main`. Return a `Result` and use `?`.
- Take `&str` and `&[T]` parameters, not `&String` or `&Vec<T>`. Borrow unless you need ownership.
- Library errors are typed enums (`thiserror`). Application code may use `anyhow`.
- No blocking calls inside `async fn`. Use the async version, or `spawn_blocking`.
- Give every new dependency an explicit major version in Cargo.toml, and say why it is needed.
- Every `unsafe` block has a `// SAFETY:` comment that states the invariant.
- Model states with enums and newtypes, not strings and bare integers.
- Don't ignore a `Result`. Handle it, pass it up, or explain in a comment why dropping it is safe.



Practice these reviews in the Agent Code Review Dojo.



The same review applies to PHP written by an agent. PHP 8.5 can flag a discarded return value with #[\NoDiscard], and the flag appears at runtime, on the line that runs:




  
#[\NoDiscard('check the save result')]
function save(string $name): bool
{
    return $name !== '';
}

save('ana');        // warns at runtime
(void) save('bo');  // the cast says: ignored on purpose

  
fn save(name: &str) -> Result<(), String> {
    if name.is_empty() {
        Err("empty name".into())
    } else {
        Ok(())
    }
}

fn main() {
    let _ = save("bo");  // the binding says: ignored on purpose
    println!("done");
}

  
Result is #[must_use], so rustc warns at compile time when a call drops one without let _. The rulebook above turns warnings into errors. The PHP warning appears only when the line runs, so a path that no test reaches stays silent.






  
PHPStan at its highest level and Psalm catch many type mistakes, but only when someone runs them. PHP runs code that they reject, unless your pipeline stops on their output. PHP has a fix for stringly typed states too, a backed enum. A PHP enum case carries no data. A Rust variant can carry a reason, as in Banned { reason: String }, and a PHP case cannot.






  
Never approve code only because it compiles and the tests pass. An agent can write a test that asserts whatever the code happens to do. For each test, ask whether it would fail if the code were wrong. A test that can't fail is not a check.

The watch loop



Watch mode has two jobs. It waits for a line you type, and it notices when a file changes. A blocking read can't do both at once. So main.rs puts stdin on its own thread, sends each line through a channel, and makes the main loop wait on that channel with a 300 ms timeout. When the wait times out, the loop checks the quest file's modified time, and it recompiles only if the time changed.



Here is the same pattern as a standalone program. It reads three fixed lines instead of the keyboard, so it finishes without any typing:



use std::sync::mpsc::{self, RecvTimeoutError};
use std::thread;
use std::time::Duration;

enum Input {
    Line(String),
    Closed,
}

fn main() {
    let (tx, rx) = mpsc::channel::<Input>();

    // The Forge reads io::stdin() on this thread. This demo sends fixed
    // lines so the example finishes without waiting for a keyboard.
    thread::spawn(move || {
        for line in ["check", "hint", "quit"] {
            thread::sleep(Duration::from_millis(50));
            if tx.send(Input::Line(line.to_string())).is_err() {
                return;
            }
        }
        let _ = tx.send(Input::Closed);
    });

    loop {
        match rx.recv_timeout(Duration::from_millis(300)) {
            Ok(Input::Line(line)) => {
                println!("got: {line}");
                if line == "quit" {
                    break;
                }
            }
            Ok(Input::Closed) => break,
            // Nothing typed for 300 ms. The Forge checks file timestamps here.
            Err(RecvTimeoutError::Timeout) => {}
            Err(RecvTimeoutError::Disconnected) => break,
        }
    }
    println!("done");
}



The move closure takes ownership of tx. thread::spawn requires that, because the thread can outlive the function that started it. The receiver stays with the main loop. recv_timeout returns Timeout when nothing has arrived, and Disconnected when every sender is gone.




  Read the real watch loop. Three questions to answer first
  

    
    
      
  1. In watch, why does the spawned closure need move? Answer: the thread may outlive the function that started it, so the closure must own tx.
    2. 
      
  2. Why does the loop call rx.recv_timeout and not rx.recv? Answer: recv blocks until a line arrives, so the loop could never check the file in the meantime.
    3. 
      
  3. What happens once stdin closes? Answer: stdin_open becomes false, and the loop switches from receiving to sleeping. File saves are still noticed, because the loop keeps checking the modified time.
    4. 
    

  





The timeout



A quest with an endless loop must not hang the Forge. runner.rs starts the test binary, then checks it in a loop. try_wait returns straight away, with nothing, while the child is still running. After 20 seconds the loop kills the child. wait would block until the child exited, so it could never give up.



    let started = Instant::now();
    let status = loop {
        if let Some(status) = child.try_wait()? {
            break Some(status);
        }
        if started.elapsed() > TEST_TIMEOUT {
            let _ = child.kill();
            let _ = child.wait();
            break None;
        }
        thread::sleep(Duration::from_millis(20));
    };



The same file reads the child's stdout and stderr on helper threads. A pipe holds only a small buffer. A test that prints a lot, with nobody reading, blocks on its next write and never exits, and the Forge then waits out the whole timeout. Reading on separate threads keeps the buffer empty.



The file's header comment explains one more choice. The Forge calls rustc directly instead of Cargo, because each quest is a single file, and one broken quest can never stop another from building. Read runner.rs from the top to see the other half of that decision.



Look for the newer syntax as well. The Forge uses let ... else, matches!, and let chains such as if let Some(minor) = minor && minor < 85. Let chains are the newest of these, so they are worth looking up in the Rust reference.

Recap




  
What to carry out of this chapter

  
    
    
  • A macro_rules! macro matches syntax with fragments such as expr, ident, ty and tt, and repeats with $( ... ),*. Write a function first, and reach for a macro when the input is syntax.
    • 
    
  • A procedural macro is a program that rewrites tokens. Derive adds impls, attribute macros rewrite the item they sit on, and function-like macros look like calls.
    • 
    
  • unsafe unlocks five operations: dereferencing raw pointers, calling unsafe functions, using static mut, implementing unsafe traits, and reading union fields. It never turns off the borrow checker or the type checker. Every block gets a SAFETY comment.
    • 
    
  • Measure a release build, profile before you change code, and change one thing at a time.
    • 
    
  • Idioms prevent specific bugs. Newtypes guard meaning, typestate puts state in the type, RAII guards clean up on every path, and From lets ? convert errors.
    • 
    
  • Review agent code for the smells that compile: needless clones, unwrap on input, stringly typed states, ignored results, and unsafe without a reason.

  Explain it back: pick one idiom from this chapter and explain what bug it prevents.
  

    
Typestate is a good pick. A Request<Unsent> has a send method, and a Request<Sent> does not. Because send takes self, the unsent value is gone after the call, so the program can't send it twice. A status method that exists only on the sent type can't be called before the request goes out. The bug it prevents is the kind that appears only in production: a request sent twice, or a response read before it exists. The compiler catches both before the program runs.

    
A newtype answer works just as well. Email makes a string that was never validated impossible to pass where an Email is expected.
