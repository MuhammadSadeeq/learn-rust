Five jobs in one array

A PHP array does almost everything. The same value can be a list, a lookup table, a set, a queue or a stack, and the code that uses it decides which job it does. Underneath, a PHP array is an ordered hash map, which is why one type can stand in for all of them.

Rust splits those jobs into separate types. Each type makes a different promise about speed and about order. Several of these jobs can be done with more than one type, so the choice is yours to make, and a reader of your code has to be able to see it. Before you read on, guess the type for each PHP line below.

The collection you pick is a promise about cost and order.

Unpack the trench coat Pick a PHP line. Guess the Rust collection, then open it.

In PHP, the code is the only sign of what you meant. $list[] = $x; and $byId[$id] = $user; use the same syntax on the same kind of value. Nothing in the file says which one is a list and which one is a lookup table.

In Rust the type says it. Vec<i32> and HashMap<u64, User> are different types, and each one is a visible promise about how the value is used.

Question to think about: a PHP array with keys 0, 1 and 2 is a list. What changes after unset($list[1])?

The key 1 disappears, so the keys become 0 and 2. The array still holds its values in order, but its keys now have a gap, and PHP keeps the gap.

A Vec has no keys to leave gaps in. remove(1) shifts the later elements down, so index 1 then holds what used to be at index 2. The two languages agree on the values and disagree on what the position means.

Vec<T>: the list

A Vec<T> is a growable list. Its elements sit side by side in one heap buffer, the same idea as the buffer you met in Chapter 05. On the stack, the Vec itself is three numbers: a pointer to the buffer, a length and a capacity. The length counts the elements in use. The capacity counts the slots in the buffer.

There are three ways to create one. They differ only in what they allocate up front.

fn main() {
    let a: Vec<i32> = vec![];                  // a literal, empty
    let b = Vec::<i32>::new();                 // allocates nothing yet
    let c: Vec<i32> = Vec::with_capacity(10); // room for 10, length 0
    println!("{} {} {}", a.len(), b.len(), c.capacity() >= 10);
}

vec![] is a literal. Vec::new() allocates nothing until the first push. with_capacity(n) allocates the buffer now, so pushing up to n elements never has to grow it. The length is still 0 in every case. Capacity is room, and length is what is in use.

fn main() {
    let mut v = Vec::new();
    v.push(1);
    v.extend([2, 3]);
    v.insert(0, 0);
    let gone = v.remove(1);
    let last = v.pop();
    v.truncate(1);
    println!("{v:?} {gone} {last:?} {}", v.is_empty());
    v.clear();
    println!("{} {}", v.len(), v.is_empty());
}

push and pop work at the end, and they are cheap. insert and remove work at any position, but every element after that position moves one slot, to make room or to close the gap. truncate and clear drop elements from the end.

Reading one element: index or get

Indexing with v[i] gives you the element itself, and it panics if i is out of range. get(i) returns an Option, either Some(&element) or None. The caller then has to decide what a missing index means.

fn main() {
    let v = vec![1, 2, 3];
    println!("{:?}", v.get(10));
    println!("{:?}", v.get(1));
}

Now the other one. This program asks for an index that is not there, and it stops.

fn main() {
    let v = vec![1, 2, 3];
    println!("{}", v[10]);
}
thread 'main' (process id) panicked at src/main.rs:3:21:
index out of bounds: the len is 3 but the index is 10
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

A panic stops the program with a message. It is not an error value that you handle in the normal flow. Use indexing when a missing index is a bug in your code, and use get when the index comes from outside, such as a query string or a form.

Which line can't panic when i is 10 and v holds three elements?

  1. let x = v[i];
  2. let x = v.get(i);
  3. let x = v.get(i).unwrap();

get never panics. It returns None and leaves the decision to you. Calling unwrap on that None brings the panic back, so the safe form is the one that keeps the Option around until you have a plan.

Iterating: three forms, three meanings

A loop over a Vec can borrow the list, borrow it mutably, or take it. The form you write decides whether the list is still there after the loop.

fn main() {
    let mut v = vec![1, 2, 3];

    for x in &v {
        println!("{x}");
    }

    for x in &mut v {
        *x += 10;
    }
    println!("{v:?}");
}

for x in &v reads each element through a shared reference. for x in &mut v gives you a mutable reference, so *x += 10 changes the element in place. Both leave v usable afterward. The third form, for x in v, takes the vector itself, and that brings ownership back into the picture.

fn main() {
    let scores = vec![90, 75, 82];
    let mut total = 0;
    for s in scores {
        total += s;
    }
    println!("total {total}, count {}", scores.len());
}
  1. Yes. The numbers are Copy, so scores is still usable.
  2. No. The loop moved the Vec, even though each number is Copy.

Copy applies to the elements. The Vec owns a heap buffer, so the Vec itself is not Copy, which is the rule from Chapter 06. for s in scores moved it into the loop. Write for s in &scores to read the elements and keep the Vec.

Sorting, de-duplicating and searching

These are methods on the Vec itself, and they change it in place. Two rules keep them honest. dedup only removes neighbors that are equal, so sort first. binary_search needs a sorted list, or its answer means nothing.

fn main() {
    let mut v = vec![5, 3, 8, 3, 1, 8];
    v.sort();
    v.dedup();
    println!("{v:?}");
    v.retain(|&x| x != 5);
    println!("{v:?} has 8: {}", v.contains(&8));
    println!("{:?}", v.binary_search(&3));
    let front: Vec<i32> = v.drain(..2).collect();
    println!("{front:?} {v:?}");
    let mut words = vec!["pear", "fig", "banana"];
    words.sort_by_key(|w| w.len());
    println!("{words:?}");
}

retain keeps the elements that match a closure. drain(..2) removes a range and gives you the removed elements as an iterator, so you collect them if you want to keep them. sort_by_key sorts by a value you compute from each element.

Growth

When a push finds the buffer full, the Vec gets a bigger buffer, copies the elements over and frees the old one. Watch it happen on the fifth push.

Exact growth is an implementation detail, not a promise. In Rust 1.97, a vector of i32 gets room for four elements on its first push, and then it doubles: 8, 16, 32. If you know the count in advance, with_capacity means the copy never happens at all.

Ownership traps

A Vec owns its elements, and that changes what it means to take one out. In Chapter 06 you learned that moving a value gives its name away. Try to move a String out of a Vec by index, and the compiler stops you.

fn main() {
    let names = vec![String::from("Ana"), String::from("Bo")];
    let name = names[0];
    println!("{name}");
}
error[E0507]: cannot move out of index of `Vec<String>`
 --> src/main.rs:3:16
  |
3 |     let name = names[0];
  |                ^^^^^^^^ move occurs because value has type `String`, which does not implement the `Copy` trait
  |
help: consider borrowing here
  |
3 |     let name = &names[0];
  |                +
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let name = names[0].clone();
  |                        ++++++++

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0507`.

The error is E0507, and the caret points at names[0], not at the let. Rust refuses for a reason. The buffer is a row of slots, and each slot holds a String that the Vec owns. Moving names[0] out would leave a hole in that row. When the Vec is dropped, it would try to drop every slot, including the one you took. That is a double free.

The same line compiles for a Vec<i32>. An i32 is Copy, so let x = v[0]; copies the number and leaves the Vec alone. The rule only bites for elements that own heap memory.

There are five ways out. Each one says something different about what you want to happen to the element.

fn main() {
    let names = vec![String::from("Ana"), String::from("Bo")];
    let first = &names[0];
    println!("{first}");
}

Use when the code only needs to read the element. Nothing is copied and nothing leaves the Vec.

fn main() {
    let names = vec![String::from("Ana"), String::from("Bo")];
    let first = names[0].clone();
    println!("{first} {}", names.len());
}

Use when you need your own copy and the Vec must keep its element. It costs an allocation.

fn main() {
    let mut names = vec![String::from("Ana"), String::from("Bo")];
    let first = names.remove(0);
    println!("{first} {names:?}");
}

Use when the element should leave the list and the order of the rest matters. Every later element moves one slot left, so the cost is O(n).

fn main() {
    let mut names = vec![String::from("Ana"), String::from("Bo"), String::from("Cy")];
    let first = names.swap_remove(0);
    println!("{first} {names:?}");
}

Use when the element should leave the list and the order does not matter. The last element moves into the gap, so the cost is O(1) and the order changes.

fn main() {
    let mut names = vec![String::from("Ana"), String::from("Bo")];
    let first = std::mem::take(&mut names[0]);
    println!("{first} [{}] {}", names[0], names.len());
}

Use when you want the value out and something harmless left in its slot. take leaves an empty value behind, which works for any type with a Default.

One more way is for name in names. It takes every element and consumes the Vec, so use it when you are finished with the whole list.

Holding a borrow while you push

This trap comes from Chapter 07. A reference into a Vec is a borrow of its buffer. A push can need a bigger buffer, and then the old one is gone, so Rust does not let a reference live across a push.

fn main() {
    let mut scores = vec![10, 20, 30];
    let first = &scores[0];
    scores.push(40);
    println!("{first}");
}
  1. Yes. first is a copy of the number, so it doesn't hold on to scores.
  2. No. first borrows scores, and push needs a mutable borrow while that borrow is still used.
  3. No, because push can't be used on a Vec of numbers.

first is a reference into the buffer. The push may move the buffer, which would free the old one and leave first pointing at freed memory. The borrow checker refuses the program before it runs. Chapter 07 covers the rule in full.

HashMap<K, V>: the map

A HashMap finds a value from its key without scanning the others. It hashes the key to pick a bucket, then compares keys inside that bucket. Four methods cover most of the work.

use std::collections::HashMap;

fn main() {
    let mut ages: HashMap<String, u32> = HashMap::new();
    ages.insert(String::from("Ana"), 31);
    ages.insert(String::from("Bo"), 27);

    println!("{:?}", ages.get("Ana"));
    println!("{}", ages.contains_key("Cy"));
    println!("{:?}", ages.remove("Bo"));
    println!("{}", ages.len());
}

get returns an Option<&V>. Notice that it took a &str even though the keys are String. That works because String can be borrowed as a str, so the map can compare keys through the borrowed form. contains_key and remove accept a &str in the same way.

Keys and values move in. insert takes both by value, so the map owns them afterward.

use std::collections::HashMap;

fn main() {
    let mut ages: HashMap<String, u32> = HashMap::new();
    let name = String::from("Ana");
    ages.insert(name, 31);
    println!("{name} is {}", ages.len());
}
  1. Yes. insert borrows the key.
  2. No. insert takes ownership of name, so the map owns the String now.
  3. No. HashMap keys must be &str.

This is the move rule from Chapter 06, applied to a key. Clone the key if you need it after the insert: ages.insert(name.clone(), 31). The value 31 is a number, so it is copied, and only the key moves.

The order trap

PHP arrays remember the order you inserted things in. A HashMap promises no order at all. Rust seeds each map's hash with random values, so the iteration order can change from one run to the next.

use std::collections::HashMap;

fn main() {
    let mut ages = HashMap::new();
    ages.insert("ana", 31);
    ages.insert("bo", 27);
    ages.insert("cy", 44);
    for (name, age) in &ages {
        println!("{name} {age}");
    }
}

This program is valid, and it prints all three people. Run it several times and the lines can come out in a different order. If that order reaches a user, an export or a test expectation, you have a bug that shows up only some of the time. Choose a type for the job: BTreeMap for key order, or a Vec of pairs for insertion order.

Counting with the entry API

Counting is the classic map job. In PHP you read the key, add one and write it back. The entry API does the lookup once, and it says what to do when the key is missing.

use std::collections::HashMap;

fn main() {
    let text = "the cat and the hat and the bat";
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for word in text.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }

    // The map has no order, so sort the pairs before printing.
    let mut pairs: Vec<(&str, u32)> = counts.into_iter().collect();
    pairs.sort();
    for (word, n) in pairs {
        println!("{word} {n}");
    }
}

entry(word) finds the slot for the key. or_insert(0) inserts 0 if the slot is empty, and it returns a mutable reference to the value either way. The * writes through that reference. The map still has no order, so the program sorts the pairs before it prints them.

use std::collections::HashMap;

fn main() {
    let mut stock: HashMap<&str, u32> = HashMap::new();
    stock.entry("apple").and_modify(|n| *n += 1).or_insert(1);
    stock.entry("apple").and_modify(|n| *n += 1).or_insert(1);

    let pears = stock.entry("pear").or_insert_with(|| 10 * 2);
    *pears += 1;

    *stock.entry("plum").or_default() += 5;

    println!("apple {}", stock["apple"]);
    println!("pear {}", stock["pear"]);
    println!("plum {}", stock["plum"]);
}

Three more methods cover the other cases. and_modify runs only when the key exists. or_insert_with takes a closure that runs only when the key is missing, which matters when the default is expensive to build. or_default uses the value type's Default, which is 0 for numbers and an empty list for a Vec.

Sets, sorted maps, queues

These three types fill the gaps that a Vec and a HashMap leave. Each one answers a question that the other two answer badly.

HashSet: membership without values

A HashSet is a HashMap without values. Each value is stored once. insert returns whether the value was new. The set operations, intersection, union and difference, return iterators, so you collect them, and sort them when you want a stable print.

use std::collections::HashSet;

fn main() {
    let a: HashSet<i32> = [1, 2, 3, 4].into_iter().collect();
    let b: HashSet<i32> = [3, 4, 5].into_iter().collect();

    let mut both: Vec<i32> = a.intersection(&b).copied().collect();
    both.sort();
    let mut either: Vec<i32> = a.union(&b).copied().collect();
    either.sort();
    let mut only_a: Vec<i32> = a.difference(&b).copied().collect();
    only_a.sort();

    println!("both {both:?}");
    println!("either {either:?}");
    println!("only a {only_a:?}");
}
use std::collections::HashSet;

fn main() {
    let mut seen = HashSet::new();
    seen.insert(3);
    println!("{}", seen.insert(3));
}
  1. true
  2. false
  3. It panics, because the value is already in the set.

insert returns true when the value was new and false when it was already there. It never panics for a duplicate. That return value is how you de-duplicate a stream of values in a single pass.

BTreeMap: keys in order

A BTreeMap keeps its keys sorted at all times. Use it when order is part of the output, or when you need range queries. A lookup costs O(log n), where a HashMap averages O(1). That is the price of the order.

use std::collections::BTreeMap;

fn main() {
    let mut prices = BTreeMap::new();
    prices.insert("tea", 3);
    prices.insert("bread", 2);
    prices.insert("milk", 1);

    for (item, price) in &prices {
        println!("{item} {price}");
    }
    for (item, price) in prices.range("c".."n") {
        println!("in c..n: {item} {price}");
    }
}

VecDeque: a queue from both ends

A VecDeque is a double-ended queue. Pushing and popping at either end are cheap. PHP does this job with array_shift, which has to renumber the rest of the array on every call. A VecDeque keeps its elements in a ring, so taking from the front moves nothing else.

use std::collections::VecDeque;

fn main() {
    let mut jobs = VecDeque::new();
    jobs.push_back("email");
    jobs.push_back("invoice");
    jobs.push_back("report");

    while let Some(job) = jobs.pop_front() {
        println!("run {job}");
    }
}

Which collection?

Start from the operation that happens most often, not from the data. The table below is the check to run your choice against.

You needUseTypical cost
An ordered list, read and changed by positionVec<T>push and index O(1); search O(n)
A stack, last in first outVec<T>push and pop at the end, O(1) amortized
A queue, first in first outVecDeque<T>push and pop at either end, O(1) amortized
To know whether a value is present, or to remove duplicatesHashSet<T>insert and contains, O(1) on average
Find a value by its keyHashMap<K, V>get, insert and remove, O(1) on average; no order
Keys kept in sorted order, or range queriesBTreeMap<K, V>O(log n) for each operation; always sorted
A few key-value pairs, in the order you wrote themVec<(K, V)>scan O(n) by key; keeps the order

You keep the last 100 log lines, newest first. New lines arrive at one end, and the oldest line leaves from the other. Which type fits best?

  1. Vec<String>, and remove(0) when it is full
  2. HashMap<usize, String>
  3. VecDeque<String>

Adding and removing at the two ends are both cheap in a VecDeque. A Vec with remove(0) would shift all 100 lines on every new entry. A HashMap would keep the lines but say nothing about which one is oldest.

Agents often reach for a Vec and call contains inside a loop. When both lists grow with the input, that is O(n·m), which is O(n²) in the worst case. The code is correct, and it gets slow as the data grows. The review question is the one from the table: which operation happens most? If it is membership, build a HashSet once.

Agents also choose a HashMap when the output has to come out in a stable order. The output then changes from run to run, and tests start to fail now and then. Ask for a BTreeMap, or a sorted Vec, when the order matters.

$byRole = collect($users)->groupBy('role');
  
use std::collections::HashMap;

struct User {
    name: String,
    role: String,
}

fn main() {
    let users = vec![
        User { name: String::from("Ana"), role: String::from("admin") },
        User { name: String::from("Bo"), role: String::from("member") },
        User { name: String::from("Cy"), role: String::from("admin") },
    ];

    let mut by_role: HashMap<String, Vec<User>> = HashMap::new();
    for user in users {
        by_role.entry(user.role.clone()).or_default().push(user);
    }
    let names: Vec<&str> = by_role["admin"].iter().map(|u| u.name.as_str()).collect();
    println!("{}", names.join(", "));
}

Where it holds: both give you a list for each key. Where it breaks: the Rust loop consumes users, because each User moves into its group. The role is cloned because the key and the user both need their own String. Chapter 13 maps the rest of Laravel's Collection methods onto iterators.

Practice

Work through these before you run anything. The explanation after each one says why the answer is right.

struct Lesson {
    title: String,
}

fn main() {
    let lessons = vec![Lesson { title: String::from("Vec") }];
    let first = lessons[0];
    println!("{}", first.title);
}
  1. Yes. Struct fields are copied one at a time.
  2. No. Lesson is not Copy, so indexing cannot move it out of the Vec.
  3. No, because a struct can never be stored in a Vec.

The same rule as the String example, with a struct. The element owns a String, so it is not Copy, and lessons[0] would move it out of the buffer. Use &lessons[0] and read first.title from the reference.

A program inserts ana, bo and cy into a HashMap, then prints each pair with a for loop. Will it always print them in that order?

  1. Yes. Maps keep insertion order.
  2. No. HashMap makes no promise about iteration order, and the order can change between runs.
  3. Yes, because the keys are sorted before they are stored.

Insertion order is a property of a Vec, and sorted order is a property of a BTreeMap. A HashMap places keys by hash, and its hash is seeded randomly. A test that depends on the order of a HashMap can pass for weeks and then fail once.

Inside a loop over words, which line adds one to counts[w] and starts from 0 when the word is new? Here counts is a HashMap<&str, u32>.

  1. counts.insert(w, 1);
  2. *counts.entry(w).or_insert(0) += 1;
  3. counts.get(w).unwrap_or(0) += 1;
  4. counts.entry(w).or_insert(0);

entry(w) finds the slot, or_insert(0) creates it when it is missing, and the * writes the new count through the returned reference. Every other option either resets the count or never adds to it.

  • Vec::push
  • Vec::pop
  • VecDeque::pop_front
  • HashMap::contains_key
  • HashSet<T>
  • BTreeMap<K, V>

Two of these pairs are close but not identical. isset returns false for a key whose value is null, while contains_key returns true for any key that exists. array_unique keeps the first occurrence of each value in order, and a HashSet keeps no order at all.

Recap

Pick the job first

  • A PHP array does five jobs. Rust gives each job a type: Vec, HashMap, HashSet, BTreeMap and VecDeque.
  • v.get(i) returns an Option. v[i] panics when the index is out of range.
  • Loop with &v to read, &mut v to change, and v to consume the Vec.
  • You cannot move a value out of an index. Borrow it, clone it, remove it, or take it with std::mem::take.
  • HashMap::insert moves the key and the value in. Map iteration order is not promised, so sort before you print.
  • The entry API counts and groups in one line: *m.entry(k).or_insert(0) += 1.
Explain it back: why doesn't Rust have one array type like PHP?

One good answer: "Every collection makes a different promise about cost and order. PHP's array makes all of those promises at once, so the code doesn't say which one it relies on. Rust gives each job its own type. A Vec promises positions and cheap pushes, a HashMap promises fast lookups and no order, and a BTreeMap promises sorted keys. The type tells the next reader which promise the code depends on."

If your version mentioned cost, order and the type says what the code relies on, you have the idea.
