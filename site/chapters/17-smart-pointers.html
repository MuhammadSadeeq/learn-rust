What makes a pointer smart

Chapter 06 gave every value one owner, and the owner frees the value at its closing brace. A smart pointer is a value that owns something, usually on the heap, and adds behavior on top of that ownership. Two traits do most of the work:

Deref lets you use the pointer like the value it points to.

*b reads through it, and a &String turns into a &str wherever a function asks for one.

Drop runs cleanup when the owner goes away.

For a String that means freeing its bytes. For a file handle it means closing the file.

You have been using smart pointers since the early chapters. String and Vec<T> each own heap memory, dereference to a view of their contents, and free that memory when they are dropped. The types in this chapter differ in one question: who owns the value, and who may change it?

Keep the parcel picture from Chapter 06. Box is a parcel stored on the heap, with one name on its label. Rc is a shared parcel with an owner counter printed on the label. RefCell is a borrow desk that checks the rules every time someone asks for the parcel, and panics when the rules are broken.

String has no * and no & in its name. Is it a smart pointer?

Yes. A String holds a pointer, a length and a capacity. It owns the heap bytes, it dereferences to &str, and its Drop frees the buffer. The test is what a type does, not what its name looks like.

Here is Deref at work. The function asks for a &str, and we pass a &String. Nothing converts it by hand.

fn count_words(text: &str) -> usize {
    text.split_whitespace().count()
}

fn main() {
    let owned = String::from("smart pointers own their data");
    println!("{}", count_words(&owned));
}

String implements Deref<Target = str>, so the compiler turns the &String into a &str at the call. This is called deref coercion. You will meet it in most functions that take text.

Box<T>: one owner, on the heap

Box<T> is the simplest smart pointer. It puts one value on the heap and owns it. The value on the stack is only a pointer. Make a box with Box::new and read through it with *.

fn main() {
    let b = Box::new(5);
    println!("{}", *b + 1);
}

Watch the two lanes. b is a pointer, eight bytes on a 64-bit machine. The 5 sits in the heap lane. When b ends, the box frees it. A box has exactly one owner, so it moves like a String: after let c = b;, the name b is unusable.

There are three common reasons to reach for a box:

  • To move a large value cheaply. Moving a box copies one pointer, and the value stays where it is on the heap.
  • For a recursive type, where the compiler needs a finite size. That is the next topic.
  • For a trait object, Box<dyn Trait>, when the concrete type is chosen at runtime. Chapter 14 covers it.

A recursive type needs a box

Now a type that contains itself. A list is a number followed by the rest of the list, and the rest is another list. Try to write it with no pointer in the middle:

enum List {
    Cons(i32, List),
    Nil,
}

fn main() {
    let list = List::Nil;
}
error[E0072]: recursive type `List` has infinite size
 --> src/main.rs:1:1
  |
1 | enum List {
  | ^^^^^^^^^
2 |     Cons(i32, List),
  |               ---- recursive without indirection
  |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
2 |     Cons(i32, Box<List>),
  |               ++++    +

For more information about this error, try `rustc --explain E0072`.
Which field in the enum is the cycle? Name it before you read on.

The List inside Cons. The i32 already has a fixed size, so it needs no help. Only the field that refers back to the enum has to go behind a pointer.

Read the error the way Chapter 06 taught. The code and summary come first. The arrows say what is wrong: the field marked recursive without indirection is the one that makes the type contain itself. The help line shows the fix.

Why does the compiler care? To place a List on the stack, it has to know the size at compile time. A List holds an i32 and a List, which holds an i32 and another List, with no end. No size fits that. A Box<List> is one pointer, so the size is fixed, whatever the length of the list.

enum List {
    Cons(i32, Box<List>),
    Nil,
}

use List::{Cons, Nil};

fn sum(list: &List) -> i32 {
    match list {
        Cons(value, rest) => value + sum(rest),
        Nil => 0,
    }
}

fn main() {
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
    println!("{}", sum(&list));
}

match looks at the list through a reference, so value and rest borrow from it. The recursion stops at Nil. Each Cons cell is its own heap box, and the whole chain is freed when the outermost list goes out of scope.

In PHP a linked list is objects holding other objects. Each object is a handle, so the question of size never comes up. Rust needs the size of every value, so it asks you to say where the indirection lives. The Box is that answer.

Rc<T>: shared ownership

Sometimes one owner is not enough. Two parts of a program need the same configuration, and neither is the natural owner. Rc<T>, short for reference counted, gives one value several owners in one thread. Each owner holds an Rc handle, and the value keeps a count of how many handles exist. When the count reaches zero, the value is freed.

PHP already works this way for objects. $b = $a gives a second handle to the same object, and PHP keeps a count of the handles. Rc is the same idea with the counting written out. Rc::strong_count shows the number, and the value is freed as soon as the number reaches zero. PHP adds one thing for loops, which the cycles section covers.

Look at this program. Right after which statement does the line freed shared print?

use std::rc::Rc;

struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("freed {}", self.0);
    }
}

fn main() {
    let a = Rc::new(Noisy("shared"));
    println!("count = {}", Rc::strong_count(&a));

    let b = Rc::clone(&a);
    println!("count = {}", Rc::strong_count(&a));

    {
        let c = Rc::clone(&a);
        println!("count = {}", Rc::strong_count(&c));
    }
    println!("count = {}", Rc::strong_count(&a));

    drop(a);
    println!("count = {}", Rc::strong_count(&b));
    drop(b);
    println!("end of main");
}
  1. Right after drop(a), because a was the first owner.
  2. Right after the inner block closes, because c was the last clone.
  3. Right after drop(b), because that was the last handle.
  4. At the very end, when main returns.

The count is 2 while a and b exist, 3 inside the block, and back to 2 when c ends. drop(a) makes it 1, which is the line count = 1. drop(b) makes it 0, and the Noisy inside is dropped at that moment.

Whichever handle is dropped last frees the value. Every earlier drop only lowers the count.

Cloning an Rc is the cheap part. Rc::clone(&a) copies a pointer and adds one to the counter. The value is never copied, however large it is. Write Rc::clone(&a) rather than a.clone(). Both mean the same thing for an Rc, but the long form makes it obvious that you are cloning the handle and not the data.

Each clone adds one, each drop subtracts one, and only a drop that finds the count at 1 frees the value. That is the whole rule. The X-Ray keeps the counter on the box, so you can watch it move.

Rc gives read-only access

An Rc hands out shared references and nothing else. If several owners could change the same Vec, one of them could hold a reference into it while another pushed and reallocated it. Rust forbids that, so an Rc is read-only:

use std::rc::Rc;

fn main() {
    let shared = Rc::new(vec![1, 2, 3]);
    shared.push(4);
    println!("{shared:?}");
}
error[E0596]: cannot borrow data in an `Rc` as mutable
 --> src/main.rs:5:5
  |
5 |     shared.push(4);
  |     ^^^^^^ cannot borrow as mutable
  |
  = help: trait `DerefMut` is required to modify through a dereference, but it is not implemented for `Rc<Vec<i32>>`

For more information about this error, try `rustc --explain E0596`.

There are two ways out. Rc::get_mut returns a &mut T, but only when there are no other handles, strong or weak. That means the value is no longer shared. The other way is a RefCell, the next section, which allows mutation through a shared handle.

One more limit: Rc is for one thread. Sending an Rc into another thread is compile error E0277, Rc<String> cannot be sent between threads safely. Chapter 18 introduces Arc, the same idea with an atomic counter that is safe to share across threads.

RefCell<T>: borrow rules at runtime

Chapter 07 gave you the borrow rules: any number of shared borrows, or one exclusive borrow, never both. The compiler checks them before the program runs. Some programs only know who is borrowing once they run. RefCell<T> moves the same rules into the running program. It hands out a guard for each borrow, and it panics if you break a rule.

The useful trick is that a RefCell can change its contents through a plain &. This is called interior mutability. The cell itself is shared, and each change goes through a short borrow that the cell checks.

first is still alive on the next line. What should log.borrow_mut() do?

Refuse. A shared borrow is still alive, and an exclusive borrow must be the only one. A RefCell cannot know, when the code is written, which borrows will overlap. So it checks each call as the program makes it, and panics if the rule is broken.

use std::cell::RefCell;

fn main() {
    let log = RefCell::new(Vec::<String>::new());
    let first = log.borrow();
    println!("{} entries", first.len());
    log.borrow_mut().push(String::from("oops"));
    println!("never printed");
}
0 entries

thread 'main' (8040) panicked at src/main.rs:7:9:
RefCell already borrowed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

Line 7 is the call that broke the rule. The message names the problem: a RefCell was already borrowed. The 0 entries line printed first, because the panic comes after it. A panic like this is a bug in your program, the same kind as an index past the end of a Vec. The fix is to end the first borrow before you ask for the second.

When a conflict is a real possibility, ask first. try_borrow_mut returns a Result instead of panicking:

use std::cell::RefCell;

fn main() {
    let notes = RefCell::new(String::from("draft"));
    let reader = notes.borrow();
    match notes.try_borrow_mut() {
        Ok(mut text) => text.push_str(" + edit"),
        Err(e) => println!("busy: {e}"),
    }
    println!("reader sees: {reader}");
}

A guard lives until the end of the statement that made it, or until its variable goes out of scope. In the line below, the borrow_mut() guard is alive while Rust evaluates the argument. The argument calls borrow() on the same cell, so it panics before push runs. The message this time is RefCell already mutably borrowed.

use std::cell::RefCell;

fn main() {
    let v = RefCell::new(vec![1, 2]);
    v.borrow_mut().push(v.borrow().len() as i32);
    println!("{:?}", v.borrow());
}

The fix is to split the work into two statements: compute the length first, then borrow mutably to push.

For a Copy value, Cell<T> is simpler. It never hands out a guard. You copy the value in with set and out with get, so there is nothing to conflict:

use std::cell::Cell;

struct Counter {
    hits: Cell<u32>,
}

impl Counter {
    fn hit(&self) {
        self.hits.set(self.hits.get() + 1);
    }
}

fn main() {
    let c = Counter { hits: Cell::new(0) };
    c.hit();
    c.hit();
    println!("{}", c.hits.get());
}

A test double that records calls

Interior mutability earns its keep in a common job: a fake that records what the code under test asked for. A trait method takes &self, so the fake cannot push to a field without &mut self. It stores its records in a RefCell and writes through the shared reference. In Laravel you would call Mail::fake() and assert afterwards what was sent. Here is the same job in Rust:

use std::cell::RefCell;

trait Mailer {
    fn send(&self, to: &str, subject: &str);
}

struct MockMailer {
    sent: RefCell<Vec<String>>,
}

impl Mailer for MockMailer {
    fn send(&self, to: &str, subject: &str) {
        self.sent.borrow_mut().push(format!("{to}: {subject}"));
    }
}

fn welcome_user(mailer: &dyn Mailer, email: &str) {
    mailer.send(email, "Welcome!");
}

fn main() {
    let mailer = MockMailer { sent: RefCell::new(Vec::new()) };
    welcome_user(&mailer, "ana@example.com");
    welcome_user(&mailer, "bo@example.com");
    for line in mailer.sent.borrow().iter() {
        println!("{line}");
    }
}

The function receives a &dyn Mailer, so production code and the fake look the same to it. Afterwards, mailer.sent.borrow() reads the record. Nothing in the program needed mut.

Rc<RefCell<T>>: shared and mutable

Put the two together and you get the shape of a PHP object: several owners, and any of them may change the value. Rc supplies the owners. RefCell supplies mutation through a handle that is shared.

use std::cell::RefCell;
use std::rc::Rc;

struct Cart {
    items: Vec<u32>,
}

impl Cart {
    fn total(&self) -> u32 {
        self.items.iter().sum()
    }
}

struct CartView {
    name: &'static str,
    cart: Rc<RefCell<Cart>>,
}

impl CartView {
    fn add(&self, cents: u32) {
        self.cart.borrow_mut().items.push(cents);
    }
}

fn main() {
    let cart = Rc::new(RefCell::new(Cart { items: Vec::new() }));
    let sidebar = CartView { name: "sidebar", cart: Rc::clone(&cart) };
    let checkout = CartView { name: "checkout", cart: Rc::clone(&cart) };

    sidebar.add(1200);
    checkout.add(350);
    println!("{} sees {} cents", sidebar.name, sidebar.cart.borrow().total());
    println!("{} sees {} cents", checkout.name, checkout.cart.borrow().total());
    println!("owners: {}", Rc::strong_count(&cart));
}

Each view holds its own Rc handle to the same cart. add takes &self, so both views can call it. It borrows the RefCell mutably only for the push. Both views read the same items, because there is only one cart. The last line counts three handles: cart, and one inside each view.

Every PHP object handle behaves like Rc<RefCell<T>>. Several variables can hold one object, any of them can change it, and PHP counts the handles and runs a cycle collector for the loops. Rust makes you spell out each part. Most Rust code never needs the combination, and when it does, the first question is whether the data really has many owners. Section 8 comes back to that question.

Which type gives you shared ownership and mutation, all on one thread?

  1. Rc<T> on its own
  2. Rc<RefCell<T>>
  3. Box<T>
  4. &mut T

Rc on its own shares but never mutates. RefCell on its own mutates through & but has one owner. Together they give several owners, and each of them can borrow the value mutably, with the rules checked at runtime. &mut T is exclusive: only one holder can exist at a time.

See it work

Two instruments, one for each half of this chapter. The left one is an owner counter. Handles come and go, and the value is freed when the last strong handle is dropped. The right one is a borrow desk, a RefCell that enforces its rules while you press buttons.

Same rules as Chapter 07, where the compiler checked them before the program ran. Here the desk checks them as you go.

Try these in order. Clone once, downgrade once, then drop the strong handles and call upgrade() on the weak one. On the desk, take a read guard, then try a write. Each rule is one you have already seen in this chapter.

You have one Rc, a, and a Weak made from it, w. Then you run drop(a). What does w.upgrade() return?

  1. Some, because the Weak still points at the value.
  2. None. The last strong handle is gone, so the value was freed.
  3. It doesn't compile, because upgrade needs a mutable handle.

A Weak does not count as an owner. Dropping the last Rc frees the value, and upgrade() then returns None. The balloon shows exactly that.

Cycles leak; Weak breaks them

Rc frees a value when its count reaches zero. A cycle stops the count from ever reaching zero. Two nodes that point at each other keep each other alive, even after nothing outside refers to them:

use std::cell::RefCell;
use std::rc::Rc;

struct Node {
    name: &'static str,
    next: RefCell<Option<Rc<Node>>>,
}

impl Drop for Node {
    fn drop(&mut self) {
        println!("drop {}", self.name);
    }
}

fn main() {
    let a = Rc::new(Node { name: "a", next: RefCell::new(None) });
    let b = Rc::new(Node { name: "b", next: RefCell::new(None) });
    *a.next.borrow_mut() = Some(Rc::clone(&b));
    *b.next.borrow_mut() = Some(Rc::clone(&a));
    println!("a: {}, b: {}", Rc::strong_count(&a), Rc::strong_count(&b));
    println!("end of main");
}

Each node is owned by its variable and by the other node. When main ends, both variables let go, and each count drops from 2 to 1. Neither reaches zero, so neither drop line ever prints. The memory is never freed.

Rust's safety guarantees cover use after free and double free. They do not promise that every value is freed. Leaking memory is considered safe, so the compiler accepts a cycle without a word. The leak is still your bug, and no compiler message will point at it.

PHP has the same loop, and PHP does not leak it. The reference count never reaches zero, so the engine has a second mechanism: a cycle collector. It looks for groups of objects that refer only to each other, and it frees them. It runs on its own once enough candidates build up, and gc_collect_cycles() forces a run. Rust has no collector. An Rc cycle stays in memory until the process exits, and no drop ever runs.

declare(strict_types=1);

final class Node
{
    public ?Node $next = null;

    public function __construct(public readonly string $name) {}

    public function __destruct()
    {
        echo "drop {$this->name}\n";
    }
}

function build(): void
{
    $a = new Node('a');
    $b = new Node('b');
    $a->next = $b;
    $b->next = $a;
    echo "built\n";
}

build();
echo "after build, before gc\n";
$freed = gc_collect_cycles();
echo "collected: $freed\n";
echo "end\n";

built
after build, before gc
drop a
drop b
collected: 2
end

The output shows the same loop as the Rust program above, with the collector added. The two drop lines wait until gc_collect_cycles() runs. Then the collector frees both objects and reports how many it freed.

The fix is to make one direction of the link a Weak. A Weak<T> points at a value without owning it. It does not add to the strong count, so it cannot keep the value alive. You create one with Rc::downgrade(&rc), and you read it with upgrade(), which returns Option<Rc<T>>. Some means the value is still alive. None means it was freed.

The classic use is a tree. A parent owns its children with strong handles, and each child points back at its parent with a weak one:

use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });
    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade().map(|p| p.value));
    println!("leaf strong = {}, weak = {}", Rc::strong_count(&leaf), Rc::weak_count(&leaf));

    {
        let branch = Rc::new(Node {
            value: 5,
            parent: RefCell::new(Weak::new()),
            children: RefCell::new(vec![Rc::clone(&leaf)]),
        });
        *leaf.parent.borrow_mut() = Rc::downgrade(&branch);
        println!("branch strong = {}, weak = {}", Rc::strong_count(&branch), Rc::weak_count(&branch));
        println!("branch children = {}", branch.children.borrow().len());
        println!("leaf strong = {}, weak = {}", Rc::strong_count(&leaf), Rc::weak_count(&leaf));
        println!("leaf parent = {:?}", leaf.parent.borrow().upgrade().map(|p| p.value));
    }

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade().map(|p| p.value));
    println!("leaf strong = {}, weak = {}", Rc::strong_count(&leaf), Rc::weak_count(&leaf));
}

Read the counts as the program runs. branch strong = 1, weak = 1: the branch has one owner, the variable, and the leaf's parent link is weak. leaf strong = 2: the variable and the branch's children vector each own the leaf. When the inner block closes, the branch's count reaches zero. The branch is freed, its children vector goes with it, and the leaf falls back to one owner. The weak link now upgrades to None.

What a Weak keeps alive

An Rc allocates one box that holds the strong count, the weak count and the value. When the strong count reaches zero, the value is dropped. The box itself is freed only when the weak count also reaches zero. That is why upgrade() can safely return None: the box still exists, and it knows no strong owners are left.

Suppose the child's link to its parent were a strong Rc instead. What would the counts look like after the block ends?

The parent would still hold the child, and the child would still hold the parent. Neither count would reach zero, so both would leak. There would be no drop message and no way for the program to free them.

PHP has the same kind of handle. A WeakReference points at an object without keeping it alive, which is what Weak<T> does. Here is a small class, and then the two side by side:

final readonly class Session
{
    public function __construct(public string $user) {}
}
$session = new Session('ana');
$handle = WeakReference::create($session);
echo $handle->get()?->user ?? 'gone', "\n";  // ana

unset($session);
echo $handle->get()?->user ?? 'gone', "\n";  // gone
use std::rc::{Rc, Weak};

struct Session {
    user: &'static str,
}

fn main() {
    let session = Rc::new(Session { user: "ana" });
    let handle: Weak<Session> = Rc::downgrade(&session);
    println!("{}", handle.upgrade().map_or("gone", |s| s.user));

    drop(session);
    println!("{}", handle.upgrade().map_or("gone", |s| s.user));
}

Both handles follow the lifetime of one object. When the last owner goes, the object is freed, and the handle reports it. Rust returns an Option, so the compiler makes you handle the empty case before you touch the value. PHP returns null, and its type says so. The check comes at runtime, when the code uses that null.

PHP's WeakMap covers the cache case. Its keys are objects, and an entry disappears when its key is freed:

$cache = new WeakMap();
$key = new Session('bo');
$cache[$key] = 'computed';
echo count($cache), "\n";  // 1

unset($key);
echo count($cache), "\n";  // 0

The standard library has no weak map. In Rust you keep a Vec or a HashMap of Weak handles, and remove each entry whose upgrade() returns None.

Cow<str>: borrow until you must change it

Cow stands for clone on write. It holds either a borrowed &str or an owned String. It stays borrowed, and allocates nothing, until a change forces it to own a copy:

use std::borrow::Cow;

fn clean(input: &str) -> Cow<'_, str> {
    if input.contains(' ') {
        Cow::Owned(input.replace(' ', "_"))
    } else {
        Cow::Borrowed(input)
    }
}

fn main() {
    let a = clean("plain");
    let b = clean("has space");
    println!("{a} {b}");
}

The '_ tells the reader that the result borrows from the input. Chapter 15 explains that notation.

Which one when?

Start from the question the type answers: who owns this value, and who may change it? Then pick the smallest tool that answers it.

The situationReach for
One owner, value on the heap, or a recursive typeBox<T>
Many owners in one thread, read-onlyRc<T> (across threads: Arc<T>)
Many owners in one thread, and they mutateRc<RefCell<T>> (across threads: Arc<Mutex<T>>)
One owner, but mutation through a shared &RefCell<T>, or Cell<T> for a Copy value
A link that must not keep its target alive, such as a parent pointerWeak<T>, paired with an Rc

Coding agents reach for Rc<RefCell<...>> and Arc<Mutex<...>> the moment the borrow checker complains. The error goes away and the code runs, so the change looks like a success. Often it is the wrong fix. The better change is usually structural: pass &mut down the call chain, return the new value instead of mutating a shared one, or split a struct so that each borrow touches a different field.

When you review generated Rust, ask who should own this? before you accept a smart pointer. If the honest answer is one owner, the wrapper hides a design problem, and every access now pays for a runtime check.

A sidebar and a checkout both show the same cart, one at a time, during a single request. Who should own the cart?

Probably the request or the page state, as a single owner. Pass a &Cart to the sidebar and a &mut Cart to the checkout, one after the other. Reach for Rc<RefCell<Cart>> only when two views must keep the cart alive for longer than one call.

Practice

Six checks across the chapter's ideas: recursive types, the cost of cloning, counting owners, borrow panics, filling in a box, and choosing a pointer. Answer each one before you open its explanation.

Does this compile?

struct Node {
    value: i32,
    next: Option<Node>,
}

fn main() {
    let node = Node { value: 1, next: None };
    println!("{}", node.value);
}
  1. Yes. Option makes the next node optional, so the size is fixed.
  2. No. Option<Node> stores a whole Node inline when it is Some, so Node contains itself. E0072.
  3. No, because a struct can never refer to its own type.

Option does not break the cycle. Its Some variant holds the value directly. Put the inner node in a box, as Option<Box<Node>>, and the size is finite again.

You hold an Rc<String> whose text is very large. What does Rc::clone(&a) cost?

  1. About as much as the text, because the bytes are copied.
  2. A pointer copy and a counter increment. The text is not copied, so the cost does not depend on its size.
  3. A new heap allocation for the handle, but no copy of the text.

The counter lives in the shared box, and bumping it is one add. The text is never touched. That is why cloning an Rc inside a loop is fine, while cloning a String there may not be.

What does this print? It prints two lines.

  3. 3, then 1
  4. 2, then 1

Inside the block, a, b and _c all exist, so the first line is 3. The block then closes and _c is dropped, leaving 2. drop(b) leaves 1, and the second line prints that.

Does this compile, and what happens when it runs?

use std::cell::RefCell;

fn main() {
    let total = RefCell::new(10);
    let seen = total.borrow();
    *total.borrow_mut() += 5;
    println!("seen {seen}");
}
  1. It doesn't compile. borrow_mut needs a mut binding.
  2. It compiles, prints seen 15, and exits cleanly.
  3. It compiles, then panics at the borrow_mut line with RefCell already borrowed.

It compiles. borrow_mut takes &self, so total does not need mut. The rules are checked when the call runs. seen is still alive on the last line, so the exclusive borrow fails and the program panics. Dropping seen before the borrow_mut call would fix it.

Fill the blank so the list compiles. Each cell must own the rest of the list through a pointer.

enum List {
    Cons(i32, [[Box<List>|std::boxed::Box<List>]]),
    Nil,
}

use List::{Cons, Nil};

fn sum(list: &List) -> i32 {
    match list {
        Cons(value, rest) => value + sum(rest),
        Nil => 0,
    }
}

fn main() {
    let list = Cons(4, Box::new(Cons(5, Box::new(Nil))));
    println!("{}", sum(&list));
}

The field must be a Box<List>, not a bare List, because a List cannot hold a List by value. With a bare List here you get E0072 again. The program prints 9.

Act IV wrap-up

Act IV was about abstraction without a runtime tax. Five tools carry forward:

  • Traits (Chapter 14): a contract a type can satisfy, including types you did not write. dyn Trait lets the concrete type be chosen at runtime.
  • Generics (Chapter 14): the compiler stamps out a version for each type you use, so generic code costs nothing extra at runtime.
  • Lifetimes (Chapter 15): labels that say which input a borrow came from and how long it must stay valid. They never make a value live longer.
  • Modules, crates and tests (Chapter 16): how a project is organized, and the checks that keep it honest. cargo test runs them.
  • Smart pointers (this chapter): Box for one owner on the heap, Rc and RefCell for shared and mutable data, and Weak to break cycles.

The Act IV boss, Mini Blade, asks you to build a tiny template engine that uses traits and lifetimes together. It is in the quest list below, marked as a boss.

A template engine keeps the pieces it parses as slices of the template text. Which Act IV tool keeps those slices valid, and what does the struct need?

Lifetimes. A struct such as Template<'a> holds &'a str slices of the source, and its signature says the pieces cannot outlive the input they point into.

Recap

Who owns what, and who may change it

  • A smart pointer owns what it points to and adds behavior: Deref to use the value like a reference, and Drop to clean up.
  • Box<T>: one owner, the value on the heap, and a fixed-size pointer on the stack. Use it for recursive types and trait objects.
  • Rc<T>: many owners in one thread, read-only. Rc::clone adds one to the count. The value is dropped when the count reaches zero.
  • RefCell<T>: the borrow rules, checked at runtime. Many borrow() guards, or one borrow_mut(). A conflict panics, and try_borrow_mut returns an error instead. Cell<T> does the same job for Copy values.
  • Rc<RefCell<T>>: shared and mutable in one thread. This is the PHP object model, written out.
  • Weak<T>: a handle that does not own. Use it to break cycles. upgrade() returns Option<Rc<T>>.
Explain it back: why is a PHP object like an Rc<RefCell<T>>, and why doesn't Rust do that by default?

One good answer: "A PHP object is a handle. Several variables can point at one object, any of them can change it, and PHP counts the handles to free it, with a cycle collector for the loops. That is shared ownership with mutation, which is what Rc<RefCell<T>> expresses. Rust does not make it the default, because the combination costs a count and a runtime borrow check on every use, and it hides who really owns the data. Most Rust code has one clear owner, so Rust asks you to say when you need several."

If your answer mentioned several owners, mutation through a handle, and the cost and the hidden ownership, you have it.
