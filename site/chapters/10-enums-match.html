One of several shapes

Most values are one kind of thing: a User, a number, a String. Some values are one of several kinds, and each kind needs different data. A message off a websocket might be a ping with no payload, a move with two coordinates, or a chat line with some text. In PHP you would probably store that as one array with a type key, and trust every reader to check the right keys.

An enum says that a value is exactly one of a fixed list of variants. Each variant can carry its own data, and the shape of that data can differ from one variant to the next:

enum Message {
    // no data
    Quit,
    // named fields
    Move { x: i32, y: i32 },
    // one unnamed field
    Write(String),
    // three unnamed fields
    Color(u8, u8, u8),
}

There are three shapes of variant. Quit carries nothing. Move has named fields, which read well when there are several. Write and Color list their types by position, which is fine for one or two.

final class Message
{
    public function __construct(
        public string  $kind,          // 'quit', 'move', 'write' or 'color'
        public ?int    $x = null,      // only set for 'move'
        public ?int    $y = null,      // only set for 'move'
        public ?string $text = null,   // only set for 'write'
        public ?array  $rgb = null,    // only set for 'color'
    ) {}
}
enum Message {
    // no data
    Quit,
    // named fields
    Move { x: i32, y: i32 },
    // one unnamed field
    Write(String),
    // three unnamed fields
    Color(u8, u8, u8),
}

PHP 8.1 has enums too, but a backed case such as case Hearts = 'H'; holds one fixed value and nothing else. Without per-case data, the PHP habit is one class with nullable fields and a kind column that says which ones matter, or a class hierarchy with one subclass per case. A Rust enum does both jobs: one type, and each variant has only the fields it needs.

The compiler is strict about the shape you build a value with. Try this one:

Does this compile?

enum Message {
    Quit,
    Move { x: i32, y: i32 },
}

fn main() {
    let m = Message::Move(3, -1);
}
  1. Yes. A variant that holds data is always called like a function.
  2. No. Move has named fields, so you build it with braces: Message::Move { x: 3, y: -1 }.
  3. No. Enums can't have struct-like variants.

The error is E0533, and its help line writes the braces form for you. A variant can only be built in the shape it was declared with.

match: handle every case

A match compares a value against a list of patterns, one arm at a time, from the top. The first arm whose pattern fits runs, and the rest are skipped. A match is also an expression, so it produces a value you can store, return or print.

enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    Color(u8, u8, u8),
}

fn main() {
    let msg = Message::Move { x: 3, y: -1 };
    let text = match msg {
        Message::Quit => String::from("quit"),
        Message::Move { x, y } => format!("move to ({x}, {y})"),
        Message::Write(text) => text,
        Message::Color(r, g, b) => format!("#{r:02x}{g:02x}{b:02x}"),
    };
    println!("{text}");
}

Read an arm as pattern => result. x and y in Message::Move { x, y } are bindings: they take the numbers out of the variant and give them names for the result. Arms are separated by commas. All the arms produce one type, because the whole match has one type.

Does this compile?

fn main() {
    let n = 1;
    let label = match n {
        1 => "one",
        _ => 0,
    };
    println!("{label}");
}
  1. Yes. The _ arm catches everything, so its type doesn't matter.
  2. No. The first arm makes the match a &str, so every other arm has to produce a &str too.
  3. Yes. Rust converts the number to text.

A match has one type, and the compiler takes it from the first arm. Here that is &str, so 0 is an error. Rust never converts between text and numbers on its own.

The next rule is the important one. A match has to handle every possible value. If you leave a case out, the program doesn't compile, and the compiler says exactly what is missing.

In review, ask whether the wildcard is meant to catch future variants. If it isn't, list the variants by name.

Patterns in depth

A pattern can be a literal, a range, a set of alternatives, a wildcard, a binding, or a destructuring of a struct or a tuple. One program with several matches shows them all:

struct Point {
    x: i32,
    y: i32,
}

struct Line {
    start: Point,
    end: Point,
}

fn classify(n: i32) -> String {
    match n {
        i32::MIN..=-1 => String::from("negative"),
        0 => String::from("zero"),
        d @ 1..=9 => format!("digit {d}"),
        10 | 20 | 30 => String::from("round"),
        x if x % 2 == 0 => format!("even {x}"),
        _ => String::from("odd"),
    }
}

fn corner(p: &Point) -> &'static str {
    match p {
        Point { x: 0, y: 0 } => "origin",
        Point { x, .. } if *x < 0 => "left of the axis",
        Point { y: 0, .. } => "on the x axis",
        _ => "somewhere else",
    }
}

fn describe_line(line: &Line) -> &'static str {
    match line {
        Line { start: Point { x: 0, y: 0 }, .. } => "starts at the origin",
        Line { end: Point { y: 0, .. }, .. } => "ends on the x axis",
        _ => "somewhere",
    }
}

fn main() {
    for n in [-4, 0, 7, 20, 12, 15] {
        println!("{}", classify(n));
    }
    println!("{}", corner(&Point { x: 0, y: 0 }));
    println!("{}", corner(&Point { x: -2, y: 5 }));
    println!("{}", corner(&Point { x: 4, y: 0 }));

    let line = Line { start: Point { x: 0, y: 0 }, end: Point { x: 5, y: 5 } };
    println!("{}", describe_line(&line));
    let line = Line { start: Point { x: 1, y: 1 }, end: Point { x: 4, y: 0 } };
    println!("{}", describe_line(&line));

    let ((a, b), c) = ((1, true), 'z');
    println!("{a} {b} {c}");
}

Patterns nest. Line { start: Point { x: 0, y: 0 }, .. } reaches inside a struct that sits inside another struct, and ((a, b), c) does the same for tuples. The .. skips every field you don't name.

PatternMatches
0, "quit"one exact value
1..=9a range, with both ends included
10 | 20 | 30any one of several patterns
d @ 1..=9a range, and binds the value to d at the same time
Point { x, .. }a struct, binding x and ignoring the other fields
x if x < 0a pattern plus a guard: the arm runs only when the guard is true
_anything, and binds nothing

A guard looks like an extra check on the value, but it is not part of the pattern. The compiler checks the pattern first, then the guard. One consequence matters a great deal for exhaustiveness. Try to predict the first line first:

What does this program print?

fn main() {
    let n = 7;
    match n {
        x if x > 5 => println!("big {x}"),
        1..=9 => println!("digit {n}"),
        _ => println!("other"),
    }
}
  1. big 7
  2. big 7, then digit 7
  3. digit 7
  4. Nothing. Overlapping arms are a compile error.

Only the first arm that fits runs. 7 fits x if x > 5, so the match is finished before the 1..=9 arm is looked at. Overlapping arms are allowed. The compiler only warns about an arm that can never run, as the next check shows.

A guard can't be counted on to cover a case. These two guarded arms look like they cover every integer. They don't:

fn sign(n: i32) -> &'static str {

        0 => "zero",

}

fn main() {
    println!("{}", sign(3));
}

The compiler states the rule directly: match arms with guards don't count towards exhaustivity. A guard might be false, so the compiler counts only the arms without one. The fix is a plain catch-all arm, or patterns that cover what is left. The help line suggests the second.

fn main() {

  3. Yes, and silently. Rust never looks at an arm that comes after a catch-all.

Option: null you have to check

In PHP, any reference can be null, and a function declared to return a User may return null anyway. You find out at runtime, when Call to a member function name() on null stops the request. Rust's ordinary types can't be null. When a value might be missing, its type is Option<T>, and the type says so.

// Simplified from the standard library.
enum Option<T> {
    None,
    Some(T),
}

The standard library defines Option much like this (the real one also derives some traits). It is built in, so you never import it: Some and None are always in scope. Think of None as an empty box. The value inside a Some stays out of reach until you open the box, and the compiler won't let you use it as if the box were already open:

fn main() {
    let n: Option<i32> = Some(5);
    let m = n + 1;
    println!("{m}");
}
error[E0369]: cannot add `{integer}` to `Option<i32>`
 --> src/main.rs:3:15
  |
3 |     let m = n + 1;
  |             - ^ - {integer}
  |             |
  |             Option<i32>
  |
note: `Option<i32>` does not implement `Add<{integer}>`
 --> /rustc/2d8144b7880597b6e6d3dfd63a9a9efae3f533d3/library/core/src/option.rs:597:0
  |
  = note: `Option<i32>` is defined in another crate

For more information about this error, try `rustc --explain E0369`.

The compiler knows n might be None, so it refuses to add to it. The fix is to decide what should happen when the box is empty. The methods in the next part do exactly that.

// The return type is the only hint that the result may be null.
function findUser(int $id): ?User
{
    return $this->users[$id] ?? null;
}

$name = $this->findUser(1)?->name ?? 'guest';
let user: Option<User> = find_user(1);
let name = user.map(|u| u.name).unwrap_or(String::from("guest"));

?-> and ?? are two PHP operators for one job, and map and unwrap_or are the Rust methods for it. The Rust versions work on any Option, and the compiler makes sure the None case was handled. The analogy breaks at one point: in PHP a missing value quietly flows on as null. In Rust it stays an Option until you turn it back into a plain value.

These are the methods you will use most. Each one takes an Option and says what to do when the box is empty.

MethodWhat you get
unwrap_or(v)the value inside, or v when empty
unwrap_or_else(f)the value inside, or the result of closure f, which runs only when empty
unwrap_or_default()the value inside, or the type's default: 0, "", an empty Vec
map(f)Some(f(value)), or None stays None
and_then(f)runs f on the value; f returns an Option itself, so the result is not nested
filter(p)keeps the value only if p returns true
is_some_and(p)true only when it is Some and p returns true
ok_or(e)Ok(v) for Some(v), Err(e) for None. Chapter 11 covers Result.
take()moves the value out and leaves None in its place. Needs a mut binding.
 
fn main() {
    let some: Option<i32> = Some(4);
    let none: Option<i32> = None;

    println!("{}", some.unwrap_or(0));
    println!("{}", none.unwrap_or(0));
    println!("{}", none.unwrap_or_else(|| 6 * 7));
    println!("{:?}", some.map(|n| n * 10));
    println!("{:?}", some.filter(|n| *n > 10));
    println!("{}", some.is_some_and(|n| n % 2 == 0));

    let mut slot = Some(3);
    let taken = slot.take();
    println!("{taken:?} {slot:?}");
}

some is still usable after map and filter. An Option<i32> is Copy, because the number inside is. An Option<String> is not, and it follows the same move rules as the String from Chapter 06.

What does this program print?

fn main() {
    let a: Option<i32> = Some(4);
    let b: Option<i32> = None;
    println!("{}", a.map(|n| n * 2).unwrap_or(-1));
    println!("{}", b.map(|n| n * 2).unwrap_or(-1));
}
  1. 8, then -1
  2. 8, then 8
  3. 8, then 0
  4. It panics on the second line, because map can't run on None.

map runs its closure only for Some. On None it returns None without calling the closure, and unwrap_or(-1) supplies the fallback. Nothing panics.

if let, let else, while let

A match that cares about one case gets noisy: an arm for the case you want, and an arm that says _ => {}. These forms say what you mean.

struct User {
    name: String,
}

fn find_user(id: u32) -> Option<User> {
    match id {
        1 => Some(User { name: String::from("Ana") }),
        2 => Some(User { name: String::from("Bo") }),
        _ => None,
    }
}

fn greet(id: u32) {
    if let Some(user) = find_user(id) {
        println!("hello {}", user.name);
    } else {
        println!("no user {id}");
    }
}

fn greet_or_stop(id: u32) {
    let Some(user) = find_user(id) else {
        println!("stopping at {id}");
        return;
    };
    println!("welcome {}", user.name);
}

fn main() {
    greet(1);
    greet(9);
    greet_or_stop(2);
    greet_or_stop(9);

    let mut queue = vec![1, 2, 3];
    while let Some(next) = queue.pop() {
        println!("pop {next}");
    }
}

if let PATTERN = value { … } else { … }

One case, with an optional else for everything else.

let PATTERN = value else { … };

When the pattern fits, its bindings stay in scope for the rest of the block. When it doesn't, the else block runs, and it has to leave the block.

while let PATTERN = value { … }

Loops for as long as the pattern fits. pop() returns an Option, so the loop ends when the stack is empty.

matches!(value, PATTERN)

The same pattern test, answered as a bool.

enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    Color(u8, u8, u8),
}

fn main() {
    let msg = Message::Move { x: 3, y: -1 };
    println!("{}", matches!(msg, Message::Quit));
    println!("{}", matches!(msg, Message::Move { x, .. } if x > 0));
}

Does this compile?

fn main() {
    let Some(n) = "42".parse::<i32>().ok() else {
        println!("not a number");
    };
    println!("{n}");
}
  1. Yes. The else block prints a message, and the program goes on.
  2. No. The else block of a let must diverge. It has to leave the block with return, break, continue or panic!.
  3. No. let ... else doesn't exist in Rust.

After the let, the code expects n to exist. If the else block could finish normally, the code after it would run with no n. So the compiler requires the else block to never finish normally.

Fill in the blanks. The first is the pattern. The second is the keyword that starts the else block.

fn double(s: &str) -> i32 {
    let [[Some(n)]] = s.parse::<i32>().ok() [[else]] { return 0; };
    n * 2
}

fn main() {
    println!("{}", double("21"));
}

The pattern Some(n) says the parse worked, and n stays in scope for the rest of the function. The else block returns 0, so it diverges and the compiler is satisfied. main prints 42.

unwrap() takes the value out of a Some, and panics on None. That is a crash you wrote on purpose. It is fine in tests, in quick experiments, and where you can state why the value must be there. Then say that reason in the message, where the next reader will see it:

let port: u16 = "8080".parse().expect("config was validated at startup");

Everywhere else, use the methods from the section above.

How big is an enum?

An enum needs room for its largest variant, plus a tag that says which variant is live. Padding adds bytes so each field starts at an aligned address, and the total is the size. Measure rather than guess:

use std::mem::size_of;

#[allow(dead_code)]
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    Color(u8, u8, u8),
}

fn main() {
    println!("Option<u8>       {}", size_of::<Option<u8>>());
    println!("Option<u32>      {}", size_of::<Option<u32>>());
    println!("Option<bool>     {}", size_of::<Option<bool>>());
    println!("Option<char>     {}", size_of::<Option<char>>());
    println!("Option<&i32>     {}", size_of::<Option<&i32>>());
    println!("Option<Box<i32>> {}", size_of::<Option<Box<i32>>>());
    println!("String           {}", size_of::<String>());
    println!("Message          {}", size_of::<Message>());
}

Option<u8> is 2 bytes: a tag and the value. Option<&i32> is the same size as a plain pointer, and has no tag at all. A reference can never be null in safe Rust, so the compiler uses the zero address to mean None. The same trick gives Option<bool> one byte, because a bool is only ever 0 or 1 and the spare value 2 can stand for None.

Message has four variants and is 24 bytes, the same size as a String. Its Write variant holds a String, so that variant sets the size. Rust can store the tag in a spare value of the String's capacity field, because a capacity can never be larger than isize::MAX. The other variants store their fields in the rest of those 24 bytes. This is also why Option<String> is 24 bytes.

How many bytes is Option<&i32> on a 64-bit machine?

  1. 16: a tag, then the pointer
  2. 9: one tag byte, then the pointer
  3. 8: None is the all-zero address, so no tag is needed
  4. 4: the size of an i32

A reference is never null in safe Rust, so the compiler uses the zero address for None. Option<&i32> then costs the same as &i32. Rust doesn't promise this layout, so use size_of when it matters.

Make invalid states unrepresentable

Here is an orders table, built the way most of us build one first:

$order->status          = 'shipped';
$order->paid_at         = null;
$order->tracking_number = null;
$order->save();   // the database accepts this row

Nothing stops a shipped order with no tracking number. The database stores it without a complaint, and you find out when a customer asks where their parcel is. You could add a CHECK constraint or a validator, but each rule lives somewhere else, and the code can still forget to call it.

In Rust you describe the states themselves. Each variant carries exactly what that state needs:

enum OrderStatus {
    Pending,
    Paid { at: u64 },
    Shipped { at: u64, tracking: String },
    Cancelled { reason: String },
}

impl OrderStatus {
    // Only a paid order can ship. Any other state gives None.
    fn ship(self, tracking: String) -> Option<OrderStatus> {
        match self {
            OrderStatus::Paid { at } => Some(OrderStatus::Shipped { at, tracking }),
            _ => None,
        }
    }
}

fn main() {
    let paid = OrderStatus::Paid { at: 1_700_000_000 };
    match paid.ship(String::from("1Z999")) {
        Some(OrderStatus::Shipped { tracking, .. }) => println!("shipped, tracking {tracking}"),
        _ => println!("cannot ship"),
    }

    let pending = OrderStatus::Pending;
    match pending.ship(String::from("1Z000")) {
        Some(_) => println!("shipped"),
        None => println!("cannot ship a pending order"),
    }
}

A Shipped order can't exist without a tracking string, because its only constructor needs one. ship accepts a paid order, and any other state gives None. There is no way to write a status that says shipped while the tracking number is missing, because the enum has no such value.

final class Order
{
    public string  $status = 'pending';      // pending, paid, shipped or cancelled
    public ?int    $paid_at = null;          // only meaningful once paid
    public ?string $tracking_number = null;  // only meaningful once shipped
}
enum OrderStatus {
    Pending,
    Paid { at: u64 },
    Shipped { at: u64, tracking: String },
    Cancelled { reason: String },
}

PHP's typed properties help a little, but a class always has every property, and nullable ones can be set in any combination. A Rust enum has one shape per state. The PHP model asks you to remember which fields belong together. The Rust model makes you say it once, in the type, so the mistake can't be written.

  • x.unwrap_or("default")
  • enum Suit with an impl block
  • match n { x if x < 0 => … }
  • E0004 from rustc, before the program runs

Agents tend to model state as a String status with Option fields beside it, because that is the shape of most code they have read. Ask for an enum instead. Then, when a new state is added later, every match over the enum that has no wildcard stops compiling until it handles the new state. That list of errors is the list of places to update.

The list only works if the compiler can check every case. A _ arm in one of those matches quietly removes that check.

Recap

Enums hold one shape, and match covers every shape

  • An enum is exactly one of its variants. A variant can carry nothing (Quit), named fields (Move { x, y }), or positional fields (Write(String)).
  • match is an expression. It tests arms from the top and takes the first one that fits. Every case needs an arm, or the compiler reports E0004.
  • Patterns can be literals, ranges, | alternatives, .. to skip fields, @ bindings and guards. A guard doesn't count toward exhaustiveness.
  • Option<T> is Some(value) or None. Reach for map, unwrap_or and and_then first. Use unwrap() only when you can say why it can't panic.
  • if let, while let and let ... else handle one case. The else of let ... else must diverge.
  • An enum costs its largest variant plus a tag, and the compiler can hide the tag in spare values. That is why an Option of a reference costs nothing extra.
  • Model each state as a variant, so each state carries only the data that belongs to it.
Explain it back: why is Option better than null? Answer in two sentences.

One good answer: "With null, any reference might be empty, and nothing in the type says so, so the failure shows up at runtime. Option puts the empty case into the type, so you can't use the value until you have handled None, and the compiler checks that you did."

If your version mentioned the type says so and the compiler checks it, you have the core of it.
