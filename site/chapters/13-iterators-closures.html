Closures

A closure is a function with no name, written where you need it. In PHP you have seen it as function ($x) { … } or fn ($x) => …. Rust has the same idea with a shorter syntax: parameters between vertical bars, then the body.

fn main() {
    let add = |a, b| a + b;
    println!("{}", add(2, 3));

    let describe = |n: i32| -> String {
        let doubled = n * 2;
        format!("{n} doubled is {doubled}")
    };
    println!("{}", describe(4));
}

You don't write the types of a and b. Rust infers them from how the closure is used, and then they are fixed. Annotate a closure when its body is long or its types are not obvious, as in |n: i32| -> String { … }. A closure with more than one statement needs braces, just like a function body.

Does this compile?

fn main() {
    let add = |a, b| a + b;
    println!("{}", add(1, 2));
    println!("{}", add(1.5, 2.0));
}
  1. Yes. Closures accept any numeric type.
  2. No. The first call fixed a and b to integers, so the second call doesn't match.
  3. No. A closure can't take two parameters.

A closure's parameter types are inferred from its first use, and then they stay put. If you want both kinds of numbers, annotate the parameters with one type, as in |a: f64, b: f64|, and pass floats to every call.

PHP has the same two forms, and they capture differently. This is the comparison that matters here:

declare(strict_types=1);

$factor = 2;
$byValue = function (int $x) use ($factor): int {
    return $x * $factor;
};
$byRef = function (int $x) use (&$factor): int {
    return $x * $factor;
};
$arrow = fn (int $x): int => $x * $factor;
fn main() {
    let factor = 2;
    let times = |x: i32| x * factor;
    println!("{}", times(3));
}

PHP writes the capture list into the closure's header, and that list decides what is copied. A plain use ($factor) copies the value when the closure is created, and use (&$factor) shares the variable. The arrow form fn copies too, but it needs no list. It captures each outer variable it uses, by value, when the closure is created. Rust reads the body and picks the least it needs. This closure only reads factor, so it takes a shared borrow. Nothing is copied, and no list is required. Where the comparison breaks: the compiler enforces the borrow. While the closure is alive, it won't let you change factor (E0506). PHP has no such check. A closure that captured by reference sees every later change to the variable, and nothing complains. A Rust move closure takes ownership of its captures instead, and PHP has no word for that. The next section covers it.

What a closure is at runtime

The compiler turns each closure into a small struct, with one field for each thing it captured. The body becomes a method that reads those fields. Every closure gets its own unnamed type, so even two closures with identical code are different types. The struct lives on the stack unless you put it in a Box. Passing a closure to a generic function gives you a separate, specialized copy of that function, the same way generics work in Chapter 14.

What a closure captures decides what it is

A closure can use variables from the scope where it was written. It captures them. How its body uses them decides which of three traits the closure implements, and the trait tells you how the closure may be called. Read the trait off the body, and you know what the closure can do.

TraitThe body…How you may call it
Fnonly reads captured valuesas many times as you like
FnMutchanges a captured valuemany times, and the binding must be mut
FnOncemoves a captured value outexactly once

Three short programs, one for each trait. Each one compiles.

Fn. greet reads name, so it borrows it. You can call it again and again, and name is still yours outside the closure.

fn main() {
    let name = String::from("Ana");
    let greet = || println!("hello {name}");
    greet();
    greet();
    println!("still have {name}");
}

FnMut. bump changes count, so it holds a mutable borrow of it. Calling it changes the closure's captured state, which is why the binding itself has to be mut.

fn main() {
    let mut count = 0;
    let mut bump = || count += 1;
    bump();
    bump();
    println!("count = {count}");
}

FnOnce. take returns name, which moves it out of the closure. There is only one name to give away, so the closure can run once.

fn main() {
    let name = String::from("Ana");
    let take = || name;
    let got = take();
    println!("got {got}");
}

Which trait does the closure || count += 1 implement?

fn main() {
    let mut count = 0;
    let mut inc = || count += 1;
    inc();
    println!("{count}");
}
  1. Fn, because it only reads count.
  2. FnMut, because it changes count through a mutable borrow.
  3. FnOnce, because it moves count out.

count += 1 changes a captured variable, so the closure is FnMut. It is not Fn, because Fn can't change its captures. It is not FnOnce, because nothing is moved out, so you can call it again. Every Fn closure is also an FnMut, and every FnMut is also an FnOnce.

Calling an FnMut closure takes a mutable borrow of the closure itself. Write let inc = || count += 1; without mut, and rustc stops with E0596: cannot borrow inc as mutable, as it is not declared as mutable. The quiz above has the mut it needs.

Move closures take the value with them

The move keyword before the bars makes the closure take ownership of everything it captures, instead of borrowing it. It matters when the closure has to outlive the variables it used. Returning a closure from a function is the common case.

fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n
}

fn main() {
    let add5 = make_adder(5);
    println!("{}", add5(10));
}

The return type impl Fn(i32) -> i32 says: some closure that takes an i32 and returns an i32. You don't name its type. Now leave out move:

fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    |x| x + n
}

fn main() {
    let add5 = make_adder(5);
    println!("{}", add5(10));
}

Passing closures to functions

A function that takes a closure names the trait it needs. Ask for the weakest one you can. FnOnce accepts every closure, FnMut accepts every closure that can be called more than once, whether it reads or changes state, and Fn accepts only the ones that just read. Two common forms:

fn apply(f: impl Fn(i32) -> i32, x: i32) -> i32 {
    f(x)
}

fn repeat<F: FnMut()>(times: usize, mut f: F) {
    for _ in 0..times {
        f();
    }
}

fn main() {
    let double = |n| n * 2;
    println!("{}", apply(double, 21));

    let mut hits = 0;
    repeat(3, || hits += 1);
    println!("hits = {hits}");
}

apply takes impl Fn(i32) -> i32, so a caller may pass any closure that only reads what it captured. repeat takes F: FnMut(), because it calls the closure over and over and the closure may change state on every call. Its parameter is written mut f, because calling an FnMut needs a mutable borrow of it. The impl Fn(i32) -> i32 and F: FnMut() forms use the same syntax as Chapter 14's impl Trait and trait bounds.

Named functions as values

PHP 8.1 added first-class callable syntax. strlen(...) turns a named function into a Closure that you can pass anywhere a callable is expected. Rust has the same move with a fn item: the function's name, used as a value.

declare(strict_types=1);

function double(int $n): int
{
    return $n * 2;
}

function apply(callable $f, int $x): int
{
    return $f($x);
}

echo apply(double(...), 21), "\n";
echo implode(", ", array_map(strlen(...), ["rust", "php"])), "\n";
fn double(n: i32) -> i32 {
    n * 2
}

fn apply(f: impl Fn(i32) -> i32, x: i32) -> i32 {
    f(x)
}

fn main() {
    println!("{}", apply(double, 21));
    let lengths: Vec<usize> = ["rust", "php"].into_iter().map(str::len).collect();
    println!("{lengths:?}");
}

Where it holds: you pass a name, and the function gets called. Where it breaks: double(...) builds a Closure object when the line runs, and every call goes through that object. Rust's double is its own zero-sized type, known at compile time, and apply gets a separate copy for it, the same as for a closure. The signature is checked at compile time, so passing a function with the wrong parameter type is a compile error.

Closures of different types in one list

impl Fn(i32) -> i32 stands for one closure type, and every closure has a type of its own. So a Vec cannot hold two different closures by that rule. Box<dyn Fn(i32) -> i32> erases the closure's type and keeps only what it does. Each box holds one closure on the heap, so closures with different captures can share one list.

fn main() {
    let offset = 10;
    let steps: Vec<Box<dyn Fn(i32) -> i32>> = vec![
        Box::new(|x| x + 1),
        Box::new(move |x| x * offset),
        Box::new(i32::abs),
    ];
    let results: Vec<i32> = steps.iter().map(|f| f(-4)).collect();
    println!("{results:?}");
}

The first closure captures nothing. The second one captures offset with move, so it owns its copy. The third is a named function, and it fits in the same list.

The Iterator trait in one method

An iterator is any type that implements the Iterator trait. A trait is a named set of methods a type promises to provide, and Chapter 14 explains traits, including associated types. This one is small. It has one associated type, Item, and one method you must write:

trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
    // dozens of other methods, all built on next()
}

PHP's Iterator interface asks you to implement five methods: current, key, next, rewind and valid. Rust asks for one, next. Everything else, map, filter, sum and the rest, is a default method that calls next for you.

Here is next called by hand on v.iter(). Each call returns the next item, wrapped in Some, and the call after the last item returns None. The iterator has to be mut, because next moves its position forward.

fn main() {
    let v = vec![10, 20, 30];
    let mut it = v.iter();
    println!("{:?}", it.next());
    println!("{:?}", it.next());
    println!("{:?}", it.next());
    println!("{:?}", it.next());
}

Implementing the trait for your own type gives you every adapter and consumer from the next sections, for free. This countdown yields 3, 2, 1:

struct Countdown {
    n: u32,
}

impl Iterator for Countdown {
    type Item = u32;

    fn next(&mut self) -> Option<u32> {
        if self.n == 0 {
            None
        } else {
            self.n -= 1;
            Some(self.n + 1)
        }
    }
}

fn main() {
    let rockets: Vec<u32> = Countdown { n: 3 }.collect();
    println!("{rockets:?}");
    let total: u32 = Countdown { n: 4 }.filter(|x| x % 2 == 0).sum();
    println!("{total}");
}

collect, filter and sum all work on Countdown because they are built on next. The second line counts down from 4 through 1, keeps the even numbers, 4 and 2, and sums them to 6.

Three ways to walk a vector

Most of the time you walk a vector with one of three methods. They differ in what each item is, and in whether the vector is still yours afterward.

MethodEach item isThe vector afterwardUse it when
v.iter()&T, a shared borrowstill yours, unchangedyou only read
v.iter_mut()&mut T, a mutable borrowstill yours, items can changeyou change items in place
v.into_iter()T, the value itselfmoved, and you can't use v againyou want the values and are done with the vector

A for loop calls one of these for you, depending on what comes after in. for x in &v is v.iter(). for x in &mut v is v.iter_mut(). for x in v is v.into_iter().

fn main() {
    let mut v = vec![1, 2, 3];

    for x in &v {
        println!("read {x}");
    }

    for x in &mut v {
        *x *= 10;
    }
    println!("{v:?}");

    for x in v {
        println!("took {x}");
    }
}

Does this compile?

fn main() {
    let v = vec![1, 2, 3];
    for x in &v {
        *x += 1;
    }
    println!("{v:?}");
}
  1. Yes. x is a copy of each item, so changing it is fine.
  2. No. &v gives shared references, and you can't assign through one. Write &mut v instead.

for x in &v gives x the type &i32. A shared reference lets you read the value, not write it. Change the loop to for x in &mut v, and x becomes &mut i32, which you can assign through.

Lazy: nothing happens until you pull

Building an iterator chain does no work. v.iter().map(|x| x * 2) creates a value that describes the work: the vector, and the closure to run on each item. Nothing is multiplied until a consumer asks for an item. Consumers are collect, sum, count, a for loop and the others you will meet in the next section.

Both belts share one step counter, so the same step is the same moment for both. The Laravel belt needs 17 steps: eight map calls, eight filter calls and then take. The Rust belt is finished after eight. On that belt, items 5 to 8 never reach map.

Here is the Rust pipeline with its two call counters. Each counter is a closure that changes a captured variable, the FnMut pattern from above.

fn main() {
    let mut map_calls = 0;
    let mut filter_calls = 0;
    let out: Vec<i32> = (1..=8)
        .map(|x| {
            map_calls += 1;
            x * 10
        })
        .filter(|x| {
            filter_calls += 1;
            x % 20 == 0
        })
        .take(2)
        .collect();
    println!("{out:?}");
    println!("map called {map_calls} times");
    println!("filter called {filter_calls} times");
}

The laziness pays off at the end of the line. take(2) stops asking after the second item it keeps, and the stages before it stop with it. The eager version has no such stop. Each stage must finish its whole array first, so take throws away the last items after they were already computed.

Laravel's Collection is eager. Each method runs over every item and returns a new Collection, so a chain builds one complete collection per step. For lazy behavior, call ->lazy(). That returns a LazyCollection, which uses PHP generators, so each item moves through the chain only when the next step asks for it.

PHP 8.5 added the pipe operator, |>. Its steps look like an iterator chain, but the pipe is eager. Each step takes the whole value and returns a whole value, so one step finishes before the next one starts.

declare(strict_types=1);

function scaled(array $xs): array
{
    return array_map(fn (int $x): int => $x * 10, $xs);
}

function bigEnough(array $xs): array
{
    return array_values(array_filter($xs, fn (int $x): bool => $x % 20 === 0));
}

$out = range(1, 8)
    |> scaled(...)
    |> bigEnough(...)
    |> (fn (array $xs): array => array_slice($xs, 0, 2));
fn main() {
    let out: Vec<i32> = (1..=8)
        .map(|x| x * 10)
        .filter(|x| x % 20 == 0)
        .take(2)
        .collect();
    println!("{out:?}");
}

Where it holds: the same numbers come out, and the steps read top to bottom. Where it breaks: the pipe is eager. scaled maps all eight numbers before bigEnough sees the first one. The Rust chain is lazy. take(2) stops the pulling after the second match, which is 40, so map runs only four times. The belt above shows the same difference.

Read the chain top to bottom and it looks like a pipeline that pushes items forward. At runtime it runs the other way. The last stage asks the stage before it, and that asks the one before, until the range is reached. A stage does work only when the stage after it asks. The order game in the practice section walks through one of these pulls.

Adapters and consumers

Iterator methods come in two kinds. Adapters take an iterator and return another iterator, so they stay lazy. Consumers pull the items and produce a value. A chain is a line of adapters that ends in a consumer.

AdapterWhat it does
map(f)transforms each item
filter(p)keeps items where p is true. The closure gets a reference, so you write *n to read the value.
filter_map(f)f returns an Option. Some keeps the value it holds, and None drops the item.
enumerate()pairs each item with its index, as (usize, T)
zip(other)pairs items from two iterators, and stops at the shorter one
take(n), skip(n)the first n items, or everything after the first n
take_while(p)items while p is true, then it stops for good
chain(other)this iterator's items, then the other's
flat_map(f)f returns an iterator for each item, and the results are joined into one stream
rev()walks backward. It needs an iterator that can walk both ways, such as a vector or a range.
peekable()lets you peek() at the next item without taking it

Slices have two more: windows(n) yields every run of n items, overlapping, and chunks(n) yields non-overlapping pieces, where the last one may be shorter. Here are the adapters you will use most, with their output:

fn main() {
    let nums = vec![1, 2, 3, 4, 5, 6];

    let evens: Vec<i32> = nums.iter().filter(|n| *n % 2 == 0).copied().collect();
    println!("{evens:?}");

    let words = ["7", "x", "9"];
    let parsed: Vec<i32> = words.iter().filter_map(|s| s.parse().ok()).collect();
    println!("{parsed:?}");

    for (i, n) in nums.iter().enumerate().skip(4) {
        println!("{i}:{n}");
    }
}

filter on iter() gives the closure a &&i32, so *n is the &i32 that % accepts. copied() turns each &i32 into an i32, which is what collect needs for a Vec<i32>. filter_map does the filtering and the conversion in one step, and the "x" that fails to parse just disappears.

Collect into four targets

use std::collections::HashMap;

fn main() {
    let names = vec!["Ana", "Bartholomew", "Cy"];

    let lengths: HashMap<&str, usize> = names.iter().map(|s| (*s, s.len())).collect();
    println!("Ana -> {}", lengths["Ana"]);

    let letters = vec!['r', 'u', 's', 't'];
    let word: String = letters.iter().collect();
    println!("{word}");

    let ok: Result<Vec<i32>, _> = ["1", "2", "3"].iter().map(|s| s.parse::<i32>()).collect();
    println!("{ok:?}");

    let bad: Result<Vec<i32>, _> = ["1", "x", "y"].iter().map(|s| s.parse::<i32>()).collect();
    println!("{bad:?}");
}
  • Vec is the default. It keeps the order of the items.
  • HashMap collects (key, value) pairs. If two pairs share a key, the later one wins.
  • String collects from characters, or from string pieces, and joins them.
  • Result<Vec<T>, E> is the all-or-nothing collect. You get Ok with every value, or the first Err. Once an error appears, collect stops pulling, and the items after it are never looked at.

iter::from_fn: an iterator from a closure

std::iter::from_fn builds an iterator out of a closure. The closure returns Some(item) for each value, and None to stop. Use it when the next value depends on state that a range cannot express.

fn main() {
    let mut n = 1;
    let powers: Vec<i32> = std::iter::from_fn(|| {
        if n > 100 {
            None
        } else {
            let current = n;
            n *= 2;
            Some(current)
        }
    })
    .collect();
    println!("{powers:?}");
}

chunk_by: groups of neighbors

chunk_by splits a slice into groups. A new group starts whenever the closure returns false for two neighbors. It groups runs, so equal values that are far apart land in separate groups. It is stable since Rust 1.77.

fn main() {
    let readings = [1, 1, 2, 2, 2, 5, 1];
    let groups: Vec<&[i32]> = readings.chunk_by(|a, b| a == b).collect();
    println!("{groups:?}");
}

split_once: split at the first separator

str::split_once splits a string at its first match. It returns the two halves as a tuple, or None when the separator is missing. For a line such as key=value, you get both parts in one call, with no index arithmetic. It is stable since Rust 1.52.

fn main() {
    let line = "name=oxidize";
    if let Some((key, value)) = line.split_once('=') {
        println!("{key} is {value}");
    }
    println!("{:?}", "no equals sign".split_once('='));
}

What does this program print?

fn main() {
    let raw = ["1", "x", "3"];
    let parsed: Result<Vec<i32>, _> = raw.iter().map(|s| s.parse::<i32>()).collect();
    println!("{parsed:?}");
}
  1. Ok([1, 3]), because collect skips the item that fails
  2. Err(ParseIntError { kind: InvalidDigit }), the first failure. The 3 is never read.
  3. Err(ParseIntError { kind: InvalidDigit }), but only after reading all three items

collect into a Result stops at the first Err and returns it. The "x" fails, and "3" is never parsed. This is the first-error-wins behavior you want when a batch of input must be valid.

Laravel Collections, translated

Most of your Collection habits carry over. The names change, and a few things that PHP left implicit become explicit in Rust. This table covers the methods you use most.

Here is a whole chain. This is a PHP pipeline over users, which keeps the active ones, sorts them by age, and returns their names:

$names = collect($users)
    ->filter(fn (User $u): bool => $u->active)
    ->sortBy('age')
    ->pluck('name')
    ->values()
    ->all();
struct User {
    name: String,
    age: u32,
    active: bool,
}

fn main() {
    let users = vec![
        User { name: "Ana".to_string(), age: 34, active: true },
        User { name: "Bo".to_string(), age: 27, active: false },
        User { name: "Cy".to_string(), age: 19, active: true },
        User { name: "Di".to_string(), age: 52, active: true },
    ];

    let mut active: Vec<&User> = users.iter().filter(|u| u.active).collect();
    active.sort_by_key(|u| u.age);
    let names: Vec<&str> = active.iter().map(|u| u.name.as_str()).collect();
    println!("{names:?}");
}

The shape matches up to sortBy, and there the Rust chain has to pause. Sorting needs a Vec you can change, so the iterator is collected first, and sort_by_key runs on that Vec. The PHP chain also calls values() to renumber the keys that filter and sortBy left behind. A Rust Vec has positions rather than keys, so there is nothing to renumber.

first() in Laravel returns null when the collection is empty, and null can slip through a chain unnoticed. Rust's .next() and .find() return an Option. You can't use the value inside it until you open the box with match, if let, or a method such as unwrap_or.

  • .map(|u| u.name.as_str())
  • .filter(|u| !u.active)
  • .join(", ") on a slice of strings
  • .fold(0, |sum, u| sum + u.age)
  • .find(|u| u.active)
  • a loop that calls entry(dept).or_default().push(user)

Zero-cost: as fast as the loop you'd write

Rust's promise is that an abstraction does not add a runtime cost you couldn't have avoided by hand. Iterators are the everyday test of that promise. Here are two ways to sum a slice:

fn sum_index(v: &[u64]) -> u64 {
    let mut total = 0;
    for i in 0..v.len() {
        total += v[i];
    }
    total
}

fn sum_iter(v: &[u64]) -> u64 {
    let mut total = 0;
    for x in v {
        total += x;
    }
    total
}

fn main() {
    let v: Vec<u64> = (1..=10).collect();
    println!("{} {}", sum_index(&v), sum_iter(&v));
}
Predict first: in an optimized build, does v[i] in sum_index still check the index on every pass?

No. An optimized build removes the check here. The loop runs from 0 up to v.len(), so every index is in range, and the optimizer can prove it. A debug build keeps the check, because debug builds don't optimize.

The iterator version has no index at all, so there is nothing to check.

The check comes back as soon as the bound is no longer tied to the vector. Change the loop to 0..n, where n is an unrelated number, and the optimizer can't prove the index is safe. Then it stays:

fn sum_first_n(v: &[u64], n: usize) -> u64 {
    let mut total = 0;
    for i in 0..n {
        total += v[i];
    }
    total
}

fn main() {
    let v: Vec<u64> = (1..=10).collect();
    println!("{}", sum_first_n(&v, 20));
}

That program compiles, then panics with index out of bounds: the len is 10 but the index is 10 and exits with code 101. The failure is loud and happens at the bad index. C would not check the index at all, and would read whatever memory sits past the end of the buffer.

You can check the first claim yourself. Compile the two-function version with optimizations and search the assembly for the bounds-check function:

rustc -C opt-level=3 --emit=asm zero_cost.rs
grep panic_bounds_check zero_cost.s

For the file above, grep prints nothing: neither loop has a bounds check left in optimized code. That is a fact about this code, not a speed number. Measure your own program before you tune anything.

What the optimizer does with the iterator loop

The iterator loop reads the slice from start to end. The compiler knows the length and the stride, so it doesn't need an index that could be out of range. In one optimized build, LLVM turned sum_iter into SIMD instructions, which add several numbers at once. You don't write that. You write a plain loop, and the optimizer does the rest.

Agents often write for i in 0..v.len() with a v[i].clone() inside, or they collect() into a Vec and then call .iter() on it straight away. The first clones every item. The second builds a Vec only to walk it again.

In review, ask for the chain with borrows: v.iter().map(|x| …), collected once at the end, and only when the caller needs an owned result. Each .clone() inside a loop is an allocation for every item, and each middle collect() is an allocation for the whole stage.

Practice

Seven short checks. Answer each one before you open its explanation. Each is a mistake that reviewers see in real code.

Does this compile?

fn call_twice<F: Fn()>(f: F) {
    f();
    f();
}

fn main() {
    let mut count = 0;
    call_twice(|| count += 1);
    println!("{count}");
}
  1. Yes. The closure makes one change per call, so it's fine.
  2. No. call_twice asks for Fn, which can't change what it captured. Ask for FnMut, and make the parameter mut f.

F: Fn() promises the caller that the closure only reads its captures. count += 1 breaks that promise, so rustc reports E0594. Change the bound to FnMut() and the parameter to mut f: F, and the program compiles.

What does this program print?

fn main() {
    let mut calls = 0;
    let total: i32 = (1..=5)
        .map(|x| {
            calls += 1;
            x * x
        })
        .filter(|sq| sq % 2 == 1)
        .take(2)
        .sum();
    println!("total {total} after {calls} calls");
}
  1. total 35 after 5 calls
  2. total 10 after 5 calls
  3. total 10 after 3 calls

The pipeline is lazy. sum pulls 1, which passes the filter. It pulls 4, which doesn't, and then 9, which does. take(2) is full, so 25 is never mapped. The sum is 1 + 9 = 10, after three calls to map. The second option is what an eager, Laravel-style pipeline would count.

Does this compile?

fn main() {
    let token = String::from("abc");
    let revoke = move || drop(token);
    revoke();
    revoke();
}
  1. Yes. The move keyword lets a closure run any number of times.
  2. No. drop(token) moves token out of the closure, so the closure can run only once.

move decides how values are captured: by value. The body here moves token out, which makes the closure FnOnce. The second call is E0382, use of moved value: revoke. Look at the body, not at the keyword.

Does this compile, and what does it print?

fn main() {
    let order = String::from("A-17");
    let ship = move || println!("shipping {order}");
    ship();
    ship();
}
  1. No. A move closure can only be called once.
  2. Yes. It only reads order, so it is Fn, even with move. It prints the line twice.

The move keyword doesn't make this closure one-shot, and it doesn't make it reusable on its own either. The body decides. Here the closure only reads order, so it is Fn, and it can be called as many times as you like.

Does this compile?

fn main() {
    let nums = vec![1, 2, 3, 4];
    let evens: Vec<&i32> = nums.iter().filter(|n| n % 2 == 0).collect();
    println!("{evens:?}");
}
  1. Yes. % works on references.
  2. No. In filter, n is a &&i32, and % isn't defined for that. Write *n % 2.

In iter().filter, the item is a reference, and the closure gets a reference to that, so it's &&i32. Dereference once with *n, and the arithmetic compiles. This error shows up in agent-written code all the time.

Keep the even numbers. Fill in the two method names. The chain must compile and print [2, 4, 6].

fn main() {
    let nums = vec![1, 2, 3, 4, 5, 6];
    let evens: Vec<i32> = nums.iter().[[filter]](|n| *n % 2 == 0).[[copied|cloned]]().collect();
    println!("{evens:?}");
}

filter is the adapter that keeps items. copied turns the &i32 items into i32 values. cloned also works here, because i32 is Copy, so the two produce the same result. Use cloned when the items aren't Copy, such as String.

Put these steps in the order they happen, for one pull on (1..=8).map(...).filter(...).take(2), which produces the first item.

  1. collect asks take for the first item.
  2. take asks filter for an item.
  3. filter asks map for an item.
  4. map pulls 1 from the range and returns 10.
  5. filter rejects 10 and asks map again.
  6. map pulls 2 and returns 20.
  7. filter keeps 20 and returns it to take.
  8. take returns 20 to collect.

Each step asks for the one before it. That is the whole mechanism: a stage works only when the stage after it asks, and the asking starts at the end of the chain.

Recap

Closures and iterators

  • A closure is Fn if its body only reads, FnMut if it changes a capture, and FnOnce if it moves a capture out. The body decides, not the move keyword.
  • move makes a closure take ownership of its captures. You need it when the closure outlives them, for example when you return it.
  • An iterator implements one method, next. Adapters such as map and filter are built on it, and they are lazy.
  • Nothing runs until a consumer pulls. take(n) stops the pulling early, so the stages before it do less work.
  • collect needs a target type. It can build a Vec, a HashMap, a String, or a Result<Vec<T>, E> that stops at the first error.
  • Laravel's Collection methods are eager, and each returns a new collection. A Rust chain pulls one item at a time through every stage. The PHP 8.5 pipe is eager too, so it works like the Laravel chain.
Explain it back: why does take(2) make a Rust chain do less work than the same Laravel chain?

One good answer: "Rust iterators are lazy. Each item travels through map and filter only when take asks for it. Once take(2) has two items, it stops asking, so the earlier stages never run again. In the example, map and filter each run four times. Laravel's Collection methods are eager: map and filter each build a full array before take runs, so all eight items go through both stages, and take cuts the result down afterward."

If your version mentions lazy pulling, take stops asking, and eager arrays, you have the core of it.
