Looking without taking

Chapter 06 ended with a frustration. To let a function read a String, you handed the string over and got it back as part of the return value. Here is that pattern for a length check:

fn len(s: String) -> (String, usize) {
    let n = s.len();
    (s, n)
}

fn main() {
    let s = String::from("hello");
    let (s, n) = len(s);
    println!("{s} has {n} bytes");
}

It works, but every caller has to unpack the tuple, and every function has to repeat the trick. A borrow removes the need. An & in front of a value makes a reference: a pointer that lets the callee look at the value while the caller keeps ownership.

fn len(s: &String) -> usize {
    s.len()
}

fn main() {
    let s = String::from("hello");
    let n = len(&s);
    println!("{s} has {n} bytes");
}

The parameter type &String means "a borrowed String". The call len(&s) lends s for as long as len runs, and s is still usable on the next line. Nothing moved, and nothing was freed.

Step through that call. The question comes at the end of len.

A reference is a pointer with a promise attached. It will never outlive the value it points to, and it obeys the rule you'll meet in section four. Everything else in this chapter follows from that promise.

Does this compile?

fn len(s: &String) -> usize {
    s.len()
}

fn main() {
    let s = String::from("hello");
    let n = len(s);
    println!("{s} {n}");
}
  1. Yes. Rust turns a String into a reference when it is passed to a function.
  2. No. len asks for a &String and gets a String. The types don't match, which is error E0308.
  3. No. s is moved into the call, so println! can't use it.

The compiler reports the type mismatch before it looks at ownership. The fix it suggests is the borrow itself.

Using a reference

A reference is a different type from the value it points to. &i32 is not i32. Two rules keep that manageable:

  • Arithmetic and comparisons want the value itself, so you follow the pointer with *.
  • Method calls don't need the star. rs.len() works on a &String, because the compiler dereferences automatically when it looks up a method.
fn main() {
    let x = 5;
    let r = &x;
    println!("{}", *r + 1);
    println!("{}", *r == 5);

    let s = String::from("hi");
    let rs = &s;
    println!("{}", rs.len());
}

Does this compile?

fn main() {
    let x = 5;
    let r = &x;
    if r == 5 {
        println!("five");
    }
}
  1. Yes. Comparisons see through references, the same way method calls do.
  2. No. &i32 and i32 are different types. Write *r == 5.

Method calls dereference automatically. Operators such as == and + don't. They compare the types you wrote, so you say which level you mean.

&mut: borrowing to change

A shared borrow only reads. To change a value through a borrow you need &mut, and the owner has to allow it, which means its binding is declared mut.

fn add_one(v: &mut Vec<i32>) {
    v.push(1);
}

fn main() {
    let mut v = vec![0];
    add_one(&mut v);
    println!("{v:?}");
}

Both halves are visible. The parameter says &mut Vec<i32>, and the call says &mut v. Leave out the mut on the let and the call stops compiling:

Does this compile?

fn add_one(v: &mut Vec<i32>) {
    v.push(1);
}

fn main() {
    let v = vec![0];
    add_one(&mut v);
    println!("{v:?}");
}
  1. Yes. The call borrows v mutably, which is always allowed.
  2. No. v isn't declared mut, so it can't be borrowed mutably. That is error E0596.

The mut on the binding is the permission. The &mut at the call site is the request, and the compiler checks the permission first.

error[E0596]: cannot borrow `v` as mutable, as it is not declared as mutable
 --> src/main.rs:7:13
  |
7 |     add_one(&mut v);
  |             ^^^^^^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
6 |     let mut v = vec![0];
  |         +++


For more information about this error, try `rustc --explain E0596`.

An exclusive borrow is the one key to the editing room. While it exists, nobody else may even look.

The rule: many readers or one writer

Those two kinds of borrow come with one rule. Read it slowly. Everything after this section applies it.

Any number of shared borrows, &T, may exist at the same time.

Readers never get in each other's way.

Or exactly one mutable borrow, &mut T, and nothing else alongside it.

While it is alive, no other borrow of that value may exist, shared or mutable.

A reference must always be valid.

It can never outlive the value it points to, and the value can't move out from under a live reference.

Many readers or one writer. Never both.

The first half prevents data races. Two readers can't corrupt each other. A writer that changes data while a reader is looking at it can, and that is a race. Chapter 18 shows how the same rule keeps threads apart.

Does this compile?

fn main() {
    let v = vec![1, 2, 3];
    let a = &v[0];
    let b = &v[1];
    println!("{a} {b}");
}
  1. Yes. Any number of shared borrows can coexist.
  2. No. Two borrows of the same vector can't exist at once.

Both borrows are &T. The first half of the rule allows any number of them, so a and b can both be alive.

The second half protects against something you can't see from the reference. A change to the owner can move the memory the reference points into.

Take a Vec. Its elements live in a heap buffer with a fixed size. When a push finds the buffer full, it allocates a bigger one, copies the elements across and frees the old one. A reference into the old buffer is then a pointer to freed memory. Rust refuses that. This diagram shows where it stops:

A borrow lasts until its last use

Here is the part that surprises people. A borrow does not last until the end of the block where its reference is declared. It lasts until the last place that reference is used. Each bar below is one borrow's life, from its creation to its last use.

In this program the bar of r ends on line 4, before the push. The push is allowed, even though r is still in scope.

Move one use, and the bar of r reaches past the push. Here is the compiler's report for that version:

error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let r = &s;
  |             -- immutable borrow occurs here
4 |     s.push('!');
  |     ^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("{r}");
  |                - immutable borrow later used here


For more information about this error, try `rustc --explain E0502`.

Now a program that is easy to misjudge. Predict it before you read the verdict.

Does this compile?

fn main() {
    let mut scores = vec![10, 20];
    let first = &scores[0];
    println!("first = {first}");
    scores.push(30);
    println!("{}", scores.len());
}
  1. No. first is still in scope when push runs, so the borrow is still alive.
  2. Yes. The last use of first comes before the push, so its borrow has already ended.

Scope doesn't decide it. first is in scope until the end of main, but the borrow ends at the last line that uses it. Move the println! that reads first below the push, and the program stops compiling.

No dangling references

What happens if a function returns a reference to something it created?

fn dangle() -> &String {
    let s = String::from("x");
    &s
}

fn main() {
    let r = dangle();
    println!("{r}");
}

error[E0106]: missing lifetime specifier
 --> src/main.rs:1:16
  |
1 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const` or a `static`
  |
1 | fn dangle() -> &'static String {
  |                 +++++++
help: instead, you are more likely to want to return an owned value
  |
1 - fn dangle() -> &String {
1 + fn dangle() -> String {
  |


For more information about this error, try `rustc --explain E0106`.

s is a local. It is dropped when dangle returns, so a reference to it would point at memory that has already been freed. The signature has no input to borrow from, and the compiler reports that as a missing lifetime. The help text offers two fixes. Ignore the 'static one, which is almost never what you want here. The second one is the right answer: return an owned value, so ownership moves out to the caller.

fn fixed() -> String {
    let s = String::from("x");
    s
}

fn main() {
    let t = fixed();
    println!("{t}");
}

The signature tells the story. A function that returns a String hands ownership out. A function that returns a &String claims to borrow from one of its inputs, and the compiler checks that claim. Chapter 15 covers lifetimes in depth.

Why is returning the String the right fix, and not a reference with a longer life?

The String is created inside fixed, so the only owner that can outlive the function is the caller. Returning it moves ownership to the caller, who frees it when its own scope ends. A reference could only be valid if something outside the function owned the data, and this function has nothing outside to borrow from.

    PHP references are a different thing

    PHP's & makes an alias: a second name for the same storage. No rules come with it. Here is the classic way it bites:

    $arr = [1, 2, 3];
foreach ($arr as &$v) {}
foreach ($arr as $v) {}
print_r($arr); // [0] => 1, [1] => 2, [2] => 2

    The first loop leaves $v as an alias of $arr[2], and nothing ends that alias. On the second loop's first pass, the value 1 is written into the slot that $v still aliases. The second pass copies 2 into it, and the third pass copies the 2 that is already there.

    Rust makes that kind of overlap impossible to write. Here is the safe loop in both languages:

    $arr = [1, 2, 3];
foreach ($arr as &$v) {
    $v *= 2;
}
// $v still aliases $arr[2]
  
    let mut v = vec![1, 2, 3];
for v in v.iter_mut() {
    *v *= 2;
}

    The Rust loop borrows the vector mutably for exactly as long as the loop runs. The loop variable is a &mut i32 to one element, and nothing else can see the vector while that borrow is alive. When the loop ends, the borrow ends with it, and there is no alias left to surprise you.

    The bug from the PHP example has a Rust cousin: a mutable alias that is still used after a read of the same vector. It doesn't compile.

    Does this compile?

    fn main() {
    let mut v = vec![1, 2, 3];
    let last = v.last_mut().unwrap();
    for x in &v {
        println!("{x}");
    }
    *last = 9;
}
    1. Yes. last is only used after the loop, so the loop is fine.
    2. No. last is a mutable borrow of v that is still used after the loop. Reading v inside the loop is error E0502.

    The loop needs a shared borrow of v, and last is still a live mutable borrow of it. Rust doesn't allow a second path into the vector alongside the first.

    error[E0502]: cannot borrow `v` as immutable because it is also borrowed as mutable
 --> src/main.rs:4:14
  |
3 |     let last = v.last_mut().unwrap();
  |                - mutable borrow occurs here
4 |     for x in &v {
  |              ^^ immutable borrow occurs here
...
7 |     *last = 9;
  |     --------- mutable borrow later used here


For more information about this error, try `rustc --explain E0502`.

    In PHP, $v is a name for a slot, and a reference makes a second name for the same slot. Nothing tracks which names are still alive, so a leftover alias from an earlier loop can change data you didn't touch in the current one.

    Rust's references are checked. The compiler knows where each one is alive, so it can reject an overlap before the program runs.

    Reading borrow errors

    You have met E0502 and E0106. Two more codes come up constantly. Here are their real reports, with a plain reading and a fix for each.

    E0499: two mutable borrows

    fn main() {
    let mut s = String::from("hi");
    let a = &mut s;
    let b = &mut s;
    a.push('!');
    b.push('?');
}

    error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:4:13
  |
3 |     let a = &mut s;
  |             ------ first mutable borrow occurs here
4 |     let b = &mut s;
  |             ^^^^^^ second mutable borrow occurs here
5 |     a.push('!');
  |     - first borrow later used here


For more information about this error, try `rustc --explain E0499`.

    The compiler points at the second &mut s. It labels the first borrow and marks where it is still used, on line 5. The fix is to finish with a before you create b, or to keep only one of them.

    E0506: assigning to a borrowed value

    fn main() {
    let mut s = String::from("hi");
    let r = &s;
    s = String::from("new");
    println!("{r} {s}");
}

    error[E0506]: cannot assign to `s` because it is borrowed
 --> src/main.rs:4:5
  |
3 |     let r = &s;
  |             -- `s` is borrowed here
4 |     s = String::from("new");
  |     ^ `s` is assigned to here but it was already borrowed
5 |     println!("{r} {s}");
  |                - borrow later used here


For more information about this error, try `rustc --explain E0506`.

    You can't overwrite s while r still needs the old value. Finish with r first, or copy out whatever you still need before the assignment.

    In the E0499 report, the compiler points at the second borrow, not the first. Why?

    The first borrow is fine by itself. What breaks the rule is creating the second borrow while the first is still used later. The error belongs to the access that conflicts, and the label on the first borrow explains why it conflicts.

    Two-phase borrows: why v.push(v.len()) compiles

    push takes &mut v, and v.len() takes &v. They overlap on one line, yet the program is accepted. The compiler treats the mutable borrow in two phases. It first reserves &mut v, which still allows reads, and it activates the borrow when the call happens. The argument is evaluated in between, and its shared borrow has ended before the activation.

    fn main() {
    let mut v = vec![1, 2];
    v.push(v.len());
    println!("{v:?}");
}

    Passing a &mut variable to a function doesn't move it. The compiler reborrows it, giving the callee a temporary &mut *m, so m is usable again afterwards:

    fn bump(n: &mut i32) {
    *n += 1;
}

fn main() {
    let mut x = 1;
    let m = &mut x;
    bump(m);
    bump(m);
    println!("{m}");
}

    Agents tend to silence E0502 in two ways. They add .clone() until the error goes away, or they change a &T parameter to &mut T "to be safe". Both compile, and neither is a design.

    In review, ask two questions. Does this function really need to mutate, or does it only need to look? And if it changes a value, is that change visible to the caller in a way the caller expects? A parameter of type &T, &str or &[T] says "I only read", and that is the signature to prefer when it fits.

    Be the borrow checker

    Four short programs and two practice exercises. For each one, decide what rustc does before you look at the answer.

    Does this compile?

    fn main() {
    let mut name = String::from("Ana");
    let a = &mut name;
    let b = &mut name;
    b.push('!');
    a.push('?');
}
    1. Yes. The second &mut simply takes over from the first.
    2. No. a is still used on line 6, so creating b on line 4 is error E0499.

    Two mutable borrows of the same value can't be alive together. a is alive until its use on line 6, so it is still alive when b is created.

    error[E0499]: cannot borrow `name` as mutable more than once at a time
 --> src/main.rs:4:13
  |
3 |     let a = &mut name;
  |             --------- first mutable borrow occurs here
4 |     let b = &mut name;
  |             ^^^^^^^^^ second mutable borrow occurs here
5 |     b.push('!');
6 |     a.push('?');
  |     - first borrow later used here


For more information about this error, try `rustc --explain E0499`.

    Does this compile?

    fn main() {
    let mut nums = vec![1, 2, 3];
    for n in &nums {
        nums.push(*n * 10);
    }
}
    1. Yes. The loop only reads nums, and the push is quick.
    2. No. The loop holds a shared borrow of nums for its whole run, and push needs &mut nums. That is error E0502.

    The for loop borrows the vector for as long as it runs. The push inside the loop asks for an exclusive borrow while that shared one is still in use.

    error[E0502]: cannot borrow `nums` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:9
  |
3 |     for n in &nums {
  |              -----
  |              |
  |              immutable borrow occurs here
  |              immutable borrow later used here
4 |         nums.push(*n * 10);
  |         ^^^^^^^^^^^^^^^^^^ mutable borrow occurs here


For more information about this error, try `rustc --explain E0502`.

    Does this compile?

    fn main() {
    let mut count = 1;
    let view = &count;
    count += 1;
    println!("{count}");
}
    1. No. view is still in scope when count changes.
    2. Yes. view is never used after the change, so its borrow has already ended.

    Scope doesn't decide it. A borrow ends at its last use, and view has none after the change. The compiler also warns that view is unused, which is a hint in itself.

    Does this compile?

    fn main() {
    let mut words = vec!["a"];
    words.insert(words.len(), "b");
    println!("{words:?}");
}
    1. No. insert borrows words mutably, so words.len() can't read it.
    2. Yes. The argument is evaluated while the mutable borrow is only reserved, the same as v.push(v.len()).

    This is a two-phase borrow. The read in the argument happens before the mutable borrow is activated, so it doesn't clash.

    Complete the parameter so byte_count borrows its text, and word stays usable after the call.

    fn byte_count(text: [[&String|&str]]) -> usize {
    text.len()
}

fn main() {
    let word = String::from("rust");
    println!("{}", byte_count(&word));
    println!("{word}");
}

    Either answer works. &word is a &String, and Rust turns it into a &str automatically when a function asks for one. The borrow is the point: word is still usable on the next line. You'll meet &str properly in Chapter 08.

    Recap

    Many readers or one writer

    • &s lends a value without taking it. The owner stays usable, and nothing is freed.
    • &mut s is exclusive. While it is alive, no other borrow of s may exist, and the binding must be mut.
    • Any number of &T, or exactly one &mut T, never both. A reference can't outlive its value.
    • A borrow lasts until its last use, not until the end of its scope. That is NLL.
    • E0502 and E0499 mean a conflicting borrow is still used later: end the earlier borrow first. E0506 means you assigned while borrowed. E0106 on a return means you returned a reference to a local, so return the owned value instead.
    Explain it back: explain to a PHP developer why Rust rejects reading v[0] across a push.

    One good answer: "In PHP, $first = $v[0]; copies the value, so the array can grow freely. In Rust, let first = &v[0]; points into the Vec's heap buffer. A push that finds the buffer full moves every element to a new buffer, so first would point at freed memory. The compiler rejects the push because first is still used afterwards, so the bug can never reach a running program."

    If your version mentions the buffer can move, the reference would dangle and the borrow lasts until its last use, you've got it.
